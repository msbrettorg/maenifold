# T-51.8 — Pipeline Delete and Schema Update

**Requirement**: FR-40 (Pipeline Active Executor)
**RTM**: RTM-164 / TC-164
**Component**: `crates/maenifold-core/src/workflow/pipeline/handler.rs`, `crates/maenifold-core/src/mcp/schema/workflow_tools.rs`

## Context

Delete removes a pipeline and its associated workflow sessions. The schema update adds all new operations to the MCP tool definition so agents and UI can discover them.

Depends on: T-51.1 (petgraph foundation).

## Acceptance Criteria

### Delete

1. Add `delete` operation, triggered by `sessionId + delete: true`
2. Implement delete logic:
   - Read pipeline session
   - If pipeline is currently running (has Active nodes): REJECT — must pause or cancel first
   - Delete all associated workflow session files (from `nodeStates[*].sessionId`)
   - Delete the pipeline session file itself
   - Return confirmation with deleted session ID and count of cleaned-up files
3. Deletion is permanent — no archive. (The graph already has the knowledge; session files are ephemeral state.)

### Schema Update

4. Update the Pipeline tool schema in `workflow_tools.rs` to include all new operations:
   - `run: boolean` — start autonomous execution
   - `pause: boolean` — pause a running pipeline
   - `resume: boolean` — resume a paused pipeline
   - `cancel: boolean` — cancel a running pipeline
   - `rewind: { nodeIds: [string] }` — rewind specified nodes + downstream
   - `delete: boolean` — delete pipeline and associated sessions
   - `graft: { nodes: [...], edges: [...] }` — add nodes/edges to existing pipeline
   - `join: { sourceSessionId: string, edges: [...] }` — merge another pipeline into this one
   - `fork: { fromNodeId: string, newSessionId?: string }` — clone subgraph into new pipeline
5. Each new operation must have clear description in the schema
6. Update the handler multiplexer in `handler.rs` to route new operation payloads to the correct handler functions
7. The `learn` output (help text) must document all new operations

### F-1 — HIGH: Delete permanently fails if any workflow session file is missing

**Where**: `session_io.rs::derive_pipeline_node_states` (line 51-56) + `paths.rs::delete_file` (line 68-72)

**What**: `delete_pipeline` calls `derive_pipeline_node_states` before deleting anything. That function hard-errors (`return Err(...)`) if _any_ workflow session file does not exist on disk. `delete_file` does the same: it errors if the file is absent at deletion time. Both paths return `Err` rather than skipping the missing file.

**Attack scenario**: A pipeline is left in a partially-orphaned state — for example because a `join` operation previously shared its sessions, because the user manually cleaned a session file, or because a storage error interrupted a prior create. Now the pipeline session file exists but one workflow session is missing. Every `delete: true` call returns `"Workflow session X doesn't exist"` and aborts _before_ touching anything. The pipeline is permanently un-deletable.

**Reproduction**:
```
1. Create a pipeline with two nodes (root, child).
2. Manually delete the child workflow session file.
3. Call { "sessionId": "...", "delete": true }.
4. Observe: error "Workflow session workflow-...-child doesn't exist" — pipeline session not cleaned up.
```

**Impact**: Stranded pipeline sessions that cannot be self-healed through the tool. Must be removed manually via the filesystem. Worsened by the shared-ownership state that F-2's join can silently produce.

**Remediation**: For delete, use best-effort cleanup: skip workflow sessions that don't exist on disk (they're already gone), and always delete the pipeline session file at the end regardless. The spec says "deletion is permanent — no archive" and does not require all workflow sessions to be present. The Active-node guard can still run against the frontmatter states (not derived) to avoid the chicken-and-egg problem on partially-missing sessions.

### F-2 — MEDIUM: Join creates dual session ownership and accepts running source pipelines

**Where**: `handler.rs::join_pipeline` (lines 326-430)

**Part A — dual ownership after join**: After a successful `join`, the _source_ pipeline session still exists on disk and still references the exact same workflow session files (same `session_id` values) now also tracked by the target. Two pipeline sessions own the same files. If the source is subsequently deleted, `delete_pipeline_session_files` removes those workflow session files — silently corrupting the target pipeline whose nodes now have dangling session references.

**Part B — no guard for running source**: `join_pipeline` calls `resolve_join_node_states`, which skips missing sessions but does _not_ check whether either the source or target has Active nodes. A live source pipeline can be absorbed mid-execution. The merged pipeline would expose nodes currently being executed by another agent, creating a split-brain: the active agent's status updates land on the session, but the target pipeline's view of node state diverges from the source's.

**Attack scenario (Part A)**:
```
1. Create source (S) and target (T).
2. Join S into T — T now tracks all sessions from both.
3. Delete S — delete_pipeline_session_files removes S's workflow sessions.
4. T's nodes that came from S have dangling session_id references.
```

**Attack scenario (Part B)**:
```
1. Create source with an Active node (dispatch called, agent executing).
2. Join source into target — succeeds with no error.
3. Target now references a session actively being written by another agent.
```

**Impact**: Silent data loss on delete-after-join (Part A). Split-brain node state if source is running (Part B).

**Remediation**:
- Part A: Either document explicitly that join is non-destructive and the caller is responsible for deleting the source (add a note in help text and a `sourceSessionId` field in the response for clarity), or have `join` delete the source on success to enforce single-ownership. Either choice is defensible; the ambiguity is the problem.
- Part B: Add a running-node guard in `join_pipeline` matching `graft_pipeline`'s guard (lines 554-563), rejecting if either pipeline has Active nodes.

### F-3 — LOW: Error message has misaligned indentation for `view` and `dispatch` entries

**Where**: `handler.rs` lines 192-193

```
              Graft pipeline: sessionId + graft\n  \
             View pipeline: sessionId + view=true\n  \       ← 3 spaces (should be 4)
             Dispatch ready nodes: sessionId + dispatch=true\n  \  ← 3 spaces
              Restart node: sessionId + nodeId + restart=true\n  \
```

`View pipeline` and `Dispatch ready nodes` are indented 3 spaces while every other operation uses 4, causing a jagged column in CLI error output.

**Remediation**: Align both lines to 4-space indent, consistent with all other entries.

- **Delete active-node guard uses derived (live) states**: reads workflow session files, not stale frontmatter. A node marked Completed in frontmatter but actually Active on disk is correctly caught.

- **Schema field types and `required` constraints**: all correct. `rewind.nodeIds`, `join.sourceSessionId + edges`, `fork.fromNodeId` all required. `graft.required: ["nodes", "edges"]` is correct (empty arrays are valid and useful for edges-only grafts).
