# T-243.7.0 — Schedules tab delta review

> **Headline:** This tab is **not** "feature missing." Backend is genuinely full-featured
> (`Schedule` MCP tool exposes `create / update / delete / list / get / run_now / logs`,
> with launchd + systemd installation, supervisor execution, log capture, parsed-schedule
> human descriptions, allowed-tools allowlist, auto-grant permissions toggle). The **UI**
> bolts on a thin CRUD form over that backend and stops there. The gap is not capability —
> it's that the UI exposes maybe 40% of what the backend already does, and almost none of
> the workflows a real operator needs (history, logs, cron preview, validation, calendar,
> global controls, permission diagnostics).
>
> The user's flag — *"we haven't even tried Schedules yet"* — is well-placed: this surface
> has CRUD wiring but no operator UX, no observability, and no live end-to-end fire test
> on record.

## Voice 1 — claude-opus-4.7 (architecture / completeness)

What I see is a textbook "scaffolding shipped, operations forgotten" surface. The schedule
domain is one of the few in this app where execution happens **without a human in the loop**
— so the UI has a categorically higher bar than, say, the Knowledge tab. A schedule that
silently fails at 03:00 and never surfaces is worse than no schedule at all. Measured
against that bar:

- **The form is a JSON editor in disguise.** It collects `id`, `schedule` (free-text),
  `agent`, `prompt`, `description`, `allowed_tools` (comma/newline string),
  `auto_grant_permissions`, `enabled`. The backend `parse_schedule` accepts both cron
  *and* natural language ("every weekday at 9am"), and the placeholder hints at NL — but
  there is no preview, no validation feedback, no "what does this resolve to" surface.
  The user types a schedule string and finds out at save time whether the parser liked it.
  For a primitive that defines *when code runs unattended on the user's machine*, that is
  a P0 UX failure.
- **`last_run` is the entire observability story.** A single timestamp + optional error
  string per task, in the table cell. The backend supervisor writes per-run log files
  (`schedule://logs/{id}` resource exists; `Schedule action=logs` exists in the tool;
  `read_recent_logs` reads from `task_dir(id)/logs`). The Vue UI **never calls `logs`**
  (`grep "logs" useSchedulesSettings.ts` → zero hits). The data is sitting there, on
  disk, indexed, MCP-addressable, and the UI shows none of it.
- **No history.** Same root cause: only `last_run` is surfaced. There's no "previous runs"
  drawer, no per-run output, no failure timeline. If a schedule fired 50 times and the
  47th failed, the user sees only that 50 succeeded (because run 48–50 overwrote `last_run`).
- **Backend fields the UI silently drops:** `timeout_seconds` (backend default 300s, not
  user-editable), `workdir` (backend supports per-task working directory, UI has no input).
  Anyone running a schedule that needs >5 min, or that must run from a specific repo
  worktree, has to hand-edit JSON outside the UI.
- **Permissions flow is absent.** macOS launchd LaunchAgents written into
  `~/Library/LaunchAgents` will not fire while the user is logged out unless they're
  installed with `RunAtLoad`/login-item registration; on first run macOS may require the
  user to grant Background Items permission. The UI says "macOS supported, installs
  LaunchAgents." It does **not** detect whether the agent is actually loaded
  (`launchctl print gui/<uid>/<label>`), whether the LaunchAgent has fired since
  install, or whether System Settings → General → Login Items is blocking it. A "Running"
  status badge means "config exists and `enabled=true`," not "the OS scheduler will
  actually fire this."
- **No end-to-end fire test in the acceptance evidence.** The UAT spec asks for one
  ("Schedule a 1-minute-from-now test. Wait. Verify it actually fired."). Until that
  exists, every claim about backend integration is theoretical. The supervisor and
  launchd code have unit tests; nobody has confirmed the Electron-launched app, with its
  packaged binary path resolution (`std::env::current_exe()` in `resolve_maenifold_bin`),
  produces a LaunchAgent that actually executes.

The architectural shape I'd want before shipping this to users:

1. Form decomposes into **schedule** (cron builder + NL input + "Next 5 fires" preview),
   **what to run** (agent + prompt + workdir + timeout), **trust** (auto-grant +
   allowedTools), **lifecycle** (enabled + name/desc).
2. Each row expands into a **history drawer** that calls `Schedule action=logs` and the
   `schedule://logs/{id}` resource and shows last N runs with status, duration, output,
   and error.
3. A **"Verify install"** button per row that probes the OS scheduler (`launchctl
   print` / `systemctl --user status`) and reports the truth, not the config intent.
4. A page-level **"Pause all"** kill switch that calls `update enabled=false` across the
   list — because when something goes wrong at 03:00 you want one button, not N.
5. An **upcoming-fires** panel (calendar or simple list) computed from cron expressions
   across all enabled schedules.

## Voice 2 — gpt-5.5 (operator UX / signal-to-noise)

Opus is right that the backend is mostly there. I'm going to be more specific about *what
hurts when you actually try to use this tab as a person*, and what's a P0 vs polish.

**P0 — this will burn someone:**

1. **Cron expression has no validation, no preview, no timezone affordance.** Type
   `0 9 * * MON-FRI` (or "every weekday at 9am"). You see the literal string echoed back
   in the table cell. You don't see "next run: Tuesday 09:00 PST" anywhere. You don't
   know whether the cron is interpreted as local time or UTC (the `parse_schedule`
   function returns a `cron` string and a human description; the supervisor presumably
   uses local time but the UI is silent about which TZ the user is in). The first time
   somebody schedules an "every Friday at 17:00" job that fires at 09:00 PST because
   they're on a UTC system, this hits a Slack channel.
2. **No "Run now" log surfacing.** `runSchedule()` calls `action=run_now`, gets a
   `{message}` back, and shows the message as `statusMessage`. The supervisor returns a
   full `run` object (with output) in the response (`"run":run` in the JSON), but the
   composable destructures only `message`. So the "Run now" button gives you "Scheduled
   task 'foo' executed." regardless of whether it succeeded, failed, or produced any
   output. To see what actually happened you reload the table and look at `last_run`.
3. **Failure surfacing is one line of red text in a table cell.** `job.last_run.error` is
   shown as 12px destructive text under the timestamp. Multi-line stack traces or
   stderr are truncated by the cell width (`max-w-[18rem]`). For a feature whose entire
   value is "tell me when my unattended job broke," the error UI is borderline useless.
4. **No way to see logs from the UI at all.** The MCP backend has `Schedule action=logs`
   *and* `schedule://logs/{id}` as a resource. UI calls neither. To see logs, an
   operator has to either know the resource URI and use the chat tab, or `cat
   ~/.maenifold/schedules/<id>/logs/*` from a terminal.
5. **No "Verify it's actually installed in launchd/systemd."** If `sync_os_scheduler`
   silently fails — say, write permissions on `~/Library/LaunchAgents` are revoked, or
   systemd `--user` isn't running — the only signal is whether the create/update call
   threw. A `launchctl list | grep maenifold` button would close this gap.
6. **No 1-minute end-to-end test of record.** Nobody has signed off that the path
   *Vue → MCP → schedule.rs → launchd plist → supervisor → log file → updated `last_run`*
   actually closes the loop in the packaged Electron app on the user's machine. Until
   that's checked, every other UI improvement is decoration.

**P1 — this will frustrate someone:**

7. **Empty state has no template / examples / "what is a schedule?" link.** Just
   "No schedules configured yet." plus the New schedule button up in the toolbar.
   Compare to GitHub Actions schedules ("paste this YAML") or Hangfire ("here are
   recurring job examples").
8. **Edit form `id` is locked but editable elsewhere.** Good. But `description` is a
   second free-text field whose only function in the backend is to populate
   `task.name`, which is *only* shown nowhere in the UI (the table column shows `job.id`,
   not `job.name`). Either show name, or drop the field.
9. **`allowed_tools` is a comma-or-newline string parsed client-side.** Fine for v1, but
   there's no autocomplete against the *actual* tool list available from
   `DiscoverMcpTools`. So the user can blithely typo `ReadMmemory` and have their
   schedule fire and silently allow nothing.
10. **No global "Pause all" / "Resume all."** When a misconfigured schedule starts
    spamming, the only mitigation is N clicks of N edit dialogs.
11. **No filter / sort.** Inventory called out sortable column hints that don't actually
    sort. Confirmed: `<TableHead>` is plain. With 20+ schedules this becomes a wall.
12. **No upcoming-fires / calendar view.** "Show me my next 5 fires across all
    schedules" is a very common operator question and is unanswerable here.
13. **No backfill.** Spec asked. Backend has no `backfill` action either. Fair as a
    "not yet" — but worth recording.
14. **Permission warning for `auto_grant_permissions` is good** (red border, explicit
    copy). One of the few bright spots — keep this pattern.

**P2 — polish:**

15. Schedule string placeholder shows NL ("every weekday at 9am") but doesn't tell the
    user that cron is also accepted. Add "Cron or natural language. e.g. `0 9 * * 1-5`
    or `every weekday at 9am`."
16. Per-row "Run now" should disable while a global save is in progress — currently
    only blocks while *that row* is running.
17. Windows users see a destructive red banner saying it's not implemented but can
    *still create paused schedules.* Confusing. Either hide create on Windows or make
    the destructive banner less alarmist (it's correct, just visually shouty).
18. The `parse_schedule` result returns `cron` and `description` — UI never shows the
    user the canonicalised cron after it parses their NL input. Showing "We parsed
    'every weekday at 9am' as `0 9 * * 1-5`" would close a major confidence gap.

## Synthesis

**Status of the tab:** Backend ~85% complete, UI ~35% of what the backend supports,
operator workflow ~10% of what an operator needs. Net: not "feature missing," but
**not safe to ship to users who will rely on it for unattended execution.**
