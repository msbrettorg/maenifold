# T-207.11 — Gateway resource proxying

## Problem

The MCP Apps epic (T-203.0) requires fetching `ui://` resources from upstream MCP servers. The gateway currently only proxies `tools/call` and `tools/list`. MCP Apps need `resources/read` proxied to the upstream server that declared the tool with `_meta.ui.resourceUri`.

T-203.8 (McpAppFrame resource fetch) is blocked on this.

## Solution

Add `read_resource` to `StdioSession` and `StdioPool`, then extend `MaenifoldHandler::read_resource` to proxy `ui://` URIs to gateway servers.

### Design

1. **`StdioSession::read_resource(uri: &str) -> Result<ReadResourceResult>`**
   - Mirror the `call_tool` pattern: check usability, acquire IO lock, send `resources/read` JSON-RPC with `{"uri": uri}` params, parse response as `ReadResourceResult`
   - Use same timeout/cancellation/poisoning logic as `call_tool`

2. **`StdioPool::read_resource(server_name: &str, uri: &str) -> Result<ReadResourceResult>`**
   - Mirror `call_tool`: get session, try call, restart on pre-write failure
   - Same error contract as `call_tool`

3. **`MaenifoldHandler::read_resource` update**
   - Current: always delegates to native resource handlers
   - New: if URI starts with `ui://` AND gateway pool exists, try each gateway server (broadcast to all, take first success)
   - If no gateway server returns the resource, return existing resource error
   - If URI doesn't start with `ui://`, use existing native resource path

### Broadcast rationale

We don't have a resource→server mapping (only tool→server via ToolRoutingRegistry). Since `ui://` resources are declared in tool `_meta.ui.resourceUri`, the server that owns the tool owns the resource. Broadcasting to all gateway servers is correct because:
- Typically 1-5 gateway servers, so broadcast is fast
- Only one server will have the resource; others return error
- No need for a new registry

## Scope

- Only proxy `resources/read` for `ui://` URIs (not `resources/list`, `resources/subscribe`)
- Native resources (`asset://`, `memory://`, etc.) unchanged
- Error: if no gateway server returns the resource → existing "resource not found" error

## Key Files

- Modify: `crates/maenifold-core/src/mcp/stdio_session.rs` (add `read_resource`)
- Modify: `crates/maenifold-core/src/mcp/stdio_pool.rs` (add `read_resource`)
- Modify: `crates/maenifold-core/src/mcp/mod.rs` (extend `read_resource` for `ui://` gateway routing)

## Acceptance criteria

1. `resources/read` with a `ui://` URI proxied to the correct upstream server
2. Non-`ui://` URIs use existing native resource handlers
3. Error handling: no gateway server has the resource → resource not found error
4. `cargo build --release -p maenifold-core` passes
5. All modified files under 300 LOC
