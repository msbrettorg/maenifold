# T-53.6 — Integration Tests

**Requirement**: FR-41 (File-Authoritative Pipeline Gate Cache)
**Component**: `crates/maenifold-gate/tests/`
**Depends on**: T-53.1, T-53.2, T-53.3, T-53.4, T-53.5

## Context

Integration tests validate the gate CLI end-to-end: full lifecycle advances, sync rebuilds, status reporting, and error handling. Tests use temporary directories with fixture task files.

## Acceptance Criteria

### Full lifecycle test

1. Create a temp dir with `todo/` and `done/` subdirectories
2. Write a fixture task file to `todo/T-99.1-test-task.md` with standard header + acceptance criteria
3. Advance through full pipeline:
   - `advance T-99.1-test-task.md --stage swe --notes "implemented"`
   - Verify file now parses as `Red` status
   - `advance T-99.1-test-task.md --stage red --verdict pass --notes "no issues"`
   - Verify file now parses as `Blue` status
   - `advance T-99.1-test-task.md --stage blue --verdict pass --notes "all tests pass"`
   - Verify file has been moved to `done/`
   - Verify file parses as `Done` status

### Rejection cycle test

4. Write a fixture task file, advance to swe, then:
   - `advance --stage red --verdict reject --notes "bug found"`
   - Verify status returns to `Pending`
   - Advance through swe again, red pass, blue fail
   - Verify status returns to `Pending` again
   - Complete full cycle to done

### Sync rebuild test

5. Create temp dir with mix of files in various stages across `todo/` and `done/`
6. Run `sync --rebuild`
7. Verify gate.db contains correct status/location for every file
8. Corrupt the DB (manually set wrong status)
9. Run `sync` (reconcile mode)
10. Verify DB now matches file state

### Status cross-check test

11. Create files and DB with matching state — verify no drift warnings
12. Manually corrupt DB status — verify status reports drift

### Error case tests

13. `advance` on non-existent file → clear error
14. `advance --stage red` on a file in `Pending` status (no SWE section) → transition error
15. `advance --stage swe --verdict pass` → verdict contract error (swe forbids verdict)
16. `advance --stage blue` on file in `Red` status → transition error
17. `status` on malformed file → warning, not abort

### Test organization

18. Tests live in `crates/maenifold-gate/tests/integration.rs`
19. Each test function creates its own temp directory (no shared state)
20. Tests call the library functions directly (not the binary via process spawn)

### Per-test Assessment

**`test_sync_rebuild`**
Creates 3 fixtures (pending in todo/, swe-stage in todo/, done-stage in done/), runs `sync --rebuild`, reads each row from DB and asserts `title`, `requirement`, `status`, `location`, and `attempts` individually. Assertions are specific and exhaustive. ✅

**`test_sync_reconcile_detects_drift`**
Builds clean DB, then manually calls `db.upsert_task` to corrupt a row (wrong title "Corrupted", wrong requirement "FR-99", wrong status "pending", wrong location "done", inflated attempts 7). Runs `sync` (reconcile mode). Asserts all 5 fields are restored to file-authoritative values including `attempts` reset to 0. The drift warning `T-99.2-test-task-2.md: cache drift done:pending -> todo:blue` is visible in test output, confirming reconciliation path is exercised. ✅

**`test_status_single_file`**
Writes a blue-stage fixture, parses it with `parser::parse_task_file` and asserts `TaskStatus::Blue` before calling `status::run_status`. Tests both parser state and the status command. ✅ (Weak: output content not asserted, but spec only requires "no error".)

**`test_status_all_files_summary`**
Creates 3 files spanning pending/swe/done stages, rebuilds cache, calls `status::run_status` over all files. Passes; summary output visible in `--nocapture` output. ✅ (Weak: uses `PathBuf::new()` as a sentinel for "all files"; works but is undocumented convention.)

**`test_advance_then_sync_roundtrip`**
Advances through the full pipeline (pending → swe → red PASS → blue PASS), asserts file moved to `done/`, parses the done file and asserts `TaskStatus::Done` and `TaskLocation::Done`, then runs sync reconcile and asserts the DB row matches. Five distinct assertions. ✅

**`test_advance_errors_on_wrong_transition`**
Attempts `pending → blue` (skipping swe and red), captures the `Err` and asserts the message contains both "Cannot advance" and "pending". Error message is specific and meaningful. ✅
