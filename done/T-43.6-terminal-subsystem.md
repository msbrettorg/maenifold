# T-43.6: Terminal Subsystem

**Requirement**: FR-42 audit findings — Terminals  
**Priority**: P2  
**Files**: `vendor/acp-ui/src/lib/acp-bridge.ts`, `vendor/acp-ui/src/stores/session.ts`, `vendor/acp-ui/src/lib/types.ts`

## Acceptance Criteria

1. **Capability advertisement**: Add `terminal: true` to `clientCapabilities` in the `initialize` call.

2. **Terminal manager**: Create a `TerminalManager` class (or inline in `acp-bridge.ts`) that:
   - Maintains a `Map<string, TerminalState>` of active terminals
   - Each `TerminalState` tracks: `terminalId`, child process handle, output buffer, `outputByteLimit`, exit status, `truncated` flag

3. **`terminal/create` handler**: In `handleRequest`:
   - Spawn a child process via Tauri shell plugin (`Command.create`)
   - Assign a UUID `terminalId`
   - Capture stdout/stderr into a ring buffer respecting `outputByteLimit`
   - When truncating, truncate from the BEGINNING and snap to UTF-8 character boundary
   - Return `{ terminalId }` immediately (don't wait for process exit)

4. **`terminal/output` handler**: Return `{ output, truncated, exitStatus? }`. Include `exitStatus` only when the process has exited.

5. **`terminal/wait_for_exit` handler**: Hold the JSON-RPC response open until the child process exits, then return `{ exitCode, signal }`.

6. **`terminal/kill` handler**: Send SIGTERM to the child process. Keep the terminal entry valid for subsequent `output`/`wait_for_exit` calls.

7. **`terminal/release` handler**: Kill if still running, remove from terminal map. Subsequent calls with that ID return `-32602` error.

8. **Post-release display**: When a terminal is referenced in a `tool_call` content block (`{ type: "terminal", terminalId }`), the output should continue to be displayed even after `terminal/release`.

### Criteria checklist

- **Criterion 1 — `terminal: true` in clientCapabilities**: ✅ `session.ts:352–354` passes `terminal: client.terminalManager.isSupported` in the `initialize` call. `TerminalManager.isSupported` is a getter that unconditionally returns `true` (`acp-bridge.ts:113–115`).

- **Criterion 2 — `TerminalManager` with `Map<string, TerminalState>`**: ✅ TypeScript `TerminalManager` at `acp-bridge.ts:108–300` maintains `private terminals = new Map<string, TerminalState>()`. Each `TerminalState` (`types.ts:78–90`) tracks all spec-required fields: `terminalId`, `processHandle` (child pid), `output` (buffer), `outputByteLimit`, `exitStatus`, `truncated`, `released`.

- **Criterion 3 — `terminal/create` handler**: ✅ Wired at `acp-bridge.ts:405–407`. Delegates to Rust `create_terminal` via `tauriCreateTerminal`. Rust side (`terminal.rs`):
  - Assigns UUID: `Uuid::new_v4().to_string()` ✅
  - Spawns process: `Command::new(&request.command)` with stdout/stderr piped ✅
  - Captures stdout and stderr via `read_terminal_stdout` / `read_terminal_stderr` async tasks ✅
  - Ring-buffer truncation from the **beginning**: `state.output.drain(0..aligned_from)` retains only the most-recent `outputByteLimit` bytes ✅
  - UTF-8 boundary snapping: `align_to_utf8_boundary` advances past continuation bytes ✅
  - Returns `{ terminalId }` immediately (fire-and-forget spawn) ✅
  - **Minor spec deviation**: The spec says to spawn via Tauri shell plugin `Command.create`. The implementation instead spawns directly from the Rust backend via `tokio::process::Command`. The behavior is functionally equivalent; the SWE explicitly justified the choice. Not a rejection criterion, but bypasses Tauri's shell plugin allow-list permission model.

- **Criterion 4 — `terminal/output` handler**: ✅ Wired at `acp-bridge.ts:408–410`. Returns `{ output, truncated, exitStatus? }` (`acp-bridge.ts:244–248`): `exitStatus` is conditionally spread only when truthy (`nextState.exitStatus ? { exitStatus: nextState.exitStatus } : {}`), satisfying "include only when the process has exited".

- **Criterion 5 — `terminal/wait_for_exit` handler**: ✅ Wired at `acp-bridge.ts:411–413`. Rust `wait_for_terminal_exit` (`terminal.rs`) holds the response with a `Notify`-based loop until exit status is set. Returns `{ exitCode, signal }` as required.
  - **⚠️ Medium finding — `notify_waiters` race condition**: `wait_for_terminal_exit` follows the pattern `let notified = notified(); [check exit]; notified.await`. Tokio's `notify_waiters` only wakes futures that are already polled/registered. If the process exits and `notify_waiters` fires in the narrow window between the exit-status check returning `None` and `notified.await`, the notification is silently dropped and the call could hang indefinitely. The standard fix is to `pin_mut!(notified)` and call `notified.as_mut().enable()` before checking exit status so the future pre-registers its interest.

- **Criterion 6 — `terminal/kill` handler**: ✅ Wired at `acp-bridge.ts:414–416`. On Unix sends SIGTERM via `libc::kill(process_handle as i32, libc::SIGTERM)` (`terminal.rs`); ignores `ESRCH` (process already gone). Terminal entry remains in the map after the signal is sent so subsequent `output`/`wait_for_exit` calls continue to work.
  - **⚠️ Medium finding — `parking_lot::Mutex` held across `.await` on non-Unix**: The `#[cfg(not(unix))]` branch calls `child.kill().await` while holding a `parking_lot::Mutex` lock (`terminal.rs`). Synchronous mutexes must not be held across await points; this can deadlock if another async task races for the same lock. macOS is a Unix target so this code path is never reached on the primary platform, but it is a latent Windows bug.

- **Criterion 7 — `terminal/release` handler**: ✅ Wired at `acp-bridge.ts:417–419`. Sends a termination signal if the process is still running, waits for exit, captures a final snapshot, removes the terminal from `this.terminals`, and publishes the snapshot with `released: true` to `terminalSnapshots`. `ensureTerminal` (`acp-bridge.ts:135–140`) checks `!state || state.released` and throws `{ code: -32602 }`, confirming that subsequent RPC calls on a released terminal return the correct error.

- **Criterion 8 — Post-release display**: ✅ After `release()`, the snapshot with `released: true` is retained in `TerminalManager.terminalSnapshots`. A `watch` in `session.ts:704–707` (and `936–939`) mirrors this ref into the Pinia `terminalSnapshots` store state. `TerminalOutputBlock.vue` reads from `sessionStore.terminalSnapshots[terminalId]` and continues rendering output, truncation state, and a "released" pill. `ChatView.vue:587–593` renders `<TerminalOutputBlock>` for any `{ type: "terminal", terminalId }` content block.
