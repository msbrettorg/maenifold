# T-218.28 — Teams ACP Dispatch Security Regression Tests

## Problem

Teams-triggered ACP dispatch is security-sensitive because Teams messages are untrusted input. Prior work hardcoded `autoGrantPermissions: false`, but two gaps remain: (1) no regression tests guard the mechanical permission boundary, and (2) `sender_allowed()` in `handler.rs` matches allow/deny entries against BOTH `sender_mri` AND `sender_name`, enabling display-name spoofing to bypass sender filters.

## Scope

This task covers:
- Regression tests for the `autoGrantPermissions: false` boundary
- Hardening `sender_allowed()` to match MRI-only for authorization
- Regression tests for sender filter behavior with adversarial inputs

This task does NOT cover:
- Denial observability in Teams monitor status (separate task)
- Live Teams→ACP dispatch wiring (T-218.44)
- LLM-level prompt injection defense (out of scope — we test the mechanical boundary)

## Acceptance Criteria

- [ ] A malicious Teams message containing tool-use/permission-grant instructions produces an ACP payload with `autoGrantPermissions: false`
- [ ] The same payload, parsed through AcpExec payload handling, yields `auto_approve == false`
- [ ] Teams dispatch metadata includes immutable `sender_mri` and `sender_name` as distinct fields
- [ ] `sender_allowed()` authorizes only by normalized `sender_mri`; spoofed `sender_name` matching an allow-list entry does NOT pass authorization
- [ ] Deny-list entries match only by `sender_mri`
- [ ] Tests cover: allowed MRI, denied MRI, unknown MRI, and all three with malicious message content
- [ ] `cargo build --release -p maenifold-core` succeeds
- [ ] `cargo test -p maenifold-core -- teams` succeeds

## Files Likely Touched

- `crates/maenifold-core/src/teams/handler.rs` — fix `sender_allowed()` to MRI-only matching + tests
- `crates/maenifold-core/src/teams/dispatch.rs` — prompt-injection regression tests
- `crates/maenifold-core/src/tools/acp_exec_payload.rs` — assert auto_approve=false parsing
