# T-48.3 — API: `/api/memory/recent` Endpoint

**Requirement:** FR-48
**Component:** `crates/maenifold-core/src/api/`

## Summary

Add a REST endpoint that wraps maenifold's `RecentActivity` MCP tool.

## Acceptance Criteria

1. `GET /api/memory/recent?filter=all&limit=20&timespan=7.00:00:00` returns JSON
2. Response shape: `{ items: [{ uri, title, modified, sections }] }`
3. Parameters: `filter` (optional, default "all"), `limit` (optional, default 10), `timespan` (optional), `includeContent` (optional, default false)
4. Handler reuses existing `RecentActivity` logic
5. Route registered in `api_routes()`

## Architecture Context

- Same pattern as T-48.1/T-48.2
- RecentActivity logic in `crates/maenifold-core/src/memory/` or `crates/maenifold-core/src/recent/`

## SWE Remediation

### Changes Made

1. **`crates/maenifold-core/src/tools/recent_activity.rs`** — Made `parse_recent_activity_timespan` public (`fn` → `pub fn`) so the API handler can reuse the existing C#-style timespan parser rather than duplicating it.

2. **`crates/maenifold-core/src/tools/mod.rs`** — Added `parse_recent_activity_timespan` to the public re-exports.

3. **`crates/maenifold-core/src/api/routes.rs`** — Added:
   - `use crate::markdown::extract_h2_sections` and `use crate::tools::{collect_recent_activity_records, parse_recent_activity_timespan}` to imports.
   - `RecentActivityItem` struct (`uri`, `title`, `modified`, `sections`) and `RecentActivityResponse` struct (`items`) for JSON serialization.
   - `memory_recent` async handler: parses `filter`, `limit`, `timespan`, `includeContent` query params following the same defaults/clamping as the MCP tool handler; calls `collect_recent_activity_records`; maps records through `extract_h2_sections` to produce section heading lists (or heading+body when `includeContent=true`).
   - `map_maenifold_api_error` helper so query-validation failures from the shared RecentActivity logic surface as `400 Bad Request`, missing-index situations surface as `404 Not Found`, and unexpected failures remain `500 Internal Server Error`, matching the existing `ApiError` pattern.
   - Registered `.route("/api/memory/recent", get(memory_recent))` in `api_routes()`.

### Decisions

- Reused `collect_recent_activity_records` (public API) which internally handles filter parsing and timespan cutoff, matching MCP tool behavior exactly.
- Invalid `timespan` and `filter` values are translated from `MaenifoldError::InvalidArgument` to `ApiError::bad_request`, since they come directly from request query parameters.
- A missing RecentActivity index (`MaenifoldError::Message("No database found...")`) is translated to `ApiError::not_found`, preserving the existing `ApiError` response style for missing API-side resources.
- Limit clamped to 1000 to match the MCP tool's unbounded-query prevention.

### Non-blocking caveat

`map_maenifold_api_error` maps **all** `MaenifoldError::Message` variants to `404 Not Found`. `MaenifoldError::Message` is a catch-all string variant (`error.rs:30`) used across the codebase. Within the current call graph of `memory_recent` the only `Message` in play is the "No database found" sentinel (`recent_activity.rs:198`), so the mapping is correct today. If any future caller introduces a `Message` variant for a non-resource-not-found condition, it will silently surface as 404 instead of 500. Recommend tightening the match to `MaenifoldError::Message(m) if m.contains("No database found")` or introducing a dedicated `MaenifoldError::NotReady` variant.
