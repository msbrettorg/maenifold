# T-77.2: Per-Task Pipeline — Delete Project-Level Pipeline

## Context

Gate currently has a layered pipeline resolution: CLI `--pipeline` flag → `pipeline.json` in project root → default SDD. This is backwards-compat complexity that no customer needs. The task's frontmatter `pipeline:` field already exists on every task file — make it the sole authority and delete everything else.

## Requirements

1. **Task frontmatter `pipeline:` is the sole pipeline authority** — `load_embedded_pipeline(frontmatter.pipeline)` directly
2. **Delete `pipeline.json`** from project root — no project-level pipeline config
3. **Delete `--pipeline` CLI flag** from pass, reject, status, sync commands
4. **Delete `pipeline` parameter** from all MCP tool definitions (gate_pass, gate_reject, gate_status, gate_sync)
5. **Delete `load_pipeline_def()`** — the fallback chain resolution function
6. **Keep `load_embedded_pipeline(name)`** — the 4 canonical definitions (sdd, tdd, gsd, lightweight) stay compiled in
7. **Tasks without `pipeline:` frontmatter are data errors** — return a clear error, not a silent default
8. **All existing tests updated** to reflect the new resolution

## Call Sites

- `pass.rs` — reads pipeline to determine next stage. Change to: read task frontmatter → `load_embedded_pipeline()`
- `reject.rs` — reads pipeline to determine rejection target. Same change.
- `status/mod.rs` — reads pipeline for stage context. Same change.
- `sync.rs` — processes all tasks. Resolve pipeline per-task inside the loop.

## Red-team Audit

**Verdict: PASS** — all primary requirements satisfied. Two findings, one pre-existing defect surfaced.

### F1 — AC #7 Violated for `sync` / `status`: warn+default ≠ clear error (Low, Deliberate)

**Spec requirement #7 and AC checkbox state:** "Task without `pipeline:` in frontmatter produces a clear error."

**What was shipped:** `sync` and `status` call `load_task_pipeline(path, content, warn_default: true)`, which emits a `warning:` to stderr and silently falls back to `sdd`. They do **not** return an error.

**Contradiction:** The SWE Remediation section of this very spec says *"legacy tasks without `pipeline:` warn and default to `sdd`"*, and the SWE Notes repeat it. The spec contradicts itself: requirement #7 / AC #7 demand an error; the remediation narrative explicitly authorises a warning+default.

**Impact:** Any task file that slips through without a `pipeline:` key will silently be processed under the `sdd` pipeline — no caller is alerted to the data error. For the `pass`/`reject` paths (which do error) this is fine. For bulk `sync`/`status` it means corrupted or unmigrated files are silently admitted.

**Remediation path:** Add `pipeline:` migration gate to `sync` (error on missing in non-legacy mode, or surface a machine-readable error field in JSON output) and formally acknowledge the AC as intentionally weakened in the spec. The current test `test_status_json_reports_legacy_done_file_as_pending` asserts the warning fires but does not assert that the returned status is trustworthy when the pipeline was defaulted. Minimum fix: annotate JSON output with `"pipeline_defaulted": true` so consumers can detect the ambiguity.

---

### F2 — `reject.rs` Does Not Write Frontmatter Status — Sync Stomps the Reject (Medium, Pre-existing)

**Not introduced by T-77.2** — the git diff shows only pipeline-resolution code was changed in `reject.rs`. This bug predates this sprint. However, T-77.2 makes it materially worse: before this sprint `sync` resolved pipeline from `pipeline.json` / CLI; after T-77.2 `sync` reads task frontmatter as authoritative state. That elevation of frontmatter authority increases the blast radius of the omission.

**The defect:** `pass.rs` calls `crate::frontmatter::write_frontmatter_status(&file_path, &next)` after every transition. `reject.rs` does not. After a reject of a task at `status: red`, the DB is correctly updated to `status: pending` and `attempts` is incremented — but the frontmatter in the `.md` file still reads `status: red`. On the next `gate sync`, `resolve_task_state` reads frontmatter and sees `status: red`; the DB is overwritten back to `red`, silently undoing the reject.

**Reproduction:**
1. Task file has `status: red` in frontmatter.
2. `gate reject T-X` → DB: `pending`, frontmatter: still `red`.
3. `gate sync .` → DB: overwritten to `red`. Reject silently lost.

**No test covers this path** — all reject tests check the DB immediately after reject without re-syncing. `pipeline_tests.rs::reject_at_red_returns_to_pending` and `reject_tests.rs::reject_at_red_returns_to_pending` both assert `row.status == "pending"` but neither calls `sync` afterward.

**Remediation:** Add `crate::frontmatter::write_frontmatter_status(&file_path, &target)?;` in `reject.rs` immediately after `append_orchestrator_section`. Add a reject+sync roundtrip test in `frontmatter_state_integration.rs`.

---

### F3 — No Explicit Test That `--pipeline` Is Rejected by CLI (Negligible)

`cli_parser.rs` tests `--bogus` for `sync` and `status` but no test sends `--pipeline` to any subcommand. Low risk: the generic unknown-flag handler will catch it, and there is zero production code path that would accept it. Mention it for completeness; no action required.

---

### F4 — `sync` warn+default path has no direct unit test (Minor Coverage Gap)

`test_status_json_reports_legacy_done_file_as_pending` (binary integration test) covers the `status` warning path. No test calls `sync::run_sync` directly with a pipeline-less task and asserts the warning is emitted. Add a `sync_isolation_tests.rs` case that captures stderr and checks for `"defaulting to sdd"`.
