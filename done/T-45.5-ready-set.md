# T-45.5: Ready Set Computation

**Requirement**: FR-45.5
**RTM**: RTM-329, RTM-330, RTM-331, RTM-332
**Priority**: P0 — Core scheduling logic

## Context

The pipeline engine needs a pure function to compute which nodes are ready for dispatch. A node is "ready" when all its upstream dependencies are satisfied and it hasn't been claimed yet. This function reads the pipeline definition + node states and returns the set of ready node IDs.

## Scope

Add `compute_ready_set` and related functions to `crates/maenifold-core/src/workflow/pipeline/`.

## Acceptance Criteria

1. **`compute_ready_set` function**: `fn compute_ready_set(definition: &PipelineDefinition, node_states: &HashMap<String, NodeState>) -> Vec<String>` — returns node IDs that are ready for dispatch.
2. **Ready condition**: A node is ready when:
   - Its own status is `Pending`
   - ALL upstream nodes connected by `Success` edges have status `Completed`
   - ALL upstream nodes connected by `Always` edges have status `Completed` OR `Abandoned`
3. **Root nodes**: Nodes with no incoming edges are ready if their status is `Pending` (they have no upstream dependencies).
4. **`always` edge semantics**: An `Always` edge is satisfied when the upstream node is `Completed` OR `Abandoned`. This enables fault-tolerant pipelines where downstream nodes run regardless of upstream success.
5. **Pure function**: The function takes immutable references and returns a new Vec. No side effects, no file I/O, no database. Dropping and recomputing yields identical results.
6. **`compute_pipeline_status` function**: `fn compute_pipeline_status(node_states: &HashMap<String, NodeState>) -> &'static str` — returns overall pipeline status:
   - `"completed"` if all nodes are `Completed`
   - `"stuck"` if any node is `Stuck` and no nodes are `Active` or `Ready`
   - `"active"` otherwise
7. **Blocked detection**: A node is blocked when at least one upstream `Success` edge connects to a node that is `Abandoned` or `Stuck` (and the edge is NOT `Always` type).

## Implementation Notes

- Create `crates/maenifold-core/src/workflow/pipeline/engine.rs` for these functions
- Build an adjacency list from edges for efficient traversal
- For each node: find all incoming edges, check if all upstream nodes satisfy the edge condition
- `HashMap<String, NodeState>` maps node ID → current state

### Criteria Checklist

- **AC1 — Ready condition (Pending + Success-upstream Completed + Always-upstream Completed/Abandoned)**: ✅  
  `compute_ready_set` (engine.rs:4–31) applies two filter stages. First filter (lines 8–14) gates on `NodeStatus::Pending`. Second filter (lines 15–25) calls `is_node_blocked` + `edges.iter().all(is_edge_satisfied)`. `is_edge_satisfied` (lines 72–80) correctly maps `EdgeType::Success → Completed` and `EdgeType::Always → Completed | Abandoned`.

- **AC2 — Root nodes ready when Pending**: ✅  
  `build_incoming_edges` (lines 47–65) seeds every node with an empty vec via `incoming_edges.entry(node.id.as_str()).or_default()`, guaranteeing root nodes receive an empty slice. `is_node_blocked(&[])` short-circuits to `false`; `[].iter().all(...)` evaluates vacuously `true`. Root + Pending → in ready set.

- **AC3 — `always` edge semantics (Completed OR Abandoned)**: ✅  
  `is_edge_satisfied` line 76–78: `matches!(state.status, NodeStatus::Completed | NodeStatus::Abandoned)`. Test `ready_set_accepts_abandoned_upstream_for_always_edges` covers the Abandoned branch. Completed branch is covered implicitly by `ready_set_requires_success_dependencies_completed` (middle→tail uses Success, but the Completed-upstream Always path is implicitly exercised by the vacuous-root test).

- **AC4 — Pure function**: ✅  
  Both public functions accept only immutable references (`&PipelineDefinition`, `&HashMap<String, NodeState>`). No `mut` external state, no `static` mutation, no `unsafe`, no file or DB I/O. `build_incoming_edges` allocates a local `HashMap` that is dropped at the end of each call. Determinism test `ready_set_recomputes_deterministically` confirms identical results across two calls.

- **AC5 — `compute_pipeline_status` correctness**: ✅  
  - `"completed"`: `!node_states.is_empty() && all(Completed)` — lines 33–38. Guard prevents empty-map false-positive. ✅  
  - `"stuck"`: `has_stuck && !has_active_or_ready` — lines 40–48. ✅  
  - `"active"`: default fall-through — line 50. ✅  
  All three paths tested by `pipeline_status_returns_completed_when_all_nodes_completed`, `pipeline_status_returns_stuck_when_stuck_without_active_or_ready`, and `pipeline_status_returns_active_when_ready_or_active_nodes_exist`.

- **AC6 (Blocked detection — Success edge to Abandoned/Stuck)**: ✅  
  `is_node_blocked` (lines 67–74) iterates incoming edges, returns `true` if any has `EdgeType::Success` AND upstream is `Abandoned | Stuck`. `Always` edges are explicitly excluded (only `Success` is checked). Test `ready_set_blocks_success_edge_from_abandoned_or_stuck` exercises both the Abandoned and Stuck cases in a two-edge chain.

---

### Observations (non-blocking)

1. **Unnecessary clone on `EdgeType`** (`engine.rs:72`): `is_edge_satisfied` uses `match (edge.edge_type.clone(), ...)`. `EdgeType` derives `Clone` but not `Copy`, so a heap clone is incurred per edge per call. A ref-match (`match (&edge.edge_type, ...)`) would eliminate the allocation at zero logic cost. Minor code smell; no correctness impact.

2. **Test gap — `Always` edge satisfied by `Completed` upstream**: No explicit test asserts that `Always + Completed → ready`. The code path is logically correct (`Completed | Abandoned`), but the only explicit Always test uses Abandoned. Low risk; worth adding for completeness.

3. **`Always` edge with `Stuck` upstream is an unspecified limbo state**: If upstream is `Stuck` on an `Always` edge, `is_edge_satisfied` returns `false` (Stuck ∉ {Completed, Abandoned}) while `is_node_blocked` returns `false` (only guards Success edges). The downstream node stays `Pending` indefinitely. `compute_pipeline_status` will eventually surface this as `"stuck"` (has_stuck=true, no Active/Ready), so the pipeline doesn't silently hang — but this spec gap means an `Always` edge cannot rescue from a Stuck upstream. The spec defines Always semantics only for Completed/Abandoned, so the implementation is not in violation; the spec should define the Stuck+Always case explicitly.

4. **Empty-map edge case**: `compute_pipeline_status` with an empty `node_states` map returns `"active"` (not `"completed"`). The `!node_states.is_empty()` guard is the correct defensive choice here — a pipeline with no tracked nodes is not "completed" — but the spec does not address this case. Callers should always pass non-empty state maps; `validate_pipeline` already enforces at least one node.
