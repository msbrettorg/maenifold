# T-207.0 — Epic: MCP Tool Gateway

## Problem

Maenifold serves its own tools via Streamable HTTP MCP at `127.0.0.1:8080/mcp`. Dashboard iframes can call these tools directly via `fetch()` (proven by gate-pipeline.html calling gate at `127.0.0.1:8081/mcp`).

However, most MCP servers configured in `maenifold.json` (MSX, WorkIQ, mail, calendar, Teams, etc.) are **stdio** servers: they run as child processes of the Copilot CLI, not as HTTP endpoints. Dashboard iframes cannot spawn subprocesses, so they cannot reach these servers.

## Solution

Extend maenifold's existing Streamable HTTP MCP endpoint to act as a **tool gateway**, proxying `tools/call` requests for tools that belong to configured stdio MCP servers. From the client's perspective, all tools (native + gateway) appear at the same `/mcp` endpoint. The client calls `tools/list` and gets everything. The client calls `tools/call` with any tool name and gets the result, regardless of whether that tool is native or proxied through stdio.

This is protocol-correct per the MCP spec (2025-03-26): the protocol is transport-agnostic, and a Streamable HTTP frontend backed by stdio backends is a standard gateway pattern. No custom extensions to the protocol are required.

## Scope

**In scope:** tool proxying (`tools/list`, `tools/call`) for gateway-enabled stdio servers.

**Explicitly out of scope (future sprints):**
- Resource proxying (`resources/list`, `resources/read`) — gateway does not forward upstream resource capabilities
- Prompt proxying (`prompts/list`, `prompts/get`) — same
- `notifications/tools/list_changed` propagation from upstream — stateless `NeverSessionManager` has no connected clients to notify; clients re-discover on next `tools/list`
- Upstream server-to-client requests — gateway sends `capabilities: {}` during init, upstream SHOULD NOT send requests requiring a response
- Upstream `notifications/message` (logging) — silently consumed by the pool, optionally forwarded to maenifold tracing

## Architecture

```text
Dashboard iframe
  -> HTTP POST /mcp (with Accept: application/json, text/event-stream)
  -> JSON-RPC tools/list | tools/call

Maenifold HTTP MCP service (axum + rmcp StreamableHttpService)
  -> native ToolRegistry for built-in tools
  -> ToolRoutingRegistry lookup for gateway tools
  -> StdioPool[server_name] for delegated stdio calls

Configured stdio MCP server (child process)
  -> JSON-RPC over stdin/stdout (newline-delimited)
  -> response returned through the same /mcp endpoint
```

**Shared state model:** `StdioPool` and `ToolRoutingRegistry` are constructed once in `serve_http_listener_with_shutdown`, wrapped in `Arc`, and captured by the `MaenifoldHandler` factory closure. They are NOT created per-handler — `MaenifoldHandler::new()` is called per connection by rmcp.

## Shared Pool — All Consumers

The `StdioPool` is the **single owner** of all gateway-enabled stdio MCP child processes in maenifold. Every codepath that currently spawns stdio MCP servers independently MUST migrate to the shared pool:

| Consumer | Current pattern | After T-207 |
|---|---|---|
| **HTTP gateway** (dashboards) | N/A (new) | `MaenifoldHandler` delegates via `Arc<StdioPool>` |
| **Pipeline designer UI** | `GET /api/discovery/mcp-tools` spawns-discovers-kills per server | Reads cached tools from pool (instant) |
| **Pipeline driver** (execution) | `external_mcp.rs` spawns per `tools/call` | `pool.call_tool()` (T-207.8) |
| **Discovery endpoint** | `mcp_discovery/stdio.rs` spawns-discovers-kills per server | Reads from pool cache; discovery is init-time only (T-207.9) |

**Not migrated** (out of scope): Jockey ACP sessions pass `Vec<acp::McpServer>` configs to ACP agent processes — the agent spawns its own MCP servers. That's the agent's responsibility, not maenifold's.

### Benefits of convergence
- MCP servers that take 5-15s to spawn+init pay that cost **once** at maenifold startup
- No orphaned child processes from pipeline cancellation or discovery timeout
- One crash recovery policy, one error contract, one shutdown path
- Discovery becomes a cache read, not a 60s spawn-and-probe cycle

## Key Constraints

- MUST comply with MCP protocol spec 2025-03-26 (Streamable HTTP transport, stdio transport, Lifecycle)
- MUST reuse maenifold's existing axum router and CORS config (localhost-only)
- MUST handle stdio process crashes: retry only on connection-establishment failure, NOT on mid-call EOF (non-idempotent safety)
- MUST NOT expose servers unless `gateway: true` in config
- Tool name collisions across servers MUST be detected eagerly at startup and rejected with a clear error
- Stateless HTTP mode (`NeverSessionManager`) is preserved; each gateway call is independent
- `StdioPool` + `ToolRoutingRegistry` MUST be shared `Arc` state, NOT per-handler
- Upstream `protocolVersion` mismatch MUST be handled per Lifecycle § Version Negotiation: gateway supports `{"2025-03-26", "2024-11-05"}` exactly; reject others with clear error
- Per-call timeout MUST be enforced per Lifecycle § Timeouts (default 60s, configurable); on timeout, send `notifications/cancelled` per Cancellation utility and mark session poisoned
- Shared gateway state uses `ArcSwap<GatewayRuntime>` in `ApiState` for lock-free reads + atomic reload swaps
- Localhost-only binding + Origin CORS is the auth model; explicitly documented as sufficient for local-machine use
