# T-205.715 — Fix AppTabBar active-tab chrome to match design system

## Problem

Repeated Sprint 205 UAT tasks against `AppTabBar` are failing because the selected tab renders hard border chrome instead of a subtle selected-state treatment. The current implementation uses a custom 3px brand underline on the active tab, which keeps surfacing as a crisp border/underline defect in interactive testing.

## Verified ground truth

- `apps/desktop/src/components/AppTabBar.vue:33` renders the shell nav with `border-b border-border-subtle`
- `apps/desktop/src/components/AppTabBar.vue:42` adds `border-b-[3px] border-b-transparent ... data-[state=active]:border-b-brand` to each tab trigger
- `apps/desktop/src/components/ui/tabs/TabsTrigger.vue:19-22` already provides a shared line-variant active-state treatment using transparent borders plus an `after:` indicator, so `AppTabBar` does not need custom hard-border chrome to show selection
- `apps/desktop/DESIGN.md:102-105` says: use `1px` borders by default and `1.5px` only when emphasizing selected/interactive tiles
- `apps/desktop/DESIGN.md:123-129` says semantic colors encode state or intent and are not decorative neon accents
- `done/T-205.11-uat-tab-bar.md:27` records the current failure: the selected tab shows crisp active border/underline lines after keyboard navigation succeeds

## File

- `apps/desktop/src/components/AppTabBar.vue`

## Changes required

1. Remove the custom active-tab hard-border treatment from `AppTabBar.vue`
2. Delegate selected-tab chrome to the shared `TabsTrigger` + `TabsList variant="line"` primitive instead of defining custom active chrome in `AppTabBar.vue`
3. Preserve current tab behavior: click, keyboard navigation, active-state semantics, icon + label layout
4. Do not regress the shell tab order or tab switching behavior already covered by Sprint 205 UAT
5. `AppTabBar.vue` must not define its own selected-tab underline, border, side-border, or pseudo-element indicator

## Acceptance criteria

1. `AppTabBar` no longer uses `border-b-[3px]`, `data-[state=active]:border-b-brand`, or `data-active:border-b-brand` for the selected tab
2. `AppTabBar` trigger classes do not define AppTabBar-owned active chrome tokens, including custom `border-b-*`, `data-[state=active]:border-*`, `data-active:border-*`, side-border classes, or custom `after:*` indicator overrides
3. Selected-tab chrome is inherited from the shared `TabsTrigger` line variant rather than reimplemented in `AppTabBar.vue`
4. Tab click and keyboard navigation behavior remain unchanged
5. `npx vue-tsc --noEmit` passes in `apps/desktop`
6. The failing AppTabBar UAT slice is rerun after the fix to confirm rendered chrome, not just DOM/class contract

## TDD — Blue-team writes test FIRST

Blue-team: add a focused test for `AppTabBar` that proves the current bug before implementation and guards the fix afterward. The test must verify:

- the selected-tab chrome contract does not depend on `border-b-[3px]` or `data-[state=active]:border-b-brand`
- the component still renders the expected tab set and active value
- click behavior and keyboard-driven selection semantics are preserved at the component level as far as the existing test harness allows
- the DOM/class contract only; rendered visual confirmation still requires rerunning the AppTabBar UAT slice after implementation
