# T-243.14.0 — Delta review (architect duo)

Plain-English review of the T-243.14 audit plan against the code as it stands today. Goal: identify the failure modes the spec under-emphasises so the UAT operator files concrete child tickets, not just confirms what we already know.

## TL;DR

The spec is a fair audit checklist but it implicitly assumes the app already has the *primitives* required to recover gracefully. It largely doesn't. We have a toast library wired up (vue-sonner) and that's it. There is **no global connection-status surface**, **no inline reconnect indicator in chat**, **no autosave for the user's draft**, and **at least a dozen empty `} catch {}` blocks** that the user will hit before they hit a "nice toast." The audit should be reframed: stop counting toasts, start counting silent failures, and treat the missing primitives as their own backlog rows.

## Method

- Read `todo/T-243.14-error-recovery-ux.md` (the audit script).
- Re-read the closest available inventory artifact: `outputs/uat/cdp-tab-enumeration.md` (the file referenced in the prompt as `outputs/uat/tab-inventory.md` does not exist; flagged below).
- Walked the actual code paths: `apps/desktop/src/stores/session.ts`, `stores/config.ts`, `composables/useMcpClient.ts`, `composables/useAppSession.ts`, `composables/useSessionPersistence.ts`, `App.vue`, every `<pre>` fallback, every `} catch` in `apps/desktop/src/{stores,composables}`.
- Compared against the parity bar in the prompt (Linear graceful errors, Notion offline banner, Slack reconnection banner).

## What the spec gets right

- Forces the operator to *induce* failures rather than wait for them. Good.
- Calls out severity, queueing, and click-to-act on toasts (J/K/L). These are the right knobs.
- Section O ("don't lose user data") is the single most important line in the document. It is also the line we are most likely to fail.
- "No `[object Object]` or `undefined`" is a useful zero-tolerance rule.

## Deltas — what the spec is missing or weak on

### D1. The "tab-inventory.md" referenced in the prompt does not exist
- The audit references `outputs/uat/tab-inventory.md`; the actual file is `outputs/uat/cdp-tab-enumeration.md`. The three flagged findings ("reconnection fails silently", "errors fall back to `<pre>` silently", "no toast on config reload") are not present verbatim in the enumeration file. Either the inventory was never written or it was written and lost. **File T-243.14.1** to either produce the missing inventory or correct the cross-reference. Otherwise we're auditing against a phantom artifact.

### D2. There is no "daemon offline" surface anywhere
- Searched `apps/desktop/src` for `Banner`, `StatusBar`, `ConnectionStatus`, `offline`, `daemon down`. Zero hits in app code.
- `useMcpClient.ts` exposes a `reconnecting` ref but **only the pipeline polling path consumes it** (`composables/pipeline-mcp-polling.ts`). Chat, Memory, Settings, Gate, Workflow, Composer all silently no-op when the daemon is gone — exactly the failure-mode A says to look for.
- The audit asks the operator to *check* this per tab. It should instead require **one global persistent banner** (Slack-style) bound to a single `useDaemonHealth()` composable. Filing a per-tab gap list will produce 8 duplicate tickets that all want the same fix. Recommend: one parent ticket "Add global daemon connectivity banner," then per-tab tickets only for tabs that need *additional* affordances (e.g. chat needs an inline reconnect pill on the active turn).

### D3. Reconnect *can* be silent by design
- `stores/session.ts:183` — `reportReconnectError` accepts `{ suppressErrors: true }` and, when set, **does not call `setError` and therefore never toasts.** Several call sites exercise this flag. That is the literal "reconnection fails silently" finding from the prompt, and it is structural, not cosmetic.
- The audit (B) says "should show the connection error inline AND a retry button." The current code can suppress the error entirely. Add an explicit child ticket: **always surface reconnect failure, even if non-modal — `suppressErrors` must downgrade to a banner/inline pill, never to nothing.**

### D4. Mid-stream chat disconnect has no inline indicator
- `session.ts` toasts on terminal failure but the chat transcript itself shows no "reconnecting…" state on the in-flight turn. The user sees their message hanging with no spinner change, no greyed-out send button, no resume affordance.
- Parity reference: Slack shows a yellow bar; ChatGPT shows "Network error — Regenerate." We have neither. File T-243.14.* "Inline reconnect / regenerate affordance on the active chat turn."

### D5. MCP server down ≠ tool disabled
- `stores/mcp-tool-discovery.ts` warns *once* via toast on discovery failure. Tool buttons in the UI are not put into a disabled state with hover-tooltip explaining *why*. The operator running test C will likely see "tools just don't appear" and tick the box; that's a false pass. Spec should require: **tools that depended on a now-down MCP server remain visible, disabled, with tooltip "Server X unavailable — last seen HH:MM. Retry."**

### D6. Config reload has no success feedback
- `stores/config.ts:loadConfig` toasts only on failure. Save (`saveConfig`, not shown but checked) similarly. The "did it save?" question in the prompt is answered by *silence*, which is the worst answer. Add: **success toast on save and reload, error banner pinned in Settings tab when load fails (don't rely on auto-dismissed toast for a startup-blocking error).**

### D7. The `<pre>` fallback is a real anti-pattern, not just one component
- 14 `<pre>` blocks across `SemanticZoomOverlayFailure.vue`, `ChatToolCallDetails.vue`, `PipelineRunner.vue`, `WorkflowStepProgress.vue`, `PromotionDialog*.vue`, `PermissionEntry.vue`. Most of these are *intentional* (raw JSON / raw output viewers — that's correct).
- The one that matches the flag is `SemanticZoomOverlayFailure.vue`: it dumps `failureReason` raw, with no structure, no "what to try next," no error-class differentiation. That's the thing the prompt is calling out.
- Recommendation: don't broad-strike "no `<pre>`." Be surgical — file a single ticket against `SemanticZoomOverlayFailure.vue` and any other failure-display surface that lacks (a) error category, (b) suggested action, (c) copyable correlation id.

### D8. Empty `} catch {}` blocks — silent failures by construction
- Grep found at minimum: `composables/pipeline-mcp-transport.ts:32,56`, `composables/workflowTreeBuilder.ts:106,228`, `composables/useSessionPersistence.ts:29`, `composables/useAppSession.ts:55`, `composables/useOnboarding.ts:51`. These are *literally* the silent-failure anti-pattern called out as the user's #1 sin.
- Audit doesn't cover this — it's only behavioural ("induce X, observe Y"). Add a **static code rule** subtask: zero empty catches in app code. Each must either rethrow, log to a user-visible surface, or carry an inline comment justifying why swallowing is correct (e.g. cleanup on unmount).

### D9. No autosave / draft recovery — section O will fail
- Searched for `localStorage` writes for chat input, gate notes, settings JSON drafts. Found none for chat or gate; settings is dirty-tracked in memory only.
- Section O of the spec ("user's draft preserved when daemon comes back") will fail on the first attempt. The fix is non-trivial (debounced localStorage per-session for ChatInputBar; draft restore on mount). File this as its own P1, don't bury it as a checkbox.
- Parity: Notion autosaves every keystroke; Linear preserves issue-create drafts across reloads. We do neither.

### D10. Toast queueing / persistence policy is undefined
- vue-sonner is mounted in `App.vue:239` with default config. No `richColors`, no explicit `duration`, no distinction between transient and "must-acknowledge" toasts.
- Connection-level errors (D2/D3) **must not auto-dismiss**. Today they do. The audit asks the operator to *observe* this; the spec should require setting an explicit policy: `info/success` ≤ 4s auto-dismiss, `warning` ≤ 8s, `error` requires dismissal, **persistent banner for connection-class events instead of a toast**.

### D11. "What can I send right now?" has no answer when the agent is unhealthy
- The send button in `ChatInputBar` does not disable when `agent-capabilities` reports the agent is unreachable. The user clicks send, gets nothing. Spec covers this implicitly under (A) but it deserves an explicit subtask: **send button reflects agent health, with tooltip explaining the block.**

### D12. Severity grading in the spec is too coarse
- "silent failure = P0; missing retry = P1; verbose error = P2" is fine but misses the most common case we ship: **wrong-but-confident error messages** (e.g. toasting "Failed to load config" when the real problem is the daemon socket isn't open). Add a P1 grade: **error message blames the wrong layer.**

## Architect duo verdict

**claude-opus-4.7 voice:** The audit is well-scoped behaviourally but treats symptoms, not infrastructure. We will write 30 tickets that all reduce to "we never built a connection-status primitive and we never built a draft persistence primitive." Build the primitives first, audit second.

**gpt-5.5 voice:** Agreed, with one addition — the `suppressErrors` flag in `session.ts` is the kind of thing that looks defensible in code review and is indefensible in production. Reviewing the code surfaced one real bug (D3) the behavioural audit might not even reproduce reliably. Static code review should be a peer of the UAT pass, not a follow-up.

**Joint recommendation:** Promote D2, D3, D8, D9 to P0 *before* running the UAT pass. The UAT then becomes a confirmation exercise rather than a discovery exercise, which is faster and produces less duplicate ticketing.
