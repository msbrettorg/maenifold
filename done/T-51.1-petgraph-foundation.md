# T-51.1 — Replace DAG Backend with petgraph

**Requirement**: FR-40 (Pipeline Active Executor)
**RTM**: RTM-157 / TC-157
**Component**: `crates/maenifold-core/src/workflow/pipeline/engine.rs`, `mod.rs`, `types.rs`

## Context

The pipeline module currently hand-rolls Kahn's algorithm for cycle detection (`validate_pipeline` in `mod.rs`) and manual ready-set computation (`compute_ready_set` in `engine.rs`). These need to be replaced with `petgraph::stable_graph::StableGraph` which gives us:

- Stable node indices that survive `remove_node()` (critical for later graft/join/fork)
- `algo::is_cyclic_directed()` for validation
- `neighbors_directed(n, Incoming)` for ready-set predecessor queries
- serde support for persistence

## Acceptance Criteria

1. Add `petgraph = { version = "0.8", features = ["stable_graph", "serde-1"] }` to `crates/maenifold-core/Cargo.toml`
2. Add a conversion function: `PipelineDefinition → StableGraph<String, EdgeType>` where node weights are node IDs and edge weights are `EdgeType`
3. Refactor `validate_pipeline()` in `mod.rs` to use `petgraph::algo::is_cyclic_directed()` instead of manual Kahn's algorithm. Keep all existing validation (empty nodes, duplicate IDs, dangling edges) — only replace the cycle detection.
4. Refactor `compute_ready_set()` in `engine.rs` to use `graph.neighbors_directed(node, Incoming)` instead of manual incoming-edge map construction. **Keep existing edge semantics unchanged**: `Success` edges require `Completed` upstream; `Always` edges accept `Completed|Abandoned|Stuck`.
5. Refactor `is_node_blocked()` to use petgraph neighbor queries.
6. `compute_pipeline_status()` remains unchanged (it operates on node states, not graph topology).
7. ALL existing pipeline tests must pass unchanged — this is a pure refactor with no behavioral change.

**PASS** — Blocking semantics preserved. `is_node_blocked` in the petgraph version iterates `neighbors_directed(Incoming)` then `edges_connecting(source, node)` to reproduce the original's per-edge check: any `Success` edge from an `Abandoned|Stuck` upstream blocks the target. Logic is equivalent.

**PASS** — Ready-set ordering preserved. `compute_ready_set` still iterates `definition.nodes` in declaration order, using petgraph only for predecessor lookup. The output `Vec<String>` is produced in the same insertion order as before.

**PASS** — Root-node (no-predecessor) case correct. `neighbors_directed(root, Incoming)` returns an empty iterator; `.all()` over empty is `true` (vacuous); `.any()` over empty is `false` (not blocked). Root nodes in `Pending` state are still correctly included.

**PASS** — Missing `node_states` entries handled identically. `is_edge_satisfied` still returns `false` for `(_, None)`, keeping predecessors without state from satisfying edges. `is_node_blocked` treats a missing-state source as neither Abandoned nor Stuck (not blocking), same as the original.

**PASS** — Cycle detection coverage unchanged. `is_cyclic_directed` handles self-loops, back-edges, and cycles spanning disconnected components — all cases Kahn's counted via `processed != nodes.len()`. The existing cycle test (A→B, B→A) passes.

**PASS** — All structural validations preserved: empty-node rejection, duplicate-ID rejection, dangling-source rejection, dangling-target rejection. Only the cycle-check internals changed.

---

### API Misuse

**PASS** — `StableGraph` used correctly. Node indices are allocated via `add_node`, stored in a local `HashMap<String, NodeIndex>`, and used only within the same call frame. No indices are persisted across calls, so there is no risk of stale indices from removals at this stage.

**PASS** — `build_graph()` silently skips edges with unknown endpoints as a defensive measure. This is unreachable in practice because `validate_pipeline` already rejects such definitions before any graph is built.

---

### Dependency Hygiene

**WARN: petgraph default features pulled in unnecessarily.** The entry `petgraph = { version = "0.8", features = ["stable_graph", "serde-1"] }` does not set `default-features = false`. Petgraph's defaults are `["std", "graphmap", "stable_graph", "matrix_graph"]`; `graphmap` and `matrix_graph` are unused by this codebase and add compile weight. Minimal declaration should be: `petgraph = { version = "0.8", default-features = false, features = ["stable_graph", "serde-1"] }`. (`algo` is always compiled unconditionally and requires no feature flag.) Non-blocking; no correctness or security impact.

---

### Performance Regression

**WARN: Graph is rebuilt on every `compute_ready_set` call.** `build_graph()` allocates a new `StableGraph` and a `HashMap<String, NodeIndex>` (O(n+e)) on every dispatch cycle. The original `build_incoming_edges` also allocated a `HashMap`, so the per-call cost is comparable today, but the graph allocation carries a heavier constant factor. As dispatch frequency scales (concurrent pipelines, tight poll loops), this will surface. Suggested mitigation: cache the `StableGraph` alongside `PipelineDefinition` at creation time, or accept `&StableGraph` as a parameter. Non-blocking for current load.

---

### Test Coverage Gaps

**WARN: Multi-edge (parallel edges) scenario not tested.** A `PipelineDefinition` can legally contain two edges from the same source to the same target with different `EdgeType` values (e.g., one `Success` and one `Always`). Confirmed via experiment: `StableGraph::neighbors_directed(Incoming)` returns the source node **twice** in this case (once per edge), causing `edges_connecting(source, node).all(...)` to be evaluated twice. Both `.all()` and `.any()` are idempotent under repetition, so correctness is unaffected — but the behaviour is subtle and untested. A test covering the mixed-parallel-edge case would provide an explicit regression guard.

**WARN: No test for `compute_ready_set` with a node absent from `node_states`.** The pipeline engine can theoretically be called with a `node_states` map that is missing entries for some nodes (e.g., during partial initialization). Both the original and the new code handle this consistently (`is_edge_satisfied` returns `false`; `is_node_blocked` treats missing state as non-blocking), but there is no test asserting this contract.

---

### Notes

**NOTE-1** — Pre-existing test failures: `pipeline_dispatch_persists_partial_progress_when_activation_fails` and `pipeline_dispatch_renders_first_step_into_session_body` both panic in `dispatch.rs` with `PathTraversal("Resolved path escapes base directory: ...")`. `git diff features/dag -- .../dispatch.rs` produces no output — `dispatch.rs` was not modified by this refactor. These failures pre-date the petgraph work.

**NOTE-2** — Dead code branch: the `let Some(&node_index) = node_indices.get(&node.id) else { return false; }` guard in `compute_ready_set` can never fire. `build_graph()` inserts every node from `definition.nodes` into `node_indices`, and the outer iterator also ranges over `definition.nodes`. The guard is harmless but could be replaced with `unwrap()` plus a comment explaining the invariant, or removed.

**NOTE-3** — `is_node_blocked` is semantically redundant with `is_edge_satisfied`. Any `Success` edge from an `Abandoned|Stuck` predecessor would fail `is_edge_satisfied`, preventing the node from becoming ready regardless. The separate `is_node_blocked` check short-circuits earlier on the `!... && ...` chain but changes no outcome. The redundancy mirrors the original structure and is fine to retain for clarity.
