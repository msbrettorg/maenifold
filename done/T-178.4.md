# T-178.4 — Mind dashboard — desktop Vue implementation with MCP resources

## Intent

Land the "mind" dashboard inside the desktop app (`apps/desktop/src/`) as native Vue 3 + Pinia + shadcn-vue components, consuming the new MCP resources from [[T-178.3a]] / [[T-178.3c]] via the desktop resource client from [[T-178.0]]. This is where the constitutional principle "AI is the new UI — our UI uses MCP" first ships in the actual product surface (not in a memory-folder HTML prototype).

The Mind view shows the live cognitive state of the corpus: communities in a left rail, an activity stream in a right rail, and a center stage that hosts the existing graph canvas plus signal-driven flourishes.

### mind.html is LAYOUT / INTERACTION REFERENCE ONLY

`/Users/brett/maenifold/memory/Dashboards/mind.html` is the source of truth for **layout and interaction patterns** ONLY:
- Three-column layout (signal+community rail / center stage / activity rail)
- Signal halo + edge sweep flourishes on `thinking` events
- Click-to-focus interaction for local subgraph overlay
- Backdrop "ley line" rendering of strongest edges

**It is NOT a styling reference.** All visual tokens (color, type, spacing, radius, shadow, motion) come from `apps/desktop/DESIGN.md` (Fluent 2 Web). Do not port `mind.html`'s CSS. Do not embed its `<style>` block. The HTML prototype's purpose ends at "this is the shape of the UI" — past that point, `DESIGN.md` is authoritative.

### 2. Resource consumption via the desktop client

Use the `useMcpResources` composable from [[T-178.0]] — do not invent a parallel resource client.

| Resource URI | Consumer | Cadence |
|---|---|---|
| `graph://corpus/snapshot` | `KnowledgeGraphPanel.vue` (backdrop edges) | One initial read on mount, re-read on `notifications/resources/updated` |
| `graph://corpus/communities` | `MindSignalRail.vue` (left rail community list) | One initial read on mount, re-read on update notifications |
| `graph://activity/recent` | `MindActivityStream.vue` (right rail) + signal-driven flourish hooks in graph panel | Subscribe; on each notification re-read and diff against last seen `events[]` to find new ones |
| `graph://stats` | Status footer / header chip | Subscribe; re-read on update |
| `graph://concept/{name}` | Click-to-focus overlay (lazy) | `resources/read` on click; do NOT auto-subscribe — subscribe only while overlay is open, unsubscribe on close |

Subscription lifetime owners: each component that subscribes is responsible for unsubscribing in `onScopeDispose` / `onUnmounted`. Reconnect contract from T-178.0 applies — re-subscribe in the `connected` watcher.

### 3. Focus zoom flourish

On signal `type === "thinking"` arriving via `graph://activity/recent`:
- If the signal carries a `conceptName`, call `tools/call Visualize { conceptName, depth: 1, maxNodes: 40, format: "graph" }` (lowercase `"graph"` per [[T-178.1]]).
- Use the returned `edges[]` (sorted desc by `weight`) to animate edges drawing outward from the activated node — strongest first, fading to weakest. Animation timing pulls from DESIGN.md motion tokens (no hardcoded `200ms` magic numbers).

On click of any concept node in the canvas:
- Open a focus overlay populated from `resources/read` on `graph://concept/{percent_encode(name)}`.
- Subscribe while overlay is open; unsubscribe on close.

### 4. Backdrop edges

On `graph://corpus/snapshot` load, populate the backdrop with the top ~5% of edges by weight (the "ley lines"). Render budget cap is a `const` near the canvas component and is documented inline. Re-render when a notification arrives.

### 5. Throttle alignment

`graph://activity/recent` coalesces at 250ms (per [[T-178.3c]]). The activity stream component must:
- Treat one notification as "0 or more new events arrived" — always diff against last-seen state, never assume one notification = one signal.
- Animate signals with a queue+drain pattern (incoming batch → enqueue → drain at a smooth visual rate) rather than firing all halos simultaneously when a batch arrives.

### 6. Pinia integration

Extend `apps/desktop/src/stores/knowledge.ts`:
- Add resource-subscription state slices: `corpusSnapshot`, `corpusCommunities`, `activityEvents`, `stats`. Each slice carries `data`, `loading`, `error`, `lastUpdated`.
- Add actions to read/subscribe/unsubscribe each resource. Unsubscribe on `$dispose`.
- Use Setup Store form ONLY if needed for composables; otherwise stick to Option Store for clarity (per the pinia skill conventions).
- Use `storeToRefs` in components — never destructure store state directly.
