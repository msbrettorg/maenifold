# T-63.3 — YAML Frontmatter Warning Accumulator

## Problem
`markdown/storage.rs` `parse_frontmatter()` logs a warning to stderr and returns `None` when YAML is corrupt. User loses timestamps, status, and concept metadata silently. The warning is ephemeral — no way to query which files have broken frontmatter.

## Requirements
1. Add `FRONTMATTER_WARNINGS: Mutex<Vec<(String, String)>>` static (file URI, error message)
2. In `parse_frontmatter()` error branch (line ~152), push `(uri.to_string(), error.to_string())` into the accumulator alongside the existing `eprintln!`
3. Cap accumulator at 100 entries (drop oldest on overflow)
4. Expose `pub fn drain_frontmatter_warnings() -> Vec<(String, String)>` — returns and clears the list
5. Wire into `render_system_health()` in `benchmark/render.rs` — show count + file paths of corrupt frontmatter
6. Keep the existing `eprintln!` for backward compatibility

## Files
- `crates/maenifold-core/src/markdown/storage.rs` — add static, push in error branch, expose drain
- `crates/maenifold-core/src/benchmark/render.rs` — add frontmatter warnings section

## Tests
- Unit test: feed corrupt YAML through `parse_frontmatter()` → assert warning appears in `drain_frontmatter_warnings()`
- Unit test: feed 101 warnings → assert only 100 retained (oldest dropped)
- Existing `cargo test -p maenifold-core` must pass

## Acceptance
- Corrupt frontmatter files are queryable via `drain_frontmatter_warnings()`
- `MemoryStatus` shows corrupt frontmatter count and file paths
- No warnings, no panics
