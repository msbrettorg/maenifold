# T-51.9 — Pipeline Executor Script

**Requirement**: FR-40 (Pipeline Active Executor)
**RTM**: RTM-159 / TC-159
**Component**: `maenifold-acp`

## Context

The existing `maenifold-acp` bash script already drives workflows and thinking via `acpx` + `maenifold --tool`. We extend it with a `pipeline` subcommand that drives DAG execution using the same CLI scripting pattern from `docs/SCRIPTING.md`.

The Rust side handles state (create/view/dispatch/update via MCP). The bash script handles execution (compute ready set → dispatch to acpx → write completion → repeat).

## Acceptance Criteria

1. Add `pipeline` subcommand to `maenifold-acp`:
   ```
   maenifold-acp pipeline <pipeline-session-id> <prompt> [acpx-flags...]
   ```
2. Implement `run_pipeline()`:
   - Call `mf Pipeline '{"sessionId":"...","view":true}'` to get current state
   - Extract `maxConcurrency` from pipeline state
   - Main loop:
     a. Call `mf Pipeline '{"sessionId":"...","dispatch":true}'` to get dispatched nodes
     b. For each dispatched node (has `acpClient` + workflow `sessionId`):
        - Run `run_workflow` in background (`&`), passing the node's `workflowId`, `acpClient`, and the pipeline prompt
        - Track background PIDs
     c. Respect `maxConcurrency`: if active background jobs >= max, `wait -n` for one to finish
     d. On workflow completion: call `mf Pipeline '{"sessionId":"...","nodeId":"...","status":"completed","conclusion":"..."}'`
     e. On workflow failure: call `mf Pipeline '{"sessionId":"...","nodeId":"...","status":"abandoned"}'`
     f. Loop until pipeline status is `completed`, `stuck`, or all nodes terminal
   - Log progress with `log()` helper (same as existing)
3. Background job management:
   - Use bash `wait -n` (wait for any single background job) for concurrency control
   - Track `node_id → PID` mapping in an associative array
   - On PID exit: check exit code, map to completed/abandoned
4. Signal handling:
   - `trap` SIGINT/SIGTERM → send cancel to all active acpx sessions, mark nodes abandoned
   - This is the "cancel" lifecycle control
5. Pause/resume: NOT in scope for bash. Pause = Ctrl+C (cancel). Resume = re-run the command (dispatch picks up from current state).
6. Rewind: NOT in scope for bash. Use `maenifold --tool Pipeline '{"sessionId":"...","rewind":{"nodeIds":[...]}}'` directly via CLI.
7. The script MUST reuse existing `mf()`, `acp()`, `run_workflow()`, `run_think()`, `tag()`, `strip()` helpers unchanged.
8. Add to the case statement at the bottom of the script:
   ```bash
   pipeline) shift; run_pipeline "$@" ;;
   ```

### FINDING 1 — HIGH: `wait -n` is a no-op on stock macOS bash 3.2, turning the main loop into a tight busy-wait

**Location**: `pipeline_wait_for_any()` (line 326)

**Evidence**:
```
$ bash --version
GNU bash, version 3.2.57(1)-release (arm64-apple-darwin25)
$ bash -c 'sleep 2 & if wait -n; then :; fi; echo "returned immediately"'
bash: line 1: wait: -n: invalid option
returned immediately   # ← returned in 0s, not 2s
```

The script uses `#!/usr/bin/env bash` and `wait -n` (bash 4.3+). macOS ships bash 3.2 (GPLv3 exclusion). On this development machine itself there is no Homebrew bash installed (`/opt/homebrew/bin/bash` and `/usr/local/bin/bash` both absent). The `if wait -n; then :; fi` guard correctly prevents `set -e` from killing the script — but the guard also silently discards the failure, making `pipeline_wait_for_any` a **no-op**. The function returns immediately without waiting for any worker to finish.

**Impact**: The main loop becomes an unconstrained busy-wait:
1. `while (( ${#PIPELINE_PID_TO_NODE_ID[@]} >= max_concurrency ))` → calls `pipeline_wait_for_any` → returns immediately → never drains below `max_concurrency` → infinite spin
2. `(( dispatch_count == 0 && workers > 0 ))` path → same busy spin
3. Every spin fires `mf Pipeline view:true` + `mf Pipeline dispatch:true` against the MCP server — unlimited RPC hammering
4. Error string `"wait: -n: invalid option"` leaks to stderr on every iteration

The script nominally passes syntax check and _appears_ to function (workers do launch and complete via exit files), but the concurrency throttle is completely broken and the loop never actually yields.

**Remediation**: Add a bash version check at the top of `run_pipeline` (or at script load time) and abort with a clear message if `$BASH_VERSION` is below 4.3. Alternatively, implement a portable polling fallback using `sleep 0.5` when `wait -n` is unavailable.

```bash
# At top of run_pipeline (or as a global guard):
if [[ "${BASH_VERSINFO[0]}" -lt 4 || ( "${BASH_VERSINFO[0]}" -eq 4 && "${BASH_VERSINFO[1]}" -lt 3 ) ]]; then
  echo "maenifold-acp pipeline requires bash >= 4.3 (current: $BASH_VERSION)" >&2
  echo "Install a newer bash: brew install bash" >&2
  exit 1
fi
```

### FINDING 2 — MEDIUM: `kill $pid` on worker subshell orphans `acpx` grandchildren when log file is unpopulated

**Location**: `pipeline_cancel_active()` (lines 338–349)

**Mechanism**: When SIGINT/SIGTERM arrives, `pipeline_cancel_active` attempts to cancel the running `acpx` session before killing the worker subshell:
```bash
session_name=$(pipeline_extract_session_name "${PIPELINE_PID_TO_LOG[$pid]}")
if [[ -n "$agent" && -n "$session_name" ]]; then
  acpx "$agent" cancel -s "$session_name" >/dev/null 2>&1 || true
fi
kill "$pid" >/dev/null 2>&1 || true
```
`pipeline_extract_session_name` parses the log file for the line `[macp] workflow <session-id>`, which is written by `run_workflow` only _after_ the `mf Workflow` call succeeds. If the signal arrives during subprocess startup (before `run_workflow` has reached that log line), `session_name` is empty and the `acpx` cancel call is silently skipped.

`kill "$pid"` kills the bash subshell, but `acpx` is a child of that subshell. In a non-interactive shell, background workers are in the same process group as the parent; `kill $pid` only sends the signal to the specific PID, not to its children. The `acpx` child process (and any `maenifold` grandchildren it spawned) become **adopted by PID 1** and run to completion unsupervised.

**Impact**: Orphaned `acpx` agent sessions continue executing after the user hit Ctrl-C. Depending on the agent and workflow, this could perform unintended writes, consume API credits, or leave sessions in untracked state.

**Remediation**: Use a process group kill to catch the full subprocess tree, or `setsid` the worker so it gets its own group that can be cleanly targeted:
```bash
# In pipeline_launch_node, replace:
pipeline_worker "$exit_file" "$log_file" "$workflow_id" "$agent" "$prompt" "$@" &
# With: (sets the worker in its own process group)
set -m; pipeline_worker ... &; set +m
# Then in cancel:
kill -- -"$pid" 2>/dev/null || kill "$pid" 2>/dev/null || true
```

### FINDING 3 — MEDIUM: No guard against double-dispatch of already-running nodes

**Location**: Inner dispatch loop in `run_pipeline()` (lines 387–411)

The inner loop processes nodes returned by `mf Pipeline dispatch:true`. Before calling `pipeline_launch_node`, there is no check whether `PIPELINE_NODE_TO_PID["$node_id"]` is already populated. If the Rust state machine ever returns a node in the `dispatched` array that the script is already executing (edge case: retry after a view/dispatch race, or a server bug), `pipeline_launch_node` launches a second worker for the same node:

```bash
PIPELINE_PID_TO_NODE_ID["$pid"]="$node_id"
PIPELINE_NODE_TO_PID["$node_id"]="$pid"   # ← overwrites old PID
```

The old PID is now untracked — it will never be reaped, the old worker's completion is never written back to pipeline state, and both workers race to write `completed`/`abandoned` for the same node. Exit files from both workers share the same path (derived from `node_id`), so the second worker's exit file silently clobbers the first.

**Remediation**: Add a skip guard before `pipeline_launch_node`:
```bash
if [[ -n "${PIPELINE_NODE_TO_PID[$node_id]+x}" ]]; then
  log "node $node_id already running (PID ${PIPELINE_NODE_TO_PID[$node_id]}); skipping re-dispatch"
  continue
fi
```

### FINDING 4 — LOW: Temp directory leaked on `set -e` exit; no EXIT trap

**Location**: `run_pipeline()` (lines 437–438)

```bash
trap - INT TERM
rm -rf "$PIPELINE_STATE_DIR"
```

`PIPELINE_STATE_DIR` is cleaned up only when `run_pipeline` reaches its natural end. If any command inside the loop causes `set -e` to trigger (e.g., `mf Pipeline` exits non-zero, `json_get` fails, or `pipeline_mark_completed` fails), bash exits the function immediately, leaving the temp directory behind. Each invocation leaks a `mktemp`-created directory containing per-node `.log` and `.exit` files.

**Remediation**: Register an EXIT trap at the start of `run_pipeline`:
```bash
local _state_dir_to_clean=""
_pipeline_cleanup() { [[ -n "$_state_dir_to_clean" ]] && rm -rf "$_state_dir_to_clean"; }
trap _pipeline_cleanup EXIT
PIPELINE_STATE_DIR=$(mktemp -d ...)
_state_dir_to_clean="$PIPELINE_STATE_DIR"
```

### FINDING 5 — LOW: Non-numeric `maxConcurrency` from server causes arithmetic abort

**Location**: `run_pipeline()` (line 367) and concurrency throttle (line 406)

```bash
max_concurrency=$(json_get maxConcurrency <<< "$state_json")
[[ -n "$max_concurrency" ]] || max_concurrency=8
```

The empty-string fallback is correct. However, if the server returns a non-numeric value (e.g., `"unlimited"`, `null`, or `0.5`), `json_get` prints it as a bare string. The subsequent arithmetic:
```bash
while (( ${#PIPELINE_PID_TO_NODE_ID[@]} >= max_concurrency )); do
```
fails with:
```
bash: ((: unlimited: value too great for base (error token is "unlimited")
```
With `set -euo pipefail`, this is an unhandled error that exits the script mid-execution, potentially leaving workers running and nodes in `dispatching` state permanently.

Note that `maxConcurrency=0` is not caught and causes `(( N >= 0 ))` to always be true — the loop will call `pipeline_wait_for_any` before every single node launch, serializing all execution regardless of intent.

**Remediation**: Validate after extraction:
```bash
if ! [[ "$max_concurrency" =~ ^[1-9][0-9]*$ ]]; then
  log "invalid maxConcurrency '$max_concurrency'; defaulting to 8"
  max_concurrency=8
fi
```

  - Used `run_workflow` inside a background worker wrapper so the script can still record per-node exit state and map finished jobs back to pipeline node IDs without changing the existing workflow driver.
  - Resolved `acpClient` by preferring the dispatched node payload and then falling back to matching node data from pipeline state, so the script tolerates either response shape.
  - Defaulted `maxConcurrency` to `8` if the viewed pipeline state does not expose it directly, matching the Pipeline tool’s documented default.
  - Verified shell syntax with `bash -n maenifold-acp`.

## SWE Fix Remediation

- Added a `bash 4.3+` guard at the start of `run_pipeline()` so `wait -n` fails fast with an explicit Homebrew install hint instead of spinning on unsupported shells.
- Wrapped pipeline worker launch with monitor mode so each background worker gets its own process group, then updated cancellation to prefer `kill -- "-$pid"` before falling back to `kill "$pid"` so spawned `acpx` descendants are terminated too.
- Added a duplicate-dispatch guard in the pipeline dispatch loop so an already-tracked node is logged and skipped instead of launching a second worker for the same `nodeId`.
- Added an `EXIT` trap immediately after creating `PIPELINE_STATE_DIR` so temp state is cleaned up even if `run_pipeline()` exits early under `set -e`.
- Hardened `maxConcurrency` parsing with a numeric regex guard; invalid, zero, fractional, or non-numeric values now fall back to `8`.
