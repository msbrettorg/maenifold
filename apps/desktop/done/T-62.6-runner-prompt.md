# T-62.6 — Run-Level Prompt Input on Runner

**Requirement**: FR-47
**Component**: `pipeline-ui/src/components/PipelineRunner.vue`
**Design Reference**: `pipeline-ui/docs/design/node-types-ui.md` §4
**Depends on**: T-62.2

## Context

PipelineRunner.vue (230 lines) has lifecycle controls (create/run/pause/resume/cancel/delete), an event log tab, and a mermaid tab. The Run button calls `store.runPipeline()` but there is NO prompt input — the run-level prompt parameter is always empty.

## Acceptance Criteria

1. Add a `<textarea>` for the run-level prompt, positioned above the lifecycle control buttons.
   - Placeholder: "Optional: ambient context for all nodes..."
   - Only visible when a pipeline is loaded and NOT running (i.e., when the Run button is available)
   - Collapsible or compact — should not dominate the runner panel

2. The Run button must pass the textarea value to `store.runPipeline(promptText)`.

3. Clear the prompt textarea after a successful run start (the prompt has been sent).

4. In the event log, if a node has `output` data (from the view response), show a preview:
   - Format: `✅ node-id completed — output: {first100chars}...`
   - This requires reading `output` from `ViewNode` (added in T-62.1)

5. Existing controls (Create, Pause, Resume, Cancel, Delete) must continue to work unchanged.

6. Existing mermaid tab must continue to work unchanged.

7. Typecheck: `cd pipeline-ui && npx vue-tsc --noEmit` must pass.

### Criterion 1 — Prompt textarea present above Run button
**PASS**

`<div v-if="canShowRunPrompt" class="prompt-panel">` (line 134) containing the `<textarea>` appears before the `.control-bar` div (line 145) that holds the Run button. DOM order is correct. Placeholder text is exactly `"Optional: ambient context for all nodes..."` as specified. Label `"Run prompt"` is present with a `for` attribute wired to the `id`.

---

### Criterion 2 — Prompt is optional — pipeline can run without one
**PASS**

`handleRun` (line 123) passes `undefined` when the trimmed textarea is empty:
```ts
await store.runPipeline(prompt.length > 0 ? prompt : undefined);
```
`store.runPipeline(prompt?: string)` (line 149) accepts an optional parameter and forwards it cleanly to the MCP layer. An empty textarea is a no-op for the backend — no empty string is ever sent.

---

### Criterion 3 — Prompt passed to `store.runPipeline(prompt)` on Run
**PASS**

`handleRun` (lines 123–129) is the sole handler wired to the Run button (`@click="handleRun"`, line 147). It reads `runPrompt.value`, trims it, and routes it to `store.runPipeline`. No other code path bypasses this (Pause/Resume/Cancel/Delete all call distinct store methods).

---

### Criterion 4 — Node output displayed in event log when `ViewNode.output` is available
**PASS**

`formatLogEntry` (lines 83–98) reads `viewNodesById.value.get(entry.nodeId)?.output`. `ViewNode.output` is declared `output?: string` on `ViewNodeBase` (pipeline-types.ts line 68), so the field is typed — not widened to `unknown`. The output path fires only when `entry.to === 'completed'` AND `nodeOutput` is a non-empty string, producing:
```
[HH:MM:SS] ✅ node-id completed — output: <first 100 chars>...
```

`formattedLog` is a `computed()` that takes a dependency on both `eventLog` and `currentView` (via `viewNodesById`), so if `output` arrives in a later poll cycle than the completion event, the formatted log self-heals on the next view update without requiring a page refresh.

**Minor deviation from spec template**: The spec shows `✅ node-id completed — output: {first100chars}...` (ellipsis always present), but the implementation conditionally appends `...` only when `preview.length > 100`. This is strictly better UX and does not represent a defect.

---

### Criterion 5 — Prompt clears after successful run start
**PASS**

`runPrompt.value = ''` (line 127) is placed *after* the `await store.runPipeline(...)` and only executes when that call resolves successfully. If `runPipeline` rejects (e.g., network error), the prompt is preserved so the user can retry — this is intentional and correct. The `runAction` wrapper's `finally` block (line 113) only clears `busyAction`, not the prompt, which is the right separation of concerns.

### Advisory Observations (non-blocking)

**OBS-1 — `canShowRunPrompt` is a transparent alias for `canRun`** (severity: Low)

```ts
const canShowRunPrompt = computed(() => canRun.value);  // line 33
```

The computed adds no independent logic. If the visibility rules for the prompt textarea ever need to diverge from the Run button's availability (e.g., "show prompt even when paused so the user can pre-fill it"), this alias will need to be broken out. For now it is correct but slightly misleading — a future developer may not realise they are the same condition. Suggest inlining `canRun` in the `v-if` or adding a comment.

**OBS-2 — `v-html="renderedSvg"` is a latent XSS surface** (severity: Low / pre-existing)

Line 167 renders raw SVG via `v-html`. The SVG originates from `mermaid.render()`, which takes `currentView.value?.mermaid` sourced from the server. Mermaid sanitises its output, and this pattern pre-dates T-62.6, so it is **out of scope for this sprint**. However, if `viewPipeline` ever returns attacker-controlled Mermaid source (e.g., via a compromised pipeline definition), a crafted `<script>` or event-handler injection inside the SVG could execute in the app's origin context. Recommend tracking this as a follow-on hardening item (CSP `script-src`, or using `DOMPurify` over the rendered SVG).
