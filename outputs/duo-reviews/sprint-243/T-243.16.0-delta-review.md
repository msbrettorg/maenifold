## 2. PromptDialog UX is the most likely source of papercuts

`PromptDialog.vue` is the freeform-input cousin of `ConfirmDialog`. The UAT
doesn't mention it at all. Linear/Notion conventions for a rename prompt:

- Field is **focused and selected** on open (so typing replaces, not appends).
- **Enter submits**, Esc cancels, Cmd+Enter for multi-line variants.
- Validation errors render **inline under the field**, not in an alert.
- Submit button is disabled while invalid; primary action label matches verb
  ("Rename", not "OK").
- Field shows current value as the default; placeholder is not a substitute.

Add a subsection **B'** (or new T-243.16.X) for PromptDialog covering the above.

## 3. Unsaved-changes prompt — explicitly missing on Workflows

CDP enumeration flagged the Workflows tab. Section F (modal stacking) doesn't
ask the deeper question: **when the user navigates away from a dirty editor,
is there a guard?** Spots to walk:

- Workflows authoring view (flagged).
- Pipelines designer (`DesignNodeConfigModal` close, full pipeline tab nav).
- Promotion editor (`PromotionDialogEditor` — closing mid-edit).
- Settings tabs with form state.
- Knowledge note editor (close tab / switch note while dirty).

Standard pattern: dialog with "Discard / Cancel / Save". Esc maps to **Cancel**
(stay), not Discard. Add this as cross-cutting section **I. Unsaved-changes
guard** with the above five entry points.

## 4. Permission dialog — "always allow" semantics underspecified

UAT C says "Selection persisted for always-allow — verify by triggering same
tool twice." That's the happy path. Missing:

- **Scope of "always":** this session? this agent? this workspace? forever?
  macOS users expect Keychain-style "Always Allow" = forever; Notion-style
  toggles are session-only. Pick one and label the buttons accordingly.
- **Where to revoke:** if "always allow" is persistent, there must be a
  Settings → Permissions list to revoke. Walk that.
- **Dedupe of identical prompts:** if the agent fires the same tool with the
  same args twice while the first prompt is open, do we stack two dialogs or
  collapse to one? (Section F implies "never two open" — but dedupe is a
  different mechanism than stacking suppression.)
- **Args preview:** "shows tool name, intended args" — verify args are
  rendered in a way a human can read (JSON dump is not enough; for `bash`
  the actual command must be foregrounded).
- **Diff between allow and always-allow:** explain in body copy or hover.

## 5. Auth method dialog — D is one bullet, should be a matrix

UAT D doesn't enumerate which methods are actually offered. Looking at
`AuthMethodDialog.vue` + `ToolAuthSetupDialog.vue`, the UAT must list each
method explicitly with its acceptance criteria:

- **OAuth:** browser opens, callback returns, token stored where, error path
  (user denies in browser → app shows what?), token-refresh path.
- **API key:** masked input (`type="password"`), paste works, show/hide toggle,
  validation against the provider before save.
- **Cert / mTLS:** if supported — file picker integration with FolderPicker?
- **None / no-auth:** is "skip" an option?

Also: relationship between the two dialogs (`AuthMethodDialog` picks the
method, `ToolAuthSetupDialog` configures it?) needs a single sentence in the
UAT so testers know the expected two-step flow.

## 6. Traffic monitor — "if present" is a tell

If we don't know whether it ships, the UAT can't validate it. Resolve before
running:

- Confirm component + entry point. Header? Debug menu? Cmd-shift-something?
- Real-time vs polled (pause/resume button?).
- Filter by: agent, session, method, success/error.
- Copy-as-curl / copy-as-JSON for one row.
- Behaviour when traffic volume is high (virtual scroll? truncation?).
- "Doesn't block the rest of the app" — is it a dialog or a slide-over?
  If it's modal, large traffic blocks the user from acting on what they see.
  Linear-style **slide-over** is the right pattern; flag if it's currently a
  modal.

## 7. Z-index — sprint 241 lesson under-applied

Section G says "Dialogs appear above all UI." The sprint 241 P0 (T-241.1) was
specifically about a dialog **inside a Resizable panel** rendering under the
panel splitter. The UAT must spot-check:

- Every dialog opened **from** a `Resizable` panel (Knowledge, Pipelines,
  Sessions all use them).
- Dialogs opened on top of the OnboardingWizard (re-entrant flow if the
  wizard triggers a folder pick).
- Dialogs opened on top of `CommandDialog` (cmd-K → action that prompts).
- Toasts vs dialogs vs popovers — three layers, verify ordering at least
  once.

Add explicit checklist items naming **each dialog × each panel host** rather
than the single generic line currently in G.

## 8. Esc behaviour — the asymmetry needs to be in the test

UAT H says "Esc triggers cancel where allowed." That's vague. The asymmetry
testers should walk:

- **Destructive confirm (delete X):** Esc = cancel ✓ (safe).
- **Permission dialog:** Esc = **deny** (treated as a choice, not a dismiss
  — section C already says this, good).
- **Auth method:** Esc = cancel the auth attempt; the agent that requested
  auth should receive a clean "auth-cancelled" not a hang.
- **Onboarding wizard:** Esc should **not** dismiss (user would lose progress).
  Verify.
- **PromptDialog mid-edit:** Esc cancels — but if the user typed something,
  no "discard?" guard; that's intentional, just confirm consistency.

---

## 9. Click-outside — same asymmetry, currently one bullet

Section G has "Click-outside doesn't dismiss permission/auth dialogs." Extend
to a small matrix:

| Dialog class | Click-outside |
|---|---|
| Confirm (destructive) | dismiss = cancel |
| Confirm (benign) | dismiss = cancel |
| Permission | **no dismiss** (must choose) |
| Auth | **no dismiss** (must choose or cancel button) |
| Prompt | dismiss = cancel (but warn if dirty? probably not) |
| Folder picker | native — n/a |
| Onboarding wizard | **no dismiss** mid-flow |
| Traffic monitor | dismiss freely |

## 10. Smaller items

- **Initial focus:** UAT H says "sensible action." Spell it out per dialog —
  destructive confirm should focus **Cancel**, prompt should focus the **input**,
  permission should focus **Deny** (not Allow — Allow being default-focused
  is a real CVE pattern).
- **Tab trap:** verify with a screen reader, not just visually. (Out of
  10-min scope but worth a follow-up T.)
- **Animation on open/close:** if reduced-motion is on, dialogs should appear
  instantly. macOS HIG.
- **Dialog title vs body verb agreement:** "Delete pipeline?" title +
  "Delete" primary button (not "OK").
- **Width:** PromotionDialog and DesignNodeConfigModal are likely larger —
  do they exceed viewport on a 13" laptop? Resize once during UAT.

## Recommendation

Two-phase fix before the UAT runs:

1. **Author T-243.16.1 (roster expansion):** add Prompt, Promotion, Graft,
   JoinPipeline, DesignNodeConfig, SessionPicker, ToolAuthSetup,
   SettingsEmbeddingsConfirm, Command. Resolve the traffic-monitor "if
   present" question.
2. **Author T-243.16.2 (cross-cutting matrices):** unsaved-changes guard (5
   entry points), Esc-behaviour matrix, click-outside matrix, z-index ×
   panel-host matrix. These are 4 tables that turn vague bullets into pass/
   fail items.

After those, the UAT is runnable. Without them, expect 30–40% of real bugs
to slip through because the checklist points elsewhere.
