# T-45.6c: Pipeline Node Status Updates

**Requirement**: FR-45.6
**RTM**: RTM-338, RTM-339, RTM-341
**Priority**: P0 — Pipeline progress tracking

## Context

When a workflow completes or fails, the pipeline needs to update the node's status and trigger downstream readiness. Two operations: `completed` (success) and `abandoned` (failure). The Pipeline tool owns the `active → completed` transition at the pipeline level, while the Workflow tool handles the session-internal completion.

## Scope

Add node status update handling to the Pipeline tool handler.

## Acceptance Criteria

1. **Complete operation**: `pipeline(sessionId=X, nodeId=Y, status="completed", conclusion="...")`:
   a. Verify node exists and is currently `active`
   b. Update `nodeStates[Y].status` to `completed` in pipeline session
   c. Update the node's workflow session frontmatter `status` to `completed`
   d. Store `conclusion` in node's workflow session frontmatter
   e. Trigger predecessor context injection for downstream nodes (write `## Predecessor Context` section with upstream `last` values)
   f. Recompute and return new ready set
2. **Abandon operation**: `pipeline(sessionId=X, nodeId=Y, status="abandoned")`:
   a. Verify node exists and is currently `active`
   b. Update `nodeStates[Y].status` to `abandoned` in pipeline session
   c. Update the node's workflow session frontmatter `status` to `abandoned`
   d. Recompute ready set — `always` edges may now be satisfied
   e. Return new ready set
3. **Ownership boundary**: Pipeline tool updates `nodeStates` in the pipeline session. The Workflow tool's `handle_completed_workflow_status` handles the workflow-internal completion. Both can coexist — the pipeline status is the orchestration-level status.
4. **Predecessor context injection**: When a node completes, for each downstream node connected via `success` or `always` edges:
   a. Read `last` from the completed node's workflow session frontmatter
   b. Write/replace a `## Predecessor Context` section in the downstream node's session file
   c. If multiple upstream nodes are complete, concatenate all their `last` values with node ID labels
5. **Error on invalid transition**: Reject status updates for nodes not in `active` state.
6. **Return shape**: Same as `view=true` response (full pipeline state after update).

## Implementation Notes

- Predecessor context injection: `append_h2_section` for new, or find-and-replace for existing `## Predecessor Context` sections
- The `last` field comes from FR-45.3 — this spec depends on T-45.3 being implemented
- Multiple predecessors: format as `### From {nodeId}\n\n{last_content}` for each upstream node

## Red-team Audit

**Verdict: REJECT**

---

### Findings

#### 1. `replace_h2_section` terminates on H3 sub-headings — stale predecessor context leaks through [HIGH]

**File**: `crates/maenifold-core/src/workflow/pipeline/handler.rs`, line 930

**The bug**: `replace_h2_section` iterates lines and, once the target section start is found, breaks as soon as it encounters **any** heading (`trimmed.starts_with('#')`). Predecessor context content uses `### From {nodeId}` H3 sub-headings (per spec AC-4c and line 894). When an existing `## Predecessor Context` section already contains these H3 lines, the loop fires the `section_start.is_some()` branch on the *first* H3 (not the next H2), setting `section_end` to that H3's byte offset — leaving every byte from that H3 onward as un-replaced content that is appended verbatim after the replacement block.

**Reproduction trace** (simulated from the test setup):

```
Existing child content:
  ## Predecessor Context\n\n### From root-a\n\nOld [[context]] only\n\n## Step 1/1\n...
```

`replace_h2_section`:
- `section_start = 0` (matches `## Predecessor Context`)
- Next heading hit → `### From root-a` → `section_end = 24` ← **H3, not H2**
- Replacement spliced in, then the old tail (`### From root-a\n\nOld [[context]] only\n\n## Step 1/1\n...`) is appended

Result contains **both** the new context **and** the stale `### From root-a\n\nOld [[context]] only` content, violating the spec's "write/replace" requirement (AC-4b: "Write/replace a `## Predecessor Context` section").

**The fix** is to change line 930 from matching any heading level to only ending the section on the same or higher heading level:
```rust
// Before (terminates on ### too):
if trimmed.starts_with('#') {

// After (only H1/H2 end an H2 section):
if trimmed.starts_with("# ") || trimmed.starts_with("## ") {
```

#### 2. Test `predecessor_context_replaces_existing_section_with_all_completed_upstreams` does not catch the stale-content bug [MEDIUM]

**File**: `crates/maenifold-core/src/workflow/pipeline/handler.rs`, lines 2519–2526

The test seeds an existing `## Predecessor Context` section containing `### From root-a\n\nOld [[context]] only` (line 2496) and then asserts only with `contains`. Because `replace_h2_section` leaves the stale `Old [[context]] only` text in place (confirmed above), the test passes despite the wrong output — it never asserts the stale string is absent.

Missing assertion:
```rust
assert!(
    !child_content.contains("Old [[context]] only"),
    "stale predecessor context content should have been fully replaced"
);
```

Without this guard the acceptance test for AC-4b provides false confidence.
