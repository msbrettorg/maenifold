## Decision

The standalone `gate` service is dead. It caused the GatewayExecute routing regression (T-236.1/T-236.2) and represents exactly the kind of fragmented surface we refuse to maintain. Gate functionality is absorbed into `maenifold` as first-class MCP tools prefixed with `gate_`. One service. One interface. Done.

## What dies

- `maenifold-gate` crate as a standalone binary/service
- `gate --mcp` and `gate --http` service modes
- macOS tray icon for gate
- Open-at-login LaunchAgent for gate
- The `gate` CLI binary entirely
- All gate MCP client configuration in the desktop app pointing at a separate gate server
- Any frontend composables / stores that connect to a separate gate MCP endpoint

## What replaces it

All gate operations become `gate_` MCP tools served by the maenifold server, identical in behavior to the current gate CLI/MCP surface:

| Old | New |
|-----|-----|
| `gate status` / MCP `status` | `gate_Status` |
| `gate pass` / MCP `pass` | `gate_Pass` |
| `gate fail` / MCP `fail` | `gate_Fail` |
| `gate append` / MCP `append` | `gate_Append` |
| `gate sync` / MCP `sync` | `gate_Sync` |
| MCP `history` | `gate_History` |
| MCP `task_body` | `gate_TaskBody` |

File-authoritative model stays: `todo/` and `done/` are still the source of truth. `.gate/gate.db` is still a rebuildable cache. Because the current `maenifold-gate` crate depends on `maenifold-core`, `maenifold-core` must not directly depend on it. The state machine and read-model logic must first move into a new cycle-free library crate, tentatively `maenifold-gate-core`, with no dependency on `maenifold-core`. Both the retiring standalone `maenifold-gate` binary crate and `maenifold-core` native MCP handlers may depend on that library during the staged migration.

- Dual-mode code that supports both old and new surface simultaneously
- Any TODO/FIXME/deprecation notices — the old surface is simply gone
- Keeping the gate tray or service mode "just in case"

### Summary

T-237.1 should be treated as an architecture/spec parent, not a single implementation task. The requested change spans Rust crate shape, native MCP tool registration, GatewayExecute catalog/domain routing, desktop gate UI transport, legacy service/tray removal, repository docs/config cleanup, and packaged-app UI verification. That is too large for one SWE pass under the 12-file / 600-LOC limit.

The implementation must therefore be split into child tasks. The target architecture is:

- `maenifold-gate-core` becomes the cycle-free library crate that owns the file-authoritative [[gate-backlog]] logic; the retiring `maenifold-gate` crate is only a temporary adapter until the standalone surface is removed.
- The standalone `gate` binary, `gate --mcp`, `gate --http`, gate tray, gate open-at-login, and separate desktop gate MCP endpoint are removed.
- Maenifold exposes native [[MCP]] tools `gate_Status`, `gate_Pass`, `gate_Fail`, `gate_Append`, `gate_Sync`, `gate_History`, and `gate_TaskBody`.
- `GatewayIndex` lists those tools under domain `maenifold.gate`; `GatewayExecute` executes them as native commands, not as an upstream `gate` server.
- Desktop gate UI calls the maenifold server through [[GatewayExecute]] domain `maenifold.gate`.
- Work remains grounded in parent [[sequential-thinking]] session `session-1777236650835-22077`.

### Remediation decisions from failed duo review

1. **Desktop detail flow stays.** Add `gate_History` and `gate_TaskBody` to native scope. Do not remove or degrade task detail, gate history, or task body display in the desktop Gate tab.
2. **Break the crate cycle before native registration.** Introduce a new pure library crate (`crates/maenifold-gate-core/`, final name may be adjusted by architects) that contains [[gate-backlog]] parsing, state machine, cache DB, catalog, definition, and tool-service functions without depending on `maenifold-core`. The current `maenifold-gate` crate depends on that library during transition; `maenifold-core` also depends on it to expose native tools. `maenifold-core -> maenifold-gate` is forbidden.
3. **No phantom server crate.** There is no separate server-crate scope in this repo. Native MCP registration happens in `crates/maenifold-core`.
4. **Ordering is sequential.** Crate boundary first, native MCP/Gateway second, desktop GatewayExecute third, service removal fourth, docs/skill cleanup fifth, end-to-end verification last. No child task should claim parallelism across those dependencies.
5. **Clean release verification must avoid stale artifacts.** Use a clean target directory or remove only the specific stale `target/release/gate` artifact before release build, then verify both `cargo metadata` target list and filesystem output.

### ACP / MCP interface constraints

Relevant [[Agent-Client-Protocol]] lines that constrain this work:

> "The Agent Client Protocol allows Agents and Clients to communicate by exposing methods that each side can call and sending notifications to inform each other of events." — `agent-client-protocol/references/overview.md:7`

> "The protocol follows the JSON-RPC 2.0 specification with two types of messages: Methods: Request-response pairs that expect a result or error; Notifications: One-way messages that don't expect a response." — `overview.md:11-14`

> "The protocol provides built-in mechanisms for adding custom functionality while maintaining compatibility: Add custom data using `_meta` fields; Create custom methods by prefixing their name with underscore (`_`); Advertise custom capabilities during initialization." — `overview.md:95-101`

> "Before a Session can be created, Clients MUST initialize the connection by calling the `initialize` method with: The latest protocol version supported; The capabilities supported." — `initialization.md:28-32`

> "The Agent MUST respond with the chosen protocol version and the capabilities it supports." — `initialization.md:58`

> "Capabilities describe features supported by the Client and the Agent." — `initialization.md:102-104`

> "Implementations can also advertise custom capabilities using the `_meta` field to indicate support for protocol extensions." — `initialization.md:110`

> "MCP capabilities: `http` — The Agent supports connecting to MCP servers over HTTP; `sse` — The Agent supports connecting to MCP servers over SSE. Note: This transport has been deprecated by the MCP spec." — `initialization.md:142-145`

> "Tool calls represent actions that language models request Agents to perform during a prompt turn." — `tool-calls.md:7`

> "Agents report tool calls through `session/update` notifications, allowing Clients to display real-time progress and results to users." — `tool-calls.md:9`

> "The Agent MAY request permission from the user before executing a tool call by calling the `session/request_permission` method." — `tool-calls.md:56`

> "If the current prompt turn gets cancelled, the Client MUST respond with the `cancelled` outcome." — `tool-calls.md:62`

> "Implementations MUST NOT add any custom fields at the root of a type that's part of the specification. All possible names are reserved for future protocol versions." — `extensibility.md:21`

> "The protocol reserves any method name starting with an underscore (`_`) for custom extensions." — `extensibility.md:23-25`

> "Extensions SHOULD advertise their custom capabilities so that callers can check their availability first and adapt their behavior or interface accordingly." — `extensibility.md:35`

Implications:

- This work must not invent non-standard ACP root fields for gate routing.
- Gate operations should be ordinary MCP tools exposed by maenifold, not ACP extension methods.
- Any ACP custom metadata must live under `_meta`.
- GatewayExecute remains the desktop-facing routing boundary; direct hidden native calls should still return the existing hidden-tool guidance.
- Mutating gate tools (`gate_Pass`, `gate_Fail`, `gate_Append`, `gate_Sync`) need clear safety classification because ACP clients may request/mediate permissions for tool execution. `gate_History`, `gate_TaskBody`, and `gate_Status` are read operations.

### Existing surfaces observed during spec

- `crates/maenifold-gate/Cargo.toml` currently declares `[[bin]] name = "gate"` and depends on `clap`, `eframe`, `egui_*`, `tray-icon`, `winit`, `axum`, `tower-http`, and `rmcp` HTTP features for standalone CLI/service/UI behavior.
- `crates/maenifold-gate/src/main.rs` dispatches `gate --mcp` and `gate --http` through tray lifecycle code.
- `crates/maenifold-gate/src/gate_tool_service.rs` already centralizes callable operations (`status`, `append`, `pass`, `fail`, `sync`, plus legacy `cancel`, `history`, and `task_body`). Native scope keeps `history` and `task_body` as `gate_History` and `gate_TaskBody` because the desktop detail flow requires them.
- `crates/maenifold-core/src/registry.rs` is the native maenifold tool registry used by gateway native invocation.
- `crates/maenifold-core/src/mcp/domain_mapping.rs` maps native tools to gateway domains and safety classes.
- `crates/maenifold-core/src/mcp/gateway_catalog.rs` currently treats server name `gate` specially only for upstream tools; native `maenifold.gate` must replace that.
- `crates/maenifold-core/src/mcp/gateway_handler.rs` executes `GatewayExecute` by resolving native vs upstream targets.
- `apps/desktop/src/composables/useGateMcp.ts` currently connects to `DEFAULT_GATE_MCP_BASE_URL`, calls old tool names like `sync`, `status`, and `task_body`, and falls back across legacy names.

- No UI redesign beyond preserving current gate tab behavior through the new transport.
- No fix for the T-236.2 routing regression beyond ensuring this task uses GatewayExecute correctly.
