## Problem

Concurrent `gate pass`/`gate fail`/`gate sync` calls through the MCP service hit `sqlite error: database is locked` despite 5-second busy_timeout. Each mutating call does `pass_task() → refresh_read_model() → task_status_from_read_model()` — the refresh syncs all 376 task files to the DB, which holds the write lock long enough to exceed the busy timeout on concurrent calls.

## Root cause

`GateToolService::pass/fail/cancel/sync` are all `pub fn` with no serialization. The MCP dispatch handler calls them directly. When RALPH dispatches parallel agents that all call `gate pass`, they race.

## Fix

Add a `Mutex<()>` (or `tokio::sync::Mutex`) to the gate MCP service. All mutating operations (`pass`, `fail`, `cancel`, `sync`, `append`) acquire the lock before executing. Read operations (`status`, `history`, `task_body`) don't need the lock — SQLite WAL mode handles concurrent reads.

## Files

- `crates/maenifold-gate/src/mcp/dispatch.rs` — add mutex, wrap mutating dispatches
- `crates/maenifold-gate/src/mcp/mod.rs` — hold the mutex in the service struct

## Acceptance Criteria

- 10 concurrent `gate pass` calls through MCP all succeed (no database-is-locked)
- Read operations (`status`) are not blocked by the mutex
- Existing concurrent test in `cache_db_concurrent_tests.rs` still passes
