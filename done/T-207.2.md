# T-207.2 — StdioPool: server pool manager

## Requirement

Create a `StdioPool` that manages multiple `StdioSession` instances — one per gateway-enabled stdio server. Handles eager initialization at startup, crash detection, and safe restart.

## Interface

```rust
pub struct StdioPool { /* ... */ }

impl StdioPool {
    /// Eagerly start all gateway-enabled servers. Returns tool collision errors.
    /// Called once in serve_http_listener_with_shutdown, result wrapped in Arc.
    pub async fn start(servers: Vec<McpServerStdioConfig>) -> Result<Self>;

    /// Call a tool on a named server.
    /// If session is dead: restart ONLY if the request was never written (connection-establishment failure).
    /// If session died mid-call (EOF after write): return error, do NOT retry.
    pub async fn call_tool(&self, server_name: &str, tool_name: &str, arguments: Value) -> Result<CallToolResult>;

    /// All tools from all servers (cached from init).
    pub fn all_gateway_tools(&self) -> Vec<Tool>;

    /// Rebuild: shutdown all, re-start with new config. For config reload.
    /// Drains in-flight calls before shutdown (waits up to 5s).
    pub async fn rebuild(&self, servers: Vec<McpServerStdioConfig>) -> Result<()>;

    /// Shutdown all child processes.
    pub async fn shutdown(&self);
}
```

## Behavior

### Eager initialization
- On `start()`, spawn and initialize ALL gateway-enabled servers in parallel via `JoinSet`.
- If a server fails to start: log warning, exclude from pool, continue with remaining servers. Do NOT fail the entire pool.
- After all servers start: collect all tool names, check for collisions (same tool name from two servers, or gateway tool shadowing a native maenifold tool). Collision = return `Err` with a clear message naming both servers and the conflicting tool.

### Per-server state machine
```
Uninitialized → Starting → Running → Dead
                                ↓
                            Restarting → Running | Dead
```
- Prevent concurrent spawn/init attempts with per-server state guard (not just a Mutex on stdin/stdout).

### Crash recovery
- On `call_tool`: check `session.is_usable()` first (alive AND not poisoned).
- If not usable (dead OR poisoned) AND the call hasn't been written yet: kill the session, restart, then call.
- If not usable AND a previous call was mid-flight (wrote to stdin, never got response): return error immediately. Do NOT retry — the tool may have partially executed (non-idempotent safety per duo review).
- On successful restart: re-discover tools, verify no new collisions.

### Config reload
- `rebuild()` drains in-flight calls (Mutex acquisition with 5s timeout), shuts down all sessions, starts fresh from new config.
- Wire into existing `/api/config/reload` handler.

### Shared state ownership
The pool and routing registry must be accessible from both the HTTP handler factory and the config reload handler. Use `arc_swap::ArcSwap<GatewayRuntime>` where:

```rust
pub struct GatewayRuntime {
    pub pool: StdioPool,
    pub routing: ToolRoutingRegistry,
}
```

- `ArcSwap<GatewayRuntime>` is stored in `ApiState` (already shared across routes and passed to the service factory).
- Handler factory reads via `ArcSwap::load()` — lock-free, no tearing during in-flight calls.
- `rebuild()` constructs a new `GatewayRuntime`, then calls `ArcSwap::store()` — old runtime is dropped when the last `Arc` reference dies (after in-flight calls complete).
- This is the same pattern used by `Arc<RwLock<Config>>` in `ApiState` today, but `ArcSwap` avoids reader contention on the hot path.

### Shutdown
- Called from `serve_http_listener_with_shutdown` shutdown path (before HTTP drain completes).
- Shut down all sessions in parallel.
