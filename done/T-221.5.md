# T-221.5 - ACP/Jockey Intent Resolver

## Problem

The gateway needs natural-language routing without client MCP sampling. Existing `AcpExec` proves ACP/Jockey can call configured agents, but intent routing needs a dedicated resolver that returns validated structured candidates, not free-form prose.

## Scope

Implement an internal resolver module that:

- Builds a compact catalog prompt from `GatewayIndex` data.
- Invokes Jockey/ACP with the configured resolver agent.
- Applies configured model and thought level.
- Sends no automatic permission grants.
- Requests structured JSON output only.
- Parses resolver output with `serde_json` and typed Serde structs.
- Returns ranked route candidates or a clear resolver error.
- Attaches zero MCP servers by default.
- Attaches only MCP servers explicitly listed in `settings.gateway.intentResolver.mcpServers`.
- Bounds the catalog prompt by `settings.gateway.intentResolver.maxCatalogCharacters`.

Resolver output schema:

```json
{
  "intentSummary": "string",
  "candidates": [
    {
      "domain": "string",
      "command": "string",
      "confidence": 0.0,
      "reason": "string",
      "safetyClass": "read|write|mutate|destructive|orchestration",
      "requiresExactExecute": true,
      "parametersDraft": {}
    }
  ]
}
```

Candidate validation rules:

- `confidence` must be a number from 0.0 through 1.0.
- `domain` and `command` must exist in the deterministic registry.
- `safetyClass` must match the registry safety class for that command.
- `requiresExactExecute` must be true for write, mutate, destructive, and orchestration commands.
- `parametersDraft` must be an object and is advisory only; execution still requires `GatewayExecute`.

Validation implementation policy:

- Resolver output is deserialized into typed structs using `#[serde(deny_unknown_fields)]`.
- Semantic fields are validated against the deterministic `GatewayCatalog` from T-221.2.
- `schemars` may be used only if a schema is needed for prompt/documentation generation.
- No new structured-output framework dependency may be added.
- No JSON Schema validation dependency may be added solely for resolver-output validation.
- Catalog trimming is generated from the same `GatewayCatalog`, not a separate prompt-only catalog.

## Acceptance Criteria

- [ ] Resolver uses Jockey/ACP execution path rather than MCP sampling.
- [ ] Resolver uses configured model, defaulting to `gpt-5.4-mini`.
- [ ] Resolver uses configured thought level, with `none` omitting thought-level config.
- [ ] Resolver has a bounded timeout.
- [ ] Resolver attaches zero MCP servers by default.
- [ ] Resolver attaches only MCP servers explicitly listed in `settings.gateway.intentResolver.mcpServers`.
- [ ] Catalog prompt length is bounded by `maxCatalogCharacters`.
- [ ] Catalog trimming order is examples first, then schemas, then long descriptions; domain names and command names are never silently removed without an explicit omitted-count marker.
- [ ] Resolver output is parsed with `serde_json`, deserialized into typed Serde structs with denied unknown fields, and validated with semantic registry checks.
- [ ] Resolver output candidates are validated against the deterministic `GatewayCatalog` from T-221.2.
- [ ] No new JSON Schema validation dependency is added solely for resolver-output validation.
- [ ] No new structured-output framework dependency is added.
- [ ] Catalog prompt data is generated from the same `GatewayCatalog` used by `GatewayIndex` and `GatewayExecute`.
- [ ] Malformed resolver output returns a structured error and deterministic fallback instructions.
- [ ] Resolver never executes the selected command directly.
- [ ] Tests cover one clear route, ambiguous route, malformed JSON, missing configured resolver, and timeout.
- [ ] `cargo build --release -p maenifold-cli` succeeds.

**Note:** `acp_exec.rs` is NOT modified. The resolver uses `jockey::acp::execute_runtime()` directly (public re-export, cross-crate accessible). No extraction of private helpers needed.

**Note:** Catalog trimming (`render_compact_catalog`) lives in `gateway_resolver.rs`, NOT in `gateway_catalog.rs` — prevents gateway_catalog.rs from exceeding 300 LOC. The resolver builds the catalog prompt by iterating `catalog.domains()` then `catalog.commands(domain)` to include command-level details (names, descriptions, schemas, examples), then applies char-bounded trimming.

**Estimated net delta:** ~480-550 LOC across 6 files (3 new + 3 modified)

### Phase 1: Resolver Types

**New:** `mcp/gateway_resolver_types.rs`
- `ResolverOutput` — `intentSummary: String`, `candidates: Vec<ResolverCandidate>`
- `ResolverCandidate` — domain, command, confidence, reason, safetyClass, requiresExactExecute, parametersDraft
- `#[serde(deny_unknown_fields, rename_all = "camelCase")]`
- `ResolverError` enum — Disabled, NoAgent, Timeout, Malformed, AcpError

### Phase 2: Catalog Validation Extension

**Modified:** `gateway_catalog.rs`
- Add `pub(crate) fn validate_candidate(&self, domain: &str, command: &str, safety_class: &str) -> Result<bool>` (~25 LOC)
- Validates domain+command exist, safety_class matches
- DO NOT add trimming here (stays in resolver)

### Phase 3: Core Resolver

**New:** `mcp/gateway_resolver.rs`
- `pub(crate) async fn resolve_intent(catalog, settings, user_intent, root) -> Result<ResolverOutput>`
- Catalog prompt building: iterate `catalog.domains()` then `catalog.commands(domain)` to build a full catalog prompt including command names, descriptions, schemas, and examples. Then apply char-bounded trimming:
  - Tier 1: strip examples
  - Tier 2: strip schemas
  - Tier 3: truncate long descriptions
  - Include omitted-count marker if content was stripped
- ACP invocation: use the public re-export `jockey::acp::execute_runtime()` directly (cross-crate accessible). Build function arguments manually from resolver settings:
  - `runtime_kind`: inferred from configured agent command (e.g., "claude-code", "codex")
  - `role_name`: from `settings.agent`
  - `prompt`: built from catalog prompt + user intent
  - `context`: resolver metadata only (do NOT use for model/thoughtLevel config)
  - `cwd`: from root path
  - `event_tx`: broadcast channel (create a throwaway channel for resolver)
  - `auto_approve`: false
  - `mcp_servers`: from `settings.mcp_servers.iter().map(McpServerEntry::to_acp).collect()`
  - `role_mode`: None
  - `role_config_options`: include `("model", settings.model)` and, when `effective_thought_level()` returns Some, include `("thoughtLevel", level)`
  - `_state`: None
  - `app_session_id`: generated UUID for resolver session
  - `resume_session_id`: None
  - Timeout: wrap the future in `tokio::time::timeout(settings.timeout_seconds)`
- Parse response with `serde_json::from_str::<ResolverOutput>()`
- Validate each candidate via `catalog.validate_candidate()`
- Return validated candidates or structured error with fallback instructions

### Phase 4: Wiring

**Modified:** `gateway_handler.rs`
- Add `pub(crate) fn catalog(&self) -> &GatewayCatalog` accessor on `GatewayState`
**Modified:** `mod.rs`
- Add `mod gateway_resolver;`, `mod gateway_resolver_types;`, `#[cfg(test)] mod gateway_resolver_tests;`

### Phase 5: Tests

**New:** `mcp/gateway_resolver_tests.rs`
- Clear route: well-formed resolver output with valid domain/command → parsed correctly
- Ambiguous route: multiple candidates with varying confidence
- Malformed JSON: invalid resolver output → structured error
- Missing resolver agent: settings.enabled=false or no agent → ResolverError::Disabled
- Timeout: verify timeout propagation
- Safety class mismatch: candidate claims "read" for a mutating command → validation rejects
