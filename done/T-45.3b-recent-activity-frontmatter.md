# T-45.3b: RecentActivity — Use `first`/`last` Frontmatter

**Requirement**: FR-45.3 (RTM-324)
**RTM**: RTM-324
**Priority**: P1 — Simplification, not blocking pipeline

## Context

The `RecentActivity` tool currently extracts "first" and "last" content by parsing H2 sections from the markdown body (via `extract_h2_sections()` on the `content` field from the SQLite `file_content` table). Now that `append_h2_section` populates `first` and `last` in YAML frontmatter (T-45.3, done), the tool should read these fields directly instead of parsing markdown.

This simplifies the code and makes it consistent with how the pipeline engine reads session state.

## Scope

Modify `crates/maenifold-core/src/tools/recent_activity.rs` and `recent_activity_format.rs` to:
1. Read `first`/`last` from the database or frontmatter instead of parsing H2 sections
2. Fall back to H2 parsing when `first`/`last` are not present (backward compat with old files)

## Acceptance Criteria

1. **Read from frontmatter**: When `first` and/or `last` fields exist in the file's frontmatter (available via the SQLite `file_content` table or direct file read), use them directly for the "First" and "Last" display lines.
2. **Fallback**: When `first`/`last` fields are absent (legacy files written before T-45.3), fall back to the current `extract_h2_sections()` parsing behavior.
3. **Output unchanged**: The formatted output structure remains identical — `First: "..."` and `Last/Current: "..."` lines display the same kind of content.
4. **`include_content` mode**: When `include_content: true`, display the `first`/`last` field values as the content snippets instead of full H2 section bodies.
5. **No database schema changes**: The `file_content` table already stores frontmatter fields — use existing columns or parse from the stored content.

## Implementation Notes

- `collect_recent_activity_records_with_filter` in `recent_activity.rs` queries SQLite `file_content` table
- The `RecentActivityRecord` struct likely needs `first: Option<String>` and `last: Option<String>` fields
- Check if `file_content` table stores individual frontmatter fields or the raw YAML — may need to parse frontmatter from stored content
- `format_thinking_entry` and `format_memory_entry` in `recent_activity_format.rs` currently call `extract_h2_sections()` then use `sections.first()` and `sections.last()` — replace with frontmatter fields when available

## Red-team Audit

**Verdict: PASS**

All acceptance criteria verified:

- **AC1 — Read from frontmatter**: ✅ Verified in `recent_activity.rs:populate_recent_activity_summaries` (line ~252). Two-stage hydration: (1) `parse_frontmatter_summaries(&record.content)` parses YAML frontmatter embedded in the DB-stored `content` column; (2) if either field is still `None`, `read_markdown(&record.file_path, config)` reads from disk and extracts `first`/`last` via `frontmatter_map_string`. Covered by `collect_recent_activity_parses_frontmatter_embedded_in_stored_content` and `collect_recent_activity_reads_first_and_last_from_frontmatter`.

- **AC2 — Fallback to H2 parsing**: ✅ `format_recent_activity_report` always calls `extract_h2_sections(&row.content)` (format.rs line ~62). `render_recent_activity_summary_or_snippet` (format.rs line ~344) uses frontmatter summary only if non-empty, otherwise delegates to `render_recent_activity_snippet(fallback)` using the H2-parsed sections. All pre-existing format tests pass with records that have `first: None, last: None`.

- **AC3 — Output format unchanged**: ✅ Non-`include_content` lines remain `First: "..."` and `Last/Current: "..."` — same label/quoting/structure. `include_content` lines remain `First H2: {heading}` / `First H2 Content: {body}`. Verified in `format_activity_report_sequential_entry_include_content_toggle` and `format_activity_report_memory_entry_include_content_toggle`.

- **AC4 — `include_content` uses first/last values**: ✅ `summary_section_details` (format.rs line ~277) checks the frontmatter summary first and returns `(derived_heading, summary_string)` as the content. Heading is derived by splitting the summary on the first `:`. Covered by `format_activity_report_prefers_frontmatter_summaries_for_first_and_last` and `recent_activity_prefers_frontmatter_summaries_when_available`.

- **AC5 — No database schema changes**: ✅ `db/schema.rs` has no new `ALTER TABLE` or `CREATE TABLE` statements touching `file_content`. The SQL query in `collect_recent_activity_records_with_filter` selects the same 5 columns (`file_path, title, last_indexed, content, status`) as before. `first`/`last` are derived entirely from the existing `content` field or disk reads.

**Observations (not spec violations):**

1. **Empty heading when frontmatter value lacks a colon** (`summary_section_details`): If a `first`/`last` frontmatter value contains no `:` (e.g., `"plain summary"`), the derived heading becomes an empty string, producing `First H2: ` (blank) while `First H2 Content: plain summary` remains correct. The spec does not define what heading to use in `include_content` mode when frontmatter is the source, so this is an unspecified edge case rather than a violation. No test covers it.

2. **`has_distinct_summary_last` requires both `first` and `last` to be `Some`** (`.zip()` semantics): A record with frontmatter `last` but no frontmatter `first` does not trigger the "distinct last" path; it falls back to `meaningful.len() > 1`. This is conservative and correct — it does not suppress a valid Last line; it just defers to the H2 count check.

3. **H2 parsing runs on every record** regardless of frontmatter presence (needed for Thoughts/Steps/Sections counts). This is correct behavior, not a defect.
