# T-61.4 — PipelineNode Tagged Enum + NodeState.output

**Requirement**: FR-47
**Test Cases**: TC-200
**Component**: `crates/maenifold-core/src/workflow/pipeline/types.rs`

## Context

`PipelineNode` is currently a flat struct with `id`, `workflow_id`, `acp_client` fields (types.rs:37-41). All pipeline nodes are implicitly workflow nodes. There are no prompt or sequential-thinking node types.

`NodeState` has `session_id`, `status`, `attempts` (types.rs:67-71) but no `output` field, so completed node results cannot be consumed by downstream nodes.

A complete design exists at `docs/design/pipeline-node-types.rs` with a wire-type adapter pattern for backwards-compatible serde. Use this design as the implementation reference.

## Acceptance Criteria

1. Replace the flat `PipelineNode` struct with a tagged enum having three variants:
   - `Workflow { id, workflow_id, acp_client: Option, prompt: Option }`
   - `Prompt { id, prompt, agent, tool_mode }` — `tool_mode` defaults to `"disabled"` (NOT "completion" — security decision)
   - `SequentialThinking { id, topic, total_thoughts, analysis_type: Option, agent }` — note `agent` field is REQUIRED

2. Implement a wire-type adapter (`PipelineNodeWire`) for serde:
   - `#[serde(try_from = "PipelineNodeWire", into = "PipelineNodeWire")]` on the enum
   - `PipelineNodeWire` is a flat struct with `#[serde(rename = "type", default)] kind: PipelineNodeKind`
   - `PipelineNodeKind` is an enum with `#[default] Workflow`, `Prompt`, `SequentialThinking`
   - `TryFrom<PipelineNodeWire>` validates required fields per variant
   - `From<PipelineNode>` converts back for serialization
   - `skip_serializing_if` on all Optional/default fields

3. Backwards compatibility: JSON `{ "id": "n1", "workflowId": "wf", "acpClient": "agent" }` (no `type` field) MUST deserialize as a Workflow node.

4. Add accessor methods to `PipelineNode`:
   - `id() -> &str`
   - `workflow_id() -> Option<&str>` (Some for Workflow, None for others)
   - `acp_client() -> Option<&str>` (Some for Workflow/Prompt via agent field, None for SequentialThinking)
   - `prompt() -> Option<&str>` (Some for Workflow prompt/Prompt prompt, None for SequentialThinking)
   - `node_type_name() -> &str` ("workflow", "prompt", "sequentialThinking")

5. Add `output: Option<String>` to `NodeState` with `#[serde(default, skip_serializing_if = "Option::is_none")]`.

6. Update ALL references to `node.id`, `node.workflow_id`, `node.acp_client` throughout the pipeline module to use the new accessor methods. The code MUST compile. Run `cargo build -p maenifold-core` to verify.

7. All existing pipeline tests MUST continue to pass.

## Red-team Audit

**Verdict: PASS**

All acceptance criteria verified. The three mandated FAIL fixes are confirmed applied.

### Mandatory FAIL items (from prior design review)

- **FAIL-1** (`SequentialThinking` MUST have `agent: String`): ✅ Fixed — `types.rs:60-66` shows `SequentialThinking { id, topic, total_thoughts, analysis_type, agent }`. `TryFrom<PipelineNodeWire>` at `types.rs:170-174` requires the field via `required(wire.agent, "agent")?`.
- **FAIL-2** (Wire-type adapter pattern, not `tag+flatten`): ✅ Fixed — `#[serde(try_from = "PipelineNodeWire", into = "PipelineNodeWire")]` on the enum at `types.rs:43`. Flat `PipelineNodeWire` struct with `#[serde(rename = "type", default)] kind: PipelineNodeKind` at `types.rs:72-92`.
- **FAIL-5** (`tool_mode` MUST default to `"disabled"`): ✅ Fixed — `default_prompt_tool_mode()` at `types.rs:300` returns `"disabled"`, and `is_default_prompt_tool_mode` at `types.rs:304` checks for `"disabled"`. Design reference had this wrong (`"completion"`); implementation corrects it.

### All acceptance criteria

1. **Tagged enum with three variants**: ✅ `types.rs:44-66` — `Workflow`, `Prompt`, `SequentialThinking` each with correct fields per spec.
2. **Wire-type adapter (`PipelineNodeWire`)**: ✅ `types.rs:68-196` — `PipelineNodeKind` default `Workflow`, `TryFrom` validates required fields, `From` converts back, all optional/default fields use `skip_serializing_if`.
3. **Backwards compatibility** (`{"id","workflowId","acpClient"}` deserializes as Workflow): ✅ Test `old_workflow_json_still_deserializes` at `types.rs:289-299` passes. Confirmed by `cargo test -p maenifold-core --lib types`.
4. **Accessor methods** (`id`, `workflow_id`, `acp_client`, `prompt`, `node_type_name`): ✅ All five accessors implemented at `types.rs:95-130`. **Documented deviation**: `acp_client()` returns `Some(agent)` for `SequentialThinking` (not `None` as criterion 4 states). This resolves an internal spec inconsistency: criterion 1/FAIL-1 mandates a *required* `agent: String` on `SequentialThinking`, making a `None` return contradictory and breaking executor dispatch (`executor.rs:100`). SWE documented the override explicitly. This is the correct resolution.
5. **`NodeState.output: Option<String>`**: ✅ `types.rs:258` — `#[serde(default, skip_serializing_if = "Option::is_none")]` applied correctly. Stronger than the design reference which only had `#[serde(default)]`.
6. **All callers updated, build passes**: ✅ `grep` across the pipeline module finds zero bare `.id`, `.workflow_id`, `.acp_client` field accesses — all are accessor calls. `cargo build -p maenifold-core` exits 0 in 1.78s.
7. **Existing pipeline tests pass**: ✅ `cargo test -p maenifold-core --lib pipeline` → **105 passed, 0 failed**. The pre-existing pause/resume flicker (`pipeline_pause_and_pipeline_resume_updates_status`) was also stabilized; all 105 tests are green.

### Additional observations

- The design reference (`docs/design/pipeline-node-types.rs`) still has the unfixed versions (no `agent` on `SequentialThinking`, `tool_mode = "completion"`, `SequentialThinking::acp_client() = None`). - WARN-7 (round-trip adds `type` tag) is acceptably documented: serialized Workflow nodes will include `"type":"workflow"`. Old consumers that treated the field as unknown will ignore it; this is forward-compatible.
