## Goal

Expose native maenifold [[MCP]] tools for the accepted [[gate-backlog]] operations under [[GatewayExecute]] domain `maenifold.gate`, backed by a cycle-free `maenifold-gate-core` lifecycle API. This replaces the current partial bare `gate` domain.

## Native Tool Scope

The native scope is seven tools, preserving the desktop detail flow:

- `gate_Status`
- `gate_Pass`
- `gate_Fail`
- `gate_Append`
- `gate_Sync`
- `gate_History`
- `gate_TaskBody`

`gate_History` and `gate_TaskBody` are explicitly in scope because desktop task detail currently requires history and task body. Do not remove that user value.

## Contract Decisions

- Replace the existing bare `gate` GatewayIndex domain with `maenifold.gate`.
- The bare `gate` domain must not appear in GatewayIndex after this task.
- GatewayIndex for `maenifold.gate` exposes exactly the seven command names above.
- Legacy lowercase commands `status`, `sync`, `history`, and `task_body` must not be exposed as current `maenifold.gate` commands.
- `cancel` and `gate_Cancel` must not be exposed by GatewayIndex or executable through GatewayExecute.
- The seven commands remain Gateway catalog commands backed by the native Gate gateway implementation, not a separate standalone MCP server.

## Lifecycle Semantics

- `gate_Status`, `gate_History`, and `gate_TaskBody` are read commands and must not mutate task markdown.
- `gate_Append` takes explicit `root`, `taskId`, `agent`, `notes`, and optional `model`; it derives the active stage, appends a canonical append record, and does not transition state.
- `gate_Pass` takes explicit `root`, `taskId`, `agent`, `notes`, and optional `model`; it derives the active state, appends a canonical outcome record, applies the state-machine pass transition, and moves the task to `done/` on terminal pass.
- `gate_Fail` takes explicit `root`, `taskId`, `agent`, `notes`, and optional `model`; it derives the active state, appends a canonical outcome record, and applies the state-machine fail transition.
- Errors must be explicit and actionable for unknown task IDs, invalid state transitions, missing/invalid required parameters, and file I/O failures.

## Library Boundary

- Port the high-level append/pass/fail orchestration currently owned by the retiring `maenifold-gate` command/tool-service layer into `maenifold-gate-core`, for example as `maenifold_gate_core::lifecycle`.
- `maenifold-core` must call only `maenifold-gate-core` for Gate domain behavior.
- `maenifold-core` must not import or include files from `crates/maenifold-gate/**`, including bundled gate definition assets.
- If bundled gate definitions are needed by the native gateway, move or expose them from a cycle-free source such as `maenifold-gate-core`.

## Acceptance Criteria

- `GatewayIndex` lists domain `maenifold.gate` and does not list the bare `gate` domain.
- `GatewayIndex` for `maenifold.gate` lists exactly the seven accepted `gate_*` tools.
- `GatewayIndex` for `maenifold.gate` does not list lowercase legacy command names or `cancel` / `gate_Cancel`.
- `GatewayExecute` executes all seven commands natively.
- `gate_Status`, `gate_History`, and `gate_TaskBody` are classified as `read`.
- `gate_Pass`, `gate_Fail`, `gate_Append`, and `gate_Sync` are classified as `mutate`.
- `maenifold-core` depends only on the cycle-free gate library, never on the current `maenifold-gate` crate.
- `maenifold-core` does not use `include_str!` or any path reference into `crates/maenifold-gate/**`.
- `gate_Append`, `gate_Pass`, and `gate_Fail` mutate task markdown through `maenifold-gate-core` lifecycle behavior, with terminal pass moving the task file to `done/`.
- Read commands do not modify task files.
- Gateway experiment fixtures reference renamed native gateway surfaces and no longer assume an upstream standalone `gate` server for these commands.

- `cargo test -p maenifold-core gate_gateway`

Required test assertions:

- Gateway catalog domain tests assert `maenifold.gate` exists, bare `gate` does not exist, exactly seven `gate_*` commands are exposed, and no cancel command is exposed.
- Gateway dispatch tests cover success paths for all seven commands through GatewayExecute.
- Lifecycle tests prove append/pass/fail record canonical stage sections, fail/pass apply state-machine transitions, terminal pass moves to `done/`, and read commands do not mutate task files.
- Gateway experiment tests prove no standalone `gate` MCP server, port `8081`, stdio process spawn, or upstream server named `gate` is required for these commands.

## Non-Goals

- Do not reintroduce or depend on the standalone [[gate-service]].
- Do not change desktop UI in this child.
- Do not add `gate_Cancel`.
