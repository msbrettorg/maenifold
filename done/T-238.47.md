# T-238.47 - P0 MCP OAuth auth flow missing for opencode

**Pipeline**: sdd

## Problem

`opencode mcp auth maenifold` fails against the maenifold MCP server:

```text
MCP OAuth Authentication
Authentication failed
HTTP 404: Invalid OAuth error response: SyntaxError: JSON Parse error: Unexpected EOF. Raw body:
```

Live endpoint probes show:

- `GET /mcp` returns `401 {"error":"missing or invalid bearer token"}`.
- `GET /.well-known/oauth-authorization-server` returns `404` with an empty body.
- `GET /.well-known/oauth-authorization-server/mcp` returns `404` with an empty body.
- `GET /.well-known/oauth-protected-resource` returns `404` with an empty body.
- `GET /.well-known/oauth-protected-resource/mcp` returns `404` with an empty body.
- `GET /authorize` returns `404` with an empty body.
- `GET /token` returns `404` with an empty body.

Maenifold currently supports local bearer-token auth for HTTP MCP, using `~/maenifold/auth/localhost.token`, but does not expose an OAuth discovery/auth flow that `opencode mcp auth` can complete.

## PM Spec Revision

Architect duo review on 2026-04-27 rejected the prior spec because it left SWE to choose between a bearer-token bridge and a real OAuth flow, conflated ACP with MCP HTTP authorization, and missed the `WWW-Authenticate` protected-resource discovery header. This revision is the dispatch contract.

### Protocol Boundary

This task targets the MCP Authorization spec for HTTP transports, not Agent Client Protocol auth/session behavior.

ACP is out of scope except as negative evidence:

- ACP overview says the protocol is for Agents and Clients to communicate, and the flow includes `Client -> Agent: initialize` and `Client -> Agent: authenticate if required by the Agent` (`~/.copilot/skills/agent-client-protocol/references/overview.md:7`, `:21-24`).
- ACP session setup says `session/new` includes "a list of MCP servers the Agent should connect to" (`~/.copilot/skills/agent-client-protocol/references/session-setup.md:44-50`).
- ACP session setup says HTTP MCP server configuration is gated by `mcpCapabilities.http` (`~/.copilot/skills/agent-client-protocol/references/session-setup.md:146-149`).

Therefore this task MUST NOT modify ACP relay/session/auth paths unless a fresh architect review proves a direct dependency. In particular, do not change ACP `initialize`, ACP `authenticate`, `session/new`, `session/load`, permission flow, or ACP relay behavior to solve this bug.

### Target Contract

Implement a local MCP OAuth authorization-code + PKCE bridge for the HTTP MCP server.

Use MCP Authorization spec revision `2025-06-18` as the target contract. Relevant requirements from the official MCP authorization page:

- "The Model Context Protocol provides authorization capabilities at the transport level... for HTTP-based transports."
- "MCP servers MUST implement OAuth 2.0 Protected Resource Metadata (RFC9728). MCP clients MUST use OAuth 2.0 Protected Resource Metadata for authorization server discovery."
- "MCP servers MUST use the HTTP header `WWW-Authenticate` when returning a 401 Unauthorized to indicate the location of the resource server metadata URL."
- "MCP clients MUST implement Resource Indicators for OAuth 2.0 as defined in RFC 8707."
- Access token use is via `Authorization: Bearer <access-token>`.

RFC 9728 also states that Protected Resource Metadata is a JSON document and that Section 5 describes using `WWW-Authenticate` to dynamically inform clients of the protected resource metadata URL.

### Required Behavior

Implement the OAuth path, not a bearer-token-only error bridge.

Required behavior:

- `GET /mcp` without a valid token returns `401` and includes:
  - `WWW-Authenticate: Bearer resource_metadata="http://127.0.0.1:8080/.well-known/oauth-protected-resource/mcp"` for the default local server.
  - The existing JSON error body may remain, but the discovery header is mandatory.
- OAuth protected-resource metadata endpoints return valid JSON at both:
  - `/.well-known/oauth-protected-resource`
  - `/.well-known/oauth-protected-resource/mcp`
- OAuth authorization-server metadata endpoints return valid JSON at both:
  - `/.well-known/oauth-authorization-server`
  - `/.well-known/oauth-authorization-server/mcp`
- Dynamic client registration is supported at `/register` and validates/echoes client metadata required for the flow.
- Authorization endpoint is supported at `/authorize`.
- Token exchange endpoint is supported at `/token`.
- Authorization flow supports authorization code + PKCE S256.
- The `resource` parameter is required in authorization and token requests and must identify the local MCP resource.
- Redirect URIs must be loopback-only: `http://127.0.0.1`, `http://localhost`, or `http://[::1]`.
- Non-loopback redirect URIs, non-S256 PKCE methods, expired codes, mismatched `resource`, and mismatched `client_id` are rejected with actionable HTTP errors.
- OAuth endpoints are mounted outside the bearer-auth middleware so unauthenticated clients can discover and complete auth.
- `/mcp` bearer-token protection remains intact for existing Copilot CLI, desktop, and generic MCP clients.
- Existing bearer-token config via `~/maenifold/auth/localhost.token` continues to work.
- `opencode mcp auth maenifold` no longer fails with `Unexpected EOF`.

### Token Model

Use the trusted-loopback bridge model for this task:

- The bridge may issue the existing local `localhost.token` as `access_token`.
- This is a trusted-loopback convenience bridge, not a general multi-user OAuth authorization server.
- No refresh token is required.
- No per-client token scoping is required in this task.
- The metadata/documentation must disclose the trust model: loopback-only, local user, shared local token, no expiry/refresh, and no per-client audience isolation beyond local resource validation.
