# T-59.5: Fix MCP Client SSE Response Parsing

**Requirement**: FR-43
**RTM**: RTM-192
**Priority**: P0 — Blocking: pipeline UI cannot connect

## Context

The MCP Streamable HTTP server (`maenifold --http`) returns `content-type: text/event-stream` for JSON-RPC requests. This is correct per the MCP Streamable HTTP specification — the server wraps JSON-RPC responses in SSE framing (`data: {...}\n\n`).

However, `useMcpClient.ts` calls `response.json()` unconditionally, which fails on SSE-formatted responses. The `initialize` call succeeds at the HTTP level but `response.json()` throws because the body is SSE-framed, not raw JSON.

Evidence from `curl`:
```
HTTP/1.1 200 OK
content-type: text/event-stream
mcp-session-id: 5b262b34-d83d-4530-a58a-378bd1b0ff78

data: {"jsonrpc":"2.0","id":1,"result":{...}}
```

## Scope

Fix `src/composables/useMcpClient.ts` in the pipeline-ui project to handle both `application/json` and `text/event-stream` response content types.

## Acceptance Criteria

1. **Content-type detection**: After receiving a response, check `response.headers.get('content-type')`. If it contains `text/event-stream`, parse as SSE. If it contains `application/json`, parse with `response.json()` as before.
2. **SSE parsing**: When content-type is SSE, read `response.text()`, extract lines starting with `data: `, concatenate the JSON from those lines, and parse the JSON-RPC response. Ignore empty `data:` lines, `id:` lines, and `retry:` lines (these are SSE framing).
3. **Multiple data events**: The SSE stream may contain multiple `data:` events. Find the one that contains a JSON-RPC response matching the request's `id` field. If multiple JSON-RPC messages are present, return the one with a matching `id`.
4. **Session header**: The `Mcp-Session-Id` header extraction from the `initialize` response must continue to work — it's on the HTTP response headers, not in the SSE body.
5. **Notification responses**: For notification requests (no `id`), SSE parsing is not needed since the server returns HTTP 202 with no body. The existing `options.notification` path should be unchanged.
6. **Error handling**: If SSE parsing fails to find a valid JSON-RPC response, set `error.value` and throw with a descriptive message.
7. **Existing tests**: All existing tests in `src/composables/__tests__/useMcpClient.test.ts` must continue to pass (they mock `fetch` with JSON responses, so the `application/json` path must still work).
8. **Build**: `npm run build` and `npm test` pass.

## Implementation Notes

A simple SSE parser approach:
```typescript
async function parseResponse<T>(response: Response): Promise<JsonRpcResponse<T>> {
  const contentType = response.headers.get('content-type') ?? '';
  
  if (contentType.includes('text/event-stream')) {
    const text = await response.text();
    const jsonLines = text
      .split('\n')
      .filter(line => line.startsWith('data: ') && line.trim() !== 'data:')
      .map(line => line.slice(6)); // strip 'data: ' prefix
    
    for (const jsonStr of jsonLines) {
      try {
        const parsed = JSON.parse(jsonStr);
        if (parsed.jsonrpc === '2.0') return parsed;
      } catch { /* skip non-JSON data lines */ }
    }
    
    throw new Error('No valid JSON-RPC response found in SSE stream');
  }
  
  return response.json();
}
```

The `jsonRpc` function should use this helper instead of calling `response.json()` directly.

### AC2 — SSE parsing: PASS

**Location**: `parseSseJsonRpcResponse`, lines 51–85.

The implementation exceeds the spec's reference implementation:

| Behaviour | Spec reference | Implementation |
|---|---|---|
| Line delimiter | `\n` only | `\r?\n` (CRLF safe) — verified by T7 |
| Event boundary | N/A | Splits on `\r?\n\r?\n` first (block-level) |
| `data:` detection | `startsWith('data: ')` (space required) | `trim()` + `startsWith('data:')` — catches `data:` and `data: ` |
| Prefix strip | `line.slice(6)` (6 chars) | `line.slice(5).trimStart()` — strips 5 chars + optional whitespace |
| Empty `data:` guard | `line.trim() !== 'data:'` | `filter((line) => line.length > 0)` after slice |
| `id:` / `retry:` / `event:` | Implicit (don't start with `data:`) | Implicit — verified by T3, T8 |

**Caveat (non-blocking)**: `.trim()` strips both leading *and* trailing whitespace from each line before the `data:` check. The SSE spec does not permit leading whitespace in field names, so this is over-permissive but benign — trailing whitespace on a JSON payload is harmless since `JSON.parse` is whitespace-tolerant.

### AC3 — Multiple data events, id matching: PASS

**Location**: line 74.

```typescript
if (requestId === undefined || parsed.id === requestId) {
  return parsed as JsonRpcResponse<T>;
}
```

Iterates all `eventBlocks`, evaluates each `data:` candidate, skips non-matching ids, returns the first match. Verified by T5: a stream with `id:1` followed by `id:2` correctly returns the `id:2` block when `requestId=2`.

**Low-severity concern — strict `===` type coercion on id**: The comparison is `parsed.id === requestId` where `requestId` is `number` (from `nextId++`, line 147–149) and `parsed.id` is typed as `number | string | null`. If a server returns `"id": "1"` (string) when the client sent `id: 1` (number), `"1" === 1` evaluates to `false`, no match is found, and the call throws `No valid JSON-RPC response found in SSE stream for request id 1`.

The `maenifold --http` server returns numeric ids matching the request (confirmed in the spec's curl evidence). This is **not a current production risk**. It becomes a risk only if the server is replaced or proxied by an implementation that serialises ids as strings. Flagged for awareness; no code change required.

### AC4 — Session header extraction: PASS

**Location**: `connect()`, line 205.

```typescript
const headerSessionId = response.headers.get('Mcp-Session-Id');
```

`jsonRpc` returns `{ response, result }` where `response` is the raw `Response` object, unchanged. `connect()` reads the header directly from HTTP response headers, completely independent of SSE body content. The `parseJsonRpcResponse` helper consumes the body via `response.text()` or `response.json()` but the `response` reference passed back to `connect()` is the same object — in the Fetch API, header access is not body-dependent and remains valid after body consumption.

### AC6 — Error handling for failed SSE parse: PASS

**Location**: three-layer error chain.

1. `parseSseJsonRpcResponse` (line 83): throws `No valid JSON-RPC response found in SSE stream for request id <N>` — descriptive, includes the request id.
2. `parseJsonRpcResponse` (lines 97–100): catches and rethrows as `Invalid SSE response from <method>: <inner message>` — adds method context.
3. `jsonRpc` (lines 181–183): catches, writes `error.value`, rethrows — ensures the reactive `error` ref is always set before throwing to callers.

Edge cases verified by node simulation:
- Malformed JSON line → caught, skipped, continues (T4)
- No matching id → throws with id in message (T6)
- Non-JSON-RPC JSON (missing `jsonrpc` field) → `isJsonRpcResponse` guard (line 70) returns false, skipped (T10)
