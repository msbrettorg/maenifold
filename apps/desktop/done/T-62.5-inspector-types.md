# T-62.5 — Type-Aware Inspector Editing/Viewing

**Requirement**: FR-47
**Component**: `pipeline-ui/src/components/PipelineInspector.vue`
**Design Reference**: `pipeline-ui/docs/design/node-types-ui.md` §3
**Depends on**: T-62.1, T-62.2

## Context

PipelineInspector.vue (240 lines) shows node details when selected. In design mode it shows editable fields; in server mode it shows read-only status. Currently it only handles workflow node fields (workflowId, acpClient).

## Acceptance Criteria

### Design Mode (node selected)

1. Show the node type as a non-editable badge/label.

2. Show type-specific editable fields:
   - **Workflow**: Workflow ID, ACP client, Prompt (textarea)
   - **Prompt**: Agent, Tool mode (select), Prompt template (textarea)
   - **Sequential Thinking**: Topic, Agent, Total thoughts, Analysis type

3. Edits to these fields must update the node in `store.localDefinition.nodes` in real-time (two-way binding or explicit save).

### Server Mode (node selected)

4. Show node type badge, status, attempts, session ID (existing).

5. Show type-specific read-only fields matching design mode fields.

6. Show `output` field if present — as a read-only text block or collapsible section. This is the node's captured result from the executor.

### Both Modes

7. Edge inspector (when edge selected) must continue to work unchanged.

8. Overview mode (nothing selected) must continue to work unchanged.

9. Typecheck: `cd pipeline-ui && npx vue-tsc --noEmit` must pass.

### CR4 — Uses type guards from `pipeline-types.ts`

**PARTIAL PASS — asymmetry between design and server paths**

**Design nodes**: `isWorkflowNode`, `isPromptNode`, `isSequentialThinkingNode` are imported and used correctly in all three computed properties (lines 52–62) and all four update functions (lines 136, 140, 144, 148). ✅

**View nodes**: No type guard functions for `ViewNode` exist in `pipeline-types.ts`, so the implementation falls back to inline narrowing:

```ts
// line 64
selectedViewNode.value.type === 'workflow' || selectedViewNode.value.type == null
```

This works today because `WorkflowViewNode` is the only union member with an optional `type`. However:
- It re-implements the `WorkflowNode` identity rule from `getNodeType()` without calling it
- If a new view-node type with an optional `type` field is ever added, this guard silently widens
- No parallel `isWorkflowViewNode` / `isPromptViewNode` / `isSequentialThinkingViewNode` guards exist in the types file to reuse

**Recommendation**: Add `ViewNode` type guards to `pipeline-types.ts` and use them symmetrically — or at minimum call `getNodeType` on the view node's discriminant field for consistency.

### CR7 — No `as any` or `@ts-ignore`

**PASS** (with a latent defect noted)

No `as any` or `@ts-ignore` / `@ts-expect-error` anywhere in the component. `vue-tsc --noEmit` exits 0.

**Latent defect — unchecked cast on line 143**:
```ts
const toolMode = (event.target as HTMLInputElement).value as 'disabled' | 'allowed';
```
This cast is unsound: `.value` is `string` at runtime; the cast to `'disabled' | 'allowed'` is not validated. TypeScript accepts it without complaint. If the radio `value` attributes in the template were changed to anything else, the runtime value would silently violate `ToolMode` while the type system reports no error. A narrow runtime guard (`=== 'allowed' ? 'allowed' : 'disabled'`) would eliminate this exposure.

---

### Additional Finding — `workflowId` can be silently set to `undefined` (Medium)

```ts
// line 136
updateDesignNode((node) => (isWorkflowNode(node) ? { ...node, [field]: value || undefined } : node));
```

`field` is `'workflowId' | 'acpClient' | 'prompt'`. When `field === 'workflowId'` and the user clears the input, `value || undefined` evaluates to `undefined`, producing `{ ...node, workflowId: undefined }`. `WorkflowNode.workflowId` is `string` (required). TypeScript does not catch this because a computed property key with a union type defeats property-level narrowing in spread expressions — the resulting object is accepted as `PipelineNode` without complaint.

**Impact**: A user clearing the Workflow ID field corrupts the node into an invalid state that will propagate to `store.localDefinition` and likely crash the server-side executor on dispatch.

**Remediation**: Guard the `workflowId` field specifically, or split `updateWorkflowField` into per-field functions with appropriate validation:
```ts
if (field === 'workflowId' && !value) return; // or show validation error
```
