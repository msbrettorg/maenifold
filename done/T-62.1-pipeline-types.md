# T-62.1 — TypeScript Types for Pipeline Node Types

**Requirement**: FR-47
**Component**: `pipeline-ui/src/lib/pipeline-types.ts`
**Design Reference**: `pipeline-ui/docs/design/node-types-ui.md` §5

## Context

`pipeline-types.ts` (56 lines) defines a flat `PipelineNode` interface with only `id`, `workflowId`, `acpClient`. The backend now supports 3 node types (workflow/prompt/sequentialThinking) with per-node prompts and `NodeState.output`. The TypeScript types must match.

## Acceptance Criteria

1. Replace `PipelineNode` flat interface with a discriminated union:
   ```typescript
   type PipelineNode = WorkflowNode | PromptNode | SequentialThinkingNode;

   interface WorkflowNode {
     type?: 'workflow';  // optional for backwards compat
     id: string;
     workflowId: string;
     acpClient?: string;
     prompt?: string;
   }

   interface PromptNode {
     type: 'prompt';
     id: string;
     prompt: string;
     agent: string;
     toolMode?: string; // default "disabled"
   }

   interface SequentialThinkingNode {
     type: 'sequentialThinking';
     id: string;
     topic: string;
     agent: string;
     totalThoughts?: number; // default 5
     analysisType?: string;
   }
   ```

2. Update `ViewNode` to include:
   - `type?: string` — "workflow" | "prompt" | "sequentialThinking"
   - `output?: string` — the node's captured output
   - `agent?: string` — for prompt/thinking nodes
   - `topic?: string` — for thinking nodes

3. Add helper function `createNode(type: string, fields: Record<string, any>): PipelineNode` that creates a properly typed node with defaults:
   - Generates an ID if not provided (`{type}-{timestamp}`)
   - Workflow: requires workflowId
   - Prompt: requires prompt, agent; defaults toolMode to "disabled"
   - SequentialThinking: requires topic, agent; defaults totalThoughts to 5

4. Add helper function `nodeLabel(node: PipelineNode): string`:
   - Workflow: `"wf: {workflowId}"`
   - Prompt: `"prompt: {first40chars}..."`
   - SequentialThinking: `"think: {topic}"`

5. Add helper function `getNodeType(node: PipelineNode): 'workflow' | 'prompt' | 'sequentialThinking'`:
   - Returns `node.type` if present
   - Returns `'workflow'` if `type` is missing (backwards compat)

6. Add type guard functions:
   - `isWorkflowNode(node: PipelineNode): node is WorkflowNode`
   - `isPromptNode(node: PipelineNode): node is PromptNode`
   - `isSequentialThinkingNode(node: PipelineNode): node is SequentialThinkingNode`

7. All existing type exports must remain (PipelineEdge, PipelineDefinition, NodeStatus, etc.).

8. Typecheck: `cd pipeline-ui && npx vue-tsc --noEmit` must pass.

## Red-Team Audit

**Auditor**: red-team  
**Date**: 2025-07-14  
**Verdict**: ✅ PASS — all 10 criteria pass; 4 advisories filed

---

### Criterion 1 — Discriminated union with `type` field

**PASS**

`PipelineNode` is correctly defined as a discriminated union at line 50:
```typescript
export type PipelineNode = WorkflowNode | PromptNode | SequentialThinkingNode;
```
All three member interfaces carry a `type` literal field as the discriminant (lines 29, 36, 43).

---

### Criterion 2 — `WorkflowNode.type` is optional (backwards compat)

**PASS**

Line 29: `type?: "workflow"` — the `?` makes the field optional. Legacy payloads that omit `type` will deserialize correctly as `WorkflowNode`. The Rust test at `types.rs:293` (no `type` key in JSON) confirms the backend also accepts omission, and the TypeScript `??` fallback in `getNodeType` (line 125) aligns with it.

---

### Criterion 3 — All fields match backend

**PASS**

Cross-referencing `PipelineNodeWire` (Rust `types.rs:69-96`, `#[serde(rename_all = "camelCase")]`):

| Node | Rust wire fields | TS fields | Match |
|------|-----------------|-----------|-------|
| Workflow | `id`, `workflowId?`, `acpClient?`, `prompt?` | lines 28–33 | ✓ |
| Prompt | `id`, `prompt?`, `agent?`, `toolMode` (default "disabled") | lines 35–40 | ✓ |
| SequentialThinking | `id`, `topic?`, `agent?`, `totalThoughts` (default 5), `analysisType?` | lines 42–48 | ✓ |

The Rust `skip_serializing_if` annotations mean `toolMode` (when "disabled") and `totalThoughts` (when 5) are omitted in JSON; TypeScript's `toolMode?: ToolMode` and `totalThoughts?: number` correctly handle these absent fields.

⚠️ **Advisory A1 — `toolMode` undefined ≠ "disabled" at runtime**: When the backend omits `toolMode` (the default case), TypeScript receives `undefined`, not `"disabled"`. `PromptNode.toolMode` is optional, so `node.toolMode ?? "disabled"` is the correct consumption pattern — but this contract is not documented anywhere in the file. Consumer code that reads `node.toolMode` directly without a fallback will silently see `undefined`. Consider adding a JSDoc comment or re-exporting a `DEFAULT_TOOL_MODE` constant.

---

### Criterion 4 — `ViewNode` expanded with type/output for all 3 variants

**PASS**

The SWE replaced the flat `ViewNode` with a discriminated union (`ViewNode = WorkflowViewNode | PromptViewNode | SequentialThinkingViewNode`, lines 93–96). All three variants satisfy the spec requirements:

- `type`: present in all three variants (lines 72, 79, 86) ✓  
- `output?`: in `ViewNodeBase` (line 68), inherited by all variants ✓  
- `agent?`: in `PromptViewNode` (line 82) and `SequentialThinkingViewNode` (line 88) ✓  
- `topic?`: in `SequentialThinkingViewNode` (line 89) ✓  

⚠️ **Advisory A2 — `ViewNode` union requires narrowing for `agent`/`topic`**: The spec's AC describes a flat interface where `agent?` and `topic?` would be directly accessible on any `ViewNode`. The union implementation is more type-safe but means `viewNode.agent` is a compile error without narrowing (`isPromptNode` / `isSequentialThinkingNode`). Any existing consumer code expecting flat access to `agent` or `topic` on a raw `ViewNode` will break. The SWE notes downstream fixes in `PipelineComposer.vue` and `PipelineInspector.vue`, which should be verified by the blue-team.

---

### Criterion 5 — `createNode(type, fields)` validates required fields per type

**PASS**

All required-field checks are present and correct:
- `"workflow"` case: throws if `workflowId` is not a non-empty string (lines 153–157) ✓  
- `"prompt"` case: throws if `prompt` or `agent` is not a non-empty string (lines 173–178) ✓  
- `"sequentialThinking"` case: throws if `topic` or `agent` is not a non-empty string (lines 189–194) ✓  
- ID generation: `${type}-${Date.now()}` if `fields.id` is absent/empty (lines 146–149) ✓  
- `default` branch throws `Error` for unknown types (line 213) ✓  

⚠️ **Advisory A3 — `createNode` type parameter is `string`, not `PipelineNodeType`**: The function signature at line 142 accepts `type: string`. A misspelled call like `createNode("workfow", ...)` compiles without error and throws at runtime. This could be hardened to `type: PipelineNodeType` for compile-time exhaustiveness. The switch has a `default` throw as a runtime backstop, but the compile-time gap is a surface for typo-bugs.

---

### Criterion 6 — `nodeLabel(node)` returns display string

**PASS**

- Workflow: `wf: ${node.workflowId}` (line 219) — matches spec `"wf: {workflowId}"` ✓  
- Prompt: `prompt: ${preview}` where `preview` truncates at 40 chars with `...` (lines 222–225) — matches spec `"prompt: {first40chars}..."` for prompts longer than 40 chars ✓  
- SequentialThinking: `think: ${node.topic}` (line 228) — matches spec `"think: {topic}"` ✓  

⚠️ **Advisory A4 — ellipsis omitted for short prompts**: Line 224: `node.prompt.length > 40 ? \`...\` : node.prompt`. For prompts ≤ 40 characters the spec's template `"prompt: {first40chars}..."` implies `...` always. The implementation sensibly omits `...` when there is no truncation (correct UX), but it deviates from the literal spec wording. Low risk — the spec wording is likely imprecise, not the implementation.

---

### Criterion 7 — Type guards

**PASS**

All three guards are exported (lines 128–140):
- `isWorkflowNode`: delegates to `getNodeType(node) === "workflow"` ✓  
- `isPromptNode`: delegates to `getNodeType(node) === "prompt"` ✓  
- `isSequentialThinkingNode`: delegates to `getNodeType(node) === "sequentialThinking"` ✓  

The guards correctly handle the `WorkflowNode` case where `type` is `undefined` by routing through `getNodeType` (which applies the `?? "workflow"` fallback) rather than comparing `node.type` directly, avoiding a false-negative for legacy nodes.

### Criterion 8 — `getNodeType(node)` defaults to `"workflow"`

**PASS**

Lines 124–126:
```typescript
export function getNodeType(node: PipelineNode): PipelineNodeType {
  return node.type ?? "workflow";
}
```
Returns the node's `type` field if present; falls back to `"workflow"` for legacy `WorkflowNode` payloads where `type` is absent. Return type is `PipelineNodeType`, not `string` — compile-safe. ✓

---

### Criterion 9 — `toolMode` defaults to `"disabled"`

**PASS**

Line 185:
```typescript
toolMode: fields.toolMode === "allowed" ? "allowed" : "disabled",
```
This is an explicit allow-list check — any value other than the exact string `"allowed"` (including `null`, `undefined`, `""`, or any other string) produces `"disabled"`. This is correct deny-by-default security posture and matches the Rust backend's `default_prompt_tool_mode()` → `"disabled"`. ✓

### Advisory Summary

| ID | Severity | Description |
|----|----------|-------------|
| A1 | Medium | `toolMode` absent in JSON = `undefined` in TS, not `"disabled"`; consumption contract undocumented |
| A2 | Low | Union `ViewNode` requires narrowing for `agent`/`topic`; verify downstream consumer fixes in blue-team |
| A3 | Low | `createNode` accepts `type: string` — no compile-time exhaustiveness; typos reach runtime |
| A4 | Info | `nodeLabel` omits `...` for prompts ≤ 40 chars; spec wording implies always present |

None of the advisories are blocking. **A1** is the only one with security/correctness implications and warrants a follow-up doc comment or constant export.
