# T-44.5b: View State Oracle Research Against OG ACP-UI

**Requirement**: FR-44.5
**RTM**: RTM-350
**Priority**: P0 — diagnose broken per-tab view state before more UI churn
**Component**: `vendor/acp-ui/src/components/ChatView.vue`, `vendor/acp-ui/src/stores/session.ts`, `vendor/acp-ui/src/App.vue`, OG ACP-UI reference implementation

## Context

Our current ACP UI integration has a [[view-state]] bug: the rendered UI state is not behaving the way users expect. We need a research pass that uses the OG [[ACP-UI]] implementation as the oracle and compares it against our current implementation to determine where our adaptation diverged.

This is a research-only task. The goal is to produce a crisp diagnosis we can turn into one or more file-scoped remediation tasks, not to make speculative code changes.

## Acceptance Criteria

2. **Evidence-backed divergence**: Identify the specific divergence(s), omission(s), or adaptation mistakes most likely causing the broken view state, with file- and function-level evidence.
3. **Confidence labeling**: Separate confirmed root causes from hypotheses/open questions. Do not present guesses as facts.
4. **Remediation plan**: Recommend the smallest follow-up implementation task(s), each with target files, change scope, and a proposed acceptance-criteria sketch.
5. **No code changes**: Do not modify production code, tests, PRD, RTM, or other todo files. Append findings only to this spec.

- If the upstream implementation does **not** have a directly analogous mechanism, state that explicitly.
- Prefer exact file/function comparisons over broad architectural commentary.
- Keep the deliverable actionable for a follow-up SWE task.

## Research Findings

### 1. Observed symptom

The fork’s per-tab chat UI can preserve the wrong viewport and leak local UI state when switching tabs, especially while a response is still streaming. The underlying message data is stored per tab, but the **view-state layer** diverges from OG ACP-UI in two important ways:

- auto-scroll is no longer driven by **all message mutations**;
- the same `ChatView` component instance is reused across tabs, so local refs that are **not** persisted in `TabState` can bleed across sessions.

This matches the class of bug described in the spec: broken per-tab view state rather than broken transport/session state.

### 2. Current implementation path

**Fork source used:** `vendor/acp-ui/src/`

1. **Per-tab state now lives in the store.**
   - `TabState` adds per-tab `messages`, `toolCalls`, `scrollPosition`, and `inputDraft` in `vendor/acp-ui/src/lib/types.ts:281-370`.
   - `createEmptyTabState()` initializes those fields (`scrollPosition: 0`, `inputDraft: ''`).

2. **The session store is now tab-driven instead of singleton-driven.**
   - `tabs` is a `shallowRef<Map<string, TabState>>`, with `activeTabId` selecting the active tab in `vendor/acp-ui/src/stores/session.ts:190-223`.
   - `currentSession`, `messages`, `messageList`, `isConnected`, etc. are now computed from `activeTab` in `vendor/acp-ui/src/stores/session.ts:435-494`.
   - New sessions and resumed sessions each create a new tab via `createSession()` / `resumeSession()` in `vendor/acp-ui/src/stores/session.ts:907-1155`.

3. **`App.vue` switches tabs but keeps a single `ChatView` instance alive.**
   - The fork adds `TabStrip` and tab selection/close handlers in `vendor/acp-ui/src/App.vue:173-196, 319-327`.
   - The main view renders an unkeyed `ChatView` with `v-if="sessionStore.activeTab?.isConnected"` in `vendor/acp-ui/src/App.vue:319-352`.
   - There is no `:key="sessionStore.activeTabId"`, so tab switches do **not** remount `ChatView`.

4. **`ChatView.vue` manually saves/restores per-tab draft + scroll.**
   - `getTabState()`, `saveTabViewState()`, `restoreScrollPosition()`, and `handleMessagesScroll()` manage per-tab view state in `vendor/acp-ui/src/components/ChatView.vue:88-132`.
   - A watcher on `activeTabId` saves the old tab’s draft/scroll, swaps in the new tab’s `inputDraft`, and either restores `scrollPosition` or scrolls to bottom depending on whether the tab has “unseen” messages (`vendor/acp-ui/src/components/ChatView.vue:134-164`).
   - A second watcher auto-scrolls only when `tabId`, `messageIds`, or `messageCount` change (`vendor/acp-ui/src/components/ChatView.vue:166-202`).

5. **Several other `ChatView` refs remain component-local, not tab-local.**
   - Examples: `expandedThoughts`, `expandedToolCalls`, `pendingAttachments`, `activeCommandHint` in `vendor/acp-ui/src/components/ChatView.vue:35-42`.
   - These are not stored in `TabState` and are not reset on tab switch.

### 3. OG ACP-UI path

**Oracle actually used:** `formulahendry/acp-ui` (`v0.1.10`, commit `3d68fc6`).

Note: the prompt pointed at `nicepkg/acp`, but that repository URL returned `404`. The vendored ACP-UI README points to `https://github.com/formulahendry/acp-ui`, and its file layout matches the vendored code, so I used that as the behavioral oracle.

1. **OG has one global active session, not tabs.**
   - `currentSession`, `messages`, `isConnected`, `isConnecting`, etc. are plain refs in `/tmp/acp-ui-og/src/stores/session.ts:39-80`.
   - `handleSessionUpdate()` mutates the singleton `messages.value` array directly in `/tmp/acp-ui-og/src/stores/session.ts:110-220`.

2. **OG `App.vue` renders one chat surface for the one connected session.**
   - `ChatView` is shown only when `isConnected` in `/tmp/acp-ui-og/src/App.vue:243-245`.
   - There is no tab strip and no per-session/per-tab view restoration logic.

3. **OG `ChatView.vue` uses local component state plus deep auto-scroll.**
   - `inputText` and `messagesContainer` are local refs in `/tmp/acp-ui-og/src/components/ChatView.vue:10-25`.
   - Auto-scroll is a deep watch on `messages` in `/tmp/acp-ui-og/src/components/ChatView.vue:43-49`:
     - any mutation to the current message,
     - any streamed chunk append,
     - any thought/tool update
     moves the viewport to the bottom after `nextTick()`.

In short: OG’s view state is simple because there is only one session surface. The fork introduced tabs, but the tabbed view-state behavior is custom rather than inherited from OG.

### 4. Key divergences

1. **OG deep auto-scroll vs fork heuristic auto-scroll**
   - OG: `watch(messages, ..., { deep: true })` scrolls on any message mutation (`/tmp/acp-ui-og/src/components/ChatView.vue:43-49`).
   - Fork: the scroll watcher only compares `messageIds` and `messageCount` (`vendor/acp-ui/src/components/ChatView.vue:166-202`).
   - Consequence: if an assistant response keeps streaming into the **same message object**, the fork may not scroll even though content visibly changes.

2. **OG has no tab switch semantics; fork infers “unseen” from count only**
   - On tab switch, the fork decides whether to jump to bottom using `nextTab.messages.length > previousViewedCount` (`vendor/acp-ui/src/components/ChatView.vue:149-160`).
   - That misses updates where the last assistant message continues to grow but the message count stays constant.
   - This is a direct divergence from OG’s simpler behavior, where any active message mutation causes bottom-pinning.

3. **Fork reuses one `ChatView` instance across tabs**
   - `App.vue` renders an unkeyed `ChatView` (`vendor/acp-ui/src/App.vue:327`).
   - Because the component instance is reused, local refs survive tab switches unless explicitly copied into/out of `TabState`.
   - OG never had this problem because there was no cross-tab reuse path.

4. **Only some view state is persisted per tab**
   - Persisted: `messages`, `scrollPosition`, `inputDraft` (`vendor/acp-ui/src/lib/types.ts:292-297`).
   - Not persisted/reset per tab: `expandedThoughts`, `expandedToolCalls`, `pendingAttachments`, `activeCommandHint` (`vendor/acp-ui/src/components/ChatView.vue:35-42`).
   - Result: even if message history is isolated correctly, some UI affordances can bleed between tabs.

5. **Reactive strategy changed from direct refs to `shallowRef(Map) + triggerRef()`**
   - OG relies on ordinary refs (`/tmp/acp-ui-og/src/stores/session.ts:39-80`).
   - Fork relies on mutating nested tab objects inside `tabs: shallowRef<Map<...>>` and manually calling `triggerRef(tabs)` (`vendor/acp-ui/src/stores/session.ts:193-194, 267, 314, 854, 1091, 1278`).
   - This is materially more fragile. Example: bridge watchers assign `tab.pendingPermissions` and terminal snapshots in `vendor/acp-ui/src/stores/session.ts:340-359` without an immediate `triggerRef(tabs)`, so store consumers derived from `activeTab` can miss those updates until some other trigger happens.

### 5. Most likely root cause

#### Confirmed root cause A — scroll behavior diverged from OG in a way that breaks streamed conversations

The strongest confirmed divergence is the fork’s replacement of OG’s **deep auto-scroll** with a **message-id/message-count heuristic**.

Why this matters:
- ACP updates commonly stream into the current assistant message via repeated chunk updates.
- Those updates often change **message content** without changing the message id or array length.
- OG scrolls on those updates because it watches `messages` deeply.
- The fork does **not** scroll on those updates because `messageIds` and `messageCount` stay the same.

That creates two concrete failure modes:
1. **Active tab streaming:** the viewport can stop following the live response even though new text is appearing.
2. **Switching back to a background tab:** the watcher may conclude there are no unseen changes because count did not increase, then restore an old `scrollPosition` instead of jumping to the newest content.

This is the clearest oracle-backed explanation for “wrong per-tab view state.”

#### Confirmed root cause B — `ChatView` local UI state is shared across tabs unless manually persisted

Because `App.vue` reuses a single unkeyed `ChatView`, only the state explicitly copied into `TabState` (`inputDraft`, `scrollPosition`) is tab-specific. Other local refs stay alive across tab changes.

That means the fork can leak local UI state across sessions/tabs, for example:
- expanded thought panels,
- expanded tool-call panels,
- queued attachments,
- command hint/palette-related state.

OG has no equivalent bleed path because it never switches one mounted `ChatView` instance between sessions.

#### Important non-root observation

Message storage itself appears conceptually correct: `tab.messages` is per tab, `activeTab` selects the visible session, and `handleSessionUpdate(tabId, ...)` writes updates into the correct tab in `vendor/acp-ui/src/stores/session.ts:638-855`. The main problem is **view restoration / reactivity**, not cross-session message routing.

### 6. Open questions

1. **User-facing symptom precision**
   - Is the reported bug primarily “scroll does not stay at bottom while streaming,” or are users also seeing cross-tab bleed in attachments/expanded panels/draft-adjacent UI?

2. **Desired background-tab behavior**
   - When a hidden tab receives additional chunks on the same message, should returning to that tab always jump to bottom, or only if the user had previously been near the bottom?
   - OG effectively behaves like “always keep up with new output” because there is no multi-tab background case.

3. **How much local `ChatView` state should be tab-scoped?**
   - `inputDraft` and `scrollPosition` already are.
   - It is still a product choice whether `expandedThoughts`, `expandedToolCalls`, `pendingAttachments`, and command-palette state should also be remembered per tab or should be reset on tab switch.

4. **Adjacent reactivity risk outside the strict view-state bug**
   - The store’s `shallowRef(Map)` approach likely causes additional stale-UI edge cases for `pendingPermissions`, terminal snapshots, and tab badges because some nested mutations happen without `triggerRef(tabs)`.
   - That is not the primary view-state oracle finding, but it is worth validating before further UI churn.

### 7. Recommended follow-up tasks

1. **Restore OG-equivalent auto-scroll semantics for the active tab**
   - **Target files:** `vendor/acp-ui/src/components/ChatView.vue`
   - **Scope:** Replace the current id/count-only auto-scroll detection with logic that reacts to the same class of changes OG reacts to: streamed chunk mutations, thought growth, tool-call updates, and appended messages.
   - **Acceptance sketch:**
     - While an assistant response streams into the current message, the active tab stays pinned to bottom.
     - If a background tab receives additional streamed content, switching back to it lands at the newest visible content rather than restoring a stale scroll offset.
     - Preserve manual scroll restoration only when there were truly no unseen output changes.

2. **Isolate or reset non-persisted `ChatView` local state on tab switch**
   - **Target files:** `vendor/acp-ui/src/App.vue`, `vendor/acp-ui/src/components/ChatView.vue`, possibly `vendor/acp-ui/src/lib/types.ts`
   - **Scope:** Either:
     - key `ChatView` by `activeTabId` and explicitly rehydrate the pieces that must persist, or
     - expand `TabState` so all intended per-tab UI state is stored/restored intentionally.
   - **Acceptance sketch:**
     - Switching tabs does not leak expanded thoughts/tool calls, pending attachments, or command-hint state unless explicitly intended.
     - Per-tab drafts still persist.
     - Per-tab scroll restoration still works.

3. **Reduce `shallowRef(Map)` reactivity blind spots before further UI work**
   - **Target files:** `vendor/acp-ui/src/stores/session.ts`
   - **Scope:** Audit every nested `tab.* = ...` mutation and ensure store consumers update deterministically, either by consistent `triggerRef(tabs)` calls or by moving to a more naturally reactive structure.
   - **Acceptance sketch:**
     - `pendingPermissions`, terminal state, tab badges, and other active-tab-derived UI update immediately without relying on incidental later mutations.
     - The tabbed view-state contract is documented: which fields are persisted per tab, which are reset, and which are component-local.


## Second Opinion Research

### Bottom line

After re-reading both implementations, I **agree with the prior researcher on the primary scroll diagnosis**, but I think two things need tightening:

1. the **main confirmed viewport bug** is not just “auto-scroll changed” in the abstract — it is specifically that our fork replaced OG’s **deep mutation-driven view oracle** with a **count/id heuristic** while the store still mutates the **same message object** during streaming;
2. the **component reuse problem is broader than the listed refs** — the entire unkeyed `ChatView` subtree is being multiplexed across tabs, so child-component local state also bleeds;
3. the `shallowRef(Map) + triggerRef()` issue is **not merely an adjacent risk**. There are already **confirmed stale-reactivity defects** in auth/permission/terminal/startup flows.

### 1. What the OG oracle actually guarantees

**OG ACP-UI** is single-surface and simple:

- `src/stores/session.ts:39-46` keeps one `currentSession`, one `messages` array, one connection state.
- `src/components/ChatView.vue:43-49` does `watch(messages, ..., { deep: true })` and always scrolls to bottom after any visible message mutation.
- `src/App.vue:243-245` renders one `ChatView` when connected.

That means OG’s effective contract is:

- if the currently displayed assistant message grows, the viewport follows it;
- there is no need to preserve per-tab local UI state because there are no tabs;
- component-local state is safe because it is never repurposed for another session surface.

### 2. Confirmed primary root cause: our unseen-output oracle is lossy

I agree with the earlier finding that the **scroll behavior divergence is real and primary**.

#### Evidence in our fork

In `vendor/acp-ui/src/components/ChatView.vue`:

- `watch(activeTabId, ...)` at **134-164** decides whether a returning tab has “unseen” output using only:
  - `lastViewedMessageCounts.get(newTabId)` and
  - `nextTab.messages.length`.
- the active-tab auto-scroll watcher at **166-202** only reacts to:
  - `messageIds` (`messages.map(m => m.id).join('|')`), and
  - `messageCount`.

In `vendor/acp-ui/src/stores/session.ts`, the store very often updates **existing message objects** instead of appending new ones:

- `appendMessageBlock()` mutates `message.content` or `message.blocks` at **67-78**;
- `appendThoughtBlock()` mutates `message.thought` or `message.blocks` at **80-91**;
- `agent_message_chunk` reuses the last assistant message at **666-683**;
- `agent_thought_chunk` reuses the last assistant message at **686-704**;
- `tool_call_update` mutates existing tool-call state in place at **740-780**.

So the fork’s state model says: “visible output can change without a new message id and without a longer message array.”

But the fork’s view oracle says: “I only care if ids or count changed.”

That mismatch is the confirmed root cause for:

- active-tab streaming not staying pinned to bottom;
- returning to a background tab and restoring a stale `scrollPosition` even though the last assistant/tool/thought content changed while hidden.

**This is more than a symptom.** It is the exact place where the fork stopped honoring OG’s behavioral contract.

### 3. Partial disagreement with the prior write-up: the reuse bug is larger than a few refs

The earlier findings were correct that `App.vue` keeps one unkeyed `ChatView` alive:

- `vendor/acp-ui/src/App.vue:327` renders `<ChatView v-if="sessionStore.activeTab?.isConnected" />` with **no `:key`**.

I would strengthen that conclusion:

> The bug is not limited to the top-level refs listed in `ChatView.vue`. The **entire `ChatView` subtree** is reused across tabs.

Confirmed top-level local state in `ChatView.vue` includes:

- `inputText` / `textareaRef` / file input refs at **29-32**;
- `activeCommandHint`, `pendingAttachments`, `isRestoringTabState`, `lastViewedMessageCounts` at **35-39**;
- `expandedThoughts`, `expandedToolCalls` at **41-42**.

But there is also **descendant component state** that the first research missed:

- `PlanView` is mounted inside `ChatView` at **ChatView.vue:853** and has its own local `isExpanded = ref(true)` at `vendor/acp-ui/src/components/PlanView.vue:9`; that expanded/collapsed state is not tab-scoped.
- `CommandPalette` is mounted inside `ChatView` at **ChatView.vue:1040-1047** and keeps `selectedIndex = ref(0)` at `vendor/acp-ui/src/components/CommandPalette.vue:16`, resetting only when `filter` or `visible` changes at **29-31**. If two tabs have the same slash-command draft shape, the palette’s selection state can persist across tabs.

So the deeper architectural divergence is:

- OG has one component instance for one session surface.
- Our fork reuses one component/subtree for many logical surfaces and then tries to manually persist only selected pieces of UI state.

That means the current implementation is vulnerable to **state bleed by default** unless every local/child stateful thing is either:

- reset on tab change, or
- persisted in `TabState` intentionally.

### 4. Stronger disagreement: the `shallowRef(Map)` issue is already a real bug, not just “worth validating”

The previous findings called the reactivity problem an “adjacent risk.” I think the evidence is stronger than that.

#### 4a. Permission requests are updated without notifying tab consumers

In `vendor/acp-ui/src/stores/session.ts:340-349`, `registerBridge()` watches `bridge.pendingPermissionRequests.value` and assigns:

- `tab.pendingPermissions = newValue ?? []`

There is **no `triggerRef(tabs)`** there.

But the UI reads permissions through computed values that depend on `activeTab`:

- `pendingPermissions` at **446-450**;
- `pendingPermission` at **451**;
- `App.vue` permission dialog at **362-370**.

Because `tabs` is a `shallowRef<Map<...>>` (`session.ts:193`) and `tab` is a plain nested object, that mutation is not naturally reactive to consumers of `activeTab`. So permission UI can go stale until some unrelated later `triggerRef(tabs)` happens.

#### 4b. Auth-method prompts have the same problem, and this one is especially serious

In `promptForAuthMethod()`:

- `vendor/acp-ui/src/stores/session.ts:870-874` sets `tab.pendingAuthMethods` and `tab.pendingAuthAgentName`;
- there is again **no `triggerRef(tabs)`**.

But `App.vue` shows the auth dialog from:

- `pendingAuthMethods.length > 0` at **373-379**.

That means the auth dialog depends on a nested tab mutation that is never published through `tabs`. This is not hypothetical; it is a concrete stale-reactivity path.

Similarly, `selectAuthMethod()` clears those fields at **886-890** without `triggerRef(tabs)`.

#### 4c. Terminal snapshots and startup logs/phase are also partially relying on incidental triggers

- terminal snapshots are synchronized at **351-358** with no `triggerRef(tabs)`;
- startup stderr updates mutate `startupLogs` / `startupPhase` at **947-950** with no `triggerRef(tabs)`.

The startup screen may appear to work only because the 1-second timer at **926-930** does call `triggerRef(tabs)`, which masks the missing publish step.

So I would reclassify this as:

- **confirmed separate reactive defect class**, not just an open question.

It may not be the primary cause of the chat viewport bug, but it is a real divergence from OG’s simpler reactive model and will create stale UI.

### 5. What I think the first researcher slightly overstated or understated

#### Accurate

- The scroll oracle divergence is real.
- The unkeyed `ChatView` reuse is real.
- Message routing itself appears tab-correct (`handleSessionUpdate(tabId, ...)` writes to the addressed tab at `session.ts:638-855`).

#### Understated / missed

- The reuse problem affects **child component local state**, not only `expandedThoughts`, `expandedToolCalls`, `pendingAttachments`, and `activeCommandHint`.
- The `shallowRef(Map)` publication problem already has **confirmed UI consequences** for auth/permission/terminal/startup state.
- `tool_call_update` in-place mutations (`session.ts:740-780`) are an especially important example because they change what the user sees without changing message ids/count; that directly defeats the current scroll oracle.

#### Slight reframing

I would not describe the local-state bleed as a co-equal root cause of the **viewport-following** problem. It is a **confirmed state-isolation bug**, but the **primary viewport bug** is the lossy unseen-output detection.

So my root-cause split is:

- **Primary confirmed root cause:** count/id-based unseen detection in `ChatView.vue:134-202`.
- **Secondary confirmed architecture bug:** unkeyed shared `ChatView` subtree in `App.vue:327`.
- **Separate confirmed reactive bug class:** nested tab mutations without `triggerRef(tabs)` in `session.ts` bridge/auth/startup paths.

### 6. Recommended follow-up tasks, adjusted from the prior research

1. **Replace the lossy unseen-output oracle with a content-sensitive one**
   - **Files:** `vendor/acp-ui/src/components/ChatView.vue`, possibly `vendor/acp-ui/src/stores/session.ts`
   - **Why:** The current message-count/message-id heuristic cannot represent streamed growth of an existing message/tool/thought.
   - **Acceptance sketch:**
     - Active tab stays pinned during `agent_message_chunk`, `agent_thought_chunk`, and `tool_call_update` mutations.
     - Returning to a background tab jumps to newest output when visible content changed, even if message count/id did not.

2. **Stop reusing one `ChatView` subtree across logical tabs, or explicitly model all per-tab UI state**
   - **Files:** `vendor/acp-ui/src/App.vue`, `vendor/acp-ui/src/components/ChatView.vue`, plus child components if intentionally persisted
   - **Why:** Without a key, not just top-level refs but descendant component state can bleed.
   - **Acceptance sketch:**
     - Switching tabs does not leak plan expansion state, command-palette selection state, thought/tool expansion state, or pending attachments unless explicitly designed to.
     - Draft + scroll behavior remains per tab.

3. **Eliminate stale nested-tab updates from the store**
   - **Files:** `vendor/acp-ui/src/stores/session.ts`
   - **Why:** `shallowRef(Map)` plus ad hoc nested mutation is already producing un-published state changes.
   - **Acceptance sketch:**
     - Permission dialog, auth dialog, terminal output state, and startup progress update immediately when underlying bridge/auth state changes.
     - No UI feature depends on an incidental later `triggerRef(tabs)` to become visible.
