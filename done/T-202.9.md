# T-202.9 — Embedding model management (full feature)

## Problem

The app has ZERO model management capabilities. Users see a hardcoded text list of models with no actions. They cannot:
- Discover available models from an online catalog
- Download new embedding models
- Activate a downloaded model (switch the active model)
- Delete models they don't need
- See download progress

The onboarding wizard's model step has no real download — it just says "download later" or advances if a model happens to be pre-installed.

Settings > Models is a read-only list with no buttons.

This is an SLC violation. The feature is not simple, not lovable, not complete.

## Ideal State

1. **Online catalog** — query a manifest URL or HuggingFace API for available ONNX embedding models. Filter by dimension, size, license, MTEB score, MRL support.
2. **Download** — download ONNX model files from HuggingFace with progress indicator. Store in `~/maenifold/assets/models/`.
3. **Activate** — switch the active embedding model. Show re-embedding warning when dimensions change.
4. **Delete** — remove downloaded models (except the active one).
5. **Settings > Models** — full management UI with download/activate/delete buttons per model card.
6. **Onboarding wizard** — real download flow in model step, not a bypass.

## Layers

### Backend (maenifold-core)

File: `crates/maenifold-core/src/tools/embedding_models.rs`

New `EmbeddingModels` actions:
- `download(modelId)` — fetch ONNX from HuggingFace repo to `~/maenifold/assets/models/{id}/`. Stream progress via SSE or poll.
- `activate(modelId)` — update config to point to model, reload vector engine. Return warning if dimensions differ from current.
- `delete(modelId)` — remove model directory. Refuse if active.

Research needed: how does HuggingFace ONNX download work? Is there a `hf-hub` Rust crate or do we HTTP GET the raw ONNX file?

### Frontend (desktop app)

**SettingsModels.vue** — replace read-only list with shadcn Card per model:
- Download button (not installed) → shows progress bar
- Activate button (installed, not active)
- Active badge (current model)
- Delete button (installed, not active) → AlertDialog confirmation
- MRL dimension selector (if model supports Matryoshka)

**OnboardingStepModel.vue** — wire download button to real backend action with progress.

### API

The `EmbeddingModels` MCP tool already serves JSON. New actions go through the same tool with `action: "download" | "activate" | "delete"`.

## Acceptance Criteria

1. User can download a model from Settings > Models and see progress
2. User can activate a downloaded model (with dimension-change warning)
3. User can delete a non-active model
4. Onboarding wizard downloads the selected model for real
5. No hardcoded model assumptions — catalog comes from the tool
6. All actions go through MCP (AI is the new UI)
7. CDP screenshot shows working download/activate/delete buttons
8. `cargo build --release -p maenifold-core` passes
9. `npm run build:electron` passes

## NOT in scope

- Online catalog discovery from HuggingFace search (curated catalog is fine for now, but must be loaded from backend, not hardcoded in frontend)
- Model training or fine-tuning
- Quantization options (ship FP32, optimize later)

### Root Cause

Different embedding models produce **incompatible vector spaces even at identical dimensions**. `handle_activate()` only clears vectors when dimensions differ. Switching from `all-MiniLM-L6-v2` (384d) to `bge-small-en-v1.5` (384d) silently corrupts the search index.

### Already Implemented (DO NOT RE-IMPLEMENT)

These were done by sprint 202 SWEs and verified by both duo evaluators:
- **`ensure_vec0_tables()`** (vec0.rs:97-125) — already reads `active_model_id`, compares against `vector::model_id()`, forces recreation on mismatch
- **`find_model_path()`** (discovery.rs:88-110) — already fails fatally when `active_model` is set but not found

### Fix 1: `handle_activate()` — ALWAYS clear vectors on model switch

**File:** `crates/maenifold-core/src/tools/embedding_models.rs`  
**Function:** `handle_activate()` starting at line 487  

**Current (broken):**
- Line 541: `let dims_differ = matches!((new_dims, current_dims), (Some(n), Some(c)) if n != c);`
- Line 544: `if dims_differ {` — vectors ONLY cleared when dimensions differ
- Line 552: `DELETE FROM model_metadata;` — blanket wipe of ALL metadata

**Required changes:**
1. Remove the `dims_differ` gate on vector clearing. ALWAYS clear vectors when model ID changes.
2. Replace `DELETE FROM model_metadata` with targeted upserts: `upsert("active_model_id", new_model_id)` and `upsert("embedding_dimensions", new_dims)`.
3. `dims_differ` becomes informational only — controls the warning message text, NOT whether clearing happens.
4. Simplify the message branches at lines 577-583 (they currently branch on `vectors_cleared` vs `dims_differ` — after this fix those collapse).

### Fix 2: Cold-start nuke bug in `ensure_vec0_tables()`

**File:** `crates/maenifold-core/src/db/vec0.rs`  
**Line:** 102  

**Current (broken):**
```rust
let model_changed = stored_model_id.is_some() && stored_model_id != current_model_id;
```
`vector::model_id()` returns `None` at DB init time because the ONNX model is lazily loaded (loaded on first embedding request, not at startup). So on every cold start:
- `stored_model_id` = `Some("bge-small-en-v1.5")`
- `current_model_id` = `None` (model not loaded yet)
- `model_changed` = `true` (Some != None)
- → `recreate_vec0_tables()` runs → **vectors nuked on every restart**

**Required:** Guard on BOTH sides being `Some`:
```rust
let model_changed = stored_model_id.is_some()
    && current_model_id.is_some()
    && stored_model_id != current_model_id;
```

### Fix 3: `vector::model_id()` flat-layout bug

**File:** `crates/maenifold-core/src/vector/mod.rs`  
**Function:** `model_id()` at line 108-118  

**Current (broken):** For subdir layout (`models/bge-small-en-v1.5/model.onnx`), parent dir name = `"bge-small-en-v1.5"` ✓. For flat layout (`models/all-MiniLM-L6-v2.onnx`), parent dir name = `"models"` ✗.

**Required:** When parent dir is the models root (e.g., `"models"`), fall back to file stem without extension. This ensures `model_id()` returns a meaningful identifier for both layouts.

### Acceptance Criteria

1. Activate model B (384d) from model A (384d) → vectors cleared, `active_model_id` upserted (not blanket-deleted)
2. Cold-start daemon with unchanged model → vectors NOT nuked, tables preserved
3. Cold-start daemon after model switch via `handle_activate` → vectors already cleared at activate time, startup sees matching IDs
4. Activate model C (768d) from model A (384d) → vectors cleared, dimensions updated
5. `vector::model_id()` returns correct ID for both flat and subdir layouts
6. `cargo build --release -p maenifold-core` passes
7. Verify each edit persisted (re-read modified lines after every change)

### Fix 4: Rename "Models" → "Embeddings" + add Regenerate button

**Files:**
- `apps/desktop/src/components/SettingsView.vue` — line 13: change tab id/label from `'models'`/`'Models'` to `'embeddings'`/`'Embeddings'`, update description to `'Manage embedding models and vector index.'`. Also update TabsContent value at line 42.
- `apps/desktop/src/components/SettingsModels.vue` — rename file to `SettingsEmbeddings.vue`. Update heading at line 254 from `"Models"` to `"Embeddings"`. Update aria-label at line 250.

**Regenerate button:** Add a "Regenerate Embeddings" button to the page. This is the user's insurance — a manual escape hatch that force-nukes all vector tables and triggers a full re-embed.

**Behavior:**
1. Confirmation dialog: "This will delete all vector embeddings and rebuild them from scratch. Search will be unavailable until the rebuild completes. Continue?"
2. On confirm: call the MCP tool to DROP vec_concepts + vec_memory_files + clear model_metadata dimensions
3. Show success toast: "Embeddings cleared. Run sync to rebuild."
4. Button is always available regardless of model state — it's insurance, not workflow.

**Backend:** The MCP action for this may already exist (the vector-clearing SQL in `handle_activate` lines 550-552). If not, add a `regenerate` action to the `EmbeddingModels` tool that does the same DROP + DELETE without changing the active model.
