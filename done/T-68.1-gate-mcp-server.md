# T-68.1 — Gate MCP Server

**Requirement**: FR-68
**Status**: pending

## Summary

Add an MCP server interface to the `gate` CLI binary (`crates/maenifold-gate`). Expose all 5 existing CLI commands as MCP tools with 100% CLI/MCP parity. Support `--mcp` (stdio) and `--http` (streamable HTTP + tray icon) modes, matching the `maenifold` binary's architecture.

## Acceptance Criteria

1. `gate --mcp` starts an rmcp stdio MCP server that responds to `initialize` and `tools/list`
2. `gate --http [PORT]` starts a streamable HTTP MCP server on `127.0.0.1:{PORT}` (default 9879) with a system tray icon showing a white 'g' glyph (Arial Bold 72pt, 64×64 RGBA, matching maenifold's 'm' icon style)
3. Five MCP tools are exposed: `gate_pass`, `gate_reject`, `gate_append`, `gate_status`, `gate_sync` — each maps 1:1 to the corresponding CLI command
4. Tool dispatch runs the gate binary as a subprocess for perfect CLI/MCP parity (no duplicated command logic)
5. `gate_status` always returns JSON output (passes `--json` to subprocess)
6. All new code is behind a Cargo feature flag `app` — `cargo build -p maenifold-gate` (no features) produces the lean CLI binary; `cargo build -p maenifold-gate --features app` includes MCP + tray
7. Tray icon menu includes "Open at Login" (toggling a launchd plist at `~/Library/LaunchAgents/com.ma-collective.gate.plist`) and "Quit"
8. All existing 95 gate tests pass in both feature configurations
9. Release build succeeds: `cargo build --release -p maenifold-gate --features app`
10. MCP handshake verified: `echo '{"jsonrpc":"2.0","id":1,"method":"initialize",...}' | gate --mcp` returns valid server info

## Red Notes

**Verdict**: FAIL

### Findings

**[MEDIUM] F-1: Cross-platform build break — `dep:objc2-core-foundation` in `app` feature on non-macOS**

`Cargo.toml` declares `objc2-core-foundation` as a target-specific optional dependency under `[target.'cfg(target_os = "macos")'.dependencies]` and then references it in the `app` feature as `"dep:objc2-core-foundation"`. On Linux and Windows, this dependency is not in the dependency graph at all. When `--features app` is enabled on those platforms, Cargo will produce:

```
error: Package `maenifold-gate` does not have feature `dep:objc2-core-foundation`
```

This means `gate --mcp` (pure stdio, no tray code) cannot be built on Linux with `--features app` even though nothing in the stdio path uses `objc2-core-foundation`. The code is correctly gated with `#[cfg(target_os = "macos")]`, but the Cargo feature resolution fails before compilation begins.

The reference (`maenifold-core`) avoids this entirely: `objc2-core-foundation` is declared as a **non-optional** target-specific dependency (no `optional = true`, no `dep:` in features). Fix: remove `"dep:objc2-core-foundation"` from the `app` feature list and drop `optional = true` from the target-specific dep declaration, matching core's pattern. The `#[cfg(target_os = "macos")]` guards in code already ensure it isn't linked on non-macOS.

**[MEDIUM] F-2: All tool schema properties missing `description` fields**

All 22 property definitions across the 5 tool schemas (`gate_pass`, `gate_reject`, `gate_append`, `gate_status`, `gate_sync`) carry only `{"type": "string"}` or `{"type": "boolean"}` — none include a `"description"` field. The audit checklist (item 6) explicitly requires `type`, `required`, and `description` fields. MCP clients that use property descriptions to guide argument construction will receive no semantic information about what `root`, `db`, `pipeline`, `id`, `notes`, or `agent` mean in the context of gate operations.

Example fix for `gate_pass`:
```json
"id": {"type": "string", "description": "Task ID to advance via the pipeline pass transition"},
"root": {"type": "string", "description": "Pipeline root containing todo/ and done/ (defaults to server CWD)"},
"db": {"type": "string", "description": "Path to gate.db cache (defaults to <root>/gate.db)"},
"pipeline": {"type": "string", "description": "Optional path to pipeline definition JSON"},
"notes": {"type": "string", "description": "Notes to append to the orchestrator section"}
```

**[LOW] F-3: Unconstrained `root`/`db`/`id` path arguments — path traversal risk**

`root`, `db`, and `id` are passed from the MCP tool call directly as subprocess argv entries with no validation or sanitisation. An MCP client can supply `root: "/"` to cause `gate_sync` to walk the entire filesystem, or `db: "/tmp/arbitrary.db"` to create a SQLite database at an arbitrary path. The `id` value (used as a positional arg in `gate_pass`/`gate_reject`/`gate_append`) is also unvalidated; if the underlying command logic constructs a file path from it without canonicalisation, a task ID like `../../etc/cron.d/evil` could escape the expected `todo/` directory.

Severity is Low given the CORS restriction to localhost (HTTP mode) and implicit trust of stdio callers, but the risk increases if the HTTP port is exposed through SSH port-forwarding or a misconfigured network proxy. Fix: validate that `root` and `db` resolve to paths within expected parent directories; validate that `id` matches the alphanumeric task ID format (e.g., `[A-Za-z0-9._-]+`).
