# T-203.0 — Epic: MCP Apps host support

## Problem

MCP Apps (https://modelcontextprotocol.io/extensions/apps/overview) is an MCP extension that lets tool servers declare interactive HTML UIs via `ui://` resources. Hosts render them in sandboxed iframes inline in the conversation with bidirectional JSON-RPC communication (tool calls from app → host, tool results from host → app).

Supported by Claude, Claude Desktop, VS Code Copilot, Goose, Postman, MCPJam. maenifold desktop does **not** support it — zero iframe/sandbox/postMessage infrastructure exists.

This is a core "AI is the new UI" capability. MCP Apps let connected servers deliver dashboards, forms, visualizations, and rich media directly inside the conversation without external web apps.

## Approach

**Use the official AppBridge SDK** (`@modelcontextprotocol/ext-apps/app-bridge`) — it handles iframe creation, sandbox attributes, CSP policy, permission negotiation, JSON-RPC message routing, tool call proxying, and host style injection. Do not hand-roll any of this.

Frontend-only epic. The Rust backend needs no changes — MCP Apps is a host-side rendering concern.

## Architecture

```
Tool Description (_meta.ui.resourceUri → "ui://tool/app.html")
    ↓
ChatContentBlocks detects ui:// tool result
    ↓
McpAppFrame.vue (new component)
    ↓ wraps
AppBridge (from @modelcontextprotocol/ext-apps/app-bridge)
    ↓ creates
Sandboxed <iframe> with CSP from _meta.ui.csp
    ↓ postMessage JSON-RPC
App ←→ Host bidirectional communication
    ↓ proxied via
useMcpClient.callTool() for app-initiated tool calls
```

## Key risk

Electron iframe sandboxing. AppBridge assumes browser context. Need to verify Electron's `webPreferences.sandbox` and CSP headers interact correctly with AppBridge's iframe creation. Goes in T-203.1 research.
