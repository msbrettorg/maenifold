# T-48.8 — Component: `WorkflowNodeCard`

**Requirement:** FR-48
**Component:** `vendor/acp-ui/src/components/`

## Summary

Vue component that renders a single workflow session as a card showing its steps, status, and timing.

## Acceptance Criteria

1. Create `vendor/acp-ui/src/components/WorkflowNodeCard.vue`
2. Props: `node: WorkflowSession` from `workflow-types.ts`
3. Renders:
   - **Header**: workflow name + emoji, session ID (truncated), status badge (✅/⚠️/🔄)
   - **Step progress bar**: visual indicator of completed/total steps
   - **Step list**: each step as a row with:
     - Step name
     - Status icon (●/◐/○ for completed/active/pending)
     - Submachine indicator (🧠) if `requiresSequentialThinking`
     - Timestamp (relative: "2 min ago")
   - **Timing**: started timestamp, duration if completed
4. Steps with submachines show a subtle connector line/arrow to indicate child nodes exist
5. Collapsible: step details expand on click to show response text (rendered as markdown)
6. Dark theme styling matching existing UI
7. `[[WikiLinks]]` in response text rendered as styled pills (background highlight, no link)

## Design

- Card width: ~320px
- Background: `#1e2028` (matches existing dark cards)
- Border-left: 3px colored by status (green=complete, amber=abandoned, blue=active)
- Step rows: compact, 28px height, monospace step numbers
- Progress bar: thin (4px), green fill

## SWE Remediation

### What Changed

**`vendor/acp-ui/src/components/WorkflowNodeCard.vue`** (new file)

Full implementation of the `WorkflowNodeCard` Vue component:

- **Props**: `node: WorkflowSession` imported from `../lib/workflow-types`
- **Header**: workflow emoji (derived from workflow name keywords), truncated session ID (8…6 chars), status badge (✅/⚠️/🔄)
- **Progress bar**: 4px height, `#22c55e` green fill, percentage width computed from `completed/total` steps
- **Step list**: 28px rows with monospace step numbers, status icons (●/◐/○), step name, 🧠 badge for `requiresSequentialThinking`, relative timestamp
- **Submachine connector**: subtle `│ → thinking: <sessionId>` line shown below steps where `requiresSequentialThinking && submachineSessionId`
- **Collapsible steps**: click handler on steps with a `response` field toggles an expanded `div` containing the response rendered as markdown via `marked`
- **WikiLinks**: pre-processed before `marked.parse()` — `[[label]]` becomes `<span class="wiki-pill">label</span>` with styled background highlight (no link)
- **Timing footer**: started timestamp (absolute, locale-formatted) + duration (computed from last `respondedAt − started`) shown only when `status === 'completed'`
- **Dark theme**: card `background: #1e2028`, `border-left: 3px` colored green/amber/blue by status

### Decisions

- `workflow-types.ts` already existed (created by T-48.6), so no stub was needed.
- `workflowEmoji` is derived heuristically from the workflow name/id rather than a stored field (no emoji field on `WorkflowSession`).
- Duration is computed from the last `respondedAt` across all steps minus `started`, since there is no explicit end timestamp on `WorkflowSession`.
- `marked` was already a project dependency (`"marked": "^17.0.1"`), so no new dep added.
- WikiLink pill styling is handled via `v-html` + `:deep(.wiki-pill)` since the pills are injected into `marked` HTML output.

### Advisory Findings (Non-blocking)

1. **XSS via unsanitized `v-html`** (Low/Medium advisory): `renderMarkdown` passes `step.response` through `marked.parse()` and renders the result via `v-html` without HTML sanitization (no DOMPurify or equivalent). `marked` v17 does not sanitize output by default. Impact is bounded because `step.response` originates from a local MCP server (trusted backend), not from untrusted user input. Not a spec violation, but worth adding DOMPurify if this component is ever exposed to externally-sourced content.

2. **Silent async fallback in `renderMarkdown`** (Low advisory): The guard `typeof result === 'string' ? result : ''` at line 149 silently returns empty string if `marked.parse()` ever returns a `Promise` (possible if async extensions are registered in the future). Currently safe — no async hooks are configured — but the failure mode is invisible content rather than a visible error.

Neither finding constitutes a spec violation. The implementation faithfully meets all stated acceptance criteria.
