# T-30.1: Mermaid Diagram Rendering in Chat

**Requirement**: FR-40
**Component**: `vendor/acp-ui/src/components/ChatView.vue`
**Sprint**: 30

## Context

The web UI uses `marked` (v17) to render markdown in chat messages. The `renderMarkdown()` function at line ~123 of `ChatView.vue` calls `marked.parse(content, { async: false })` and returns HTML. This HTML is injected via `v-html` at lines ~193 and ~218.

Mermaid code blocks (` ```mermaid ... ``` `) currently render as plain `<pre><code class="language-mermaid">` blocks. They need to be post-processed into SVG diagrams.

## Acceptance Criteria

1. **Install mermaid**: Add `mermaid` npm package to `vendor/acp-ui/package.json`
2. **Create composable**: New file `vendor/acp-ui/src/composables/useMermaid.ts` that:
   - Lazy-loads mermaid via dynamic `import('mermaid')` on first call
   - Initializes with `{ startOnLoad: false, theme: 'dark' }` 
   - Exports an async `renderMermaidBlocks(container: HTMLElement)` function that:
     - Finds all `<code class="language-mermaid">` elements within the container
     - For each, calls `mermaid.render()` with the text content
     - Replaces the `<pre>` parent with the rendered SVG
     - On error: adds a `.mermaid-error` CSS class to the `<pre>` block and appends a small error message, preserving the original code
3. **Integrate into ChatView.vue**:
   - Import `useMermaid` composable
   - After each message renders (via `nextTick` or `watch` on messages), call `renderMermaidBlocks()` on the chat container
   - Use a `ref` on the messages container element to pass to the composable
4. **Styling** in ChatView.vue `<style>`:
   - `.mermaid-rendered svg` should have `max-width: 100%` and `border-radius: 6px`
   - `.mermaid-error` should have a subtle red border and show the error text below the code
5. **Dark theme**: Mermaid `theme: 'dark'` matches the app's dark UI

## Verdicts

- **KEEP**: `renderMarkdown()` function — mermaid post-processes the HTML output, doesn't replace marked
- **ADD**: `useMermaid.ts` composable, mermaid npm dependency, ChatView integration, CSS

## Test Approach

Manual verification: send a message containing a mermaid flowchart block and confirm it renders as SVG. The composable is pure DOM manipulation — no Rust tests needed.

### Advisory Findings (non-blocking)

**1. XSS via `renderedBlock.innerHTML = svg` (Low)**
The SVG string from `mermaid.render()` is set via `.innerHTML` at `useMermaid.ts:53`. Mermaid v11 internally applies DOMPurify sanitization before returning SVG, so this is safe in the current library version. However, there is no defense-in-depth sanitization layer (e.g., explicit `DOMPurify.sanitize(svg)` call) in the composable itself. If a future mermaid version changes its internal sanitization, or if the library is swapped, this becomes an active XSS vector. The spec does not require additional sanitization, so this does not block acceptance.

**2. Multi-block race under concurrent watch triggers (Negligible)**
If two `renderMermaidBlocks()` calls are dispatched concurrently (e.g., two rapid `messages` watch fires during streaming) AND a message contains 2+ mermaid blocks, there is a theoretical window where both calls capture Block B in their local `mermaidBlocks` arrays (captured post-`getMermaid()` await) before either sets `data-mermaid-processed`. The worst outcome is `mermaid.render()` being called twice for the same diagram definition with different IDs — a visual duplicate that resolves on next re-render. Not a correctness or security issue. Does not block acceptance.

### Re-render guard correctness

The `preBlock.dataset.mermaidProcessed = 'true'` flag (line 43) is set **after** `await getMermaid()` but **before** `await mermaid.render()`. Because JavaScript is single-threaded and the flag assignment is synchronous, a second concurrent `renderMermaidBlocks` call that yields on `getMermaid()` will see the flag already set when it reaches the loop body. Deduplication is sound.

The empty-definition guard additionally uses `if (!preBlock.querySelector('.mermaid-error-message'))` (line 48) to prevent duplicate appends — also correct.

---

### Advisory Findings (non-blocking)

**1. Streaming messages will permanently lock mermaid blocks into error state (Medium)**

`message.content` is built incrementally via `appendMessageBlock()` in `useMessageHandler.ts` (line 104: `message.content += block.text`). The `watch(messages, ..., { deep: true })` therefore fires on every streaming chunk. If a `mermaid` code fence arrives across multiple chunks, `marked` will emit a `<pre><code class="language-mermaid">` element for an incomplete definition before the closing fence arrives. `mermaid.render()` will throw on the malformed input, the `<pre>` will be flagged `mermaidProcessed = 'true'`, and the error state will never be cleared when the full definition arrives.

The spec does not address streaming and the manual test uses a complete sent message, so this is **not a spec violation**. However it is a latent correctness bug: mermaid diagrams in streamed responses will render as errors rather than SVG. Recommendation for follow-up: consider deferring mermaid rendering until `isLoading` transitions to `false`, or using a `MutationObserver` to detect newly added complete code fences rather than reprocessing on every content change.

**2. XSS via `renderedBlock.innerHTML = svg` (Low — inherited)**

`mermaid.render()` in v11 applies internal DOMPurify sanitization before returning the SVG string, making this safe at the current dependency version. No defense-in-depth layer (e.g., explicit `DOMPurify.sanitize(svg)`) exists in the composable itself. Not a spec violation; carry-over from prior audit.
