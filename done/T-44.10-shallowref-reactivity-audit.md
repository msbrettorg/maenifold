# T-44.10: shallowRef Reactivity Audit

**Requirement**: FR-44.1
**RTM**: RTM-306
**Priority**: P0 — confirmed stale-reactivity bugs beyond tabs

## Context

Second-opinion research (T-44.5b) identified that the `shallowRef(Map) + triggerRef()` pattern in `session.ts` creates confirmed stale-reactivity bugs beyond the tab strip. Affected areas include:
- Permission request dialogs
- Auth method dialogs
- Terminal snapshots
- Startup logs/phase
- `tool_call_update` mutations defeat unseen-output logic

## Acceptance Criteria

1. **Audit all `triggerRef(tabs)` call sites**: Verify every mutation path through `TabState` properties has a corresponding `triggerRef(tabs)` call. Document any missing trigger sites.
2. **Permission/auth dialogs**: Verify that permission requests and auth method updates on non-active tabs trigger UI updates correctly.
3. **Terminal snapshots**: Verify terminal content updates trigger reactivity.
4. **tool_call_update**: Verify that in-place tool call content mutations trigger scroll and unseen-output detection.
5. **Recommend fix**: Either add missing `triggerRef` calls at each gap, or propose a structural alternative (e.g., move back to deep reactive, use per-field refs).

## Deliverable

Research-only. Append `## Research Findings` with:
- Complete list of mutation paths and whether they have triggerRef coverage
- Confirmed gaps with reproduction evidence
- Recommended fix approach

### Area 2: Scroll Behavior

**Where `scrollToBottom()` is defined**

- `vendor/acp-ui/src/components/ChatView.vue:97-103`

**What calls `scrollToBottom()`**

1. **Tab-switch watcher** — `ChatView.vue:134-164`
   - Watches `activeTabId`.
   - On entering a tab, computes `hasUnseenMessages = nextTab.messages.length > previousViewedCount` at `ChatView.vue:150-153`.
   - If true, calls `scrollToBottom()` at `ChatView.vue:154`.

2. **Active-message signature watcher** — `ChatView.vue:166-202`
   - Watches an object containing:
     - `tabId` (`ChatView.vue:168`)
     - `messageIds` (`ChatView.vue:169`)
     - `messageCount` (`ChatView.vue:170`)
   - Treats a change as “new messages” only when:
     - `messageCount` increases, or
     - joined `messageIds` changes (`ChatView.vue:181-183`)
   - Calls `scrollToBottom()` at `ChatView.vue:194`.

**What does _not_ trigger scroll**

- The deep `watch(messages, ...)` at `ChatView.vue:204-206` only calls `renderMermaidBlocks()`.
- `handleMessagesScroll()` at `ChatView.vue:125-132` only persists `tab.scrollPosition`.
- `onMounted()` at `ChatView.vue:217-223` restores `inputText`, but does not scroll.

**What message mutations the scroll watcher reacts to**

It reacts only to mutations that change:

- the number of messages, or
- the message ID list.

That means it catches:

- local `sendPrompt()` inserting a new user message (`session.ts:1299-1305`)
- `handleSessionUpdate()` cases that push a brand-new message:
  - `user_message_chunk` fallback push (`session.ts:652-660`)
  - `agent_message_chunk` fallback push (`session.ts:671-680`)
  - `agent_thought_chunk` fallback push (`session.ts:691-701`)
  - `tool_call` fallback assistant-message push (`session.ts:710-717`)
- full message-array replacement such as `tab.messages = []` during create/resume resets (`session.ts:1059`, `1152`)

**Does it react to streaming chunk updates within one message?**

No.

- Existing user text chunks append in place via `appendMessageBlock(lastUserMsg, update.content)` (`session.ts:649-650`).
- Existing assistant text chunks append in place via `appendMessageBlock(lastMsg, update.content)` (`session.ts:668-669`).
- Existing assistant thoughts append in place via `appendThoughtBlock(lastAssistantMsg, update.content)` (`session.ts:688-689`).

Those paths do **not** change `messageCount` or `messageIds`, so the scroll watcher at `ChatView.vue:166-202` does not fire.

**Does it react to `tool_call_update` content changes?**

No.

`tool_call_update` mutates existing nested objects in place:

- `existing.status/title/_meta/content/locations/rawInput/rawOutput` (`session.ts:743-756`)
- mirrored `message.toolCalls[*]` fields (`session.ts:765-778`)

Again, none of those writes change `messageCount` or `messageIds`, so `scrollToBottom()` is not called.

**OG ACP-UI comparison**

- OG `ChatView.vue` used a single deep watcher:
  - `watch(messages, async () => { ... scrollTop = scrollHeight ... }, { deep: true })`
  - `/tmp/acp-og/src/components/ChatView.vue:43-49`
- That OG watcher would respond to nested message mutations, including streaming chunk appends and in-place tool call updates, as long as the underlying message state was reactive.
- The fork replaced that with the narrower `messageIds + messageCount` signature watcher (`vendor/acp-ui/src/components/ChatView.vue:166-202`), so scroll now misses any in-place update to an existing message/tool-call object.

**Scroll verdict**

- **New message inserted:** scrolls
- **Streaming appended to existing message:** does **not** scroll
- **`tool_call_update` content/status/title/rawOutput updates:** do **not** scroll
- **Thought expansion within existing assistant message:** does **not** scroll

### Area 3: Component State Isolation

**How `ChatView` is rendered**

- Root rendering in `App.vue` is:
  - `TabStrip` at `vendor/acp-ui/src/App.vue:319-325`
  - `ChatView` at `vendor/acp-ui/src/App.vue:327`
- `ChatView` is rendered as `<ChatView v-if="sessionStore.activeTab?.isConnected" />` with **no `:key`**.
- Therefore the same `ChatView` instance is reused across tab switches; tab changes are handled by the `activeTabId` watcher in `ChatView.vue:134-164`.

**How tabs are rendered**

- `TabStrip` iterates `visibleTabs` with `:key="tab.tabId"` at `vendor/acp-ui/src/components/TabStrip.vue:53-56`.
- The tab strip itself is keyed correctly per tab entry, but `ChatView` is not keyed per active tab.

**Store-derived computed values**

The computed wrappers at `ChatView.vue:44-70` are not local persistent state; they are projections of `sessionStore` (`messages`, `isLoading`, `currentSession`, `availableModes`, `currentModeId`, `availableModels`, `currentModelId`, `configOptions`, `hasConfigOptions`, `pendingPermissionCount`, `availableCommands`, `currentPlan`, `agentPromptCapabilities`, `activeTabId`, capability/tooltips).

**Isolation verdict**

- **Persist per tab:** `inputText`/`inputDraft`, `scrollPosition`
- **Component-local and reused across tabs:** `activeCommandHint`, `pendingAttachments`, `expandedThoughts`, `expandedToolCalls`, DOM refs, `lastViewedMessageCounts`
- Because `ChatView` is **not keyed by tab ID**, component-local state survives tab switches and can bleed between tabs.

### Area 4: Unseen Output Detection

**How unseen output is detected**

The only general unseen-output heuristic lives in `ChatView.vue`, not in the store:

- `lastViewedMessageCounts` map at `ChatView.vue:38`
- When leaving a tab, store `previousTab.messages.length` at `ChatView.vue:135-140`
- When entering a tab, compare `nextTab.messages.length > previousViewedCount` at `ChatView.vue:149-153`

So unseen detection is strictly **message-count based**.

**What it detects**

- New messages added to a background tab, if they increase `messages.length`
- On revisiting that tab, `ChatView` will choose `scrollToBottom()` instead of `restoreScrollPosition(...)` (`ChatView.vue:153-157`)

**What it does _not_ detect**

- Streaming updates appended to an existing message (`session.ts:649-650`, `668-669`, `688-689`)
- In-place `tool_call_update` mutations (`session.ts:741-779`)
- In-place updates to `message.toolCalls[*]`
- Any content change that leaves `messages.length` unchanged

**Does it detect background-tab `tool_call_update` / thought growth?**

No.

Those updates mutate existing nested objects without increasing `messages.length`, so:

- `lastViewedMessageCounts` remains satisfied
- the revisited tab is treated as having no unseen content
- scroll restoration prefers saved `scrollPosition` over bottom scroll

**What triggers the tab-strip indicator**

The tab strip does **not** show a general unread/output indicator.

- `sessionStore.tabList` computes `hasPendingAction` from:
  - `tab.pendingPermissions.length > 0`
  - `tab.pendingAuthMethods.length > 0`
  - `vendor/acp-ui/src/stores/session.ts:485-493`
- `TabStrip` renders the dot only when:
  - `tab.hasPendingAction`
  - and the tab is not active
  - `vendor/acp-ui/src/components/TabStrip.vue:73-78`

So the visible dot means **pending action**, not **unseen output**.

**Reactivity risk in that indicator**

Even this pending-action indicator is vulnerable to stale updates, because the underlying mutations are missing `triggerRef(tabs)`:

- permission request updates from bridge watcher: `session.ts:340-356`, especially `345`
- auth prompt set: `session.ts:870-874`
- auth prompt clear: `session.ts:299-303`, `886-889`

Since `tabList` is computed from `tabs.value.values()` (`session.ts:485-493`) and `tabs` is a `shallowRef(Map)` (`session.ts:193`), those in-place writes may not recompute the tab strip promptly.

**Unseen-output verdict**

- Background-tab unseen detection is **count-only**
- It **misses in-place message mutations**
- There is **no true unread-output badge**
- The only badge is **pendingPermissions/pendingAuthMethods**
- That badge itself can be stale because its mutation paths lack `triggerRef(tabs)`

### Overall conclusion

The fork’s tabbed UI mixes:

1. a `shallowRef(Map)` store that requires explicit invalidation,
2. multiple in-place `TabState` mutations without `triggerRef(tabs)`, and
3. a `ChatView` instance that is reused across tabs without a `:key`.

That combination creates three separate classes of bugs:

- **stale store reactivity** for many tab fields,
- **missed auto-scroll / unseen-output detection** for in-place message updates,
- **component-local state bleed** across tab switches.
