## Summary

Add 8 config mutation MCP tools as handler-intercepted tools on `MaenifoldHandler`. These tools share daemon state with the REST API via a `ConfigMutationState` struct.

## Architectural Design

### Handler interception (not ToolRegistry native)

Config mutation tools cannot go through `ToolRegistry::try_invoke()` because `ToolContext` lacks `ConfigManager` and runtime state. Instead:

1. Add `ConfigMutationState` struct containing:
   - Shared `ConfigManager` (same instance as REST API)
   - Shared `Arc<RwLock<Config>>` for runtime settings refresh
   - Resource notification emission capability

2. Store as `Option<ConfigMutationState>` on `MaenifoldHandler`

3. In `call_tool()`, intercept config mutation tool names before gateway dispatch

4. After persistence, MUST call runtime refresh (update live `Config.settings`)

### Shared state construction

MCP HTTP service and REST API must share the same `ConfigManager` and `Arc<RwLock<Config>>`:
- Refactor `ApiState::new()` in `routes.rs` to accept shared state instead of constructing its own
- Expose `refresh_settings()` for MCP use (currently `pub(super)`)
- Construct shared state in `mcp/http.rs` daemon startup, pass to both

### Tool advertisement

Register tools in `ToolRegistry` for schema generation and `list_tools()` visibility. Add to `list_tools()` gateway-mode native allowlist. Execution is intercepted in `call_tool()` before `ToolRegistry::try_invoke()`.

### Schema registration

Add `config_tools.rs` schema module in `mcp/schema/`. Register in `mcp/schema/mod.rs`.

### UpdateSettings merge semantics

1. Load current settings from `ConfigManager`
2. Deep-merge partial input (recursive: `{ "vector": { "embeddingLogs": true } }` updates only that field)
3. Call full-replacement `ConfigManager::update_settings()` with merged result
