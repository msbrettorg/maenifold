# T-67.4: Agent Crash Recovery and Pool Health

## Requirement
FR-50 — Native ACP client must handle agent crashes gracefully.

## Problem
When an agent process crashes:
1. `io_task` returns an error, logged as warning
2. `cmd_rx` stays open — `AgentHandle::cmd_tx` is still held by `AgentPool`
3. The command loop continues, but every `conn.*` call fails with `AgentError::Acp`
4. `AgentPool::get_or_create()` returns the same dead `Arc<AgentHandle>` forever
5. The child process becomes a zombie (stdin/stdout held by dead connection)

Also: `stderr` is piped to `Stdio::null()` — agent crash logs are invisible.

## Acceptance Criteria
1. When `io_task` exits (success or error), the command loop must terminate
2. The `AgentPool` must evict the dead entry so `get_or_create()` spawns a fresh agent
3. `AgentHandle` must expose `is_alive() -> bool`
4. `get_or_create()` must check `is_alive()` before returning cached handle
5. Agent `stderr` must be piped to `tracing::debug!` via a spawned reader task
6. Child process must be reaped on connection death (no zombies)

## Files to modify
- `crates/maenifold-core/src/acp/native.rs` — io_task death handling, pool eviction, stderr capture

## Reference
- No direct pipeline-ui equivalent (WebSocket has different failure model)
- Standard Rust patterns: `tokio::process::Child::wait()`, `BufReader::lines()` for stderr

## Tests
- All existing tests must pass
- Manual verification: kill an agent process mid-session, verify pool respawns

### Observations (non-blocking)

**OBS-1 — alive flag NOT set on spawn_blocking thread panic** (`mod.rs:217, 250-251`): Three `expect()` calls inside the spawn_blocking closure (`expect("rt")`, `expect("stdin")`, `expect("stdout")`) can panic. If they do, `alive_task.store(false, ...)` at line 383 is never reached, leaving `alive = true` in a handle whose `cmd_rx` has been dropped. The pool would return this permanently-broken handle and all callers would receive `AgentError::ChannelClosed`. The trigger requires either a tokio runtime build failure or OS-level pipe setup failure — both are effectively impossible under normal conditions. A RAII `scopeguard` would eliminate this hazard, but it is not mandated by the spec.

**OBS-2 — Unbiased select! admits one extra command after io_task death** (`mod.rs:303`): `tokio::select!` without `biased` uses pseudo-random arm ordering. If both `io_result` and `cmd_rx` are ready simultaneously, a command may be dispatched before the loop breaks. The dispatched operation will return `AgentError::Acp` since the connection is dead; on the next iteration `io_result` wins and the loop exits. This is not a spec violation and is bounded by the `run_with_timeout` guard on `Prompt` commands (`mod.rs:346`).

**OBS-3 — alive flag is set AFTER loop exit, not at io_task completion** (`mod.rs:312, 383`): `io_task = None` is set at line 312 when io_task exits, but `alive.store(false)` is at line 383, after the loop finishes. A concurrent `is_alive()` call can return `true` during the window between lines 312 and 383. In that window `cmd_tx.send()` will still succeed (the channel is still open), but the loop will break on the next select! iteration and the reply channel will be dropped, returning `AgentError::ChannelClosed`. Inherent TOCTOU; not a spec requirement to close.
