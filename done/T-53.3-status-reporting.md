# T-53.3 — `status.rs` — Status Reporting

**Requirement**: FR-41 (File-Authoritative Pipeline Gate Cache)
**Component**: `crates/maenifold-gate/src/status.rs`
**Depends on**: T-53.1 (`fs.rs`), T-53.2 (`db.rs`)

## Context

`gate status` reports the file-authoritative state of pipeline tasks. It reads task files from disk, parses their stage/verdict state, and displays results. An optional `--db` flag cross-checks against `gate.db` to surface drift.

## Acceptance Criteria

1. Implement `run_status(args: &StatusArgs, root: &Path) -> Result<()>` that handles two modes:

### Single-file mode (`gate status <file>`)

2. Resolves the file in `todo/` or `done/` using `fs::resolve_task_path()`
3. Parses the file content using `parser::parse_task_content()`
4. Prints task state:
   - File name, location (todo/done), derived status (Pending/Red/Blue/Done)
   - Each stage present: SWE (yes/no), Red (verdict), Blue (verdict)
5. With `--db`: also queries `db::GateDb` and reports any discrepancy between file state and DB state (status mismatch, location mismatch)

### All-files mode (`gate status` with no file argument)

6. Discovers all task files using `fs::discover_tasks()`
7. Parses each file and collects results
8. Prints a summary table:
   ```
   STATUS    COUNT
   pending       3
   red           1
   blue          2
   done         12
   ---
   total        18
   ```
9. With `--db`: runs cross-check on every file, reports drift as warnings

### Output formatting

10. Default output is human-readable aligned text
11. With `--json`: outputs JSON (single object for one file, array for all)

### Error handling

12. Parse errors (malformed task files) are reported as warnings but don't abort the scan — the file is listed with status `error` and the parse error message

13. Module must be under 150 LOC.

### Bug 1 — `stage_text` shows `SWE: yes` for Pending tasks (Medium)

**File**: `status.rs:160–173`

```rust
fn stage_text(state: &TaskState, stage: TaskStage) -> &'static str {
    state
        .stages
        .iter()
        .find(|s| s.stage == stage)
        .and_then(|s| s.verdict.map(|v| v.as_str()))
        .unwrap_or(if stage == TaskStage::Swe {
            "yes"                      // ← always taken when SWE has no verdict
        } else {
            if state.stages.iter().any(|s| s.stage == stage) { "-" } else { "no" }
        })
}
```

For a **Pending** task the `stages` vec is empty (parser returns `TaskStatus::Pending` when no stage headings are found). `find(SWE)` returns `None`, `and_then` is a no-op, `unwrap_or` is reached and unconditionally returns `"yes"` — even though the SWE section is absent. Non-SWE stages correctly use `.any()` to distinguish "present without verdict" (`"-"`) from "absent" (`"no"`), but the SWE branch skips this check entirely.

**Attack scenario**: `gate status T-53.0-new-task.md` on a brand-new Pending task displays `SWE: yes`, which is a false assertion — SWE work has not been done.

**Fix**: mirror the non-SWE branch:
```rust
.unwrap_or(if state.stages.iter().any(|s| s.stage == stage) { "yes" } else { "no" })
```

### Bug 2 — Spurious "missing from db cache" warnings emitted without `--db` (High)

**File**: `status.rs:39`, `status.rs:75`

When `--db` is not passed, `db` is `None`. In `run_status`, `row` is `None` (correct), but then `drift(&state, row.as_ref())` is called unconditionally, and `drift(_, None)` always appends `"missing from db cache"`. The resulting vector is passed to `output_one`, which prints:

```
warning: T-53.3-status-reporting.md: missing from db cache
```

…on **every** single-file status call that omits `--db`.

In `run_all`, the same path: `rows` is an empty `BTreeMap` when `db` is `None`, so `rows.get(file)` is `None` for every task, producing the same spurious warning (and `db_drift` field in JSON) for every discovered task.

Drift computation must be gated on whether a DB was actually opened:

```rust
// single-file
let drift_items = if db.is_some() { drift(&state, row.as_ref()) } else { vec![] };

// all-files
let drift_items = if db.is_some() { drift(&state, rows.get(file)) } else { vec![] };
```

### Bug 3 — JSON output uses manual `format!()` instead of serde (Medium)

**File**: `status.rs:199–240`

`as_json()` builds JSON by concatenating format strings:

```rust
fn as_json(...) -> String {
    let mut fields = vec![
        format!("\"file\":{file:?}"),
        ...
    ];
    format!("{{{}}}", fields.join(","))
}
```

The spec explicitly requires proper serde serialization, not manual string building. Beyond the spec violation, Rust's `{:?}` Debug formatter uses `\x{HH}` notation for non-printable control characters (e.g., `\x1b` for ESC). This is **not valid JSON** — JSON requires `\uXXXX`. Any error message or file path containing a control character produces malformed JSON that will fail strict parsers.

**Required fix**: define a `#[derive(serde::Serialize)]` struct and use `serde_json::to_string`/`to_value`.
