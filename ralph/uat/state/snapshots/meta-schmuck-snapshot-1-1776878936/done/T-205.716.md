# T-205.716 — Fix ListAssets deadlock under concurrent asset access

## Problem

The maenifold MCP server has a P0 reliability bug: `ListAssets` can fail with `I/O error: Resource deadlock avoided (os error 11)`. This blocks discovery of workflows, roles, colors, and perspectives and undermines the MCP surface that other maenifold and UI flows depend on.

## Verified ground truth

- The user reported the exact failure string from the live MCP server: `Error invoking ListAssets: I/O error: Resource deadlock avoided (os error 11)`
- After killing the active agents, a direct `ListAssets` MCP call returned successfully with the four published asset types: `workflow`, `role`, `color`, `perspective`
- `crates/maenifold-core/src/mcp/schema/system_tools.rs:36-39` wires `ListAssets` to the system schema
- `crates/maenifold-core/src/tools/catalog.rs:7-19` shows the concrete path is thin: `list_assets()` constructs `AssetManager`, parses the optional `type`, and delegates to `AssetManager::list_assets()`
- `crates/maenifold-core/src/assets/manager.rs:66-77` shows the untyped `ListAssets` path only returns the four asset kinds, while typed listing delegates to metadata enumeration
- `crates/maenifold-core/src/assets/support.rs:128-145` shows metadata enumeration is a direct `read_dir` + file filter over the runtime asset root
- `crates/maenifold-core/src/assets/update.rs:14-69` and `crates/maenifold-core/src/mcp/resources/subscription.rs:52-88` / `subscription_worker.rs:15-99` show adjacent asset-update and asset-watcher flows that touch the same runtime asset roots
- Because the failure cleared when concurrent agents were removed, the defect is currently best framed as concurrent asset access / re-entrancy, not a deterministic schema or JSON parse bug
- Blue-team's first TDD pass added concurrency coverage in `crates/maenifold-core/src/assets/manager.rs`, but those tests all pass and do not reproduce the reported failure, so they are not yet a gate-worthy regression for this bug
- Additional PM verification of blue-team's root-cause lead shows `crates/maenifold-core/src/mcp/resources/mod.rs:22-28` aggregates `pipeline::list_resources()?` during resource listing, `crates/maenifold-core/src/mcp/resources/pipeline.rs:151-186` calls `ToolRegistry::global().try_invoke("Pipeline", ...)` to read sessions, and `crates/maenifold-core/src/workflow/pipeline/lease.rs:67-99` uses `fd_lock::RwLock::try_write()` for pipeline session locking
- The most likely contention path is therefore broader MCP resource listing / pipeline session lock interaction, surfaced through `ListAssets` in the live server context, rather than `AssetManager::list_assets()` alone

## Root Cause Investigation

After exhaustive analysis of the codebase and macOS locking mechanisms, I have determined why the EDEADLK error cannot be reproduced in unit tests:

### macOS Error 11 (EDEADLK) Technical Requirements

EDEADLK ("Resource deadlock avoided") is ONLY returned by:
- POSIX record locks via fcntl(F_SETLKW) when the kernel detects circular lock dependency
- NOT returned by: flock(), pthread_mutex, parking_lot::RwLock, standard file I/O

### Lock Primitives in maenifold

1. **fd_lock crate**: Uses flock() on macOS via rustix::fs::flock() - does NOT return EDEADLK
2. **parking_lot::RwLock**: User-space lock (Config::OVERRIDES) - cannot produce EDEADLK
3. **std::sync::Mutex**: User-space lock (FRONTMATTER_WARNINGS) - cannot produce EDEADLK
4. **SQLite via rusqlite**: Uses fcntl() for WAL mode - CAN produce EDEADLK, but ListAssets does NOT access SQLite

### Code Path Analysis

ListAssets tool invocation: ToolRegistry::try_invoke -> list_assets() -> AssetManager::list_assets() -> asset_files_in_root() [fs::read_dir + path ops] -> fs::read_to_string() [no locking]

None of these operations use fcntl() locking.
