# T-221.3 - First-party Gate and Maenifold Domain Adapters

## Problem

Leaving Gate and Maenifold native tools flat keeps the tool count high. They need first-party routed domains behind the gateway while preserving explicit safety boundaries.

## Scope

Create domain adapters for:

- `gate`
- `maenifold.memory`
- `maenifold.graph`
- `maenifold.workflow`
- `maenifold.thinking`
- `maenifold.system`

Each adapter must provide:

- Command metadata for `GatewayIndex`
- Exact execution for `GatewayExecute`
- Safety classification: read, write, mutate, destructive, orchestration
- JSON schema for parameters
- Clear mutation policy

## Reuse Policy

First-party adapters are projections over existing registries, schemas, and handlers:

- Maenifold adapters wrap or project existing `ToolRegistry`, `crates/maenifold-core/src/mcp/schema/*`, and existing tool handlers.
- Gate adapter wraps or projects `crates/maenifold-gate/src/mcp/schema.rs`, `crates/maenifold-gate/src/mcp/dispatch.rs`, and existing gate process invariants.
- Safety classification is a thin annotation layer attached to existing command descriptors, not a separate command catalog.
- Adapters must not duplicate handler logic or maintain independent JSON schemas for existing tools.

## Cutover Policy

This sprint is a hard cut from flat first-party tool advertisement to routed first-party domains. The affected flat tools must be enumerated by T-221.1's inventory and removed from tools/list only after their corresponding routed command is present in `GatewayIndex` and executable through `GatewayExecute`.

`GetHelp` is the explicit exception to the hard cut. It remains separately advertised as the existing help tool, is excluded from the affected flat-tool removal list, and must not be routed under `maenifold.system` or any other gateway domain.

## Safety Policy

- Gate `status` is read-safe.
- Gate `append`, `pass`, `fail`, and `sync` are mutating and require exact command selection.
- Memory read/search/build context are read-safe.
- Memory write/edit/delete/move, graph repair, asset update, and workflow execution require exact command selection.
- Sequential thinking may be invoked only with explicit session linkage in gateway-originated task specs.
- Explicit session linkage means the routed `maenifold.thinking.sequential` command requires a `sessionId` when appending to any existing reasoning thread; gateway-originated gate specs must record that session ID in task frontmatter.

## Acceptance Criteria

- [ ] `GatewayIndex` exposes Gate as a domain with command metadata and schemas.
- [ ] `GatewayIndex` exposes Maenifold memory/graph/workflow/thinking/system as domains.
- [ ] First-party domain adapters are projections over existing tool/dispatch/schema registries.
- [ ] First-party adapters do not duplicate handler logic or maintain independent JSON schemas for existing tools.
- [ ] Drift-prevention tests prove every routed first-party command maps to one existing handler.
- [ ] Drift-prevention tests prove routed command schemas do not diverge from original MCP/native schemas.
- [ ] Existing flat first-party Maenifold/Gate tools are no longer advertised individually once their domain adapter is available.
- [ ] `GetHelp` remains advertised as a standalone tool and is exempt from first-party flat-tool removal.
- [ ] The hard-cut affected flat tool names are enumerated from the T-221.1 inventory before removal from tools/list.
- [ ] The hard-cut affected flat tool inventory explicitly excludes `GetHelp`.
- [ ] Removed flat first-party tools remain reachable through `GatewayExecute`.
- [ ] `GetHelp` is not routed under `maenifold.system` and is not reimplemented as a gateway command.
- [ ] `GatewayExecute` can invoke read-safe first-party commands deterministically.
- [ ] `GatewayExecute` can invoke mutating first-party commands only with exact command and validated parameters.
- [ ] Gate mutations preserve the gate process: no manual task moves, no stage skips, no fabricated verdicts.
- [ ] Maenifold memory mutations preserve checksum/confirmation semantics.
- [ ] `cargo build --release -p maenifold-cli` succeeds.

### Phase 1: Domain Mapping + Safety Classification

**New:** `mcp/domain_mapping.rs` (≤120 LOC)
- `SafetyClass` enum: `Read`, `Write`, `Mutate`, `Destructive`, `Orchestration`
- `fn tool_domain(tool_name: &str) -> &str` — static mapping derived from schema modules:
  - memory_tools → `maenifold.memory`
  - graph_tools → `maenifold.graph`
  - workflow/pipeline_tools → `maenifold.workflow` (EXCEPT RecentActivity → `maenifold.system`)
  - thinking/assumption_tools → `maenifold.thinking`
  - system/files/embedding_models_tools → `maenifold.system`
  - `Schedule` → `maenifold.system` (no schema module — explicit mapping required. Uses generic schema `{ "type": "object" }` — handler validates internally. Known exception: gateway parameter validation defers to handler deserialization for this tool.)
  - `RecentActivity` → `maenifold.system` (override: lives in workflow_tools.rs but semantically is system/inspection)
  - GetHelp → `None` (excluded from gateway routing)
- `fn tool_safety(tool_name: &str) -> SafetyClass` — explicit per-tool classification
- Gate safety map (upstream): status/history/task_body → Read, sync/append/pass/fail → Mutate, cancel → Destructive
- **Gate precondition**: The upstream gate server MUST be named `"gate"` in maenifold.json for first-party safety annotations to apply. Other names are treated as generic upstream domains. Add a test asserting this contract.

### Phase 2: Catalog Domain Routing

**Modified:** `gateway_catalog.rs`
- Replace single "maenifold" domain in `add_native_tools()` with per-domain routing via `domain_mapping::tool_domain()`
- Exclude GetHelp from the catalog entirely
- Use `domain_mapping::tool_safety()` for safety_class instead of name-prefix heuristic
- Gate upstream tools: apply gate safety map from domain_mapping when server name is "gate"

### Phase 3: Hard-Cut in list_tools AND dispatch

**Modified:** `mod.rs`
- **list_tools**: If `self.gateway.is_some()`: advertise only `GetHelp` + `gateway.list_tools()` (GatewayIndex, GatewayExecute). If `self.gateway.is_none()`: keep full flat list (fallback for degraded startup). If `gateway_startup_error` is set: return error (existing behavior, takes precedence).
- **call_tool dispatch**: When gateway is active, change dispatch ordering:
  - If `tool_name == "GetHelp"` → `ToolRegistry::try_invoke()` (allowed standalone)
  - Else → `gateway.handle_tool_call()` FIRST (handles GatewayIndex, GatewayExecute, AND redirects routed native tools to "use GatewayExecute")
  - Only fall through to `try_invoke` when `gateway.is_none()` (flat fallback)
  - This prevents routed native tools from executing directly — they hit the gateway redirect instead of `try_invoke`

### Phase 4: Hidden Tool Redirect (gateway-side)

**Modified:** `gateway_handler.rs`
- When `handle_tool_call` receives a native tool name (not GatewayIndex/GatewayExecute), look up its domain via `domain_mapping::tool_domain()` and return redirect: "use GatewayExecute with domain=X, command=Y"
- GetHelp never reaches here (mod.rs dispatches it directly via try_invoke)

### Phase 5: Drift-Prevention Tests

**New:** `mcp/gateway_catalog_domain_tests.rs` (≤250 LOC)
- **Forward test**: For each domain: verify every tool in the mapping resolves to a valid handler via descriptor name check (NOT try_invoke on mutating tools — use `ToolRegistry::canonical_names()` containment)
- **Reverse exhaustive test**: `for name in ToolRegistry::canonical_names() { assert!(name == "GetHelp" || tool_domain(name).is_some()) }` — catches new tools added without mapping
- Verify routed command schemas match `mcp_tool_from_registry_name()` output
- Verify GetHelp is NOT in any gateway domain
- Verify GetHelp IS in the flat tools list when gateway active
- Verify flat native tools are NOT in tools/list when gateway active
- Gate-specific tests: conditional on gate upstream being available (skip gracefully in CI)
