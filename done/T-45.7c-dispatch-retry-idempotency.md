# T-45.7c: Dispatch Retry Idempotency

**Requirement**: FR-45.7
**RTM**: RTM-342
**Priority**: P1 — correctness on retry

## Context

Red-team audit of T-45.7 identified that if dispatch fails mid-loop (e.g., one node's workflow asset is missing), the pipeline frontmatter hasn't been persisted yet. A retry re-runs the full dispatch, re-activating already-active nodes and appending the first step a second time via `append_h2_section`.

This is separate from T-45.7b (single-write) — this is about the loop-level retry semantics.

## Acceptance Criteria

1. **Pre-check active status**: Before activating each node in the dispatch loop, read its current session status. If already `active`, skip it.
2. **Partial persistence**: If the dispatch loop fails mid-way, persist the pipeline frontmatter with whatever nodes were successfully activated before the failure. This prevents full re-processing on retry.
3. **Idempotent response**: The `dispatched` array SHALL only contain nodes that were actually transitioned in this call, not nodes that were already active.

## Implementation Notes

- Target: `crates/maenifold-core/src/workflow/pipeline/handler.rs`, dispatch loop
- The skip guard from T-45.7b handles per-node idempotency
- This spec handles loop-level persistence: write pipeline frontmatter after each successful activation, or at minimum catch errors and persist partial state
- Consider: should dispatch be all-or-nothing (rollback on failure) or best-effort (persist partial)?
  - Recommendation: best-effort — persist what succeeded, return error for what failed

## SWE Remediation

- **What I changed**
  - `crates/maenifold-core/src/workflow/pipeline/handler.rs`: updated `dispatch_pipeline` to increment the dispatch counter before the loop, persist pipeline frontmatter after each successfully processed node, and reuse `persist_pipeline_state` at the end so partial activation progress is saved before any later failure.
  - `crates/maenifold-core/src/workflow/pipeline/handler.rs`: added regression tests covering (1) `dispatched` only reporting nodes transitioned in the current call when another node is already active, and (2) partial pipeline state persistence when a later activation fails because a workflow asset is missing.

## Red-team Audit

**Verdict: PASS**

All three acceptance criteria verified against the implementation.

---

### AC1 — Pre-check active status ✅

Verified at two layers:

1. **`compute_ready_set`** (`crates/maenifold-core/src/workflow/pipeline/engine.rs:12–19`) filters to `NodeStatus::Pending` nodes only. Active nodes in the current pipeline frontmatter are structurally excluded from `to_dispatch` before the loop begins.

2. **`activate_workflow_node_session`** (`handler.rs:472–478`) performs a live file read of the workflow session and returns `Ok(false)` when `status == "active"`. This is the guard for the retry scenario where the workflow session file is ahead of a stale pipeline frontmatter (partial persist failure). The outer loop suppresses the `dispatched.push` for any `activated == false` result (`handler.rs:411`).

Tested by:
- `activate_workflow_node_session_skips_active_session_without_duplication` (line 2404) — direct unit test of the guard; confirms `Ok(false)` and no duplicate first-step rendering.
- `pipeline_dispatch_skips_already_active_workflow_sessions` (line 2464) — integration test simulating the stale-frontmatter retry scenario; confirms `dispatched` is empty and `## Step 1/1` appears exactly once.

**Observation (non-blocking):** When `activated == false`, the loop still executes `state.status = NodeStatus::Active` and `persist_pipeline_state` (`handler.rs:393–409`). The spec says "skip it", but this extra work is strictly idempotent and repairs the stale pipeline frontmatter to match the true workflow file state — a correct side-effect of the retry design. Not a bug.

---

### AC2 — Partial persistence ✅

`persist_pipeline_state` is called inside the loop immediately after each successful activation (`handler.rs:403–409`), before iterating to the next node. If `activate_workflow_node_session` returns `Err` for node N, the `?` operator short-circuits the loop; no persist for node N is attempted, but all prior nodes' persists have already committed to disk.

The dispatch counter `last` is incremented before the loop at `handler.rs:363`, so partial runs and full runs share the same sequence number — no ambiguity between an error-interrupted dispatch and a clean one.

Tested by `pipeline_dispatch_persists_partial_progress_when_activation_fails` (line 2332):
- Defines two parallel nodes: `root` (`test-workflow-a`) and `broken` (`missing-workflow`)
- Seeded with `definition.nodes` = [root, broken] (Vec order is deterministic)
- `compute_ready_set` returns [root, broken] in that order; root activates successfully, broken fails on `read_workflow_definition`
- Asserts: `nodeStates["root"].status == Active`, `nodeStates["broken"].status == Pending`, `last == 1`
- Confirms root workflow file has `status: active` and `## Step 1/1` rendered

---

### AC3 — Idempotent response ✅

The `dispatched` vec is only populated at `handler.rs:411–417` under an `if activated { … }` guard. `activated` is the `bool` returned by `activate_workflow_node_session`, which is `false` for any session already carrying `status: active` in its file. Already-active nodes never appear in the `dispatched` array regardless of their status in the pipeline frontmatter.

`node_ids_with_status` (`handler.rs:634–657`) iterates `definition.nodes` (a `Vec`, deterministic order), so the `active` array in the response is also stable.

Tested by:
- `pipeline_dispatch_only_reports_nodes_transitioned_in_this_call` (line 2081): pre-activates `root` directly, then dispatches; asserts `dispatched == [{nodeId: "sibling", …}]` only, `active == ["root", "sibling"]`, and `root` content has exactly one `## Step 1/1`.
- `pipeline_dispatch_skips_already_active_workflow_sessions` (line 2464): pre-activates `root` workflow file (frontmatter still shows Pending); asserts `dispatched.is_empty()` and `active == ["root"]` after dispatch. The `root → child` Success edge in `seed_dispatch_pipeline` (`handler.rs:1734–1738`) ensures `child` is not in the ready set, making the empty-dispatched assertion unambiguous.
