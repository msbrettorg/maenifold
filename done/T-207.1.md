# T-207.1 — StdioSession: single-server stdio MCP client

## Requirement

Create a `StdioSession` struct that manages one long-lived stdio MCP server child process: spawn, initialize, call tools, detect death, shutdown.

## Interface

```rust
pub struct StdioSession { /* ... */ }

impl StdioSession {
    /// Spawn child process and complete MCP initialization handshake.
    /// Returns Err if spawn fails, init times out, or version negotiation fails.
    pub async fn start(entry: &McpServerStdioConfig) -> Result<Self>;

    /// Call a tool. Serializes on internal Mutex (stdio has no multiplexing).
    /// Enforces per-call timeout (default 60s, configurable via entry).
    /// Returns JSON-RPC result or error.
    pub async fn call_tool(&self, name: &str, arguments: Value) -> Result<CallToolResult>;

    /// Cached tool list from initialization discovery.
    pub fn tools(&self) -> Arc<[Tool]>;

    /// True if the child process is still alive AND not poisoned by a prior timeout.
    pub fn is_usable(&self) -> bool;

    /// True if the child process is alive but poisoned (timeout left stale data on stdout).
    pub fn is_poisoned(&self) -> bool;

    /// Graceful shutdown: close stdin, wait, SIGTERM, SIGKILL.
    pub async fn shutdown(self);
}
```

## Behavior

### Initialization (per MCP spec Lifecycle § Initialization)
1. Spawn child process per config (command, args, env). Use `setsid` on Unix (reuse existing pattern from `mcp_discovery/stdio.rs`).
2. Send `initialize` request with `protocolVersion: "2025-03-26"` and `capabilities: {}`.
3. Read `InitializeResult`. Handle version negotiation per Lifecycle § Version Negotiation: the gateway client supports versions `{"2025-03-26", "2024-11-05"}`. If the server responds with one of these, accept. If the server responds with any other version, reject with error: `"Unsupported protocol version: {version}. Gateway supports: 2025-03-26, 2024-11-05"`. Do NOT attempt fallback or version coercion.
4. Send `notifications/initialized` notification.
5. Send `tools/list` request. Handle pagination: if response contains a `nextCursor`, send subsequent `tools/list` requests until exhausted. Cache all discovered tools.
6. Collect stderr on a background task (existing pattern).

### Tool calling
- Acquire internal `Mutex<(ChildStdin, BufReader<ChildStdout>)>`.
- Write JSON-RPC `tools/call` request (newline-delimited per Transports § stdio).
- Read response, matching by JSON-RPC `id`.
- Consume and discard any interleaved notifications (upstream may send logging notifications).
- Enforce timeout via `tokio::time::timeout`. On timeout:
  1. Send `notifications/cancelled` to the upstream server with the original request `id` (per Lifecycle § Timeouts: sender SHOULD issue cancellation notification).
  2. Set a `poisoned` flag on the session — even if the child process is still alive, the stdout stream may contain a stale late response. `is_usable()` returns `false` when poisoned.
  3. Return timeout error. The pool will see `is_usable() == false` on next call and force a full restart (kill + respawn), not just a reconnect.

### Error semantics
- Upstream JSON-RPC error (e.g. `-32602 Invalid params`) → return as `Err(McpJsonRpcError { code, message, data })`, preserving the error code.
- Upstream `CallToolResult { isError: true }` → return as `Ok(CallToolResult)` — this is a tool-level error, not a protocol error.
- Stdin write failure or stdout EOF → mark session dead, return connection error.

### Shutdown (per Transports § stdio)
1. Close stdin.
2. Wait 2s for process exit.
3. SIGTERM.
4. Wait 1s.
5. SIGKILL.
