# T-45.8: Pipeline Resume and Restart

**Requirement**: FR-45.8
**RTM**: RTM-340, RTM-345, RTM-346, RTM-347, RTM-348, RTM-349
**Priority**: P1 — Lifecycle management (core pipeline works without this)

## Context

Pipelines need to survive interruptions and handle node failures. Resume derives state from session files. Restart creates a new session for an abandoned node. Both operations are invoked through the Pipeline MCP tool.

## Scope

Add resume and restart handling to the Pipeline tool handler.

## Acceptance Criteria

1. **Resume**: `pipeline(sessionId=X, view=true)` on a pipeline with `active`/`ready` nodes correctly derives state from session files. No special "resume" operation — viewing IS resuming because state is derived, not stored.
2. **Restart**: `pipeline(sessionId=X, nodeId=Y, restart=true)`:
   a. Verify node is currently `abandoned` or `stuck`
   b. Create a NEW workflow session file for the node (new session ID, same workflow definition, same predecessor context)
   c. Update `nodeStates[Y].sessionId` to point to the new session
   d. Update `nodeStates[Y].status` to `pending`
   e. Increment `nodeStates[Y].attempts`
   f. The prior session file remains as audit trail (not deleted)
   g. Return updated pipeline state
3. **maxAttempts**: Default 3. When `attempts >= maxAttempts`, transition node to `stuck` instead of allowing restart. Return error: `"Node {id} has reached max attempts ({maxAttempts})"`.
4. **Stuck status**: A `stuck` node blocks downstream `success` edges but NOT `always` edges.
5. **Immutable topology**: Reject any attempt to modify `nodes` or `edges` after pipeline creation. The Pipeline tool has no "update definition" operation.
6. **Pipeline session format**: Pipeline session frontmatter matches the specified YAML contract:
   - `type: pipeline`
   - `status`: derived from node states
   - `definition`: full nodes + edges
   - `nodeStates`: map of nodeId → {sessionId, status, attempts}
   - `maxConcurrency`: integer
   - `first`/`last`: tracking fields

## Implementation Notes

- Restart reuses session pre-creation logic from T-45.6a but for a single node
- The old session file stays — `nodeStates[Y].sessionId` just points to the new one
- `maxAttempts` could be per-node or per-pipeline — use per-pipeline for v1 (simpler)
- Topology immutability is enforced by simply not implementing any update operation

### What I changed
- `crates/maenifold-core/src/workflow/pipeline/handler.rs`
  - Added `restart=true` handling for `pipeline(sessionId, nodeId, restart=true)`.
  - Added pipeline session loading helpers so view/dispatch/restart validate the session consistently.
  - Made `view=true` derive node status from referenced workflow session files so resume works by viewing current session state.
  - Added restart logic that creates a new workflow session, preserves the old session as audit trail, resets the node to `pending`, increments attempts, and re-injects predecessor context into the new session.

- `crates/maenifold-core/src/workflow/pipeline/engine.rs`
  - Updated `always` edges so downstream nodes are allowed to proceed when an upstream node is `stuck`.
  - Added coverage for the `stuck` + `always` edge behavior.

### AC1 — Resume: `view=true` derives state from session files ✅

`view_pipeline_session` (handler.rs:162) calls `derive_pipeline_node_states` (handler.rs:508), which iterates every `NodeState` in the pipeline frontmatter and re-reads the corresponding workflow session file to pull the live `status`. Stale pipeline frontmatter is never trusted for node status. The `workflow_status_to_node_status` mapping at handler.rs:552 covers all six statuses including `stuck`. Test `pipeline_resume_view_derives_state_from_workflow_sessions` (handler.rs:1605) confirms: seed root as `active` in pipeline frontmatter, update workflow file to `completed`, `view=true` returns `root: completed` and `child` in the ready set.

### AC2 — Restart creates a new session, preserves old, updates nodeStates ✅

Full flow in `restart_pipeline_node` (handler.rs:257):

- **(a)** Status guard at handler.rs:283: `!matches!(state.status, NodeStatus::Abandoned | NodeStatus::Stuck)` — any other status returns an immediate error.
- **(b)** New session: `allocate_node_session_id` (handler.rs:735) generates a collision-free `workflow-<ts>-<nodeId>` name; `write_workflow_node_session` creates the file (handler.rs:1017 area).
- **(c)** `state.session_id = allocate_node_session_id(...)` (handler.rs:304) — pipeline frontmatter now points to the new file.
- **(d)** `state.status = NodeStatus::Pending` (handler.rs:305).
- **(e)** `state.attempts += 1` (handler.rs:306).
- **(f)** No delete occurs anywhere in the function. Test at handler.rs:2633 explicitly asserts `file_exists(&child_uri, ...)` for the original session after restart.
- **(g)** `build_pipeline_view_result` called at handler.rs:328, returning updated pipeline state including new `sessionId`, `status: pending`, and incremented `attempts`.

Predecessor context is re-injected into the new session via `inject_predecessor_context_for_node` (handler.rs:838) reading the `last` field from completed upstream workflow files — tested end-to-end in `pipeline_restart_recreates_abandoned_node_session` (handler.rs:2530), which asserts `new_child_content.contains("## Predecessor Context")` and `contains("Root finished [[handoff]]")`.

### AC3 — maxAttempts default 3, transitions to stuck when exceeded ✅

`max_attempts` read at handler.rs:265 as `.get("maxAttempts").and_then(YamlValue::as_u64).unwrap_or(3) as u32`. Check at handler.rs:290: `state.attempts >= max_attempts`. When triggered: `state.status = NodeStatus::Stuck` (handler.rs:291), `persist_pipeline_state` called immediately, then `Err("Node {node_id} has reached max attempts ({max_attempts})")` (handler.rs:299) returned. Attempts are **not** incremented in this path. Test `pipeline_restart_rejects_when_max_attempts_reached` (handler.rs:2654) seeds `attempts: 3`, confirms the error string, and verifies the persisted state shows `NodeStatus::Stuck` with `attempts: 3` unchanged.

### AC4 — Stuck blocks downstream `success` edges but NOT `always` edges ✅

`is_node_blocked` (engine.rs:80) only fires for `EdgeType::Success` edges whose source is `Abandoned | Stuck` — `Always` edges are never checked there. `is_edge_satisfied` (engine.rs:93) for `EdgeType::Always` accepts `Completed | Abandoned | Stuck` as satisfying. The two cases are covered by separate tests: `pipeline_restart_ready_set_accepts_stuck_upstream_for_always_edges` (engine.rs:206) asserts a `stuck` root unblocks a `pending` middle via `always`; `ready_set_blocks_success_edge_from_abandoned_or_stuck` (engine.rs:224) asserts neither `abandoned` nor `stuck` upstream satisfies a `success` edge.

### AC5 — Immutable topology ✅

No `update-definition` handler path exists. The routing in `pipeline()` (handler.rs:27) routes only to: `view_pipeline_session`, `dispatch_pipeline`, `restart_pipeline_node`, `update_pipeline_node_status`, and `write_pipeline_session` (create). None modifies `nodes` or `edges`. The help text at handler.rs:86–93 enumerates exactly these five operations with no definition-update option.
