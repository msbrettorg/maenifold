# T-177.4 — Architecture guide for contributors — how maenifold actually works

## Intent

README architecture is 2 paragraphs. DEVELOPMENT.md is build commands. A new contributor has no map of how the system actually works — how data flows from a user action through MCP to the Rust backend, how pipelines execute, how the graph is built, how the desktop app talks to the daemon. This gap makes every new contributor slow and every agent less effective.

## Scope

Create `docs/ARCHITECTURE.md`:

1. **System diagram** — Mermaid or text: Desktop (Electron+Vite+Vue) ↔ Daemon (HTTP MCP) ↔ Core library. CLI (stdio MCP) ↔ Core library. Pipeline driver ↔ Core library + ACP agents.

2. **Crate map** with data flow:
   - `maenifold-core` — the library. Memory DB, search (ONNX embeddings + BM25 + RRF), graph (SQLite + community detection), sequential thinking, workflow engine, pipeline executor, ACP client, gate integration
   - `maenifold-cli` — binary. Parses CLI args, starts MCP stdio or HTTP server, delegates to core
   - `maenifold-gate` — binary. File-authoritative task management, own state machine, MCP + HTTP + tray
   - `maenifold-jockey` — library crate for ACP client/session integration used by runtime tooling
   - `maenifold-pipeline-driver` — binary. Headless pipeline executor spawned per pipeline run

3. **MCP boundary rule** — all domain operations are MCP tools. The desktop app does NOT call Rust functions directly. It hits the daemon's HTTP MCP endpoint. This is the "no capability gap between human and agent" principle in practice.

4. **Data model** — where state lives:
   - Memory files: `~/maenifold/` (markdown + WikiLinks)
   - Graph DB: `~/maenifold/.maenifold/graph.db` (SQLite)
   - Search index: `~/maenifold/.maenifold/` (embeddings + BM25)
   - Pipeline state: `~/maenifold/.maenifold/pipelines/`
   - Gate state: `todo/` + `done/` markdown files, `.gate/gate.db` cache
   - Assets: `~/maenifold/assets/` (workflows, roles, colors, perspectives)

5. **Key flows** — trace 2-3 operations end to end:
   - "User writes a memory" → desktop → HTTP MCP → WriteMemory tool → file write + WikiLink extraction + graph update + embedding generation
   - "Pipeline runs" → desktop → HTTP MCP → Pipeline tool → driver spawned → nodes execute (tool calls, ACP sessions, workflows) → results written to memory
