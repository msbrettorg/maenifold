# T-244.73 — Agents tab perf audit (vs acp-ui baseline)

## Why this is P0-CRITICAL

User direction (2026-04-28 15:48):
> "Our rendering with the agents tab is very slow. I suspect we have deeeeep issues. We need to ensure we're using the code from https://github.com/formulahendry/acp-ui as our starting point rather than YOLO-ing it."

acp-ui is the same stack (Vue 3 + Pinia, just Tauri vs Electron). Their Agents tab is fast. Ours is slow. The delta is in code we wrote on top — find it, justify it or revert it.

Read these end-to-end:

   - Uses `v-for` over `messages` keyed by `message.id`.
   - Per-message component reads `message.content` (markdown source) and only re-parses when content changes.
   - Tool-call cards iterate `message.toolCalls` keyed by `toolCallId`.
3. **`/tmp/acp-ui/src/lib/acp-bridge.ts`** — note that `handleNotification` does ONE `JSON.parse` per inbound message and forwards `params` directly to `onSessionUpdate`. No buffering, no batching.

## Hypotheses to test (in order — pick the highest-impact fix first)

### H1 — Markdown re-parse on every chunk

Streaming `agent_message_chunk` arrives as one notification per token (or per few tokens). If we re-parse the ENTIRE message markdown on every chunk, perf scales O(n²) with response length.

**Test:** Add timing around the markdown render call. For a 2000-token agent response, count how many times the parser is invoked.

**Fix candidates:**
- Memoize parsed HTML by content hash (cheap; only re-parse when content actually changes — but content changes on EVERY chunk).
- Render in two passes: streaming uses raw text in a `<pre>` while loading; on `stop` (turn end), do a single full-render with the unified markdown engine. acp-ui appears to do something similar — check what they do for streaming.
- Throttle the markdown parse to e.g. 100ms intervals during streaming.

### H2 — Deep reactivity on messages array

If `messages` is `ref<ChatMessage[]>` with default `reactive` semantics, every property mutation deep in the tree (e.g. `currentAssistantMsg.toolCalls[3].status = 'completed'`) triggers a re-render of EVERY component subscribed anywhere in `messages`.

**Test:** In Vue devtools, see how many components re-render on a single `tool_call_update`.

**Fix candidates:**
- `shallowRef<ChatMessage[]>` for the array; explicit `triggerRef` after mutations. Per-message component subscribes only to its own message.
- Use Pinia `getters` with explicit invalidation.
- Split the store: messages live in one store, tool-call status in another.

### H3 — Streaming text concatenation cost

`lastMsg.content += update.content.text` on a 50KB string is O(n) per chunk → O(n²) overall. JS engines usually rope-optimize this but Vue's reactivity proxy may force a real copy.

**Test:** Profile string concatenation on a long stream.

**Fix:** Use a chunks array (`lastMsg.contentChunks.push(text)`) and `.join('')` only on render. Or use `shallowRef` per message so Vue doesn't proxy-copy on each mutation.

### H4 — ContentBlock dispatcher repeats expensive work

If our content dispatcher (T-244.51 / current `ChatContentBlocks.vue`) does JSON.stringify, syntax highlighting, or mermaid renders on every parent re-render, those compound the cost.

**Test:** Profile time-per-render for an assistant message containing a 200-line code block.

**Fix:** `defineAsyncComponent` for heavy renderers (mermaid, KaTeX, JSON viewer); `v-memo` on the content block; cache rendered output by block hash.

### H5 — Auto-scroll thrashing

If we listen to message updates and call `scrollIntoView()` on every chunk, we cause synchronous layout on every notification.

**Test:** Profile layout cost during a streaming response.

**Fix:** Throttle scroll to `requestAnimationFrame`. Only scroll if the user is already near the bottom.

### H6 — Pinia store subscriber spam

If components reactively subscribe to `messages.length` or `toolCalls.size` and re-render the entire list on every mutation, that's wasted work.

**Test:** `storeToRefs` audit — every component that reads from session store should be confirmed to re-render only when its specific subset changes.

### H7 — IPC / ACP layer batching

acp-ui forwards each `session/update` notification immediately. If we batch them (or queue them in a microtask drain), we may delay paints. If we DON'T batch and the agent fires 100 chunks in 50ms, we may flood Vue with 100 reactive updates per frame.

**Test:** Count notifications per frame during a hot stream.

**Fix:** Microtask-batch updates at most once per `requestAnimationFrame` — coalesce text chunks for the same message ID.

## Plan

1. **Clone acp-ui at HEAD.** Set up a side-by-side: same agent (claude-code or copilot), same prompt that produces a long streaming response with a tool call.
2. **Profile both.** Vue devtools performance tab + Chrome DevTools performance flame graph. Capture: time-to-first-paint after `session/update`, total render time over a 5s stream, layout count, JS execution time.
3. **For each hypothesis above, run the targeted test.** Rank by measured impact.
4. **Fix the highest-impact regression first.** Verify with re-profile.
5. **Repeat.** Fix the next-highest. Stop when our perf is within 20% of acp-ui's.
6. **Land separate commits per fix.** Each commit references the hypothesis it addresses.
