## Problem

External MCP clients (this Copilot CLI session is the proof) are not seeing useful tool listings from the maenifold MCP HTTP server. Symptoms in the live session:

1. `tools/list` from the gateway returns sparse/empty/unlabeled entries — the assistant's available_skills sidebar shows "maenifold" but **no callable tools surface in the host's MCP tool catalog**.
2. The agent had to fall back to invoking `maenifold tool <Name>` over the local CLI to actually run `SearchMemories` / `BuildContext` / `ReadMemory`. That is the failure mode: when the agent can't *discover* the tools, it stops using them entirely.
3. Suspected root cause: the gateway domains (e.g. `maenifold.gate`, `maenifold.system`) are wired internally but their tool descriptors aren't being projected into the MCP `tools/list` response with proper names + descriptions + JSON schemas. May also be that domain-routed commands (like `gate_Sync`) need explicit registration as discoverable tools rather than only being callable through `GatewayExecute`.

## Investigation Required

1. Capture the actual `tools/list` JSON returned by `http://127.0.0.1:8080/mcp` for an authenticated client. Compare to the descriptors in `crates/maenifold-core/src/registry.rs` and the gateway domain map.
2. Confirm whether each tool descriptor populates `name`, `description`, and `inputSchema` in the MCP response. If `description` is empty or missing, the host UI shows the tool but the agent can't reason about when to use it.
3. Check if gateway-domain commands (e.g. `gate_Sync`, `gate_Pass`, `gate_Fail`) are exposed as first-class MCP tools or only reachable through `GatewayExecute(domain, command, parameters)`. If the latter, the agent has to know about `GatewayExecute` AND the domain catalog AND the parameter shape — three indirections that hurt discoverability.
4. Decide whether to expose each gateway command as its own MCP tool entry (preferred — flat tool surface, matching the constitutional tenet "AI is the new UI") or keep `GatewayExecute` and improve its description to enumerate available domains/commands.

## Acceptance Criteria

- [ ] `tools/list` returns every tool with a non-empty `name`, `description`, and `inputSchema` populated from the canonical help docs (`assets_path/help/<ToolName>.md` already exists for native tools)
- [ ] Gateway domain commands are discoverable: either (a) flat MCP tools with descriptive names like `Gate_Pass`, `Gate_Fail`, `Gate_Sync`, OR (b) a single `GatewayExecute` whose description enumerates all reachable `domain.command` pairs and their parameter schemas
- [ ] Verified end-to-end with at least two MCP clients (Copilot CLI + one other, e.g. Claude Desktop or `mcp-inspector`) — both clients show the full tool catalog with descriptions
- [ ] Reproduction steps + before/after `tools/list` JSON captured in the gate notes

## Why this matters

When tool descriptions are missing, the agent treats maenifold like a black box — falls back to grep, internal model knowledge, or generic tools. This violates the core tenet "AI is the new UI" and silently breaks the dogfooding feedback loop. This session is exhibit A.
