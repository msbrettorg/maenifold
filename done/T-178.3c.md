# T-178.3c — graph:// URI — activity/recent rolling buffer + notification throttling

## Intent

Expose the live endophasia signal stream as a single MCP resource — a rolling buffer that subscribers can read on demand and be notified about when new signals arrive. This is the high-frequency surface, so this task also lands the **shared notification throttling primitive** that earlier slices (T-178.3a's `corpus/snapshot` notifier, T-178.3b's concept-diff fan-out) reach for once they're behaving badly under load.

## Scope

1. Define and register one resource in `crates/maenifold-core/src/mcp/resources.rs`:

   | URI | Read returns | Updated when |
   |---|---|---|
   | `graph://activity/recent` | `{ events: [ActivityEvent...], window_ms, capacity, generated_at }` | Each new signal — subject to throttling (rule 4) |

2. **`ActivityEvent` schema** — frozen contract (document in `assets/help/resources/graph.md`):
   ```jsonc
   {
     "timestamp": "2025-...",      // RFC3339 string, UTC
     "type": "thinking" | "exploring" | "remembering" | "writing" | "reading" | string,
     "conceptName": "string|null", // canonical form when present; null when signal isn't concept-attached
     "fileUri": "memory://...|null",
     "sessionId": "string|null",   // session that produced the signal, when known
     "weight": 0.0,                // optional float; signals that carry intensity report it here
     "meta": { /* free-form */ }   // optional small object for type-specific extras; keep payload <= 1KB total
   }
   ```
   Forward-compat rule: consumers MUST tolerate unknown `type` values and unknown keys inside `meta`.

3. **Rolling buffer**: in-memory ring of the last `N = 200` events (constant, documented). On `resources/read`, return all currently-held events oldest→newest. `window_ms` reports the time range covered by the buffer (max event ts − min event ts); `capacity` reports `N`.

4. **Trailing-edge coalescing throttle** — shared primitive, used here and reused by T-178.3a / T-178.3b emitters:
   - Public surface: extend or wrap `notify_resource_updated` so callers can mark a URI as "throttled at 250ms (trailing edge)" when registering it.
   - Semantics: when a throttled URI fires, if no notification has been dispatched for it in the last 250ms, dispatch immediately. If one has, schedule a single trailing dispatch at the end of the current window. Additional fires within the window collapse into that pending trailing dispatch.
   - **Per-URI** budget: max 1 notification per URI per 250ms window. Multiple URIs do not share a budget.
   - The buffer itself is updated synchronously on every signal (no throttling on writes) — only the *notification* is throttled. So a subscriber that reads after a notification sees every event since their last read.
   - Implementation lives in `mcp::resources::throttle` (or sibling); document the budget in `assets/help/resources/graph.md`.

5. Wire the existing endophasia signal pipeline:
   - On every signal: append to the ring buffer + call the throttled notifier on `graph://activity/recent`.
   - Apply the same throttle wrapper to `graph://corpus/snapshot` (per-write fan-out from T-178.3b) and to the per-concept fan-out (also T-178.3b). Refactor the local coalescers in 3a/3b to use this primitive once it lands.

6. Tests:
   - `resources/read` on a fresh buffer returns `{ events: [], window_ms: 0, capacity: 200, generated_at: <ts> }`.
   - 10 rapid signals fired within 250ms → exactly 1 `notifications/resources/updated` dispatched on `graph://activity/recent`; the read-after returns all 10 events in chronological order.
   - 250 signals fired serially with 50ms between → roughly 1 notification per 250ms window; the buffer holds the last 200 events.
   - Trailing-edge correctness: fire signals at t=0, t=10ms, t=300ms → expect notifications at t=0 (immediate), t=250ms (trailing of the t=10 fire), and at t=300ms+ε if outside an existing window (or trailing again — assert the exact behavior matches the documented rule).
   - `ActivityEvent` shape regression: snapshot test asserting the JSON keys produced by the pipeline.
   - Per-URI isolation: rapid fires on `graph://corpus/snapshot` do not consume the budget for `graph://activity/recent`.

## Files in scope

- `crates/maenifold-core/src/mcp/resources.rs` (URI registration, read dispatch)
- `crates/maenifold-core/src/mcp/resources/throttle.rs` (NEW or sibling — the shared throttling primitive)
- `crates/maenifold-core/src/endophasia/*.rs` (hook signal pipeline to push into the rolling buffer + notify)
- `assets/help/resources/graph.md` (append: activity URI, ActivityEvent schema, throttle semantics + budget)

## Acceptance criteria

1. `cargo test -p maenifold-core` passes.
2. `resources/list` includes `graph://activity/recent` with documented metadata.
3. Reading the URI returns the documented shape with `events` chronologically ordered, oldest first.
4. Throttling test passes: 10 signals in 250ms → 1 notification, all 10 events readable.
5. Trailing-edge dispatch behavior matches the documented rule (verified by the t=0 / t=10ms / t=300ms test).
6. Help doc `assets/help/resources/graph.md` documents the URI, the `ActivityEvent` schema (including forward-compat rule), and the throttle budget.
7. The throttle primitive is reused by `graph://corpus/snapshot` and per-concept emitters from T-178.3a / T-178.3b (the local coalescers added in those tasks are removed in favor of this primitive).

## Out of scope

- Persisting the activity buffer across restarts (in-memory only).
- Per-subscriber filtering (e.g., "only `thinking` signals") — subscribers filter client-side.
- Cross-process fan-out — single process, single buffer.
- Dashboard consumption (T-178.4).

## Dependencies

- [[T-178.2]] (uses subscription registry + `notify_resource_updated`)
- [[T-178.3a]] and [[T-178.3b]] should land first so this task can refactor their local coalescers onto the shared primitive in a single commit. If sequencing forces this to land earlier, the refactor moves to 3a/3b instead.

## History

- Split from original T-178.3 per Sprint 178 review feedback. Reviewers flagged that (a) the activity event payload had no defined schema, (b) the throttling story was vague ("250ms" without trailing-edge semantics), and (c) packaging high-frequency emission with cold reads risked a single PR no one could review. This task isolates both the resource and the primitive.
