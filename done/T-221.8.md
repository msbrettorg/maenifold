# T-221.8 - Gateway Resource Catalog

## Problem

Resources are useful but not reliably exposed as first-class client UI in tools-only clients. The gateway should expose catalog data as native MCP resources for clients that support them.

## Scope

Expose gateway catalog resources from GatewayCatalog data:

- `gateway://domains` — list all domains
- `gateway://domains/{domain}` — domain detail
- `gateway://domains/{domain}/commands` — list commands in domain  
- `gateway://domains/{domain}/commands/{command}` — command detail + schema
- `gateway://examples` — curated usage examples

Gateway resources are generated from the deterministic `GatewayCatalog` (no independent catalog). Parameterized URIs (`{domain}`, `{command}`) are exposed via `list_resource_templates()`. Existing `gateway://diagnostics` is preserved unchanged.

Catalog resources are routed through the existing async `handle_gateway_read_resource(...)` path in `mcp/mod.rs`, alongside existing `gateway://diagnostics` routing.

**Descoped to follow-up tasks:**
- `gate://tasks`, `gate://tasks/pending` — gate data access method unspecified, may require cross-crate plumbing
- `memory://...` as resource scheme — memory is accessed via ReadMemory tool, not MCP resources; adding resource scheme requires new handler
- `maenifold://memory/...` alias — cannot alias what doesn't exist as a resource
- `maenifold://concepts/...` — deferred
- ReadMcpResource expansion — sync/async plumbing gap requires separate investigation

## Acceptance Criteria

- [ ] Gateway resources list the same domains and commands as `GatewayIndex`.
- [ ] Gateway resource catalog is generated from the deterministic `GatewayCatalog`.
- [ ] Gateway resource catalog does not maintain an independent domain/command catalog.
- [ ] Parameterized URIs (`gateway://domains/{domain}`, etc.) are exposed via `list_resource_templates()`.
- [ ] Native `resources/list` and MCP `read_resource` return gateway catalog resources correctly.
- [ ] Gateway catalog resource reads never mutate state.
- [ ] Existing `gateway://diagnostics` is preserved and unchanged.
- [ ] GatewayCatalog is accessible from resource handlers via shared state initialized at gateway startup.
- [ ] Resource not-found errors remain distinct from operational upstream errors.
- [ ] `cargo build --release -p maenifold-cli` succeeds.

### Phase 1: Shared GatewayCatalog State

**Modified:** `resources/mod.rs`
- Add `static GATEWAY_CATALOG: RwLock<Option<Arc<GatewayCatalog>>> = RwLock::new(None);`
- Add `pub(crate) fn set_gateway_catalog(catalog: Arc<GatewayCatalog>)` setter
- Add `pub(crate) fn gateway_catalog() -> Option<Arc<GatewayCatalog>>` accessor
- Use `RwLock<Option<...>>` (not OnceLock) so tests and restart scenarios can update

**Modified:** `mcp/gateway_startup.rs`
- After `GatewayCatalog::build(...)` calls in both startup paths:
  - Call `resources::set_gateway_catalog(Arc::new(catalog.clone()))`
- ~3-5 LOC addition

### Phase 2: Gateway Catalog Resources

**Modified:** `resources/gateway.rs`
- Keep existing `gateway://diagnostics` handling unchanged
- `list_resources()`: add concrete `gateway://domains` and `gateway://examples`
- `list_resource_templates()` (new function): add parameterized URIs
- Expand `is_gateway_uri()` to match all `gateway://` prefixes
- `handle_read_resource(uri)`: parse URI, dispatch to GatewayCatalog via accessor:
  - `gateway://domains` → catalog.domains() → JSON
  - `gateway://domains/{domain}` → catalog.commands(domain) → JSON
  - `gateway://domains/{domain}/commands/{command}` → catalog.render_index(...) → JSON
  - `gateway://examples` → curated examples
  - `gateway://diagnostics` → existing handler (unchanged)
  - When catalog is None: return empty/unavailable for catalog URIs

- gate:// resources, memory:// scheme, maenifold:// aliases, ReadMcpResource expansion
