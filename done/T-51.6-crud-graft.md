# T-51.6 — Pipeline Graft Operation

**Requirement**: FR-40 (Pipeline Active Executor)
**RTM**: RTM-162 / TC-162
**Component**: `crates/maenifold-core/src/workflow/pipeline/handler.rs`

## Context

Graft adds new nodes and edges to an existing pipeline. This enables extending a pipeline mid-flight (while paused) or after completion (before rewind). Uses petgraph's `StableGraph` — stable indices mean existing node references remain valid after insertion.

Depends on: T-51.1 (petgraph foundation).

## Acceptance Criteria

1. Add `graft` operation to the Pipeline tool handler, triggered by `sessionId + graft: { nodes: [...], edges: [...] }`
2. Implement graft logic:
   - Read existing pipeline session
   - Build `StableGraph` from existing definition
   - Validate graft: no duplicate node IDs with existing nodes
   - Add new nodes to the graph (status: Pending)
   - Add new edges (validate source/target exist — can reference existing or new nodes)
   - Check resulting graph is still acyclic (`is_cyclic_directed()`)
   - If cyclic: reject with error listing the cycle, no mutation
   - Create workflow sessions for new nodes (same as create flow)
   - Update pipeline definition in frontmatter with merged nodes/edges
   - Persist updated pipeline session
3. Return updated pipeline view (same format as `view` operation)
4. Graft on a running pipeline: REJECT with error. Must be paused, completed, or cancelled first.
5. Graft on a paused pipeline: allowed. New nodes participate in next `resume()`.
6. Edge validation: new edges can connect existing → new, new → existing, or new → new. All valid as long as no cycle.

## Red-Team Audit

**Tests run**: `cargo test -p maenifold-core --lib pipeline_graft -- --nocapture` → **6/6 PASS**

**Verdict: REJECT — one high-severity correctness bug, plus two lower-severity issues.**

---

### Finding 1 — HIGH: Non-Atomic Write Ordering Corrupts Pipeline on I/O Failure

**Location**: `graft_pipeline`, lines 603–614 in `handler.rs`

```rust
// WRITE 1: pipeline frontmatter committed (nodeStates includes new sessions)
persist_pipeline_state_with_status(&mut frontmatter, &node_states, ...)?;

// WRITE 2..N: workflow session files created AFTER pipeline already references them
for node_file in &new_node_files {
    write_workflow_node_session(context, session_id, node_file)?;
}
```

The pipeline frontmatter is persisted **before** the workflow session files it references exist on disk. If any `write_workflow_node_session` call fails (disk full, permission error, filesystem limit), the pipeline `nodeStates` will contain `session_id` entries for workflow files that don't exist.

Every subsequent read of this pipeline calls `derive_pipeline_node_states`, which does:

```rust
if !file_exists(&workflow_uri, &context.config)? {
    return Err(MaenifoldError::Message(format!(
        "Workflow session {} doesn't exist", state.session_id
    )));
}
```

The pipeline is **permanently unreadable** — `view`, `dispatch`, and any further graft all fail. There is no self-repair path without manual file editing.

**Contrast with join**: `join_pipeline` gets this right — it calls `ensure_workflow_sessions` first (creating missing workflow files), then writes the pipeline frontmatter. Graft should follow the same ordering: write all new workflow session files first, then `persist_pipeline_state_with_status`.

**Required fix**: move the `write_workflow_node_session` loop to execute before `persist_pipeline_state_with_status`. Same fix needed in `fork_pipeline` (`write_pipeline_session` at line 514 precedes the session loop at line 522).

### Finding 2 — MEDIUM: Graft Rejects "Stuck" Pipelines With No Recourse

**Location**: `graft_pipeline`, lines 565–571

```rust
if !matches!(pipeline_status.as_str(), "paused" | "completed" | "cancelled") {
    return Err(...);
}
```

`compute_pipeline_status` returns `"stuck"` for pipelines with Stuck nodes and no Active/Ready nodes. `"stuck"` is not in the allowed set, so a stuck pipeline cannot be grafted even though graph surgery (adding an `Always`-edge bypass node, for example) is a legitimate recovery strategy.

The spec says "must be paused, completed, or cancelled first" — the implementation is spec-compliant, but the spec omits `"stuck"` as a recoverable state. Callers must issue an explicit `pause` before grafting a stuck pipeline, which feels counterintuitive.

**Recommendation**: add `"stuck"` to the allowed-status set in both the guard and the spec, or document the required `pause → graft` workaround in the spec.

---

### Finding 3 — LOW: Graft Rejects Never-Run Pipelines (Stale "active" Frontmatter)

**Location**: `graft_pipeline`, lines 554–562; `session_io.rs` `write_pipeline_session` line 258

`write_pipeline_session` always writes `status: "active"` as the initial frontmatter value. A pipeline that was created but never dispatched therefore has `status: "active"` in frontmatter even though no node is actually running.

The graft status guard rejects `"active"` pipelines:

```rust
if matches!(pipeline_status.as_str(), "active" | "running") { ... }
```

Result: callers must issue an explicit `pause` before grafting a freshly-created, never-run pipeline. The node-level check (`any(... NodeStatus::Active)`) correctly returns false for this case, but the frontmatter string check fires first.

**Recommendation**: either gate only on the live node-state check (no Active nodes → allow graft regardless of frontmatter status), or document the `pause → graft` pre-condition for newly created pipelines in the spec.

---

### Finding 4 — LOW: Workflow Definition Validation Precedes Duplicate-Node Check

**Location**: `graft_pipeline`, lines 574–578

```rust
for node in &graft.nodes {
    read_workflow_definition(&context.config, &node.workflow_id)?;  // line 575
}
let merged_definition = merge_graft_definition(&definition, &graft)?;  // line 578 (dup check)
```

If a graft payload contains both a duplicate node ID and a missing `workflowId`, the error returned is `"workflow definition not found"` rather than `"duplicate node ID"`. The more actionable and specific error (duplicate ID) is swallowed. Swap the order: run `merge_graft_definition` first, then validate workflow definitions only for the net-new nodes that passed the dedup check.

---

### No Issues Found

- Cycle detection fires on the fully-merged graph (before any mutation) — no partial-write window for cycle injection.
- `merge_graft_definition` validates all edge endpoints against the merged node set before calling `build_graph` — dangling edges cannot reach cycle detection.
- `find_cycle_nodes` / `dfs_cycle_nodes` correctly detects and reports cycles, including self-loops (petgraph `is_cyclic_directed` handles these). The `visiting` HashSet is redundant with the `stack` but not incorrect.
- Workflow session ID collision is prevented by the `allocate_node_session_id` bump loop.
- `status_override` correctly preserves `"paused"` and `"cancelled"` while allowing `"completed"` to transition to `"active"` when new pending work is introduced.

## SWE Fix Remediation

- Reordered `graft_pipeline` persistence so new workflow session files are created before the pipeline frontmatter is rewritten, preventing unreadable pipeline sessions when workflow file creation fails mid-graft.
- Expanded graft eligibility to accept `stuck` pipelines and to allow never-dispatched pipelines whose node states are still entirely `Pending`, even if the persisted frontmatter still says `active`.
- Moved `merge_graft_definition` ahead of `read_workflow_definition` so duplicate node IDs are rejected before any downstream workflow-definition validation runs.
- Added regression coverage for stuck pipelines, all-pending pipelines with stale `active` frontmatter, duplicate-ID precedence over missing workflow definitions, and failed workflow-session creation leaving the pipeline definition unchanged.
