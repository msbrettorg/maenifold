# T-243.5.0 — Knowledge tab delta review

Plain-English review of the **Knowledge tab** (Memory + Graph subtabs). Three lenses:

1. **What the UAT doc tests** (`T-243.5-knowledge-tab-uat.md`)
2. **What's actually built today** (per `outputs/uat/cdp-tab-enumeration.md`, screenshots `05-knowledge-*.png`, and source under `apps/desktop/src/components/Knowledge*.vue` + `stores/knowledge.ts`)
3. **What a normal user expects from a knowledge manager** (Obsidian, Logseq, Roam, Notion)

The Knowledge tab is the user-facing surface of the wiki the LLMs are supposed to be compounding. If users can't curate it, only agents will — and the graph rots into noise.

---

## Snapshot of "what is actually built"

From CDP enumeration + source read of the Vue components and the `useMemoryApi` composable:

**Memory subtab**
- Three resizable panes: vault tree (left), note viewer (center), related-concepts rail (right with collapse).
- Vault tree with folder expand/collapse, file count per folder, refresh, "Search notes…" input, Tree | Search toggle.
- Tabbed note viewer (multi-tab, close button, breadcrumb), markdown rendered via `KnowledgeNoteRenderer` (markdown-it + DOMPurify + Mermaid).
- WikiLinks render as `[data-wikilink]` chips and clicking one calls `store.openNote('memory://<concept>')` (cmd/ctrl-click → new tab).
- Related-concepts rail driven by `FindSimilarConcepts` against the first concept candidate in the active note; each is clickable.
- Provenance breadcrumbs at top (gate / pipeline / thinking / parent-workflow lineage).

**Graph subtab**
- Toolbar: title, node count badge, "Filter graph" input, communities `<Select>`, Reset, Reload.
- Communities sidebar (left), force-directed canvas (center), node inspector (right) with concept name, file count, community ID, member files (clickable → opens in Memory), neighbours with edge weights.
- Double-click node → switches to Memory subtab on that note.

**MCP tools the Knowledge tab actually calls** (from `useMemoryApi.ts`, complete list):
`ReadMemory`, `SearchMemories`, `RecentActivity`, `ListMemories`, `BuildContext`, `FindSimilarConcepts`.

**MCP tools the backend exposes that the Knowledge tab does NOT call:**
`WriteMemory`, `EditMemory`, `DeleteMemory`, `MoveMemory`, `ExtractConceptsFromFile`, `Visualize`, `Sync`, `AnalyzeConceptCorruption`, `RepairConcepts`.

(Note: `WriteMemory` and `EditMemory` *are* wired up in `useMemoryPromotion.ts`, but only from the chat **PromotionDialog**. The Knowledge tab itself never invokes them.)

So today the Knowledge tab is a **read-only knowledge browser** — vault explorer + graph viewer + concept rail. There is **no path to mutate the corpus from the Knowledge UI**.

## Lens 2 — Built vs user expectations (Obsidian / Logseq / Roam / Notion)

What a normal knowledge-manager user reaches for and what we have:

| User expectation | Found in… | Have it? | Gap impact |
|---|---|---|---|
| **"+ New note" button** (header, sidebar, or `cmd-n`) | All four | ❌ | **Critical.** This is the user's call-out. There is literally no way to create a note from the Knowledge UI. Today the only entry points are MCP `WriteMemory` (agent), the chat PromotionDialog (promote a chat message), or `vim` on disk. |
| **Inline edit / "Edit mode" toggle** on the open note | Obsidian, Logseq, Notion | ❌ | **Critical.** The viewer is a `KnowledgeNoteRenderer` only. Fixing a typo means leaving the app. |
| **Delete a note** (right-click → Delete, with confirm + trash) | All four | ❌ | **Critical.** User explicit call-out. `DeleteMemory` exists in the gateway; UI never calls it. |
| **Rename / move** (right-click → Rename, drag a file between folders) | All four | ❌ | High. `MoveMemory` exists; unused. Particularly painful because folder structure *is* the ontology in maenifold. |
| **Click an unresolved `[[concept]]` → "Create note for «concept»"** | Obsidian, Logseq, Roam | ❌ | High. This is the canonical wiki growth loop. We render the chips and have `WriteMemory`; we just don't close the loop. |
| **Markdown editor with WikiLink autocomplete** | Obsidian, Logseq, Roam, Notion | ❌ | High. Without autocomplete from the existing concept set, users fragment the graph (the exact failure mode the skill warns about). |
| **Backlinks panel** (who links *to* this note) | All four | ❌ | High. We have a "related concepts" rail (forward similarity) but no "incoming WikiLinks" panel. Backlinks are the most-used Obsidian panel after the editor. |
| **Tag / concept browser** (alphabetical list of all `[[concepts]]` with file counts, click to filter) | Obsidian, Logseq | Partial — present *inside* Graph as the communities/inspector view, **not** in Memory | Medium. A flat concept index would beat the graph for many lookup tasks. |
| **Global graph search modes exposed** (Hybrid / Semantic / FullText, weight knobs) | Backend supports all three; UI defaults to whatever the composable sends (`mode` is unused by Vault search) | ❌ | Medium. Power users will want to switch. |
| **"Find similar concepts" on a selection** in the editor | Obsidian "Smart Connections" plugin, Roam | ❌ | Medium. We *have* `FindSimilarConcepts`; the rail only seeds from the note's first concept, not from arbitrary selections. |
| **Daily notes / templates** | Obsidian, Logseq, Roam | ❌ | Medium. Without templates, every new note is a blank file. Bad for consistency, bad for the "lineage / source" convention the skill enforces. |
| **Live refresh when an agent writes through MCP** | Obsidian (FS watcher), Logseq | ❌ | **High.** User explicit call-out: "Note edits made via MCP refresh in the Memory viewer." Today nothing pushes; the user must click Refresh on the vault. The maenifold daemon already knows when files change — wiring a notification here is plumbing, not research. |
| **Concept repair UX** (notice duplicates → merge) | Roam graph cleanup tools, Obsidian Janitor plugin | ❌ | Medium. `AnalyzeConceptCorruption` + `RepairConcepts` are the most powerful graph-hygiene commands maenifold has, and they're invisible to users. The Graph inspector is the obvious home: "this concept has 4 variants — review and merge." |
| **Graph snapshot export** (PNG/SVG/JSON for sharing or embedding in a note) | Obsidian, Roam | ❌ (`Visualize` exists) | Low-medium. CDP enumeration flagged this. |
| **Click a member file in node inspector → opens in Memory** | n/a (our own affordance) | ✅ already wired | — |
| **Empty-state onboarding for an empty vault** ("Create your first note") | Obsidian first-run, Notion templates | Unknown | Low until first user has an empty vault. |
| **Pin / favorite notes** | All four | ❌ | Low. |
| **Open multiple notes side-by-side** | Obsidian split-pane | Partial — multi-tab strip exists; no split | Low. |
| **Keyboard nav** (`cmd-p` quick switcher, `cmd-shift-f` global search) | All four | Likely ❌ | Medium. The doc has T-243.13 for shortcuts/a11y so we'll defer there. |

The **must-haves** to credibly call this a knowledge manager — and all of which the user implicitly or explicitly flagged — are: **create / edit / delete / rename a note from the UI**, **create-on-click for unresolved WikiLinks**, **backlinks**, and **live refresh on external mutation**. Everything else is polish.

## What we'd file as sub-tasks

In priority order:

1. **T-243.5.1 — Note CRUD scaffolding (create + delete + rename/move + confirmations)**. New-note button in the vault toolbar (folder + title + initial content with at least one `[[WikiLink]]` per skill convention). Right-click context menu on tree rows: Rename, Move, Delete (with confirm). Wires to `WriteMemory` / `MoveMemory` / `DeleteMemory`. **This is the one the user explicitly named.**
2. **T-243.5.2 — Inline markdown editor for the open note (Edit / Preview toggle, save → `EditMemory` with checksum).** Viewer becomes editor on toggle. Preserves WikiLink chips in preview. Stale-edit guard via `checksum` round-trip from `ReadMemory`.
3. **T-243.5.3 — Unresolved-WikiLink → "Create note for «concept»" affordance.** When `openNote('memory://<concept>')` 404s, render a CTA in the leaf pane that pre-fills the new-note form with `# concept` and a `[[concept]]` self-link. Closes the wiki growth loop.
4. **T-243.5.4 — Backlinks panel** (a third tab on the right rail beside Related Concepts). Computed from `BuildContext(concept, depth=1)` filtered to incoming edges, or a server-side `Backlinks` command if we add one. The skill explicitly treats backlinks as the routing index — surfacing them is overdue.
5. **T-243.5.5 — Live-refresh on external mutation.** Subscribe the Knowledge store to the daemon's recent-activity stream (or FS watcher) and invalidate `tabCache` + `folders` on writes. User explicit call-out — agents are writing constantly via MCP and the Memory viewer goes stale.
6. **T-243.5.6 — Concept-repair surface in the Graph node inspector.** When `AnalyzeConceptCorruption` reports variants for the selected concept, show a "Variants detected — review" expandable; offer `RepairConcepts` with `dryRun=true` preview then commit. Single most valuable graph-hygiene action that exists.
7. **T-243.5.7 — Search mode controls** (Hybrid / Semantic / FullText radio + an "advanced" disclosure for `semanticWeight` / `textWeight`). Backend supports it; we just default-and-hide.
8. **T-243.5.8 — Templates + folder picker for new notes.** Once T-243.5.1 lands. Templates seeded from `assets/templates/` if present; folder picker browses `ListMemories`.
9. **T-243.5.9 — `BuildContext` neighbours in the related rail.** Currently rail only runs `FindSimilarConcepts`; UAT doc claims both. Cheap fix.
10. **T-243.5.10 — Selection-driven `FindSimilarConcepts`.** Highlight a phrase in the viewer → "Find similar concepts" pops the rail with that seed.
11. **T-243.5.11 — Graph export** (PNG / SVG / JSON via `Visualize`). CDP-flagged.
12. **T-243.5.12 — Concept browser** (flat alphabetical concept list with file counts) as a third Memory subview or a left-panel tab. Bridges the Memory/Graph divide.
13. **T-243.5.13 — Daily notes** (stretch; only if the team actually uses them).

`T-243.5.1`, `T-243.5.2`, `T-243.5.3`, and `T-243.5.5` together are the credibility floor. Without them the Knowledge tab is, quoting the user, "a viewer, not a tool" — same diagnosis as Gate.

## Reviewer notes

**claude-opus-4.7:** the architectural shape is right and the read paths are well-factored — `useMemoryApi` is small and clean, the store is properly Pinia-shaped, and the WikiLink chip handler in `KnowledgeLeafPane` is exactly the right hook to extend. The omission isn't accidental; the team built the read surface first and stopped before mutation. Good news: every backend command we need (`WriteMemory`/`EditMemory`/`DeleteMemory`/`MoveMemory`/`AnalyzeConceptCorruption`/`RepairConcepts`) already exists and is documented in the maenifold skill. Adding T-243.5.1 + T-243.5.2 is one focused frontend sprint.

**gpt-5.5:** agreed. Three nuances worth flagging before T-243.5.1 starts:

- **Stale-edit protection is mandatory.** Per the skill, `EditMemory` accepts a `checksum`. Build it in from day one — the live-refresh in T-243.5.5 means two surfaces (UI + agent) will fight over the same file.
- **WikiLink discipline at write time.** New notes should require ≥1 `[[WikiLink]]` (matches `WriteMemory`'s contract) and ideally autocomplete against the existing concept set. Without autocomplete, T-243.5.1 will fragment the graph the same week it ships — exactly the "WikiLink anti-pattern" failure mode the skill calls out.
- **Delete confirmation should show "incoming WikiLinks" count** before commit ("3 notes link to this — delete anyway?"). Cheap once T-243.5.4 (backlinks) exists; consider sequencing T-243.5.4 before T-243.5.1's delete path lands, or land delete with a basic confirm and tighten it after.

Also: the Graph subtab is in much better shape than Memory. T-243.5.6 (repair UX) is the highest-leverage Graph add but the rest is polish. Don't let Graph eat the sprint that should fix Memory CRUD.
