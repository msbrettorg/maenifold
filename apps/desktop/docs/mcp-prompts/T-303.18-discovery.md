# T-303.18 — MCP prompts renderer surface — Discovery

PM-authored SLC discovery artifact. Iter-10 wave-2.

## Source

Filed iter-9 as P2 SLC follow-up after T-303.17 documented the gap in
`docs/mcp-coverage-matrix.md`. The MCP spec defines `prompts/list` and
`prompts/get` as first-class primitives; the maenifold renderer has zero
implementation today (verified: `apps/desktop/src/composables/mcpClientOps.ts`
exposes `listTools`, `listResources`, `listResourceTemplates` but NOT
`listPrompts` or `getPrompt`).

## Goal

Expose MCP prompt templates in the desktop chat UI so the user can:

1. See the list of prompts an MCP server advertises.
2. Pick a prompt template to seed the chat composer.
3. Fill in the template's named arguments (with completion in T-303.19).
4. Insert the resolved messages into the composer at submit time.

## Architectural decisions

### IPC layer

**No daemon-side work required.** The MCP renderer talks directly to the
upstream MCP server via the SDK client (`@modelcontextprotocol/sdk`).
`prompts/list` + `prompts/get` are SDK methods (`client.listPrompts()`,
`client.getPrompt()`) already available — we just call them. No daemon
protocol changes, no Electron main-process IPC.

### Composable layer

Mirror the existing `useMcpResources` pattern at
`apps/desktop/src/composables/useMcpResources.ts` (183 LOC):

- `apps/desktop/src/composables/mcpClientOps.ts` — add `listPrompts()` and
  `getPrompt(name, args?)` operations alongside the existing `listResources`
  / `listResourceTemplates` (current LOC 440; new code adds ~25 LOC).
- `apps/desktop/src/composables/useMcpPrompts.ts` (NEW, ~80 LOC) —
  composable wrapping `mcp.listPrompts()` + `mcp.getPrompt()`. Mirrors
  `useMcpResources` shape.
- Notification: `PromptListChangedNotificationSchema` registered in
  `createSdkMcpClient` (`mcpClientOps.ts:87-97`) alongside the existing 5
  schemas. ~3 LOC.

### UI layer

The chat composer already has slash-command infrastructure:

- `apps/desktop/src/composables/useBuiltInSlashCommands.ts` (76 LOC) —
  built-in `/new`, `/quit`, etc.
- `apps/desktop/src/lib/default-commands.ts` — `DEFAULT_SLASH_COMMANDS`
  registry.
- `apps/desktop/src/components/ChatInputBar.vue:14` — accepts
  `availableCommands: AvailableCommand[]` prop and emits `select-command`.
- `AvailableCommand` is a typed merge of the SDK type (`apps/desktop/src/lib/types.ts:231`).

**Decision:** surface MCP prompts as additional `AvailableCommand` entries,
prefixed with `mcp.` and grouped per server. The existing slash-command
palette (`useComposerPalette.ts`, 54 LOC) renders them. When the user
selects an `mcp.*` command, dispatch `getPrompt` and insert the resulting
messages into the composer (NOT submit — let the user review).

This avoids inventing a new dialog and matches the UX pattern users
already know.

### Argument-collection sub-UI

Some MCP prompts have named arguments (e.g., `args-prompt`,
`completable-prompt` in `server-everything`). When the selected prompt
declares arguments, present a small JSONForms-rendered form (we already
have `SchemaFormRenderer.vue` from T-302.x) with the prompt's argument
declarations as fields. On submit, call `getPrompt(name, formValues)`.

T-303.19 (argument completion) hooks completion suggestions into the
form's input controls — out of scope for T-303.18 but the form scaffolding
must leave room.

### Capability gating

`McpCapabilityUnsupportedError` already exists in
`useMcpResources.ts:7-15`. Mirror the pattern: throw if the server doesn't
advertise the `prompts` capability. UI degrades to "no prompts available"
with no error toast.

## Test approach

- **Unit:** vitest covers each new composable + the McpPromptPicker
  component. Mock the SDK client at the boundary (existing pattern in
  `useMcpResources.test.ts`).
- **Integration:** vitest covers the round-trip from
  `useMcpPromptCommands` → `AvailableCommand[]` → `ChatInputBar` selection
  → `useMcpPrompts.getPrompt()` call.
- **CDP UAT:** deferred to T-303.18.1 (file later if needed). The spec
  acceptance lists `server-everything` as the test fixture; T-303.15
  documents how to wire it.

## Out of scope

- Argument auto-completion (covered by T-303.19, blocked on T-303.18).
- `prompts/list` pagination (server-everything's prompt list is small;
  spec doesn't require pagination support yet).
- `prompts/get` server-side cancellation (out of scope for renderer).
- Settings UI to disable MCP prompts globally (not requested).
- Persistence of "favorite" prompts (not requested).

## Risks / blockers

- **Capability detection:** must call `client.getServerCapabilities()`
  before `listPrompts()` to avoid `Method not found` errors on servers
  that don't advertise the capability. `useMcpResources` does this via
  `mcp.supportsResourceSubscribe()` — we'll add `supportsPrompts()`.
- **Notification re-fetch:** `notifications/prompts/list_changed` should
  trigger a re-fetch of `listPrompts()`, not a delta merge. Simpler and
  correct for the typical small prompt list.
- **AvailableCommand collision:** built-in `/new`, `/quit` etc. must not
  collide with `mcp.*` prefixed entries. `useBuiltInSlashCommands.ts:31`
  already checks for collisions; mirror its `BUILT_IN_COMMAND_NAMES` Set
  pattern.

## Acceptance criteria for SWE

(Mirrors the spec at `todo/T-303.18-prompts-renderer-surface.md` plus
this doc's deltas.)

1. `mcpClientOps.ts` exposes `listPrompts()` → `PromptDescriptor[]` and
   `getPrompt(name, args?)` → `GetPromptResult`.
2. `useMcpPrompts.ts` lazily fetches prompt list on connect and on
   `notifications/prompts/list_changed`.
3. `ChatInputBar` shows `mcp.*` slash commands grouped per server.
4. Selecting an `mcp.*` command opens `McpPromptPicker.vue` (if args)
   or directly inserts messages (if no args).
5. `PromptListChangedNotificationSchema` registered in
   `createSdkMcpClient`.
6. All vitest tests pass.
7. `vue-tsc --noEmit` clean.
8. `npm run package` succeeds.
9. CDP UAT proof against `server-everything` deferred to T-303.18.1.
10. `docs/mcp-coverage-matrix.md` row updated to Y.
