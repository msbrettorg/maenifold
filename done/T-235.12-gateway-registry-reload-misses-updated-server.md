## Problem

During maenifold MCP remediation, the PM called authenticated `UpdateMcpServer` to change `gate` to a gateway-managed stdio MCP server:

```json
{
  "type": "stdio",
  "name": "gate",
  "command": "/usr/local/bin/gate",
  "args": ["--mcp"],
  "env": { "MAENIFOLD_ROOT": "/Users/brett/src/ma-collective/maenifold-rs" },
  "gateway": true
}
```

`ReloadConfig` then returned success, but `GatewayIndex({ "domain": "gate" })` still returned `Unknown gateway domain 'gate'`.

That means the control-plane can write/reload config without refreshing the live gateway registry used by `GatewayIndex` and `GatewayExecute`.

Repo-grounded review found the stale state is broader than one catalog lookup:

- MCP handler gateway state is built once at startup and captured into the HTTP service closure
- REST discovery holds its own startup-time gateway pool
- gateway resource/catalog state is stored separately and can also go stale

So this is not just a `GatewayIndex` bug. `ReloadConfig` needs to rebuild and atomically swap a shared gateway runtime snapshot across every surface that exposes gateway state.

## Required implementation semantics

`ReloadConfig` must:

1. Build a **new gateway runtime snapshot** before mutating the live one
2. Atomically swap the snapshot used by:
   - MCP tool dispatch
   - REST discovery / diagnostics
   - gateway catalog resources
3. Keep the prior healthy gateway live if the rebuild fails
4. Retire the old stdio pool without breaking in-flight requests
5. Avoid mixed state like:
   - new catalog + old pool
   - new pool + stale REST discovery
   - failed reload + stale success-only resource catalog

Do **not** implement this as an isolated catalog refresh. The shared runtime indirection is the fix.
