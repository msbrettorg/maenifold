# T-243.13.0 — Shortcuts & a11y: duo delta review

**Reviewers:** claude-opus-4.7 + gpt-5.5 (architect duo)
**Time-box:** 12 min
**Inputs:** `T-243.13` UAT checklist, tab-inventory note ("10+ shortcuts, ARIA partial"), live source under `apps/desktop/src` (`useAppShell.ts`, `ChatInputBar.vue`, `CommandPalette.vue`, `ChatMessageList.vue`, ui primitives), comparators VS Code / Cursor / Slack.

---

## Headline

**Maenifold has tab-switch shortcuts and a slash-popup. Almost nothing else.** No global Cmd+K, no chat-input recall, no Esc-to-cancel-turn, no Cmd+, → Settings, no per-tab shortcuts (new note, new pipeline, focus search). Accessibility is "ARIA labels exist on the components shadcn-vue gave us" — and very little beyond that. Every truly maenifold-built surface (graph canvas, pipeline composer, chat stream) is keyboard-thin and screen-reader-thin.

The UAT checklist as written is **aspirational, not descriptive** — most of what it asks the executor to "verify" is not implemented, so the executor will mostly be filing missing-feature gaps, not verifying behavior. That's fine, but PM should know the ratio up front: expect ~70 % of B/D/E rows to land as "missing".

## Section-by-section delta

### A. Tab navigation — **PARTIAL**

- ✅ Cmd+1..Cmd+8 wired in `useAppShell.ts` (`handleTabShortcut`). Correctly bails on `metaKey + altKey/ctrlKey/shiftKey` combos and on editable targets — that's good defensive hygiene.
- ✅ Bails if a modal dialog is open (`hasBlockingDialogOpen()`).
- ❌ **Cmd+, → Settings is not wired.** The mac convention every user reaches for first. Trivial addition (one branch in `handleTabShortcut`).
- ❌ No discoverability — there is no "Press Cmd+1..8" hint, no shortcut legend, no tooltip on the tab triggers. Power-users will use them; nobody else will know they exist.

**Gap → `T-243.13.1`:** add Cmd+, mapping to Settings tab; add `aria-keyshortcuts="Meta+{n}"` on `TabsTrigger`s; add a "?" → keyboard cheatsheet dialog (Slack/Linear convention).

### B. Chat input — **MOSTLY MISSING**

`ChatInputBar.handleKeyDown` implements:
- ✅ Enter → submit, Shift+Enter → newline.
- ✅ ArrowDown/Up/Enter/Tab/Esc forwarded to slash-command palette **only when palette is open**.
- ❌ **Cmd+Enter alternate submit** — not wired. Common muscle memory from Discord/Slack/Cursor; people on slow keyboards hit it accidentally hoping it works.
- ❌ **Up arrow in empty input recalls last user message** — not wired. Standard REPL/terminal behavior; users expect it.
- ❌ **Cmd+K to focus input** — not wired anywhere. The single most-requested shortcut for chat-driven apps.
- ❌ **Esc to cancel current turn** — not wired. While streaming, Esc should call the existing cancel path (whatever it is — needs a quick code check). Today the user's only escape is the Stop button.
- ❌ **Cmd+L clear chat** — not wired. iTerm/Terminal/Cursor convention.

**Gap → `T-243.13.2`:** implement chat-input shortcut bundle (Cmd+Enter submit, Up-arrow recall last user message from `sessionStore.history`, Esc → cancel-turn, Cmd+L → clear-with-confirm). Owner needs to confirm the cancel-turn API path before starting.

**Gap → `T-243.13.3`:** add a global Cmd+K that focuses the chat input regardless of which tab is active (and switches to Home if not already). Probably belongs in `useAppShell`.

### C. Command palette — **PARTIAL but local-only**

- ✅ `/` triggers slash-command popup (showCommandPalette computed in `ChatInputBar`).
- ✅ Arrow / Enter / Tab / Esc handled in `CommandPalette.handleKeyDown`.
- ❌ **No Cmd+Shift+P / Cmd+K global command palette.** "Open anything from anywhere" — switch tab, open a memory, run a workflow, jump to a pipeline. This is the single biggest UX upgrade available on this surface, and it's the shortcut every VS Code/Cursor/Linear user reaches for in the first 10 seconds. Maenifold has `ListMemories`, `ListSessions`, gateway commands — all the data exists. There's just no surface that fuses them.
- ❌ Slash palette is **input-scoped only** — invisible from any tab other than chat.

**Gap → `T-243.13.4` (P1, separate from rest):** ship a global command palette (Cmd+K / Cmd+Shift+P) that fuses: tab switch, memory open, recent thinking session, workflow run, pipeline open, settings deep-link. Reuse the existing slash-palette UI shell to keep scope tight. **This is the recommendation we'd lead a sprint with.**

### D. Knowledge tab — **ONE OF TWO PRESENT**

- ✅ Cmd/Ctrl+Click on WikiLink opens in new pane — `KnowledgeVaultNode.vue:21` and `KnowledgeLeafPane.vue:60` and `KnowledgeVaultBrowser.vue:50` all branch on `event.metaKey || event.ctrlKey`.
- ❌ **Cmd+F → focus search is not wired.** Browser default Cmd+F will trigger Electron's in-page find; it's not the search box. Users will be frustrated.
- ❌ No Cmd+N → new note. No "/" → focus search inside Knowledge.

**Gap → `T-243.13.5`:** Knowledge-tab-scoped shortcuts (Cmd+F → focus VaultBrowser search input; Cmd+N → new memory dialog with current folder pre-filled). Suppress Electron find or co-opt it.

### E. App-wide — **MIXED**

- ✅ Cmd+Q / Cmd+W / Cmd+R / Cmd+Shift+I are Electron defaults — verify in the menu builder, not application code.
- ⚠️ Cmd+R reload **must be disabled in production builds** (or scoped to `process.env.NODE_ENV === 'development'`). One-line check in the Electron main; if it's already there, the UAT step is "verify"; if not, it's a P2 fix because reloading mid-turn nukes the session.
- ⚠️ Cmd+Shift+I (devtools) — same story. Most desktop apps disable it in prod.

**Gap → `T-243.13.6`:** audit `apps/desktop/electron/main.ts` (or wherever the menu lives) for prod-disabled accelerators. File a fix if Cmd+R is live in packaged builds.

### F. Code-grep deltas

`useAppShell` is the only window-level keydown listener. Per-component listeners exist on:
- `PipelineView` (Esc handling)
- `PipelineComposer` (canvas keys via `handleFlowKeyDown` — undocumented)
- `ToolNodeFields*` (palette nav)
- `TemplateGalleryCard`, `TrafficEntry`, `WorkflowStepCard` (Enter/Space activate)

**Gap → `T-243.13.7` (documentation):** the executor must list these in the final report. The product doesn't tell the user any of these exist; Pipeline Composer has keyboard nav and a help dialog would surface it.

### G. Tab order — **UNVERIFIED, likely OK on shadcn surfaces, broken on custom canvases**

- shadcn-vue primitives (Tabs, Dialog, Select, Switch, Checkbox, Input, Textarea, Button) have correct tab semantics out of the box and ship with `focus-visible` styles. Spot-checked — they're fine.
- ⚠️ **Custom canvases are the risk:** `GraphViewCanvas`, `PipelineComposer`, `KnowledgeVaultBrowser` graph view, `SemanticZoomOverlay`. Tab order through a Vue Flow / d3 canvas is almost never sensible by default.
- ⚠️ Pipelines tab specifically — `PipelineView` has a runner pane and a flyout; verify Tab cycles `flyout → composer → runner` in reading order.

**Gap → `T-243.13.8`:** UAT step for canvas tab-order on Pipelines and Knowledge graph specifically; file separate issues per failure.

### H. Screen reader — **PARTIAL**

What's already there:
- ✅ `ChatMessageList.vue:33` has `role="log" aria-live="polite" aria-label="Chat messages"`. **This is the most important one** and it's correct.
- ✅ `aria-live="polite"` is used in ~10 places: `TrafficMonitor`, `WorkflowExportBar`, `AgentProbePreviewStatus`, `PromotionDialog`, `WorkflowBrowserFilters`, `PipelineRunner`, `WorkflowDraftBar`, `SemanticZoomOverlay`, `SettingsMcpServersList`, `GraphViewCanvas`, `PipelineFlyout`. Good baseline.
- ✅ `sr-only` close-button labels on dialog/sheet primitives.
- ✅ `aria-busy` on Button when `loading`.

What's missing:
- ❌ **Streaming chat content uses `aria-live="polite"` on the whole log** — VoiceOver will re-announce stale chunks as new ones arrive. Should be `aria-live="polite" aria-atomic="false"` on a child container per message, not on the whole log. Test with VoiceOver: a 2-paragraph reply will get read like a stutter loop.
- ❌ Tool-call cards inside chat have no SR semantics — no announcement of "tool started", "tool succeeded", "tool failed".
- ❌ Error toasts — verify the toast library (vue-sonner?) actually emits `aria-live="assertive"` on its toast container; if not, hard-to-recover failure mode for SR users.
- ❌ Graph canvas (`GraphViewCanvas`) — `aria-live` exists but the canvas itself is a `<canvas>` with no SR-readable structure. Needs an off-screen list of nodes/edges or a "view as table" toggle.
- ❌ Pipeline composer canvas — same critique.

**Gap → `T-243.13.9`:** SR audit pass with VoiceOver on Chat (assistant streaming, tool calls, error path) and on Graph canvas. File one issue per surface.

### I. Color contrast — **UNVERIFIED**

- App is hardcoded dark (per T-243.8.0 review).
- `text-text-primary` / `text-muted-foreground` / `text-[var(--text-secondary)]` vs `bg-bg-app` / `bg-bg-surface` / `bg-bg-elevated` need a contrast checker pass. Likely fine for primary, **muted-foreground on bg-surface is the canonical fail point** for shadcn-derived themes.
- Active vs inactive tab triggers in `TabsTrigger` rely on color (`text-foreground/60` vs `text-foreground`) and a border. Border is the non-color cue — verify it's visible at 100 % zoom and at high DPI.
- Disabled state — most primitives use `opacity-50`. That can fail WCAG when the underlying color was already low-contrast.

**Gap → `T-243.13.10`:** run an automated axe-core or Lighthouse contrast pass on each tab; file specific token failures (e.g. `--text-secondary` ratio against `--color-bg-surface`).

### J. Reduced motion — **NOT RESPECTED**

- `grep prefers-reduced-motion` returns nothing in the desktop app. The Mermaid composable checks `prefers-color-scheme` only.
- Animations are present in: dialogs (`animate-in/out`, `fade-in`, `zoom-in-95` on AlertDialog/Dialog), tab switches, traffic monitor, streaming dots, graph layout transitions.
- A user with vestibular sensitivity will get every dialog/tab/streamer animating regardless of OS preference.

**Gap → `T-243.13.11`:** add `@media (prefers-reduced-motion: reduce)` block in the global Tailwind layer that neutralizes `animate-*`, `transition-*`, and any custom keyframes; verify shadcn animations respect it (they don't by default — the data-state animations need explicit overrides).

### K. Resizable text — **UNVERIFIED, structurally risky**

- Chat bubbles, sidebar widths, gate columns, pipeline node bodies all use fixed Tailwind `text-sm`/`text-base`. Bumping system font size won't proportionally rescale them in Electron; only in the browser.
- Electron has `webFrame.setZoomFactor` — verify Cmd+= / Cmd+- are wired (Electron defaults usually wire them but may be stripped).

**Gap → `T-243.13.12`:** verify Cmd+= / Cmd+- / Cmd+0 zoom in packaged build; verify no `overflow: hidden` or fixed-height surfaces clip at 150 % zoom on Home, Knowledge, Pipelines.

## Cross-cutting

### Discoverability is the meta-gap

Every shortcut on this list is invisible. There is no `?` cheatsheet, no menu listing, no tooltip showing the accelerator next to the action. Even the shortcuts that **do** work (Cmd+1..8, /-palette, Cmd+Click WikiLink) are word-of-mouth features. **One small "Keyboard shortcuts" dialog (`Shift+?`) would have higher UX impact than three new shortcuts.** Cheap to build, mostly content.

### Customization (from PM brief: "I want to remap shortcuts")

Out of scope for this sprint. Note for backlog: a remappable shortcut store would belong in Settings (`SettingsPreferences.vue` if/when that gets wired in per T-243.8.2). Don't build it now — first ship a stable default set, then make it customizable when users actually ask.

### Vim/emacs mode in inputs (from PM brief)

Hard pass. Wrong audience for the cost. CodeMirror or Monaco support this if and when the JSON editor or memory editor needs it; Pinia store for chat input doesn't.

### Accessibility budget

Right now the app is "shadcn good, custom surfaces poor". The custom surfaces (graph canvas, pipeline composer, embeddings table interactions, semantic zoom overlay) carry essentially all the a11y debt. Treat those four surfaces as one budget line for any future a11y sprint, separate from the global concerns above.
