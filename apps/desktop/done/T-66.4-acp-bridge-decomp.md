# T-66.4 — ACP Bridge Decomposition

## Objective
Extract utility functions and permission handling from `src/lib/acp-bridge.ts` into focused modules.

## Scope

### Extraction 1: `src/lib/acp-meta.ts` (~100 LOC)
- Types: `AcpMeta` and any related interfaces
- Functions: `isRecord()`, `cloneMeta()`, `normalizePermissionToolCallPayload()`, `withAcpMeta()`, `readAdvertisedAgentMethods()`, `withExtensionCapabilities()`, `isAbsolutePath()`, `assertAbsolutePath()`
- All are pure functions with no class dependency

### Extraction 2: `src/lib/acp-permissions.ts` (~100 LOC)
- `PendingPermissionEntry` type
- Permission methods from `AcpClientBridge`: `requestPermission()`, `resolvePermission()`, `cancelPermission()`, `getPermissions()`, `clearPermissions()`
- Extract as a `PermissionHandler` class that owns the pending permissions map and resolver lifecycle
- `AcpClientBridge` takes a `PermissionHandler` instance and delegates permission calls

## Dependencies
- None (independent of App.vue work — can run in parallel with T-66.1–3)

- [ ] `npx vue-tsc --noEmit` passes

## Risk: Deferred Promise Pattern
The permission system uses a deferred Promise pattern where `requestPermission()` stores a resolver in a map and `resolvePermission()`/`cancelPermission()` later invoke it. The `PermissionHandler` class must own this entire lifecycle atomically. Do NOT split the resolver map from the methods that operate on it.
