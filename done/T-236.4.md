# T-236.4 - Surface MCP domain-map build failures instead of silently routing direct

**Pipeline**: sdd

## Problem

T-236.2 research identified `buildDomainMap()` in the desktop MCP client as the likely failure path: if `GatewayIndex` fails, the catch path can leave the domain map empty and mark it built, causing domain-routed tools to be called directly and fail with MCP `-32602`.

## Evidence

- Active thinking session: `session-1777236650835-22077`
- T-236.2 research report highlighted `apps/desktop/src/composables/mcpClientOps.ts` domain-map initialization and the catch path that clears/marks the map as built.
- Observed UI failures from prior verification showed direct calls to routed tools such as `GetConfig` and `ListMemories` returning `-32602` with instructions to use `GatewayExecute`.

## Scope

- `apps/desktop/src/composables/mcpClientOps.ts`
- Existing focused tests in `apps/desktop/src/composables/__tests__/mcpClientOps.test.ts`
- UI error-surfacing code only if the MCP client already exposes a shared error channel; do not invent a new UI framework in this task.

## Acceptance criteria

- [ ] `GatewayIndex` failures are not silently treated as successful empty domain maps when gateway routing is required.
- [ ] Domain-routed tool calls cannot fall back to direct bare tool names after a failed domain-map build.
- [ ] The caller receives a clear actionable error that preserves the underlying failure context.
- [ ] Tests cover the failure path for `GatewayIndex` and prove a routed tool is not called directly afterward.
- [ ] No broad catch or success-shaped fallback is introduced.

## Verification

- Run the targeted frontend test for `mcpClientOps`.
- Run the frontend typecheck for `apps/desktop`.
