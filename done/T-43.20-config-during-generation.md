# T-43.20: Allow mode/config changes during generation

**Requirement**: Config-options + session-modes audit gap  
**Priority**: P1  
**Files**: `vendor/acp-ui/src/components/ChatView.vue`

## Acceptance Criteria

1. The spec explicitly states: "The current mode can be changed at any point during a session, whether the Agent is idle or generating a response." Same for config options.

2. Remove `:disabled="isLoading"` from `ModelPicker`, `ModePicker`, and all `ConfigOptionPicker` instances in `ChatView.vue`.

3. Mode/config changes during generation should work — the agent will process them asynchronously.

## SWE Remediation

- What I changed:
  - `vendor/acp-ui/src/components/ChatView.vue`: removed `:disabled="isLoading"` from `ModelPicker`, `ModePicker`, and `ConfigOptionPicker` so these controls remain available while a prompt is in flight.
  - `vendor/acp-ui/src/lib/acp-bridge.ts`: exempted `session/set_mode`, `session/set_model`, and `session/set_config_option` from request timeouts so ACP mode/config mutations are not failed by the bridge while generation is still active; also added timeout cleanup for resolved/rejected requests.
  - `vendor/acp-ui/src/stores/session.ts`: added optimistic updates for mode, model, and config-option changes with rollback on error, and factored config-option mapping into a shared helper so in-flight changes reflect immediately while the agent processes them asynchronously.

- Test results:
  - Pass — `cd vendor/acp-ui && npx vue-tsc --noEmit && bun run build`

- Notes:
  - I kept the send box disabled during generation; only the mode/model/config controls were re-enabled per the spec.
  - Although the spec called out mode/config specifically, `ModelPicker` was included in the acceptance criteria, so I applied the same non-blocking behavior there as well.

## Red-team Audit

**Verdict: PASS**

All acceptance criteria verified:

- **AC1** (spec allows mode/config change during generation): ✅ Controls remain interactive during generation — `ModelPicker`, `ModePicker`, and all `ConfigOptionPicker` instances have no `:disabled` binding at all in the template (`ChatView.vue` lines 189–207).

- **AC2** (`:disabled="isLoading"` removed from pickers): ✅ Confirmed absent.
  - `ModelPicker` (`ChatView.vue:189–194`): no `:disabled` prop
  - `ModePicker` (`ChatView.vue:195–200`): no `:disabled` prop
  - `ConfigOptionPicker` (`ChatView.vue:201–206`): no `:disabled` prop
  - The `textarea` and send button *retain* `:disabled="isLoading"` (`ChatView.vue:284`, `290`) — correct per the SWE's stated intent and not prohibited by the spec.

- **AC3** (mode/config changes work asynchronously during generation): ✅ Three sub-changes all verified:
  - `acp-bridge.ts` (`getTimeoutForMethod`): `session/set_mode`, `session/set_model`, and `session/set_config_option` return `0`; the `sendRequest` implementation only arms the `setTimeout` when `timeoutMs > 0`, so these requests are never timed out regardless of what other requests are in flight.
  - Timeout cleanup on resolve/reject: `clearPendingRequest()` clears both the resolver/rejecter maps and calls `clearTimeout(timeoutId)` when `timeoutId !== null` — no timeout leak.
  - `session.ts` optimistic updates with rollback:
    - `setMode` (`session.ts:1031`): saves `previousModeId`, updates optimistically, rolls back on catch ✅
    - `setModel` (`session.ts:1051`): saves `previousModelId`, updates optimistically, rolls back on catch ✅
    - `setConfigOption` (`session.ts:1070`): `structuredClone` of `previousConfigOptions`, maps new value optimistically, rolls back on catch ✅
  - Shared `mapSelectConfigOptions` helper (`session.ts:49`) factored out and reused in `setConfigOption` response handling and `session/update` notification path (`session.ts:373`).
