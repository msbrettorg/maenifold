# T-225.1 — MCP Resource Subscription Matrix + Capability Gating

## Problem

The MCP server advertises `resources.subscribe` globally but only 2 resource families actually emit `notifications/resources/updated` (asset watcher for `asset://` and `teams/runtime.rs` for `teams://status`). The UI subscribes to many resource URIs that never emit updates, creating a false expectation of live behavior.

Before implementing emitters for each resource family, we need a decision on:
1. Which resources should be live vs polling vs non-subscribable
2. Whether subscribe rejection should be per-URI or remain global
3. Where the subscription matrix lives

## Deliverables

- [ ] Create a resource subscription matrix document (in `docs/resource-subscription-matrix.md`) listing every resource URI with:
  - Current behavior (live/no-emit/no-subscribe)
  - Target behavior (live/polling/non-subscribable)
  - Trigger events that would emit updates
  - Estimated implementation complexity
- [ ] Decide: Does `resources/subscribe` reject non-live URIs with a structured error, or accept silently?
- [ ] Decide: Does the UI implement automatic polling fallback for non-subscribable resources?
- [ ] Enumerate all mutation sites per resource family that would need to call `notify_resource_updated`
- [ ] Create follow-up gate tasks for each resource family emitter (T-225.2 through T-225.6)
