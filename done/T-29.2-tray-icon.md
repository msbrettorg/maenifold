# T-29.2: System Tray Icon

**Requirement**: FR-35 (System Tray Icon)

## Context

When running in `--web` or `--http` mode, maenifold should display a system tray icon (macOS menu bar) with basic controls. The tray icon appears when the server starts and disappears on shutdown.

## Acceptance Criteria

1. **`tray-icon` crate added** to `crates/maenifold-core/Cargo.toml` as an unconditional dependency.

2. **Tray menu items**:
   - "Open Web UI" — opens `http://localhost:{port}` in the default browser (use `open` command on macOS). Only shown in `--web` mode.
   - "Help" — opens `https://github.com/ma-collective/maenifold-rs/issues` in default browser.
   - "Quit" — triggers graceful shutdown of the server.

3. **Tray icon lifecycle**:
   - Icon appears when `serve_http()` or `serve_web()` starts.
   - Icon disappears on shutdown.

4. **Thread architecture**:
   - The native event loop (tray icon) runs on the **main thread** (required by macOS).
   - The tokio runtime and axum server run on a **background thread**.
   - This means `main()` must be restructured: spawn tokio on a thread, run tray event loop on main.

5. **Applicability**: Tray icon only active in `--web` and `--http` modes. Stdio mode (`--mcp`) is headless — no tray.

6. **Tray icon asset**: Use a simple "M" letter icon or the text "maenifold". The `tray-icon` crate supports PNG icons. Create a minimal icon at `assets/tray-icon.png` (32x32 or 64x64).

7. **`cargo build --release -p maenifold-cli`** succeeds with the new dep.

8. **`maenifold --mcp`** still works headlessly (no tray icon, no native event loop, no hang).

## Files

- `crates/maenifold-core/Cargo.toml` — add `tray-icon` dep

## SWE Fix (Event Loop)

Replaced the `try_recv` + `thread::sleep(100ms)` polling loop with a winit
`ApplicationHandler` / `EventLoop` pattern that properly integrates with macOS's
`NSRunLoop`.

**Files modified:**

| File | Change |
|------|--------|
| `crates/maenifold-core/Cargo.toml` | Added `winit = { version = "0.30", default-features = false, features = ["rwh_06"] }` and `[target.'cfg(target_os = "macos")'.dependencies] objc2-core-foundation = { version = "0.3", … features = ["std", "CFRunLoop"] }` |
| `crates/maenifold-core/src/tray.rs` | Rewrote event loop: `TrayApp` struct implements `ApplicationHandler`; tray icon/menu created in `new_events(StartCause::Init)`; menu events polled via `try_recv` each iteration; `ControlFlow::WaitUntil(100ms)` replaces `thread::sleep`; `CFRunLoopWakeUp` on macOS after tray creation |

**Key design decisions:**

- Tray icon + menu built inside `new_events` on `StartCause::Init` (not before `run_app`) — ensures creation happens on the winit-managed main thread.
- Tray icon stored in `TrayApp.tray_icon` (`Option<TrayIcon>`) so it is not dropped prematurely.
- `ControlFlow::WaitUntil(Instant::now() + 100ms)` re-armed each iteration — gives ~10 Hz polling for menu events and server-exit detection without busy-spinning.
- `CFRunLoopWakeUp(CFRunLoopGetMain())` called after tray creation to flush the initial render.
- `event_loop.exit()` on Quit or server-thread completion; after `run_app` returns, server thread is joined.
- All existing behaviour preserved: `ServerMode` enum, `build_icon()`, `open_url()`, runtime init, server thread spawn with `CancellationToken`.

**Thread architecture:**

- `--http` / `--web`: `main()` → `CliApp::classify()` → `tray::run_with_tray()`:
  - Main thread: tray icon + `MenuEvent` polling loop (macOS native event loop requirement).
  - Background `std::thread` ("maenifold-server"): `tokio::runtime::Runtime::new()` → `block_on(serve_http/serve_web)`.
- `--mcp` / `--tool` / `--help`: `main()` → `CliApp::classify()` returns `Headless` → `CliApp::run()` unchanged (no tray, no native event loop).

**Shutdown flow (Quit menu item):**

1. Tray "Quit" handler sends `SIGINT` via `libc::kill(getpid(), SIGINT)`.
2. Server's existing `tokio::signal::ctrl_c()` handler fires → cancellation token cancelled → `axum::serve` graceful shutdown.
3. Main-thread event loop breaks → tray icon dropped (disappears) → `server_handle.join()` → process exits.

**Assumptions:**

1. `tray-icon` 0.21 on macOS delivers `MenuEvent` via its crossbeam channel without requiring an explicit `NSApplication::run()` loop — the polling loop with `try_recv()` + 100ms sleep is sufficient for menu interaction.
2. `serve_web()` and `serve_http()` are not modified; graceful shutdown is triggered by sending `SIGINT` to self (re-using the existing `ctrl_c()` handler).
3. `start_mcp_watchers` visibility was widened to `pub(crate)` (from private) so `tray.rs` can call it for `--http` mode initialisation.
4. The 32×32 PNG icon in `assets/` is for documentation/future use; at runtime `build_icon()` generates RGBA data in code (no PNG decoder dependency).

### 4. Quit triggers clean shutdown (not process::exit) — ⚠️ CONDITIONAL PASS

The high-level flow is correct: Quit → SIGINT → `ctrl_c()` handler → graceful shutdown → `join()` → return. However three concerns apply:

**Concern A — SIGINT delivery race (Medium)**  
`tray.rs:202-206`: `libc::kill(getpid(), SIGINT)` is called, then immediately `break` exits the loop and execution falls to `server_handle.join()` at `tray.rs:228`. SIGINT delivery is asynchronous. On many POSIX systems signals are delivered to a random eligible thread that has not blocked the signal. If the OS delivers SIGINT to the **main thread** (which has not masked it) before the tokio runtime's `ctrl_c()` future in the server thread is polled, the process default action terminates it abruptly — cutting short the `join()` wait and bypassing graceful shutdown. This race is narrow but real under load.

**Concern B — Non-Unix hang (Low / theoretical)**  
`tray.rs:202-204` is wrapped in `#[cfg(unix)]`. On Windows, clicking Quit breaks the event loop at line 206 but nothing signals the server thread. `server_handle.join()` at line 228 then blocks indefinitely. macOS is Unix so this does not affect the primary target, but it is a latent portability defect.

**Concern C — `process::exit` at outer callsite (Low)**  
`main.rs:18`: `std::process::exit(code)` is called after `run_with_tray` returns. By that point the tray icon has been explicitly dropped (`tray.rs:225`) and the server thread has been joined (`tray.rs:228`), so safety-critical destructors have already run. The `process::exit` bypasses any *remaining* Rust drop glue, but nothing safety-critical is still live at that point. Low risk as-written, but violates the principle of letting `main` return normally.

> **REQUIRED ACTION (Concern A)**: Replace the SIGINT self-signal with a shared `CancellationToken` (tokio-util) or `Arc<AtomicBool>` passed into the server thread at spawn time. This eliminates the signal-delivery race, removes the `unsafe` block entirely, and fixes the non-Unix hang — no observable behaviour change for macOS users in the happy path.

- Added `use tokio_util::sync::CancellationToken;` to `crates/maenifold-core/src/tray.rs`.

### New Findings (non-blocking)

#### 🟡 Concern D — `CancellationToken` aborts server future; axum graceful-drain bypassed (Low)

`tray.rs:140-149`: the `tokio::select!` cancels the `serve_http`/`serve_web` future when the token fires. Both `serve_http` (`http.rs:53-56`) and `serve_web` (`web.rs:74-77`) register `.with_graceful_shutdown(async { let _ = tokio::signal::ctrl_c().await; ... })`. Because the outer `select!` wins, that graceful-shutdown future is never resolved — axum's connection-drain window is skipped.

In practice this means in-flight HTTP requests at the moment Quit is clicked are cut off mid-response. For a personal productivity tool, abrupt closure is acceptable. However, the `with_graceful_shutdown` mechanism is already wired in both servers; it would be straightforward to forward the token into them and get proper draining for free:

```rust
// In serve_http / serve_web: accept an optional CancellationToken and select! in with_graceful_shutdown
.with_graceful_shutdown(async move {
    tokio::select! {
        _ = tokio::signal::ctrl_c() => {},
        _ = token.cancelled() => {},
    }
})
```

**Not blocking** — the old SIGINT path had the same limitation under load (signal delivered before drain). Noting for future polish.

---

#### 🟡 Concern E — macOS `MenuEvent` delivery assumption unverified (Medium — requires smoke test)

The polling loop uses `MenuEvent::receiver().try_recv()` + `thread::sleep(100ms)` with no AppKit run loop (`NSApplication::run()` / `CFRunLoop::run_in_mode`). All `muda` examples in the registry (`tao.rs`, `winit.rs`, `wry.rs`) drive a full event loop — there are zero polling-only examples.

Source review confirms `tray-icon` 0.21 uses `NSStatusItem.setMenu:` (line 67 of tray-icon macOS impl), which causes the system menu server to handle menu-open on click without requiring the app run loop. Menu item actions (`fireMenuItemAction:`) are Objective-C action callbacks that fire via the modal tracking run loop managed by the system — independent of the app's main `NSRunLoop`. In theory this means `MenuEvent::send()` fires onto the crossbeam channel while the main thread is sleeping, and `try_recv()` picks it up within ≤100ms.

This is technically sound but **empirically unverified**. A 60-second smoke test covers the P0 criterion:
```
cargo build --release -p maenifold-cli
./target/release/maenifold --web --port 9090
# click tray icon → select Quit → server should terminate cleanly
```

If menu events are not delivered, the one-line fix is to replace `thread::sleep(100ms)` with `unsafe { objc2_core_foundation::CFRunLoop::run_in_mode(kCFRunLoopDefaultMode, 0.1, false); }` to pump the run loop each iteration.

---

#### 🟡 Concern F — Initialization code duplication between `run_with_tray(Http)` and `run_http()` (Medium — maintenance risk)

`tray.rs:111-120` calls `initialize_runtime` + `start_mcp_watchers` for `Http` mode, mirroring the identical sequence in `cli.rs:run_http()`. These two paths have already diverged and have no compile-time coupling. A future addition to `run_http()` (e.g. a new registry step) would silently not apply to the tray path.

**Remediation**: extract into `fn init_http_prerequisites() -> Result<(), i32>` shared by both sites. Non-blocking for current feature.

---

#### 🔵 Nit — `_tray_icon` variable name

`tray.rs:180`: `let _tray_icon = ...` — the `_` prefix signals "unused" by Rust convention, but the variable is explicitly `drop()`ped at line 231. Rename to `let tray_icon = ...` to remove the misleading suppression signal.
