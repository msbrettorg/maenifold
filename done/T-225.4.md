# T-225.4 — Route ChatView File Reads Through MCP

## Problem

`apps/desktop/src/components/ChatView.vue:171` calls `getDaemonUrl('/api/files/text')` — a direct REST call bypassing the MCP boundary. This violates "AI is the new UI" — agents can't access this path through MCP.

## Duo Review History

- **R1**: Unanimous FAIL — no MCP tool exists for file reads; spec implied simple swap
- **R2**: Unanimous FAIL — security constraint contradicted reuse instruction; backend file paths wrong; tool name convention unspecified; acceptance criteria too thin

## Two-Phase Approach

1. **Backend**: Create a `ReadTextFile` native MCP tool that mirrors the existing REST endpoint
2. **Frontend**: Migrate `ChatView.vue` to call the MCP tool via `callTool()`

## Phase 1 — Backend: ReadTextFile MCP Tool

### Tool Contract

- **MCP tool name**: `ReadTextFile` (PascalCase, matching existing convention: WriteMemory, ReadMemory, etc.)
- **Parameters**: `path` (required, string), `cwd` (optional, string — working directory for relative path resolution)
- **Returns**: JSON `{ path: string, content: string }` matching the existing REST endpoint shape
- **Error**: Standard MCP tool error with descriptive message on file-not-found or read failure

### Trust Model

The MCP tool inherits the **same trust posture** as the existing REST endpoint `/api/files/text`. The current `resolve_requested_file_path()` in `routes_data.rs` does not enforce traversal protection — it accepts absolute paths and joins relative paths with `cwd` without canonicalization. The MCP tool reuses this same logic as-is. Adding traversal protection is a separate concern (file a follow-up task if needed).

### Implementation Path

1. Add a `ToolDescriptor` entry to `crates/maenifold-core/src/registry.rs` DESCRIPTORS array
2. Add handler function in `crates/maenifold-core/src/tools/` (new file or extend existing)
3. Add schema definition in `crates/maenifold-core/src/mcp/schema/` (new `files_tools.rs` or extend `system_tools.rs`)
4. Add mapping in `crates/maenifold-core/src/mcp/schema/mod.rs` `mcp_tool_from_registry_name()` chain
5. Reuse `resolve_requested_file_path()` from `crates/maenifold-core/src/api/routes_data.rs:49-83` — extract to a shared location or call directly

### Key Files (Backend)

- `crates/maenifold-core/src/registry.rs` — add ToolDescriptor to DESCRIPTORS array
- `crates/maenifold-core/src/api/routes_data.rs:49-83` — existing `file_text` handler and `resolve_requested_file_path` to reuse
- `crates/maenifold-core/src/mcp/schema/mod.rs` — add schema mapping in `mcp_tool_from_registry_name()`
- `crates/maenifold-core/src/mcp/schema/system_tools.rs` (or new `files_tools.rs`) — tool JSON schema
- `crates/maenifold-core/src/tools/` — tool handler implementation

## Phase 2 — Frontend: ChatView Migration

### Scope

- Replace `getDaemonUrl('/api/files/text')` fetch at `ChatView.vue:171` with `callTool('ReadTextFile', { path, cwd })` via `useMcpClient`
- Parse the MCP tool result to extract `content` field

### Key Files (Frontend)

- `apps/desktop/src/components/ChatView.vue:171` — replace direct REST call
- `apps/desktop/src/composables/useMcpClient.ts:291-323` — existing `callTool()` method

## Acceptance Criteria

- [ ] `ReadTextFile` appears in `tools/list` response
- [ ] `tools/call` with `{ name: "ReadTextFile", arguments: { path: "Cargo.toml" , cwd: "<repo-root>" } }` returns file content
- [ ] `tools/call` with a nonexistent path returns a structured MCP error (not a crash)
- [ ] ChatView file reads use `callTool('ReadTextFile', ...)`, not `getDaemonUrl('/api/files/text')`
- [ ] `cargo build --release -p maenifold-cli` succeeds
- [ ] `cd apps/desktop && npx vue-tsc --noEmit` succeeds
