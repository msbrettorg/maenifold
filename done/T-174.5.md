# T-174.5 — Cancellation kills the child ACP process

## Why
Bug #4 from the resilience research: `CancellationToken` aborts the executor future, but the spawned ACP child process keeps running. A cancelled pipeline leaves zombie agents holding model API quota. T-174.4's TODO marker explicitly defers the kill to this task.

## Scope
**Crate:** `maenifold-core`. **Files:** `executor_nodes.rs`, `executor_run.rs`, plus a new test file.

## Acceptance
- AC-1: When a node task is cancelled (cancel branch of the biased `select!`), the spawned ACP `Child` (and any owned MCP subprocess) is killed via `Child::kill().await` followed by `wait().await`.
- AC-2: Verified end-to-end: launch a real ACP agent through a tool node, cancel mid-prompt, then assert no child process matching the agent binary path remains (`pgrep -f`-equivalent in the test).
- AC-3: Kill is best-effort — if the child has already exited, log at `debug` and continue. No panics, no error propagation.
- AC-4: Tested on a node that was already in `Active` and on one that was still in the dispatch path (race coverage).
- AC-5: Existing pipeline tests still pass.
- AC-6: Removes the TODO marker added by T-174.4.
- AC-7: `cargo build --release -p maenifold-cli`.

## Forbidden
- `pkill`, `killall`, or any name-based killing — process IDs only.
- Touching retry / backoff logic — that is T-174.6.
- Mocks or fake processes — use a real spawned agent in the test.
