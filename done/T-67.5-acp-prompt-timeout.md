# T-67.5: Add Prompt Timeout and Cancel Support

## Requirement
FR-50 — ACP operations must have configurable timeouts to prevent indefinite blocking.

## Problem
- `_timeout` parameter in `AcpxDriver::new()` is dead code (underscore-prefixed, never used)
- No `tokio::time::timeout` wraps any `conn.prompt()`, `conn.new_session()`, or other operation
- `cancel()` (ACP notification to abort a running prompt) is never called
- A hung agent blocks a pipeline node forever with no escape

## Acceptance Criteria
1. `SessionOpts` must include `timeout_seconds: Option<u64>` with a sensible default (300s)
2. `AgentHandle::prompt()` must wrap with `tokio::time::timeout`
3. On timeout, `cancel()` notification must be sent to the agent
4. After cancel, the session should be closed and error returned
5. Remove the dead `_timeout` parameter from `AcpxDriver`
6. Pipeline nodes should be able to specify timeout per-node

## Files to modify
- `crates/maenifold-core/src/acp/native.rs` — timeout wrapping, cancel support
- `crates/maenifold-core/src/workflow/pipeline/types.rs` — optional timeout field on nodes
- `crates/maenifold-core/src/workflow/pipeline/types_wire.rs` — wire format for timeout

## Reference
- `agent-client-protocol` `CancelNotification` type
- Standard pattern: `tokio::time::timeout(Duration, conn.prompt(...))`

## Tests
- All existing tests must pass
- Verify timeout fires and cancel is sent (unit test with mock or integration test)

Test count 234→236 confirms net addition.

**Red-team focus areas:**

- **CancelNotification before close_session**: ✅ Correct order in `cleanup_timed_out_prompt` (`mod.rs:502-512`): `cancel()` → `close_session()`.
- **Timeout scope**: ✅ Wraps `handle_prompt` only; `handle_new_session` is outside the timed region.
- **Error distinguishability**: ⚠️ Caveat. Timeout surfaces as `AgentError::Acp(String)` — the same variant used for all ACP transport errors — rather than a dedicated `AgentError::Timeout` variant. The timed-out session is detected by string-matching `message.contains("timed out")` (`mod.rs:355`). If an agent itself returns an ACP-level error whose message happens to contain the substring "timed out", the session-timeout tracking entry would be prematurely removed. The functional blast radius is small (next prompt for that session falls back to the 300s default), and no double-cancel occurs (cleanup_timed_out_prompt is only called from the Err branch of `run_with_timeout`). Not a spec violation, but a robustness gap.
- **All `SessionOpts` construction sites updated**: ✅ Every call site that accepts user-controlled timeout now threads it through. `runner.rs:69-75` passes `timeout_seconds` to the primary workflow driver session. Sites that hard-code `None` (`runner.rs:155`, `think_runner.rs:124`, `handlers.rs:189`) are internal sub-sessions where no per-node override applies; they correctly fall back to the 300s default via `resolved_timeout_seconds()`.
- **Timeout preserved in fork**: ✅ `handler_surgery_fork.rs:81-132` preserves `timeout` for all three node types that carry it.
- **Very short timeout on cancel path**: ⚠️ Known limitation. `cleanup_timed_out_prompt` has no timeout of its own; if the agent is hung, `cancel()` and `close_session()` can themselves block indefinitely. The SWE notes acknowledge this. Not a spec requirement, but worth flagging for future hardening.

**One behavioural note** (not a rejection criterion): `maybe_run_step_thinking()` in `runner.rs` spawns a think sub-session inside a workflow node with `timeout_seconds: None` (line 155), so embedded think sub-sessions always use the 300s default even when the parent pipeline node declares a shorter timeout. This is an underdocumented boundary condition rather than a bug.
