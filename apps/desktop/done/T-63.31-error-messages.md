# T-63.31 — Backend: Error Messages + Validation

**Requirement**: FR-11
**Test Cases**: TC-23
**Repo**: maenifold-rs
**Component**: crates/maenifold-core/src/workflow/pipeline/handler.rs, types.rs

## Context

Missing `type` field produces misleading error "missing workflowId" because it defaults to Workflow which requires workflowId. Users submitting Prompt/ST/Tool nodes without `type` get a confusing error.

## Acceptance Criteria

1. Improve deserialization error: when a node is missing both `type` AND `workflowId`, produce error: `"Node '{id}': missing 'type' field. Expected one of: workflow, prompt, sequentialThinking, tool"`
2. When `type` is present but unrecognized, produce error: `"Node '{id}': unknown type '{value}'. Expected one of: workflow, prompt, sequentialThinking, tool"`
3. Validate required fields per type at handler level with clear per-field errors:
   - Workflow: `workflowId` required, `agent` required
   - Prompt: `prompt` required (non-empty), `agent` required
   - SequentialThinking: `topic` required (non-empty), `agent` required
   - Tool: `toolName` required (non-empty), `agent` required
4. ALL existing pipeline tests pass: `cargo test -p maenifold-core -- pipeline`
5. Add a test: submit node without `type` field → clear error message about missing type

## Red-Team Audit

### Findings

- ✅ **AC1 (missing type error)**: `types.rs` `TryFrom<PipelineNodeWire>` returns `"Node '{node_id}': missing 'type' field. Expected one of: workflow, prompt, sequentialThinking, tool"` when `kind` is `None` and `workflow_id` is also `None`. Legacy backward-compat path preserved (no `type` + has `workflowId` → treated as workflow). Test `node_without_type_and_without_workflow_id_gives_clear_error` exercises the path and asserts node id, "missing 'type' field", and all expected type names appear in the message.

- ✅ **AC2 (unknown type error)**: `other =>` arm in `TryFrom<PipelineNodeWire>` returns `"Node '{node_id}': unknown type '{other}'. Expected one of: workflow, prompt, sequentialThinking, tool"`. Test `node_with_unknown_type_gives_clear_error` asserts node id, "unknown type", and the bad value all appear.

- ❌ **AC3 (Workflow `agent` not validated)**: `mod.rs` `validate_node_semantics` validates `workflowId` for Workflow nodes but does NOT validate `agent` (`acp_client`). Spec explicitly lists "Workflow: `workflowId` required, `agent` required." The field is `Option<String>` in the struct, and the same gap exists on `dagv2`—this is a carried-forward pre-existing omission, not a regression—but the spec requires it and it was not implemented. Prompt, SequentialThinking, and Tool all correctly validate both their required fields.

- ✅ **AC3 (Prompt/ST/Tool fields)**: All other type-level required-field validations are present and produce per-field messages of the form `"Pipeline node '{id}': field '{name}' must not be empty"` via `validate_non_empty_node_field`. Non-empty checks are enforced. `totalThoughts > 0` guard for ST is preserved.

- ✅ **AC4 (existing tests)**: `pipeline_pause_and_pipeline_resume_updates_status` fails with `left: Some("stuck") right: Some("paused")` on BOTH `dagv2` and `swe/T-63.31-error-messages` — confirmed pre-existing failure. All other pipeline unit tests: **116 passed, 1 pre-existing failed**, 0 new regressions introduced.

- ✅ **AC5 (missing-type test)**: `node_without_type_and_without_workflow_id_gives_clear_error` added in `types.rs` tests block. Covers the required scenario and asserts all three required message components.

### Scope Creep Findings

- ⚠️ **T-63.11 territory pre-empted — Tool execution stub ignores `tool_name`**: `executor.rs` wires `NodeExecutionRequest::Tool` through the full execution path but the execution handler destructures as `tool_name: _tool_name` (underscore-suppressed) and calls `run_prompt_node(&ctx, &agent, &session_id, &prompt, "disabled")`. The `tool_name` field is silently discarded at runtime. This is not a T-63.31 concern (validation still works), but it pre-empts T-63.11 with a stub that **must** be replaced before Tool nodes are useful. T-63.11 cannot treat executor.rs as a clean slate — it must patch this stub.

- ⚠️ **Out-of-scope behavior change — `classify_think_result`**: `executor.rs` changes SequentialThinking nodes that complete without a conclusion from `NodeOutcome::Abandoned` to `NodeOutcome::Completed(SEQUENTIAL_THINKING_NO_CONCLUSION_MESSAGE)`. This is not mentioned in T-63.31 acceptance criteria and alters pipeline state-machine semantics. Effect: an ST node that would previously have left downstream nodes ungated (Abandoned propagation) now completes with a synthetic string, potentially enabling `success` edges that should have been blocked. Not a T-63.31 scope item. Recommend the PM decide whether this should be promoted into T-63.31 criteria or reverted.
