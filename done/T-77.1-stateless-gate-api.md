# T-77.1: Stateless Gate Board API — Remove Bound Gate

## Context

The gate board HTTP server currently requires a "bind" step: the client must POST `gate_sync` with a `root` argument to bind a project root to the MCP session before `gate_status` will return results. This is single-project, stateful, and fragile — a page refresh loses the binding, and you cannot query two projects without re-binding between them.

The registry (`~/Library/Application Support/com.ma-collective.gate/registry.json`) already maps project names to root paths. The URL already carries `?gate=project-name`. The bind step adds nothing.

## Requirements

1. **Every MCP tool call accepts an explicit `root` or registry name** — no implicit session state
2. **`gate_status` resolves the project root from the registry** when given a name instead of a path
3. **`gate_sync` no longer binds** — it syncs the specified root and returns. No session mutation.
4. **The board URL `?gate=name` resolves directly from the registry** — the frontend fetches status by passing the registry name, not by first binding
5. **Multiple projects can be queried in the same session** without re-binding
6. **Remove all session-bound gate state** from the HTTP server — no `BoundGate`, no session map, no implicit root
7. **All existing tests pass** after the change
8. **Board UI continues to work** — the frontend adapts to pass `root`/name on every API call

## Acceptance Criteria

- [ ] `gate_status` works without a prior `gate_sync` call (given a valid root or registry name)
- [ ] Two different projects can be queried in sequence without re-binding
- [ ] Page refresh does not break the board
- [ ] `gate_sync` is purely a sync operation — no session side effects
- [ ] All board_tests pass
- [ ] No `BoundGate` or equivalent session state remains in the codebase

## SWE Remediation

- Removed MCP/session-bound gate root state from `mcp/tools.rs`, `mcp/mod.rs`, and `mcp/http.rs`.
- Simplified dispatch so every tool call executes only against explicitly provided arguments.
- Updated board frontend to stop binding via `gate_sync` and instead pass `root` on each `gate_status` call.
- Updated MCP tool tests for the stateless dispatch API.

## Scope

### In scope
- `crates/maenifold-gate/src/board/` — HTTP handler, MCP tool dispatch
- `crates/maenifold-gate/src/registry.rs` — registry lookup
- Board frontend JS (if it sends bind calls)

### Out of scope
- Gate CLI (`gate sync`, `gate status` commands) — these already take explicit roots
- Pipeline UI — separate project
- Multi-board simultaneous rendering (future enhancement)

### Check 2 — `dispatch()` signature in `mcp/tools.rs` ✅

```rust
pub fn dispatch(name: &str, args: &mut Map<String, Value>) -> Result<DispatchResult, String>
```

Correct. No `bound_root` parameter. Takes only tool name and caller-supplied arguments. No global or shared mutable state accessed.

**Minor observation (Low, not blocking):** `prepare_args` for `gate_sync` performs a redundant validate-then-reinsert of `root`:

```rust
"gate_sync" => {
    let root = required_string(args, "root")?;
    args.insert("root".into(), Value::String(root.clone()));
    Ok(())
}
```

`required_string` removes the key; it is immediately put back. The key is then consumed again in `dispatch_impl`. This double-validation is harmless but dead weight — the validation in `dispatch_impl` (`required_string(args, "root")?`) is already authoritative. Not a correctness issue; the worst case is a redundant error message if `root` is absent.

---

### Check 3 — `board_api()` in `mcp/http.rs` — stateless dispatch ✅

`board_api` constructs `arguments` from the request body and calls:

```rust
super::tools::dispatch(&tool_name_for_dispatch, &mut arguments)
```

No session map, no bound root lookup. `AppState` contains only a `TraceBuffer` (a capacity-bounded ring buffer for debugging; read-only from the API perspective — it has no effect on dispatch logic). `NeverSessionManager` is used, guaranteeing the MCP layer never establishes session affinity. Each request is fully independent.

---

### Check 4 — `call_tool()` in `mcp/mod.rs` ✅

```rust
let result = tokio::task::spawn_blocking(move || {
    self::tools::dispatch(&tool_name_for_dispatch, &mut arguments)
})
.await
```

No `bound_root` lock, no `requires_bound_root` guard, no session extension consulted beyond tracing metadata (session ID is read only for the trace log, never used to gate dispatch). Clean.

---

### Check 5 — Board `index.html`: `ensureBoundGate()` deleted, explicit `root` on every call ✅

`ensureBoundGate` does not exist anywhere in the file. All `gate_status` invocations pass an explicit `root`:

- **`loadTasks` (single-gate path):** `callGateTool("gate_status", { root: gate.root })`
- **`loadTasks` (show-all path):** `state.gates.map(gate => callGateTool("gate_status", { root: gate.root }))` — parallel per-gate calls, each with its own root.
- **`loadTaskDetail`:** `callGateTool("gate_status", { id: summaryTask.id, root: gate ? gate.root : undefined })`

No `gate_sync` bind calls exist anywhere in the frontend.

---

### Check 6 — Multi-project query ✅

`loadTasks()` with `showAll = true` fans out to `Promise.all(state.gates.map(...))`, calling `gate_status` with a different `root` per gate. Because there is no session state, each call is independent. Two projects can be queried simultaneously in the same browser session without re-binding. Confirmed at both the frontend and server layers.

---

### Check 7 — Page refresh ✅

`NeverSessionManager` rejects any attempt to create or resume an MCP session (`create_session`, `has_session`, `close_session` all return `Err`). The `stateful_mode: false, json_response: true` config on `StreamableHttpService` means no SSE session is established and no `Mcp-Session-Id` affinity is maintained.

On page refresh, `state.selectedGate` is re-read from `window.location.search` (`?gate=name`) and `loadTasks()` is called immediately — the page bootstraps correctly with no prior server state required.

---

### Check 8 — `gate_sync` has no session side effects ✅

`gate_sync` in `dispatch_impl` invokes `gate sync <root> [--rebuild]` as a subprocess and returns stdout/stderr. The server holds no state before or after the call. The `prepare_args` detour validates `root` but does not write to any shared structure. Confirmed: purely a sync operation.

---

### Minor Finding — `loadTaskDetail` can send `root: undefined` (Low, not blocking)

```javascript
const gate = state.gates.find(item => item.name === summaryTask.gateName);
const detail = await callGateTool("gate_status", {
  id: summaryTask.id,
  root: gate ? gate.root : undefined   // ← undefined if gate was removed from registry
});
```

If a gate is deregistered between `loadTasks` and a user clicking a task card, `gate` will be `undefined`, and `root: undefined` is omitted from the JSON object (JSON.stringify drops `undefined` values). The server receives `gate_status { id: "T-XX" }` with no `--root` flag — the CLI falls back to CWD, which may or may not match the project. The result is a degraded but graceful error response, not a crash or security issue. The happy path (gate still registered) is unaffected.

**Recommendation:** Replace `undefined` with a thrown error or a no-op early return so the UI surfaces a clear "gate no longer available" message rather than silently querying the wrong directory.
