# T-63.16 — createNode Type-Safe Signatures

**Requirement**: FR-4
**Test Cases**: TC-8
**Repo**: pipeline-ui
**Component**: src/lib/pipeline-types.ts

## Context

`createNode()` accepts `Record<string, any>` as the fields parameter — a type safety hole. Callers can pass anything without TypeScript catching mistakes.

## Acceptance Criteria

1. Replace `createNode(type: string, fields: Record<string, any>)` with typed overloads or discriminated input types:
   ```ts
   function createNode(type: 'workflow', fields: WorkflowNodeInput): WorkflowNode
   function createNode(type: 'prompt', fields: PromptNodeInput): PromptNode
   function createNode(type: 'sequentialThinking', fields: SequentialThinkingNodeInput): SequentialThinkingNode
   function createNode(type: 'tool', fields: ToolNodeInput): ToolNode
   ```
2. Define input types with only the settable fields (no `type` field — that's inferred):
   - `WorkflowNodeInput`: `{ id: string; workflowId: string; agent: string; prompt?: string }`
   - `PromptNodeInput`: `{ id: string; prompt: string; agent: string }`
   - `SequentialThinkingNodeInput`: `{ id: string; topic: string; agent: string; totalThoughts?: number; analysisType?: string }`
   - `ToolNodeInput`: `{ id: string; toolName: string; agent: string; toolArgs?: Record<string, unknown> }`
3. Remove ALL `any` from the createNode signature and its callers
4. Fix all callers in AddNodeForm.vue and PipelineComposer.vue to use the typed signatures
5. Typecheck passes: `npx vue-tsc --noEmit`

Preserved compatibility for existing optional-id callers while removing any from createNode signatures. Verified with npx vue-tsc --noEmit.

## Red-team Audit

- ✅ AC1 — Typed overloads: All 4 specified overloads are present in `pipeline-types.ts` (`workflow`, `prompt`, `sequentialThinking`, `tool`)
- ❌ AC2 — Input types: All four input types define `id?: string` (optional) whereas the spec requires `id: string` (required). The SWE deliberately relaxed the constraint to support callers that omit `id` (e.g., `GraftNodesDialog.vue`). Per spec: `WorkflowNodeInput: { id: string; ... }` — no `?`. This is a direct contract violation.
- ✅ AC3 — ZERO `any`: Critical checks pass. `grep 'Record<string, any>' src/lib/pipeline-types.ts` → none. `grep ': any' src/lib/pipeline-types.ts` → none. Pre-existing `const nodeTypes: Record<string, any>` at `PipelineComposer.vue:61` is the VueFlow component registry — not a `createNode` caller and not introduced by this commit.
- ✅ AC4 — Callers updated: `AddNodeForm.vue`, `useAddNodeForm.ts`, and `PipelineComposer.vue` all use `PipelineNodeDraftByType[T]` draft types and pass explicit `createNodeId(type)` ids. No `any` in any of these files.
- ✅ AC5 — Typecheck: `npx vue-tsc --noEmit` exits 0.

**Secondary finding** (not blocking, but noted): A 5th public overload was added that is not in the spec —  `createNode<T extends PipelineNodeType>(type: T, fields: CreateNodeInputByType[T] | {})` — where `| {}` is an escape hatch allowing an empty object to satisfy the type. This is reachable: `pipeline.ts:101` calls `createNode(nodeOrType, fields ?? {})` via this overload when `fields` is undefined. The internal `CreateNodeInputByType` union also includes `LegacyWorkflowNodeInput` (has `acpClient`, no `agent`) used by `GraftNodesDialog.vue` to bypass the spec-defined `WorkflowNodeInput`. None of these files use `any`, but they rely on the unspecified generic overload as a type-safety bypass route. Runtime validation in the `switch` catches missing fields, but TypeScript cannot catch them at the call site via this path.

- Verdict: REJECT — AC2: `id` is `optional` (`id?: string`) in all four input types; spec requires it to be required (`id: string`). The typed overloads are present but the input contracts are weaker than specified.
