# Tools-Only Gateway Surface Contract

## Purpose

This document defines the tools-only public MCP surface for the Maenifold gateway.
The contract intentionally separates the tiny public `tools/list` surface from the
larger capability catalog behind deterministic gateway commands. It is a design
contract only; implementation changes happen in later tasks.

## Target public contract

When fully implemented, default `tools/list` advertises only the portable
tools-only control plane.

### Baseline tools: always present

| Tool | Purpose | Contract notes |
|------|---------|----------------|
| `GatewayIndex` | Inspect domains, commands, schemas, examples, and safety policy. | Deterministic discovery. Must be sufficient for clients without MCP resources, prompts, sampling, or dynamic discovery. |
| `GatewayExecute` | Execute one exact selected domain command. | Deterministic execution only. No natural-language intent resolution. |
| `GatewayBatch` | Submit and inspect deterministic exact-command batches. | Covers submit/status for exact command invocations, not intent routing. |
| `ReadMcpResource` | Tool-mediated resource read. | Existing tool preserved so tools-only clients can reach resource content. |
| `GetHelp` | Standalone human/agent help. | Existing tool preserved as a flat public exception and exempt from gateway routing and hard-cut removal. |

Intent disabled public total: **5 tools**.

### Conditional tool: intent enabled only

| Tool | Purpose | Advertise only when |
|------|---------|---------------------|
| `GatewayIntent` | ACP-backed intent resolver that proposes route candidates or, for safe read-only paths, may resolve a configured exact route according to policy. | Intent routing is enabled in configuration and a valid ACP/Jockey resolver agent is configured and healthy. |

Intent enabled public total: **6 tools**.

`GatewayIntent` must be omitted from `tools/list` when intent routing is
disabled, not configured, or missing a valid ACP/Jockey resolver agent. It must
not appear as a disabled placeholder.

## Contract rules

1. **Tiny tools-only baseline.** The portable baseline is deterministic
   `GatewayIndex` + `GatewayExecute`, plus `GatewayBatch`,
   `ReadMcpResource`, and `GetHelp`.
2. **First-party domains are routed.** Gate and Maenifold capabilities are
   routed domains, not permanent flat exceptions. Only `GetHelp` and
   `ReadMcpResource` remain standalone baseline tools.
3. **Optional client features cannot be required.** MCP resources, prompts,
   sampling, roots, elicitation, and dynamic discovery are optional client
   features. Core operation must work for tools-only clients through
   `GatewayIndex`, `GatewayExecute`, `GatewayBatch`, and `ReadMcpResource`.
4. **Deterministic execution is the baseline.** `GatewayExecute` accepts an
   exact domain command selected from `GatewayIndex`; it does not guess from
   natural language.
5. **Batch is deterministic only.** `GatewayBatch` covers deterministic
   exact-command submit/status operations. It does not accept ambiguous natural
   language and does not run the ACP intent resolver.
6. **Intent is optional and ACP-backed.** `GatewayIntent` is backed by a
   configured ACP/Jockey resolver agent. It is omitted when disabled or invalid.
7. **Mutations require exact execution.** Mutating commands require explicit
   exact execution through `GatewayExecute` with validated parameters. Intent
   resolution may return candidates and safety notes for mutating commands, but
   must not silently execute them.
8. **Ambiguous intent does not execute.** If `GatewayIntent` cannot resolve a
   single safe route under policy, it returns ranked candidates and discovery
   guidance instead of executing.
9. **No duplicated metadata.** Domain command names, schemas, descriptions,
   examples, and safety annotations must be generated from or layered onto the
   existing registries. The gateway must not introduce duplicate hand-maintained
   schema tables.
10. **Existing help stays standalone.** `GetHelp` is preserved as the existing
    help tool. It is exempt from gateway routing and from hard-cut flat-tool
    removal.

## Safety policy for routed commands

`GatewayIndex` must expose enough safety metadata for clients and agents to
choose the correct path before execution.

| Command class | Examples | Required path |
|---------------|----------|---------------|
| Read-only / inspect | `SearchMemories`, `ReadMemory`, `BuildContext`, `Visualize`, `MemoryStatus`, gate `status`, gate `history`, upstream read-only commands | `GatewayExecute` exact command; `GatewayIntent` may propose or resolve only if enabled and policy allows. |
| Mutating first-party | `WriteMemory`, `EditMemory`, `DeleteMemory`, `MoveMemory`, `RepairConcepts`, `UpdateAssets`, `Sync`, gate `append`, gate `pass`, gate `fail`, gate `sync` | `GatewayExecute` exact command with validated parameters. Intent may only return candidates. |
| Orchestration / agent dispatch | `Workflow`, `Pipeline`, `SequentialThinking`, `AssumptionLedger`, `AcpExec`, `TeamsMonitor`, `Schedule` | `GatewayExecute` exact command. Intent resolver must surface risks and may not auto-grant ACP permissions. |
| Upstream commands | Any command under `upstream.*` | Policy derived from upstream metadata when available; otherwise default to exact `GatewayExecute` and conservative no-auto-mutate behavior. |

| Native graph schemas | `crates/maenifold-core/src/mcp/schema/graph_tools.rs` and associated params modules |

| Gate commands and schemas (target) | `crates/maenifold-core/src/mcp/schema/gate_tools.rs` after T-237.1g |
| Upstream tool routing | `ToolRoutingRegistry`, `StdioPool`, and discovery through configured upstream MCP servers |
| Upstream consolidation / facade behavior | `crates/maenifold-core/src/mcp/gateway_consolidation.rs` and `gateway_dispatch.rs` |
| Resources | `crates/maenifold-core/src/mcp/resources/*` plus existing resource routing/collision ownership rules |
| Tool-mediated resource reads | Existing `ReadMcpResource` native tool and resource routing implementation |
| Standalone help | Existing `GetHelp` native tool and help assets |

## Generated metadata requirement

Gateway domain catalogs must be generated from the canonical sources above:

- Command names come from `ToolRegistry::canonical_names()` / `DESCRIPTORS`
  or upstream discovery.
- Input schemas come from `crates/maenifold-core/src/mcp/schema/*_tools.rs`
  or upstream `tools/list`.
- Upstream command catalogs come from `StdioPool` discovery and the routing
  registry.
- Resource indexes come from the resource modules and routing registry.

Any additional gateway-only annotations, such as safety classification or
examples, must be attached as generated overlays keyed by canonical command
identity. They must not fork the command metadata or schema definitions.
