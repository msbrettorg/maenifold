# T-221.2 - Deterministic Gateway Index and Execute

## Problem

The current per-server facade model still leaves too many advertised tools and relies on facade-local matching. A tools-only client needs a single deterministic catalog and exact execution path.

## Scope

Implement the deterministic baseline:

- `GatewayIndex` returns domains, commands, descriptions, safety class, input schemas, examples, and resource links.
- `GatewayExecute` accepts exact domain, command, and parameters.
- Hidden upstream tools and old facade commands cannot bypass the gateway contract.
- Small-server passthrough from T-216.5 is removed or converted into indexed commands.

## Input Contract

`GatewayIndex`:

- `domain` optional
- `command` optional
- `includeSchemas` optional
- `includeExamples` optional

`GatewayExecute`:

- `domain` required
- `command` required
- `parameters` required object
- `idempotencyKey` optional for mutating commands

## Reuse and Validation Policy

Implementation must introduce one deterministic `GatewayCatalog`/registry abstraction and reuse it for:

- `GatewayIndex`
- `GatewayExecute`
- `GatewayIntent` candidate validation
- `GatewayBatch` (future T-221.10)
- gateway resource views from T-221.8

The catalog must project existing sources instead of duplicating command metadata:

- Native tool metadata via `list_mcp_tools()` / `mcp_tool_from_registry_name()` (public accessors for the private `DESCRIPTORS` const)
- existing `ToolRoutingRegistry`
- existing `ToolRegistry::try_invoke()` for native dispatch
- existing `schemars`-generated native schemas via `mcp::schema` module
- Gate and upstream MCP tools discovered at runtime via `StdioPool` / `ConsolidatedServerTool` — NOT cross-crate compile-time reference (maenifold-core cannot depend on maenifold-gate)

Validation policy:

- Native Maenifold tools prefer typed `Deserialize` validation already used by handlers.
- Native generated schemas continue to come from `schemars`; schemas are not copied by hand.
- Upstream arbitrary MCP tool schemas either preserve upstream validation/error metadata or use the mature `jsonschema` crate with minimal/default-disabled features if strict local validation is required.
- No custom JSON Schema validator may be introduced.
- `validate_dispatch_parameters` in `gateway_dispatch.rs` is currently private; either make `pub(crate)` or reuse via `dispatch_facade_call()` which already calls it.

**GatewayBatch has been moved to T-221.10.** The batch state policy is documented there.

## Acceptance Criteria

- [ ] `GatewayIndex` lists all routed domains without exposing each command as an MCP tool.
- [ ] `GatewayIndex` can return a single command schema by domain and command.
- [ ] `GatewayIndex`, `GatewayExecute`, and future consumers (GatewayIntent, GatewayBatch, gateway resources) share the same deterministic catalog/registry.
- [ ] Gateway execution validates via existing typed handlers and existing schemas; no hand-rolled JSON Schema validator is introduced.
- [ ] `GatewayExecute` dispatches exact commands to the correct native, Gate, Maenifold, or upstream handler.
- [ ] Direct calls to hidden upstream/native routed commands return a clear "use GatewayExecute" error.
- [ ] Small-server passthrough no longer increases tools/list count.
- [ ] Input validation rejects unknown domain, unknown command, missing parameters, and schema mismatch.
- [ ] Operational upstream errors preserve their original error class and metadata where available; they are never collapsed into not-found.
- [ ] Existing gateway resource routing from T-218.20 remains compatible.
- [ ] `cargo build --release -p maenifold-cli` succeeds.

### Phase 1: LOC Extraction Prerequisite

Extract from `mod.rs` to create headroom:
- Move `localhost_cors()` (lines 24-46, ~23 LOC) into a new `cors.rs` file (NOT `http.rs` — already at 283 LOC)
- Keep `initialize_runtime()` in `mod.rs` (only 6 LOC — not worth inlining into callers since `http.rs` would need modification)
- Add `mod cors;` declaration
- Target: mod.rs ≤ 276 LOC (299 - 23 for cors extraction)

### Phase 2: GatewayCatalog Abstraction

**New:** `gateway_catalog.rs`
- `DomainEntry`: name, description, command_count
- `CommandEntry`: name, description, schema (from existing schemars output), safety_class
- `GatewayCatalog`: builds from existing sources:
  - `list_mcp_tools()` / `mcp_tool_from_registry_name()` for native maenifold tool metadata (NOT `ToolRegistry::DESCRIPTORS` directly — that const is private)
  - Gate and upstream tools discovered at runtime via `StdioPool` / `ConsolidatedServerTool` (runtime discovery, NOT cross-crate compile-time reference)
  - `ToolRoutingRegistry` for routing resolution
- **Key constraint:** Project/reference existing data — do NOT duplicate schemas or metadata

### Phase 3: Tool Registration and Schemas

**New:** `mcp/schema/gateway_tools.rs`
- GatewayIndex params (matches Input Contract above)
- GatewayExecute params (matches Input Contract above)
- schemars derive for JSON schema generation

**Modified:** `mcp/schema/mod.rs` — add `mod gateway_tools;` and wire into schema lookup

**Dispatch architecture:** GatewayIndex/GatewayExecute are NOT registered in `ToolRegistry::DESCRIPTORS`. They are gateway-owned tools because:
- `GatewayExecute` needs async `StdioPool` access for upstream dispatch
- `ToolRegistry::try_invoke()` is synchronous (runs in `spawn_blocking`) with no gateway context
- Instead, `GatewayState` owns the tool definitions and advertises them via `GatewayState::list_tools()`
- `MaenifoldHandler::call_tool` flow remains: `try_invoke` → if `UnknownTool` → `gateway.handle_tool_call`
- `gateway.handle_tool_call` matches GatewayIndex/GatewayExecute FIRST, then falls through to existing facade dispatch
- This replaces per-server facade tools in `GatewayState::list_tools()` with GatewayIndex/GatewayExecute

### Phase 4: GatewayExecute Dispatch

Route `domain + command` to the correct handler:
- Native tools: `ToolRegistry::try_invoke()` (existing typed Deserialize validation)
- Upstream tools: make `validate_dispatch_parameters()` in `gateway_dispatch.rs` `pub(crate)`, then reuse + `pool.call_tool()` (existing gateway_handler.rs path)
- Gate tools: existing gate tool routing
- **Note:** `validate_dispatch_parameters` is currently private in `gateway_dispatch.rs:129`. Either make `pub(crate)` or reuse via `dispatch_facade_call()` which already calls it.

### Phase 5: Migration

- `mod.rs` `list_tools`: stop extending with `gateway.list_tools()` passthrough/consolidated
- `gateway_handler.rs`: update `hidden_tool_facades` to redirect to "use GatewayExecute"
- `gateway_consolidation.rs`: facade tool generation becomes internal catalog data only
- Verify passthrough tools no longer appear in `tools/list`

### Contingency: LOC Overflow

If Phase 1 extraction is insufficient for mod.rs headroom:
- Phase 5 migration (removing `gateway.list_tools()` call) provides additional LOC reduction
- If gateway_handler.rs exceeds 295 LOC, extract hidden-tool redirect logic to a helper function in the same module
