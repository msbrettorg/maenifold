# T-45.4: Workflow Session Status Lifecycle

**Requirement**: FR-45.4
**RTM**: RTM-325, RTM-326, RTM-327, RTM-328
**Priority**: P0 — Required before pipeline can manage session state

## Context

Currently workflow sessions use `status: active` → `completed`/`cancelled`. The pipeline engine needs richer status values: `pending`, `ready`, `active`, `completed`, `abandoned`. The `continue_workflow_session` function must gate on status to prevent operating on sessions that aren't `active`.

## Scope

Modify `crates/maenifold-core/src/workflow/handler.rs` to:
1. Accept the full status enum in frontmatter
2. Gate `continue_workflow_session` on session status

## Acceptance Criteria

1. **Extended status values**: Workflow session frontmatter accepts `pending`, `ready`, `active`, `completed`, `abandoned` as valid `status` values. No validation errors on read.
2. **Gate on pending**: `continue_workflow_session` SHALL reject sessions with `status: pending` with a clear error message: `"Session {id} is pending — cannot continue until activated"`.
3. **Gate on completed**: `continue_workflow_session` SHALL reject sessions with `status: completed` with a clear error message: `"Session {id} is already completed"`.
4. **Gate on abandoned**: `continue_workflow_session` SHALL reject sessions with `status: abandoned` with a clear error message: `"Session {id} is abandoned — use restart to create a new attempt"`.
5. **Active passes through**: Sessions with `status: active` continue to work exactly as before.
6. **Ready passes through**: Sessions with `status: ready` are treated as `active` for continuation purposes (the act of continuing an ready session implicitly activates it — update status to `active`).
7. **Backward compatibility**: Existing sessions without a `status` field or with `status: active` continue to work unchanged.

## Implementation Notes

- `continue_workflow_session` is at `crates/maenifold-core/src/workflow/handler.rs` line ~99
- It receives `session_id` and reads the session file via `read_markdown`
- Add status check after reading frontmatter, before any content modification
- The frontmatter `status` field is read via `frontmatter.get("status").and_then(|v| v.as_str())`
- For criterion 6 (ready → active): update frontmatter status to "active" before proceeding

### Ancillary Observations (non-blocking)

1. **No naming collision between payload `status` and frontmatter `status`**: The `status: Option<&str>` parameter in `continue_workflow_session` (line 105) is the caller-supplied terminal verb (`"completed"`, `"cancelled"`). It is checked at lines 162/172 *after* `gate_workflow_session_status` returns. The gate operates on `frontmatter["status"]` — a distinct variable in a separate function scope. No confusion possible.

2. **`ready` write uses pre-response `existing_content`**: The `gate_workflow_session_status` function writes the promoted frontmatter using `existing_content` captured before the step-response append. The step response is appended afterward in `continue_workflow_session`. This ordering is correct and produces a consistent file.

3. **Unknown status values pass through**: Values not in the enum (e.g., a typo like `"actve"`) silently proceed. The spec is silent on this case and the SWE explicitly documented the choice. No spec violation.
