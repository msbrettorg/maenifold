# T-28.3: Upgrade Relay to JSON-RPC Passthrough

**Requirement**: FR-39 (Replace chrome-acp with ACP UI)

## Context

Our current ACP relay at `crates/maenifold-core/src/acp/relay.rs` speaks the chrome-acp proxy protocol — a custom envelope format with message types like `connect`, `new_session`, `prompt`, `disconnect`. ACP UI speaks raw ACP JSON-RPC (initialize, sessions/new, agent/prompt).

We need to replace the proxy protocol with a transparent JSON-RPC bridge: browser sends JSON-RPC over WebSocket, relay writes it to agent stdin. Agent writes JSON-RPC to stdout, relay sends it to browser. No protocol translation.

Current file: `crates/maenifold-core/src/acp/relay.rs` (~280 lines)

### Current protocol (chrome-acp proxy):
```
Browser → { "type": "connect" } → Relay → spawns agent, runs ACP initialize
Browser → { "type": "new_session", "payload": { "cwd": "..." } } → Relay → sends sessions/new
Browser → { "type": "prompt", "payload": { "content": [...] } } → Relay → sends agent/prompt
Relay → { "type": "status", "payload": { "connected": true } } → Browser
Relay → { "type": "session_update", "payload": { "update": {...} } } → Browser
```

### New protocol (JSON-RPC passthrough):
```
Browser → { "jsonrpc": "2.0", "method": "initialize", ... } → Relay → agent stdin
Agent stdout → { "jsonrpc": "2.0", "result": ... } → Relay → Browser
Agent stdout → { "jsonrpc": "2.0", "method": "notifications/...", ... } → Relay → Browser
```

## Acceptance Criteria

1. **WebSocket at `/ws/acp`** still requires `?agent=<name>` query parameter. Missing or unknown agent → close with error (existing behavior preserved).

2. **Agent spawning**: On WebSocket connect, spawn the selected agent subprocess (command + args from agents.json). Connect stdin/stdout pipes.

3. **Browser → Agent**: Every text WebSocket message from browser is written as a line to agent stdin (+ newline). No parsing, no translation.

4. **Agent → Browser**: Every line from agent stdout is sent as a text WebSocket message to browser. No parsing, no translation.

5. **Agent stderr**: Optionally forward stderr lines as a JSON message: `{"type":"stderr","data":"..."}` — this supports ACP UI's StartupProgress component.

6. **Lifecycle**:
   - WebSocket close → kill agent subprocess
   - Agent process exit → close WebSocket with reason
   - Graceful shutdown on server stop

7. **`/api/agents` endpoint preserved** — returns `[{"name":"...","status":"available"}, ...]`

8. **No `agent-client-protocol` crate dependency needed** — relay is now pure passthrough, no ACP protocol parsing in Rust. Remove the dep from Cargo.toml if it's only used by the relay (check if other modules use it first).

9. **All existing relay tests pass or are updated** to reflect new protocol.

10. **`ProxyMessage`, `WorkerCommand`, `WorkerEvent` enums removed** — these were chrome-acp proxy protocol types. The new relay doesn't need them.

**Non-blocking observations (do not affect verdict):**

1. **`build.rs` still references `vendor/chrome-acp`** (`build.rs:6`): this is the web frontend asset path for the embedded UI, not ACP protocol code. It is outside this spec's stated file scope and predates T-28.3. Worth a separate cleanup ticket when ACP UI fully replaces the chrome-acp frontend.

2. **In-session error messages are not JSON-RPC**: When stdin write or stdout read fails mid-session, the relay sends `{"type":"error","payload":{"message":"..."}}` (relay.rs:79, 112, 130) — a custom control shape, not JSON-RPC. The spec only mandates transparent passthrough for normal ACP traffic (AC#3/AC#4) and does not specify the shape of relay-originated error signals, so this is acceptable. However, ACP UI will need to handle this shape if it ever encounters stdin/stdout I/O failures.

3. **Half-closed stream scenario**: If both stdout and stderr close (EOF) while the agent process has not yet called `exit()`, the `select!` loop continues polling `socket.recv()` and `child.wait()`. Any subsequent browser messages would still be written to stdin (which remains open). Writes to a process that has closed its output will either succeed silently or produce a broken-pipe `Err`, which is caught and closes the socket. This is a benign edge case, not a spec violation.
