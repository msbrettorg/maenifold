# T-48.7 — Component: `WorkflowTreeView`

**Requirement:** FR-48
**Component:** `vendor/acp-ui/src/components/`

## Summary

Main container component that renders the full workflow execution tree using WorkflowNodeCard and ThinkingSessionCard connected with visual hierarchy lines.

## Acceptance Criteria

1. Create `vendor/acp-ui/src/components/WorkflowTreeView.vue`
2. Props: `uri: string` (workflow session memory:// URI)
3. Uses `useWorkflowTree` composable to fetch and resolve the tree
4. Renders the tree top-to-bottom with:
   - Root workflow as a WorkflowNodeCard at the top
   - Submachine ThinkingSessionCards connected below their parent step
   - Child workflows as WorkflowNodeCards connected below the dispatching step
   - Recursive rendering for child workflows (they may have their own submachines)
5. **Connection lines**: SVG or CSS lines connecting parent nodes to children
   - Vertical line from parent step → child node
   - Horizontal bracket when multiple children exist
   - Color-coded: green for workflow→workflow, purple for workflow→thinking
6. **Loading state**: skeleton cards while tree is resolving
7. **Error state**: error message with retry button
8. **Auto-scroll**: horizontally scrollable if tree is wider than viewport
9. Zoom controls or scroll-to-fit would be nice but not required

### Notes / Decisions

- The `WorkflowTreeLevel` component is defined inline in the same SFC (in a second `<script lang="ts">` block) rather than in a separate file. This avoids circular import issues and keeps all tree-view logic in one place. Vue supports multiple `<script>` blocks — `<script setup>` for the outer component props/composable, `<script lang="ts">` for the named export.
- SVG `viewBox` widths are computed from an assumed card width of `300px` + `24px` gap, matching the `320px` width of `WorkflowNodeCard`. If cards reflow, the connector SVGs scale via `overflow: visible`.
- The unused helper functions (`thinkingChildren`, `workflowChildren`, `hasChildren`, `allChildrenWithTypes`) that were scaffolded in `<script setup>` were removed before the final typecheck pass — all logic lives in `WorkflowTreeLevel`.
- Zoom controls are not implemented (marked "nice but not required" in spec).

## Red-team Audit

**Verdict: REJECT**

### Findings

#### 1. AC5 — Multi-child SVG connector: parent drop drawn at wrong x-coordinate **[HIGH]**

**File:** `vendor/acp-ui/src/components/WorkflowTreeView.vue`, lines 154–240

The `renderConnector` function hard-codes the parent card center as `midX = nodeW / 2 = 150` (line 157). This is correct for the single-child path (where the SVG is `nodeW` wide and the parent card fills it), but it is **wrong** for the multi-child path.

**Why it's wrong — layout chain:**

1. `tree-level` uses `align-items: center` (line 325). Its width is determined by its widest child, which is the `children-row` at `totalW = n×300 + (n−1)×24`.
2. `connector-wrapper` is `width: 100%` (line 346) → expands to `totalW`.
3. The multi-connector SVG is `width: totalW` and `justify-content: center` puts its left edge at x = 0 of `connector-wrapper` (and of `children-row`).
4. The parent card (300 px) is `align-items: center`-centered inside the `totalW`-wide `tree-level`, so its SVG x-coordinate is `(totalW − nodeW)/2 + nodeW/2 = totalW/2`.

**Verified with concrete numbers (n = 2, totalW = 624):**

| | Coded | Correct |
|---|---|---|
| Parent drop x | 150 | 312 |
| `childMidXs[0]` | −12 | 150 |
| `childMidXs[1]` | 312 | 474 |
| Bracket bar | x=−12 → x=312 | x=150 → x=474 |

All SVG geometry is shifted **162 px left** of the actual card positions. The error scales: for n=3 the shift is 324 px. Even though `overflow: visible` keeps the lines visible, they do not connect to the child cards below them — the bracket floats entirely off to the left of the actual children for any tree with 2+ children.

**Fix (one line):** Replace line 157

```ts
// before (wrong)
const midX = nodeW / 2;            // 150 — assumes parent fills entire SVG width

// after (correct)
const midX = totalW / 2;           // parent is centred over the full children band
```

With `midX = totalW / 2`, `startX = 0` and `childMidXs[i] = i*(nodeW+gap) + nodeW/2`, which exactly matches card positions in the children-row.

#### 3. `WorkflowTreeLevel` used in template but not imported into `<script setup>` **[MEDIUM / Runtime risk]**

**File:** `vendor/acp-ui/src/components/WorkflowTreeView.vue`, line 81 (template) vs line 105 (`<script>` block)

`WorkflowTreeLevel` is a named export from the non-`setup` `<script>` block. It is not imported inside `<script setup>`. In Vue 3 SFC, only bindings declared inside `<script setup>` are automatically available as template components. Named exports from a sibling `<script>` block are module-level exports for *consumers*, not auto-registered template components.

`vue-tsc --noEmit` exited 0, which provides partial confidence, but the Vue SFC compiler may emit a `resolveComponent('WorkflowTreeLevel')` call that falls back to a globally registered component at runtime — which doesn't exist, causing a silent "Unknown custom element" warning and a blank tree at runtime.

The safe fix is to import the component at the top of `<script setup>`:
```ts
import { WorkflowTreeLevel } from './WorkflowTreeView.vue';
// or move WorkflowTreeLevel to its own file and import it here
```
