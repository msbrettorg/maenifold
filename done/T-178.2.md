# T-178.2 — MCP resources/subscribe + notifications/resources/updated plumbing

## Intent

Maenifold's MCP server already implements `resources/list` and `resources/read` and advertises `enable_resources_list_changed`. It does NOT implement `resources/subscribe` or emit `notifications/resources/updated`. Per the [[Model Context Protocol]] 2025-06-18 spec, subscriptions are how clients (UI, agents) get push notifications when watched resource state changes. Add this primitive so resources can become the canonical state-streaming surface for the dashboard and other clients.

This task is plumbing only. URI registration for graph state lands in [[T-178.3]].

Reference: https://modelcontextprotocol.io/specification/2025-06-18/server/resources

## Pre-flight spike (BEFORE SWE starts implementation)

This task touches rmcp's notification surface, which is moving fast. Before SWE writes production code, complete a < 30-minute spike to confirm the rmcp 1.4.0 API for the three things this task assumes:

1. **Subscribe builder method name** on the server capability builder — confirm whether it is `enable_resources_subscribe()`, `with_resources_subscribe()`, a struct field, or something else. Pin the exact symbol used.
2. **Per-session peer access inside resource handlers** — confirm the mechanism for obtaining the current session's notification sink (peer / sender / similar) from within a `resources/subscribe` handler so we can store a delivery handle, not just an opaque session id.
3. **Session-end lifecycle hook** — confirm how rmcp signals session shutdown / disconnect so the registry can clean up automatically. If no hook exists we must add a wrapping layer; the spike must surface that.

Spike output goes into the task history as either "API confirmed: <symbols>" or "Adjustment required: <plan>". Implementation does not start until the spike is recorded.

## Scope

1. Update `crates/maenifold-core/src/mcp/mod.rs::get_info`:
   - Add the rmcp builder method confirmed in the spike (e.g. `enable_resources_subscribe()`) to both `Stdio` and `Http` capability sets.
2. Implement `resources/subscribe` and `resources/unsubscribe` handlers in `crates/maenifold-core/src/mcp/resources.rs`:
   - Subscription registry: `Arc<Mutex<HashMap<ResourceUri, HashMap<SessionId, NotificationSink>>>>` (or equivalent thread-safe shape). The registry stores `(SessionId, notification delivery handle)` pairs — NOT just URIs and not just session IDs. The delivery handle is whatever rmcp surfaces in the spike for sending notifications back on a specific session's transport.
   - On subscribe: validate URI exists in the resource catalog, register pair `(session, sink)` under the URI, return success per spec.
   - On unsubscribe: remove pair; succeed even if not subscribed (idempotent).
   - On session disconnect: drop all subscriptions for that session via the lifecycle hook from the spike.
   - **Per-session subscription cap**: each session may hold at most 100 active subscription URIs. The 101st `resources/subscribe` returns a spec-compliant error (define a stable error message like `"subscription limit exceeded (max 100 per session)"`). Cap is a `const` in `resources.rs`.
3. Implement an internal API for the rest of the codebase to fire updates:
   ```rust
   pub fn notify_resource_updated(uri: &str)
   ```
   This iterates the registry entry for `uri`, and dispatches `notifications/resources/updated { uri }` per spec on each subscribed session's stored sink.
4. Tests in `crates/maenifold-core/src/mcp/resources.rs` (or sibling test module):
   - Subscribe then `notify_resource_updated` → notification delivered to that session.
   - Subscribe to URI A, fire update on URI B → no notification.
   - Two sessions subscribed to same URI → both notified.
   - Unsubscribe then notify → no delivery.
   - Subscribe to unknown URI → spec-compliant error.
   - 100 subscriptions on one session succeed; the 101st returns the cap error.
   - Session-end hook fires → registry entries for that session are removed; subsequent `notify_resource_updated` does not attempt delivery on the gone session.
5. **Streamable-HTTP integration test** (at minimum one): spin up the maenifold MCP server bound to a random localhost port (`--http`), open a streamable-HTTP MCP session as a client, call `resources/subscribe` on a synthetic URI registered by the test, fire `notify_resource_updated` from a server-side test hook, and assert the client receives a `notifications/resources/updated { uri }` frame on its open POST stream within a generous timeout (e.g. 2s). This validates that capability advertisement, subscribe handler, registry, notifier, and HTTP-transport notification delivery all compose correctly end-to-end.

## Acceptance criteria

1. `cargo test -p maenifold-core` passes.
2. Server `initialize` response advertises `resources.subscribe = true` for both stdio and http transports.
3. `resources/subscribe { uri: "valid://uri" }` succeeds; subsequent `notify_resource_updated("valid://uri")` causes a `notifications/resources/updated { uri: "valid://uri" }` to be sent on that session's transport.
4. Subscriptions are scoped per session; cross-session leaks are tested against.
5. Sessions cleaning up (drop / disconnect) automatically remove their subscriptions, verified both at unit level and through the streamable-HTTP integration test.
6. No new external dependencies beyond rmcp's existing surface.
7. Pre-flight spike outcomes are recorded in this task's history before SWE begins.
8. At least one streamable-HTTP integration test exists and passes, validating end-to-end subscribe → notify delivery on the HTTP transport.
