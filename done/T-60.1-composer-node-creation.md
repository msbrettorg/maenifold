# T-60.1: PipelineComposer Node Creation Toolbar

## Requirement
FR-44: The PipelineComposer SHALL provide a node creation toolbar in design mode.

## RTM
RTM-196 → TC-196

## Context
The PipelineComposer currently has an `addNode()` function (line ~280) that is exposed via `defineExpose` but has NO UI to invoke it. Users click "+ New" in the sidebar, enter design mode with an empty canvas, and are stuck — there's no way to add the first node. The Create button in PipelineRunner requires `nodes.length > 0` to show.

The Composer already supports:
- `addNode(workflowId, acpClient?)` — creates a node at a random position
- `deleteSelected()` — removes selected nodes/edges  
- `fitView()` — fits canvas to content
- Design mode flags: `nodesDraggable`, `nodesConnectable`, `edgesUpdatable`, `elementsSelectable`
- Vue Flow with Background, Controls, MiniMap

## Scope
**Files to modify:**
- `src/components/PipelineComposer.vue` — Add design-mode toolbar with node creation

**Files to NOT modify:**
- PipelineRunner.vue (canCreate logic is correct — nodes.length > 0 is a valid guard)
- PipelineSidebar.vue
- PipelineInspector.vue
- Any store or composable files

## Acceptance Criteria
1. When `designMode` is true, a toolbar appears at the top of the Composer canvas
2. Toolbar contains: "Add Node" button, workflow ID text input (with datalist from `store.workflows`), optional ACP client input
3. Clicking "Add Node" calls the existing `addNode(workflowId, acpClient)` function
4. A "Delete Selected" button appears when nodes/edges are selected
5. The toolbar is hidden when `designMode` is false
6. Added nodes appear on the canvas and are reflected in `localDefinition`
7. After adding at least one node, the Create button in PipelineRunner becomes visible
8. Component stays under 400 lines (currently 373)
9. Build passes: `npm run build`
10. TypeScript: `npx vue-tsc --noEmit`

### 2. Reactivity inconsistency in `addNode()` risks double-rendering new nodes

**Location**: `src/components/PipelineComposer.vue` lines 263–264

```ts
addNodes([newNode]);             // line 263 — Vue Flow internal action
nodes.value = [...nodes.value, newNode];  // line 264 — manual local-ref push
```

`addNodes` is a `useVueFlow()` action that **mutates Vue Flow's internal graph state**, which propagates back to the `v-model:nodes="nodes"` binding via Vue Flow's `update:nodes` event. That means `nodes.value` will be updated by Vue Flow as well. The manual `nodes.value = [...nodes.value, newNode]` then re-pushes the same node, creating a **duplicate node** in `nodes.value` the moment the v-model flush resolves.

Every other mutation in this file follows the correct pattern (set the ref first, then push to VueFlow):

```ts
// syncFromDefinition (line 146)
nodes.value = pipelineNodesToFlow(def.nodes);
setNodes(nodes.value);

// onConnect (line 208)
edges.value = [...edges.value, newEdge];
setEdges(edges.value);

// deleteSelected (lines 291–294)
nodes.value = remainingNodes;
setNodes(remainingNodes);
```

`addNode()` alone breaks from this pattern. The fix is:

```ts
// CORRECT — match the established pattern
nodes.value = [...nodes.value, newNode];
setNodes(nodes.value);
emitDefinitionUpdate();
```

This removes `addNodes` (already imported but only used here) in favour of the consistent `setNodes` path.
