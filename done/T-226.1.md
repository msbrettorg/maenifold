# T-226.1 — Electron MCP SDK Streamable HTTP Compatibility Spike

## Problem

Before replacing custom MCP Streamable HTTP transport code (`useMcpClient.ts`, `mcpTransport.ts`) with `@modelcontextprotocol/sdk` v1, we must verify the SDK works in the Electron renderer context. The SDK is currently a transitive dependency (v1.29.0 via package-lock.json) but NOT a direct dependency.

## Deliverable

A decision memo at `docs/mcp-sdk-electron-compat.md` covering:
- Can `@modelcontextprotocol/sdk` `StreamableHTTPClientTransport` be imported and used in the Electron renderer?
- Does SSE streaming work correctly?
- Does `Mcp-Session-Id` header handling work?
- What is the transitive dependency impact (17 new deps per prior audit)?
- Go/no-go recommendation for replacement

- [ ] Go or no-go recommendation with evidence
- [ ] If go: list specific custom code files that can be replaced
- [ ] If no-go: document the blocking issues and workarounds

## Research

- Stage ID: research
- Record Kind: append
- Agent: researcher
- Recorded At: 2026-04-26T05:54:23.471483+00:00
- Notes: Research complete: GO recommendation. SDK v1.29.0 StreamableHTTPClientTransport is fully browser-compatible — uses only fetch(), Web Streams API (ReadableStream, TextDecoderStream, TransformStream), and eventsource-parser (pure JS). Zero Node.js-only imports in the client transport path. Session header handling is built-in. The SDK is already a transitive dep (via @agentclientprotocol/sdk) so adding it as direct dep introduces 0 new packages. The ~595 LOC of custom code (mcpTransport.ts + useMcpClient.ts) can be replaced. Key caveats: (1) SDK exports `./client` separately from `./server` and the transport — import path matters for tree-shaking since `cross-spawn` is in stdio.js; (2) SDK negotiates protocol version 2025-11-25 vs our hardcoded 2025-03-26; (3) SDK includes OAuth/auth machinery not needed but harmless if unused.
