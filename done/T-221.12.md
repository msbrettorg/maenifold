## Summary

**AI is the new UI.** MCP is the universal interface — one common protocol for AI agents and human operators alike. The desktop app should fetch *all* domain data through MCP tools, the same tools that power every agent. No REST backdoors, no `/api/` shortcuts, no privileged paths.

**Current state:** The UI already uses MCP `tools/call` for memory, gate, and knowledge operations. But 10 REST endpoints for config, agents, MCP servers, and tool discovery have no MCP equivalent.

**Target state:** Zero direct `/api/` calls from the frontend for domain data. The REST API remains for health checks, machine-id, and the ACP WebSocket transport — but all domain data flows through MCP.

## Duo Findings Addressed

### Finding 1: SettingsMcpServers.vue missing from scope

**Fixed.** Added items 8-10 in the inventory above. Three REST endpoints (`POST/PUT/DELETE /api/config/mcp-servers`) need MCP tools.

### Finding 2: GatewayIndex != tool discovery

**Accepted.** `GatewayIndex` (`gateway_catalog.rs:12-139`) is a routing catalog of gateway commands organized by domain. `GET /api/discovery/mcp-tools` (`routes_config.rs:130-173`) is a live probe returning per-server discovery results with `status`/`error` and a tools array containing `name`, `description`, and `inputSchema`. The frontend locally derives health status (`deriveServerHealth()` in `palette-health.ts`) and extracts `appUi` metadata (`extractAppUiMetadata()` in `agent-capabilities-helpers.ts`). Stale-cache fallback is also frontend-local (`mergeServerResults()` in `mcp-tool-discovery.ts`).

**Resolution:** Create a new `DiscoverMcpTools` MCP tool that wraps the same handler logic as the REST endpoint. Do not overload `GatewayIndex`. Move this to Phase 5 (highest risk, lowest priority for MCP-first goal since config mutations are more impactful).

### Finding 3: GetConfig response shape mismatch

**Accepted.** REST returns `agents` as `Record<string, AgentConfig>`. MCP `GetConfig` (`diagnostics.rs:11-109`) returns agents as a sorted array with name included per-entry. MCP also redacts sensitive env values and splits `command` into `command` + `args`.

**Resolution:** Frontend normalizer in config store (~10 lines TS). Transform MCP array response back to `Record` format. The MCP surface is canonical — the frontend adapts.

### Finding 4: Config mutation tools under-specified

**Fixed.** Eight new tools required, each mirroring an existing REST handler:

| Tool | REST Equivalent | Parameters | Returns |
|------|----------------|------------|---------|
| `ReloadConfig` | `POST /api/config/reload` | none | `{ config, reloaded[], requires_restart[] }` |
| `UpdateSettings` | `POST /api/config/settings` | `settings: partial MaenifoldSettings` | `AgentsConfig` |
| `AddAgent` | `POST /api/config/agents` | `name: string, config: AgentConfig` | `AgentsConfig` |
| `UpdateAgent` | `PUT /api/config/agents/{name}` | `name: string, config: AgentConfig` | `AgentsConfig` |
| `DeleteAgent` | `DELETE /api/config/agents/{name}` | `name: string` | `AgentsConfig` |
| `AddMcpServer` | `POST /api/config/mcp-servers` | `entry: McpServerEntry` | `AgentsConfig` |
| `UpdateMcpServer` | `PUT /api/config/mcp-servers/{name}` | `name: string, entry: McpServerEntry` | `AgentsConfig` |
| `DeleteMcpServer` | `DELETE /api/config/mcp-servers/{name}` | `name: string` | `AgentsConfig` |

**Partial-update semantics for `UpdateSettings`:** The current REST `update_settings_handler` (`routes_config.rs:246-256`) does full replacement via `ConfigManager::update_settings(MaenifoldSettings)`. The MCP tool implements a JSON-merge strategy:
1. Load current settings from `ConfigManager`
2. Deep-merge the partial input: only keys present in the request override; nested objects (`decay`, `community`, `vector`, `debug`, `gateway`) are recursively merged — sending `{ "vector": { "embeddingLogs": true } }` updates only `vector.embeddingLogs`, not the entire `vector` object
3. Call the existing full-replacement `ConfigManager::update_settings()` with the merged result

This avoids the round-trip clobber problem where `GetConfig` redacts sensitive env values.

### Finding 5: config:// resources don't exist

**Accepted.** Subscription infrastructure is mature (`resources/subscription.rs`). `SUBSCRIBABLE_PREFIXES` currently has `asset://`, `pipeline://`, `workflow://`. No `config://` family registered.

**Resolution:** Register `config://` in `SUBSCRIBABLE_PREFIXES`. URI scheme:
- `config://settings` — settings changed
- `config://agents` — agent list changed
- `config://mcp-servers` — MCP server list changed

Notifications carry URI only (not payload). Client calls `GetConfig` to get new state. Each mutation tool handler calls `notify_resource_updated()` after writing. This matches the `asset://` pattern.

### Finding 6: MCP auth gap for writes

**Accepted.** REST mutation routes use `require_bearer_token` middleware (`api/auth.rs:56-80`). MCP HTTP transport (`mcp/http.rs:18-28`) has no auth middleware.

**Resolution:** Hybrid model:
- **stdio transport:** trusted (local process, no auth needed)
- **HTTP transport:** add Bearer token middleware to `/mcp` endpoint (same token as REST)
- **Frontend impact:** Current MCP transport uses bare `globalThis.fetch` via `getHttpFetch()` in `apps/desktop/src/lib/http.ts`. Adding middleware requires updating the transport to inject the `Authorization: Bearer <token>` header. The token is available via `window.electronAPI.getAuthToken()`.
- **Sequencing:** T-221.12h MUST ship before Phase 3 frontend mutations to maintain defense-in-depth.

This is a separate sub-task from the tool implementations.

### Phase 2: Config mutation tools (backend)

**T-221.12b** — Backend config mutation MCP tools

**Architectural constraint:** Native MCP tools dispatch through `ToolRegistry::global().try_invoke()` which creates a `ToolContext` containing only `Config`, `OutputFormat`, and `Option<StdioPool>`. It does NOT contain `ConfigManager`, `ApiState`, or any runtime mutation state. The REST mutation handlers (`routes_config.rs`) rely on `ApiState.config_manager.*` and `refresh_settings()`.

Additionally, when the gateway is active, `call_tool()` in `mod.rs:205-247` routes ALL tool calls through `gateway.handle_tool_call()` first — only `GetHelp` and `ReadMcpResource` fall through to the native registry. Config mutation tools must be added to this exception list.

**Implementation approach:** Config mutation tools are handler-intercepted (like `GetHelp`/`ReadMcpResource`), not native registry tools. The handler needs shared daemon state for config mutations. Add a `ConfigMutationState` struct (or reuse `ApiState`) containing:
- Shared `ConfigManager` (same instance as REST API, not a separate one)
- Shared `Arc<RwLock<Config>>` for runtime settings refresh (matching REST's `refresh_settings()` behavior)
- Resource notification emission capability (for `config://` subscriptions in Phase 4)

Store this as `Option<ConfigMutationState>` on `MaenifoldHandler`. In `call_tool()`, intercept config mutation tool names before the gateway dispatch and delegate to `ConfigMutationState` methods. After `UpdateSettings`/`ReloadConfig` persistence, the handler MUST call the runtime refresh equivalent (updating the live `Config.settings`) to match REST behavior — persistence alone is insufficient.

**Construction:** The MCP HTTP service (`mcp/http.rs`) and REST API (`api/routes.rs`) must share the same `ConfigManager` and `Arc<RwLock<Config>>`. The `ConfigMutationState` is constructed during daemon startup and passed into both `ApiState::new()` and `MaenifoldHandler`, ensuring they operate on identical in-memory state.

**Tool advertisement:** Handler-intercepted tools are NOT in `ToolRegistry`, so they won't appear in `list_mcp_tools()` or `list_tools()` automatically. To ensure discoverability: register them in `ToolRegistry` for schema generation and advertisement purposes only (so `list_mcp_tools` returns their `Tool` definitions with proper schemas), AND add them to the `list_tools()` gateway-mode native allowlist (alongside `GetHelp`/`ReadMcpResource`). Execution is intercepted in `call_tool()` before `ToolRegistry::try_invoke()` — registry registration is only for `list_tools` visibility and schema, not execution.

**Schema registration:** Each tool needs a schema entry in `mcp/schema/` so `list_mcp_tools` returns proper `inputSchema` objects instead of the generic `{"type": "object"}` fallback. Add `config_tools.rs` schema module and register in `mcp/schema/mod.rs:mcp_tool_from_registry_name`.

**UpdateSettings merge semantics:** Current REST `update_settings_handler` does full replacement via `config_manager.update_settings(MaenifoldSettings)`. The MCP tool implements a JSON-merge strategy: load current settings, deep-merge the partial input (only top-level keys present in the request override; nested objects are recursively merged), then call the existing full-replacement method. This avoids clobbering redacted secrets on round-trip.

## Boot order contract

MCP connection must be established before config loads. Sequence:
1. Electron main process starts daemon (or connects to existing)
2. MCP transport connects (`useMcpClient.ts`)
3. Config store calls `GetConfig` via MCP (replaces REST `GET /api/config`)
4. App session begins

If MCP connection fails, config store falls back to cached state or shows connection error. Config watch (MCP subscription) is optional — app works without it, just doesn't auto-refresh.
