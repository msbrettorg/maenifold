# T-43.14: Complete resource_link type in content block refactor

**Requirement**: Content audit gap  
**Priority**: P2  
**Files**: `vendor/acp-ui/src/lib/types.ts`

## Acceptance Criteria

1. The `ContentBlock` type in T-43.1 is missing `resource_link` optional fields. Update the type to include ALL spec fields:
   ```ts
   // For resource_link blocks:
   title?: string;
   description?: string;
   size?: number;
   ```

2. Render these fields when present in the resource_link chip UI:
   - `title` as display text (fallback to `name`)
   - `description` as tooltip or subtitle
   - `size` formatted as human-readable file size

## SWE Remediation

- **What I changed**
  - `vendor/acp-ui/src/lib/types.ts`: completed the local `resource_link` content block shape by exposing ACP-compliant `title`, `description`, and `size` fields on the refactored `ContentBlock` type.
  - `vendor/acp-ui/src/components/ChatView.vue`: updated resource link rendering to prefer `title` over `name`, show `description` and formatted `size` metadata when present, and surface those details in the chip tooltip.
- **Test results**
  - PASS — `cd vendor/acp-ui && bun run build`
- **Notes**
  - The installed ACP SDK already models these fields with ACP-compatible nullability and `bigint` sizing, so the local type completion mirrors that shape and the UI formatter handles both small numeric values and ACP `int64`-style `bigint` sizes.

## Red-team Audit

**Verdict: REJECT**

Findings:

1. **AC2 — `size` formatted as human-readable file size — NOT MET (bigint branch silently dropped)**

   The spec requires `size` to be formatted as a human-readable file size. The SWE's own notes state: *"the installed ACP SDK already models these fields with ACP-compatible nullability and `bigint` sizing."* The local type accordingly declares `size?: bigint | null` (`types.ts`, `ResourceLinkContentBlock`).

   However, `getResourceLinkSizeLabel` in `ChatView.vue` (line 511–513) only produces output for `typeof block.size === 'number'`:

   ```ts
   function getResourceLinkSizeLabel(block: ...): string | null {
     return typeof block.size === 'number' ? formatFileSize(block.size) : null;
   }
   ```

   When `block.size` is a `bigint` — the expected ACP wire type — the guard evaluates to `false` and the function returns `null`. The chip then renders no size at all. The `formatFileSize` helper at lines 460–510 *does* handle `bigint` correctly (with an entire dedicated branch), but `getResourceLinkSizeLabel` never invokes it for bigint values. The fix is a one-line change: `typeof block.size === 'number' || typeof block.size === 'bigint'`, or simply `block.size != null`.

   This is not a TypeScript compile-time error (narrowing is valid), which explains why `bun run build` passed — it is a pure runtime logic flaw that causes the `size` field to be invisible for any real ACP payload.

All other criteria are met:

- **AC1 — type fields added**: ✅ `types.ts` defines `ResourceLinkContentBlock` as `Extract<SdkContentBlock, { type: 'resource_link' }> & { title?: string | null; description?: string | null; size?: bigint | null }`.
- **AC2 — `title` as display text (fallback to `name`)**: ✅ `getResourceLinkLabel` at line 450–452 returns `block.title || block.name || block.uri`.
- **AC2 — `description` as tooltip or subtitle**: ✅ `getResourceLinkDescription` feeds both the chip's `:title` tooltip and the visible `.resource-link-chip__description` span.

**Recommendation**: In `ChatView.vue`, change `getResourceLinkSizeLabel` to handle both `number` and `bigint`:

```ts
function getResourceLinkSizeLabel(block: Extract<ContentBlock, { type: 'resource_link' }>): string | null {
  return (typeof block.size === 'number' || typeof block.size === 'bigint')
    ? formatFileSize(block.size)
    : null;
}
```
