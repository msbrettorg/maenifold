# T-59.6: E2E Integration Test Against Live MCP Server

**Requirement**: FR-43
**RTM**: RTM-192
**Priority**: P0 — Validates the entire MCP client actually works

## Context

The unit tests for `useMcpClient.ts` mock `fetch` and return `application/json` — but the real `maenifold --http` server returns `text/event-stream` (SSE-framed JSON-RPC). This mismatch allowed a protocol-level bug to ship undetected. We need an integration test that actually connects to the running server.

The test assumes `maenifold --http` is running on `localhost:8080`. It should be clearly marked as an integration test that requires a live server.

## Scope

Create `src/composables/__tests__/mcpIntegration.test.ts` in the pipeline-ui project.

## Acceptance Criteria

1. **Test file**: `src/composables/__tests__/mcpIntegration.test.ts`
2. **Skip when offline**: The test suite should detect if `localhost:8080` is unreachable and skip gracefully (use `beforeAll` to probe the server, skip the suite if connection fails).
3. **Test: connect and get session**: Call `connect()` on `useMcpClient()`. Assert `connected.value === true` and `sessionId.value` is a non-empty string. Assert `error.value` is null.
4. **Test: list tools**: After connecting, call `listTools()`. Assert the result is an array containing at least one tool with `name === 'Pipeline'`.
5. **Test: call pipeline list**: After connecting, call `callTool('Pipeline', { list: true })`. Assert the result is an array (may be empty if no pipelines exist). Assert no error.
6. **Test: call pipeline learn**: After connecting, call `callTool('Pipeline', { learn: true })`. Assert the result contains text (the help documentation). Assert no error.
7. **Test: full pipeline lifecycle**: Create a pipeline with 2 nodes and 1 edge, view it, then delete it. Assert:
   - Create returns a `pipelineId`
   - View returns `status`, `nodes` array with 2 entries, `edges` array
   - Delete succeeds (no error)
   - A second view after delete throws or returns an error
8. **Test: disconnect**: Call `disconnect()`. Assert `connected.value === false` and `sessionId.value` is null.
9. **Cleanup**: Each test that creates a pipeline should delete it in an `afterEach` or `finally` block.
10. **Not in default test run**: The test file should use `describe.skipIf` or equivalent so `npm test` doesn't fail when the server isn't running. Add a separate npm script `"test:e2e": "vitest run --reporter verbose src/composables/__tests__/mcpIntegration.test.ts"` to `package.json`.
11. **Build**: `npm run build` passes. `npm test` passes (integration tests skipped). `npm run test:e2e` passes when server is running.

## Implementation Notes

Server probe pattern:
```typescript
let serverAvailable = false;

beforeAll(async () => {
  try {
    const res = await fetch('http://localhost:8080/mcp', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json', 'Accept': 'application/json, text/event-stream' },
      body: JSON.stringify({ jsonrpc: '2.0', method: 'initialize', id: 0, params: { protocolVersion: '2025-03-26', capabilities: {}, clientInfo: { name: 'e2e-probe', version: '0.0.1' } } }),
    });
    serverAvailable = res.ok;
  } catch {
    serverAvailable = false;
  }
});
```

Use `describe.runIf(serverAvailable)` for the test suite.

### Finding 1 — RESOLVED (was Medium): `{ list: true }` assertion corrected in SWE Remediation Update

**Severity**: Resolved before audit was written
**File**: `mcpIntegration.test.ts`, lines 223–232
**AC**: AC5

> **Audit note**: The spec file's `### SWE Remediation Update` section (line 246) was not visible on the initial view (file exceeded the 99-line visible window). The test file was updated by the SWE before this audit was written, and the bug described below was already fixed. This finding documents the fix for traceability.

The original `{ list: true }` test (as first delivered) called `callTool<PipelineListItem[]>` and asserted `Array.isArray(result)` directly on the raw return value, bypassing the `unwrapToolData` helper used by every other structured-data test. Since the live server returns a nested envelope (`{ success, data: { pipelines }, error }`), `result` would have been the wrapper object, not the array — `Array.isArray(result)` would have returned `false` even after the server was rebuilt with `list` support.

**The SWE's fix** (currently in the file, lines 18–24 + 223–232) introduces a `PipelineListEnvelope` interface and explicitly traverses the envelope:

```typescript
interface PipelineListEnvelope {
  success?: boolean;
  data?: { pipelines?: PipelineListItem[]; };
  error?: unknown;
}

const result = await client.callTool<PipelineListEnvelope>('Pipeline', { list: true });
expect(Array.isArray(result.data?.pipelines)).toBe(true);
```

This is a valid fix. It differs from `unwrapToolData` (generic recursive unwrap) by hardcoding the `data.pipelines` path, but that is acceptable because the server's `list` envelope shape is known and stable.

**Residual observation** (not a blocker): Lines 227–229 add three redundant assertions (`toBeTruthy`, `typeof === 'object'`, `not.toBeNull`) before the definitive array check on line 230. These are satisfied automatically whenever line 230 passes and add noise without adding signal. They should be removed in a follow-up cleanup.

### Finding 2 — FRAGILE (Low): `skipSuite()` mutates undocumented Vitest internal task fields

**Severity**: Low
**File**: `mcpIntegration.test.ts`, lines 51–56, 162–172
**AC**: AC2

The `skipSuite` helper mutates `suite.mode` and iterates `suite.tasks` to set each task's `.mode = 'skip'`, casting through a hand-rolled `MutableSuite` interface to reach private Vitest internals:

```typescript
function skipSuite(suite: MutableSuite) {
  suite.mode = 'skip';
  suite.tasks?.forEach((task) => { task.mode = 'skip'; });
}
```

These fields are not part of Vitest's public API. Vitest's internal `Task` type is subject to change without a semver bump in the `vitest` package (currently `^4.1.0`). A future Vitest upgrade could rename these fields, restructure `tasks`, or move skip logic elsewhere, causing the probe-based skip to silently stop working — the suite would then run even without a server, producing hard-to-diagnose network failures in CI.

The spec suggested `describe.runIf(serverAvailable)` — which is evaluated at module parse time and cannot use a value set in `beforeAll`. The SWE worked around this correctly with `describe.skipIf(!RUN_E2E)` as the outer gate and `skipSuite()` as a runtime inner guard. The intent is correct; the mechanism is fragile.

**Recommended improvement** (not a blocker): Replace per-test `it` bodies with `it.skipIf(!serverAvailable)` once server availability is known, or check `serverAvailable` at the top of each test body via a shared helper, avoiding internal field mutation entirely.

### Finding 3 — UNDOCUMENTED PREREQUISITE (Low): Lifecycle test requires ≥1 workflow asset in the system

**Severity**: Low
**File**: `mcpIntegration.test.ts`, lines 151–159, 235
**AC**: AC7

The lifecycle test calls `getWorkflowId(client)` before creating the pipeline:

```typescript
// lines 151–158
async function getWorkflowId(client: ReturnType<typeof useMcpClient>): Promise<string> {
  const result = await client.callTool<unknown>('ListAssets', { type: 'workflow' });
  const workflows = normalizeWorkflowList(unwrapToolData<...>(result));
  expect(workflows.length).toBeGreaterThan(0);   // ← hard assert
  return workflows[0];
}
```

On a clean installation with no workflow assets loaded, this assertion fires:
```
Expected: > 0
Received: 0
```

This produces a misleading failure (the `creates, views, and deletes a pipeline` test fails) when the underlying issue is an environment precondition, not a test logic error. There is no mention of this precondition in the spec or in the SWE remediation notes, and no `skip` path is provided when `ListAssets` returns an empty array.

**Recommended improvement**: Add a guard that skips or marks the lifecycle test with `this.skip()` / `context.skip()` if `workflows.length === 0`, with a clear warning message:
```typescript
if (workflows.length === 0) {
  console.warn('[mcpIntegration] Skipping lifecycle test: no workflow assets found in system');
  return null;
}
```

### Finding 4 — INFORMATIONAL: No call-level timeout on live MCP calls

**Severity**: Informational
**File**: `mcpIntegration.test.ts`, lines 40–48

`fetchWithTimeout` (with a 3 000 ms abort timer) is used only for the `probeServer()` call. All subsequent `callTool` and `listTools` invocations go through `useMcpClient` without a timeout guard. If the live server hangs mid-request (e.g., SSE stream never closes), the test runner will block until Vitest's own global timeout fires. This is not a spec violation but could cause opaque CI hangs.

### `{ list: true }` Blocker — Confirmed Server-Side; Test Assertion Independently Fixed

The SWE's attribution of the `Pipeline { list: true }` failure to a **stale server binary** is **correct**. The live server's `tools/list` schema for `Pipeline` does not advertise the `list` parameter, meaning the `list` operation was added to the Rust backend after the currently deployed binary was compiled. This is a deployment gap, not a test authoring error.

The SWE additionally identified that the original test assertion was wrong (bare `Array.isArray(result)` without envelope unwrapping) and fixed it before closing the task. The current test correctly traverses `result.data?.pipelines`. Both the server rebuild and the assertion fix are required for the test to pass end-to-end; the SWE has addressed the half they control.
