# T-45.7: Pipeline Dispatch — Atomic Claim

**Requirement**: FR-45.6, FR-45.7
**RTM**: RTM-337, RTM-342, RTM-343, RTM-344
**Priority**: P0 — Core scheduling mechanism

## Context

The `pipeline(sessionId=X, dispatch=true)` operation computes the ready set, atomically transitions ready nodes to `active`, and returns them with session IDs. Dispatch IS the claim — there is no separate "mark as active" step. This prevents double-dispatch when multiple callers poll simultaneously.

## Scope

Add `dispatch=true` handling to the Pipeline tool handler.

## Acceptance Criteria

1. **Dispatch operation**: `pipeline(sessionId=X, dispatch=true)` computes the ready set, transitions eligible nodes to `active`, and returns the dispatch response.
2. **Dispatch-as-claim**: The transition from `pending→ready→active` happens atomically within the dispatch call. No separate status update is needed.
3. **Ready set computation**: Use `compute_ready_set` to determine which nodes are eligible. Then transition pending→active (the "ready" state is transient — computed, not stored).
4. **maxConcurrency**: Respect the `maxConcurrency` field from the pipeline session frontmatter. If N nodes are already `active`, dispatch at most `maxConcurrency - N` additional nodes.
5. **Response shape**: Return JSON matching:
   ```json
   {
     "dispatched": [
       {"nodeId": "...", "sessionId": "...", "workflowId": "..."}
     ],
     "active": ["nodeId1", "nodeId2"],
     "completed": ["nodeId3"],
     "remaining": 2
   }
   ```
6. **Session file update**: For each dispatched node, update the node's workflow session frontmatter `status` from `pending` to `active`.
7. **Pipeline session update**: Update `nodeStates` in the pipeline session file to reflect the new `active` status + increment `last` field.
8. **Empty dispatch**: If no nodes are ready (all blocked, completed, or at max concurrency), return empty `dispatched` array with current state.
9. **Activate workflow steps**: When a node transitions to `active`, render the first workflow step into the session body (the session was created with no step content — now it gets populated). This makes the session ready for an agent to continue.

## Implementation Notes

- Read pipeline session → compute ready set → update node sessions → update pipeline session → return
- For each dispatched node: read workflow definition, render first step into session, update status
- `maxConcurrency` check: `count active nodes + newly dispatched <= maxConcurrency`
- Re-use `format_workflow_step` and step rendering logic from existing workflow code

### Caveats (non-blocking)

1. **Two-phase write leaves a narrow inconsistency window** (handler.rs:325-342). `activate_workflow_node_session` writes `status=active` in one `write_markdown` call, then calls `append_h2_section` (a second read+write) to render the first step. If the process is interrupted between the two writes, a node session will carry `status: active` but contain no step content — an agent picking it up would find an empty body. In the happy path this is invisible, but it is worth noting for future hardening (e.g., render the step into `existing_content` before the single write).

2. **Re-activation on retry would double-render the first step** (handler.rs:306-346). If `activate_workflow_node_session` fails mid-loop (e.g., for node N after nodes 1..N-1 succeeded), the pipeline frontmatter write at line 276 never happens. A subsequent dispatch retry would call `activate_workflow_node_session` again for the already-activated nodes: it would re-read the session body (which already contains the first step), write the frontmatter, and then `append_h2_section` would append the step a second time. Not reachable in normal operation, but worth a future guard (`if status already active, skip`).

3. **Empty dispatch still increments `last`** (handler.rs:266-274). When no nodes are ready, `last` is still bumped by 1 and the pipeline file is written. The spec is silent on this edge case for criterion 8, so it is not a violation — but callers should not use `last` as a "nodes dispatched count".
