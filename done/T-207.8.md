# T-207.8 — Migrate pipeline driver to StdioPool

## Problem

`crates/maenifold-core/src/workflow/pipeline/external_mcp.rs` currently spawns a fresh stdio child process for every `invoke_via_stdio()` call:

```rust
let transport = TokioChildProcess::new(child)?;
let mut client = ().serve(transport).await?;
let result = client.call_tool(request).await?;
client.close().await?;
```

This means a pipeline with 10 tool calls to MSX pays the 5-15s spawn+init cost 10 times.

## Solution

Replace the spawn-per-call pattern with `StdioPool::call_tool()`. The pool keeps processes alive across calls and handles init, crash recovery, and shutdown.

## Change

1. `invoke_via_stdio()` receives `&StdioPool` instead of spawning its own process.
2. Call `pool.call_tool(server_name, remote_tool_name, arguments)` directly.
3. Remove the `TokioChildProcess::new` / `().serve(transport)` / `client.close()` lifecycle code — the pool owns it.
4. `invoke_via_http()` is unchanged (HTTP servers are already persistent endpoints).

## State Threading

The pipeline executor (`execute_pipeline` in `crates/maenifold-core/src/workflow/pipeline/`) must receive or construct a `StdioPool`. Options:
- **Shared with HTTP gateway**: if maenifold is running in `--http` mode, reuse the same `Arc<StdioPool>` from `ApiState`. One pool, two consumers.
- **Pipeline-local**: if running as a standalone pipeline driver binary, construct a local `StdioPool` in `main.rs`. Same pool code, different lifetime.

The `StdioPool` is transport-agnostic — it doesn't know or care whether its caller is an HTTP handler or a pipeline executor.

## Key Files

- Modify: `crates/maenifold-core/src/workflow/pipeline/external_mcp.rs` (replace spawn-per-call with pool call)
- Modify: `crates/maenifold-core/src/workflow/pipeline/mod.rs` (thread pool through execute_pipeline)
- Modify: `crates/maenifold-pipeline-driver/src/main.rs` (construct StdioPool at startup)
- Uses: `StdioPool` from T-207.2
