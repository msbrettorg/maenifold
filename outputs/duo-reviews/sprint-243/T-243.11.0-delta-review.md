## What's actually built (don't re-file)

1. `CommandPalette.vue` is wired into `ChatInputBar.vue` (line 95). It opens whenever `modelValue.startsWith('/') && indexOf(' ') === -1`. Arrow/Tab/Enter/Esc all handled. Filter is `name.startsWith` plus description `includes`. CDP enumeration was wrong.
2. Agent-provided commands flow through `applyAvailableCommandsUpdate` (`session-utils.ts:174`). Backend emits via the standard ACP `available_commands_update`.
3. Selecting a command either (a) runs a `clientAction` immediately (`setConfigOption`, `clearMessages`) or (b) inserts `/cmd ` into the textarea and stores `input.hint` in `activeCommandHint` (ChatView.vue:127). User must press Send. This matches Claude Code / Zed UX.
4. ACP modes are fully wired backend-side: `set_session_mode` request, `current_mode_update` notification, `available_modes` on init/reconnect (`crates/maenifold-jockey/src/acp/session/session_cmds.rs:78`, `crates/maenifold-core/src/api/acp_relay_dispatch.rs:199, 218`).
5. Frontend coerces ACP modes into a unified `configOptions` model with `category === 'mode'`, then surfaces them through one generic `ConfigOptionPicker`. Same picker also handles arbitrary agent-defined config knobs. Pragmatic; reuses one widget.
6. When the agent advertises **no** commands, `synthesizeClientCommands` (`session-utils.ts:184`) auto-creates one slash command per mode (`/plan`, `/edit`, …) plus `/clear`. Nice touch — mode-as-slash-command is exactly the parity move.
7. Capability gating in `ChatInputBar.vue` is correct: image/audio/embedded-file buttons disable with explanatory tooltips when the agent didn't advertise the capability.

## Gaps to file (proposed children)

### P0 (per user, non-negotiable)

**T-243.11.1 — Plan mode lacks any visual distinction.**
- ACP spec: <https://agentclientprotocol.com/protocol/session-modes>.
- Today the mode picker is a `ConfigOptionPicker` chip in the chat header (`ChatView.vue:222`). When the agent reports it's in plan/read-only mode, nothing else changes — same border colour, same input bar, no banner, no input placeholder change.
- Expected: persistent banner above the input ("Plan mode — agent will not execute write tools"), accent colour shift on the input border, and a placeholder rewrite.
- Severity P0 because the user explicitly named "plan mode, the works".

### P1

**T-243.11.2 — No built-in slash commands beyond `/clear`.**
- Spec mandates `/help`, `/clear`, `/sessions`, `/new`, plus a disconnect command. Today only `/clear` is synthesized client-side, and only when the agent advertises **zero** commands (`synthesizeClientCommands` is called from the `availableCommands.length > 0` else-branch at `session-utils.ts:181`). If the agent advertises any commands, even `/clear` disappears.
- Fix: maintain a stable client-side built-in set merged on top of agent-provided commands (deduped by name), with `clientAction` metadata for each.

**T-243.11.3 — Plan mode does not block client-side write tools / permission prompts.**
- Currently the client trusts the agent to honour its own mode. If a misbehaving agent calls `fs/write` or a terminal exec while `currentModeId` is the plan/read-only mode, the request is forwarded as normal.
- Recommend: when active mode declares `tools.write === false` (or analogous), the client auto-denies write-side `session/request_permission` calls and short-circuits `fs/write_text_file` with an audit message. Belt-and-braces with the agent.

### P2

**T-243.11.4 — No argument hints / multi-arg slash command UX.**
- Palette closes the moment the user types a space (`showCommandPalette` requires `indexOf(' ') === -1`). The static `cmd.input?.hint` is captured into `activeCommandHint` on select but it is never **rendered** anywhere I could find — verify in app, but ripgrep shows no template binding for `activeCommandHint`.
- Expected: hint stays visible under the textarea while typing args; Tab cycles between arg slots if the agent declares multiple.

**T-243.11.5 — No slash-command history.**
- No Up-arrow recall on empty input, no Cmd+P palette. Spec mandates both.

**T-243.11.6 — No first-class model picker / system prompt override / cwd picker.**
- The picker only reflects `configOptions` the agent advertises. If the agent doesn't expose model selection as a config option, the user can't change models mid-session. Same for system prompt and cwd.
- These are arguably out of ACP scope, but the user's spec lists them explicitly. At minimum, document the dependency on agent advertisement; ideally add app-level config layered on top.

### P3

**T-243.11.7 — Cmd+K does not open the palette.**
- Spec lists this as an alternative trigger. Easy keybinding addition in `ChatInputBar.vue`.

**T-243.11.8 — Mode picker not visually distinct from arbitrary config knobs.**
- The chat header iterates `<ConfigOptionPicker v-for="option in configOptions">` with no special treatment for `category === 'mode'`. A user with three config knobs and one mode sees four identical chips. Move the mode picker into a dedicated, prominent control (segmented control, distinct icon).

## Architectural notes (claude-opus-4.7)

The decision to **collapse ACP `session/modes` into the same `configOptions` shape** as arbitrary agent settings is clever for code reuse but loses an important affordance: modes are first-class in the ACP spec and users will look for a dedicated control. Consider keeping the unified backend representation but rendering modes through a **distinct frontend component** that:

1. lives next to the input bar, not buried in the header;
2. shows the active mode's `description` as a permanent caption;
3. mutates the chat surrounding chrome (border, banner, placeholder) when restrictive modes are active;
4. exposes mode descriptions as tooltips so the user can shop modes before switching.

Same backend, different widget.

## Skeptic notes (gpt-5.5)

1. **`synthesizeClientCommands` is gated on `availableCommands.length === 0`.** The moment any agent ships **one** custom command, the synthesized `/clear` and per-mode commands vanish. That's a regression latent in a successful agent integration. Always merge, never replace.
2. **`activeCommandHint` is set but I could not find a render site.** Either it's wired through a sub-component I missed in 20 minutes, or it's a dead write. Worth a 60-second grep.
3. **`unstable_setSessionConfigOption`** is used as the sole mode-mutation channel from the frontend. The jockey worker translates it into the standard `acp::SetSessionModeRequest` (`handler_config.rs:55`). That's fine, but it means the frontend is permanently coupled to an "unstable" extension API for **standard** ACP behaviour. Rename or split: have a stable `setSessionMode` bridge call backed by the same worker path.
4. **Mode persistence on resume is asserted but not tested in the `__tests__` directory I scanned.** `useReadyAgentProbe.test.ts` covers initial probe, not the resume re-emit. Worth a regression test.
5. **No client-side enforcement of read-only modes.** Even if the agent is well-behaved, the client should defensively deny write-side `session/request_permission` calls when the active mode forbids them. Trust-but-verify.
