# T-68.13 — Gate MCP Session Recovery

**Requirement**: FR-68

## Summary

When the gate daemon restarts (e.g. via `launchctl kickstart -k`), MCP clients that had active sessions get "Session not found" errors on subsequent calls. The daemon needs to handle stale/unknown session IDs gracefully instead of hard-failing.

**Root cause**: rmcp's `StreamableHttpService` in stateful mode stores sessions in memory. A daemon restart wipes them. Clients send the old `Mcp-Session-Id` header and get 404.

**Fix**: Configure the gate MCP server's `StreamableHttpService` to use `stateful_mode: false`. The gate tools are inherently stateless (each call runs a CLI subprocess). The board API already bypasses StreamableHttpService entirely with a custom axum handler. There's no reason for the main MCP endpoint to maintain sessions.

If `stateful_mode: false` isn't sufficient (rmcp may still require initialize), then as a fallback: catch the "Session not found" response and return a JSON-RPC error with a clear message telling the client to reconnect (error code -32000 "session expired, please reconnect").

## Acceptance Criteria

- [ ] Gate MCP endpoint handles stale session IDs without 404/500
- [ ] After daemon restart, MCP clients can immediately call tools without manual intervention
- [ ] No regressions: `gate_status`, `gate_sync`, `gate_pass`, `gate_reject`, `gate_append`, `gate_list_gates` all work
- [ ] Trace view still captures MCP traffic
