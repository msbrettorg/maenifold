# T-61.7 — Per-Node Prompt Assembly + Type-Based Execution

**Requirement**: FR-47
**Test Cases**: TC-203
**Component**: `crates/maenifold-core/src/workflow/pipeline/executor.rs`
**Depends on**: T-61.4 (types), T-61.5 (dispatch), T-61.6 (update)

## Context

The executor at `executor.rs` is the main pipeline execution loop. Currently at line 120, every spawned node calls `runner::run_workflow(&ctx, &workflow_id, &agent, &prompt)` with the SAME run-level prompt. There is no per-node prompt, no type-based execution branching, and no output capture.

After T-61.4/5/6, the executor needs to:
- Assemble a per-node prompt from predecessor context + ambient prompt + node prompt
- Branch execution based on node type (workflow/prompt/thinking)
- Capture the result into NodeState.output

The `maenifold-acp` bash script at `/Users/brett/src/ma-collective/maenifold-rs/maenifold-acp` is the PARITY TARGET. It supports `workflow`, `think`, and `pipeline` commands. The Rust executor must handle all three node types.

## Acceptance Criteria

### Prompt Assembly

1. Build a per-node prompt in this order:
   ```
   [predecessor context]     ← from predecessor_context_content() / NodeState.output
   [run-level ambient prompt] ← only if non-empty
   [node's own prompt/topic]  ← the per-node instruction
   ```
   For workflow nodes, the workflow step text is appended later by `run_workflow()`.

2. The run-level prompt from `execute_pipeline(prompt)` becomes OPTIONAL ambient context, not the primary instruction. If a node has its own prompt, the run-level prompt is prepended as context, not as the instruction.

3. If a node has no per-node prompt (e.g., a Workflow node with `prompt: None`), fall back to the run-level prompt as today.

### Type-Based Execution

4. In the spawned task (the closure at ~line 120), branch on node type:
   - `PipelineNode::Workflow { workflow_id, acp_client, prompt, .. }` → call `runner::run_workflow(&ctx, &workflow_id, &agent, &assembled_prompt)` as today but with the assembled prompt
   - `PipelineNode::Prompt { prompt, agent, tool_mode, .. }` → send a single prompt to the ACP agent via `driver.prompt(&session_id, &assembled_prompt)` and collect the response. No multi-step workflow loop. Respect `tool_mode` if the driver supports it.
   - `PipelineNode::SequentialThinking { topic, agent, total_thoughts, analysis_type, .. }` → call `runner::run_think(&ctx, &agent, &topic, total_thoughts)` using the existing think runner from T-57.2

5. For Prompt nodes: the execution is a single ACP prompt/response. Build the driver with `build_acp_driver()`, send the assembled prompt, get the response.

6. For SequentialThinking nodes: use `runner::run_think()` which already exists from Sprint 57. Pass the topic as the prompt.

### Output Capture

7. After each node completes successfully, capture the result into `NodeState.output`:
   - Workflow nodes: the workflow completion conclusion (already extracted by `classify_workflow_result()`)
   - Prompt nodes: the full agent response text
   - SequentialThinking nodes: the session conclusion text

8. `NodeState.output` is set BEFORE cascading completion to downstream nodes, so downstream nodes can read it.

### Error Handling

9. If a node fails, set `NodeState.output = None` and `status = Abandoned` (existing behavior).

10. The executor MUST NOT change behavior for existing single-type (workflow-only) pipelines. This is a pure extension.

    - Captured successful node outputs into `NodeState.output` via existing completion updates before downstream cascading.

- **Notes / decisions**
  - Prompt nodes use a single ACP `create_session` + `prompt` round-trip and store the returned response text as node output.
  - Sequential-thinking nodes pass the assembled topic string into `runner::run_think(...)`, so predecessor output and ambient context flow into the thinking prompt path.
  - The executor mirrors the predecessor-context resolution logic locally so the change stays within the allowed file scope and still prefers `NodeState.output` before falling back to workflow-session `last` content.
  - `tool_mode` is preserved in the prompt-node execution path, but the current `AcpxDriver` does not expose a separate tool-mode switch, so execution uses the existing driver behavior.

In `assemble_node_prompt`, it is pushed only when non-empty (`if !ambient_prompt.is_empty()`, line 312), after predecessor context and before the node instruction. - **AC#3 — Workflow fallback to run-level prompt when node has no prompt**: ✅ `workflow_fallback = matches!(node, PipelineNode::Workflow { .. }) && node_instruction.is_none()` at line 300–301. - **AC#4 — Type branching (Workflow/Prompt/Thinking)**: ✅ `executor.rs:135–163` — `NodeExecutionRequest::Workflow → runner::run_workflow()` (line 140), `NodeExecutionRequest::Prompt → run_prompt_node()` (line 147), `NodeExecutionRequest::SequentialThinking → runner::run_think()` (line 153). - **AC#7 — Output captured into `NodeState.output` for all 3 types**: ✅ `classify_workflow_result` captures `wf.conclusion` (line 376), `classify_prompt_result` captures the response string (line 387), `classify_think_result` captures `think.conclusion` (line 396).
