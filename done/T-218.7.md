# T-218.7 — MCP Apps Interactive E2E

## Problem

MCP Apps support was marked complete (T-203.3–T-203.8), but the core interactive callback path is not implemented. `McpAppFrame.vue:122-131` explicitly returns `"Tool calls from MCP Apps are not yet supported"` for `oncalltool`. This means iframe apps cannot call tools on their originating server — the headline interactive use case of SEP-1865.

Additionally, cross-server tool call denial has no enforcement mechanism, and the full E2E path (iframe loads HTML via `resources/read`, receives tool results, calls back through host) has never been verified in packaged Electron.

## Implementation Scope

This task requires both implementation work and E2E verification:

1. **Implement `oncalltool` proxy** in `McpAppFrame.vue`: proxy `tools/call` requests from the iframe to the originating MCP server via `useMcpClient`.
2. **Implement server-origin scoping**: track which server owns the `resourceUri` that opened the iframe; only proxy `tools/call` to that server.
3. **E2E verification** of the full interactive path in packaged Electron with a pinned example server.

## Example Server (pinned — test fixture)

Create a minimal MCP Apps test fixture at `tests/fixtures/mcp-apps-test-server/` (Node.js, ~100 lines):
- Stdio MCP server using `@modelcontextprotocol/sdk`
- Exposes tool `render_chart` with `_meta.ui.resourceUri: "ui://test-app/chart"`
- Exposes tool `get_data` as the callback target (returns `{ items: [...] }`)
- Exposes resource `ui://test-app/chart` returning HTML with:
  - `mcp-app-bridge.js` (from `@modelcontextprotocol/ext-apps`)
  - A "Refresh Data" button that calls `tools/call` for `get_data` on the same server
  - Renders the callback result in a `<div id="result">`
- Launch: `node tests/fixtures/mcp-apps-test-server/index.mjs`

A second stdio server (any existing test server or a trivial echo server) must also be configured to test cross-server denial. The iframe from server A must NOT be able to call tools on server B.

## Acceptance Criteria

### Pre-flight (component-level)
- [ ] `McpAppFrame.vue` `oncalltool` handler proxies `tools/call` to the originating MCP server instead of returning "not yet supported"
- [ ] `oncalltool` enforces server-origin scoping: only the server that owns the `resourceUri` can receive proxied calls
- [ ] `oncalltool` returns the full MCP `CallToolResult` shape (including `structuredContent` and `_meta`) to the iframe bridge

### E2E verification (packaged Electron + CDP)
- [ ] Configure the pinned MCP Apps example server as a stdio server in `maenifold.json`
- [ ] Trigger a tool call that returns `_meta.ui.resourceUri`
- [ ] Chat renders a sandboxed iframe with real `ui://` HTML fetched through MCP `resources/read` (not placeholder)
- [ ] Iframe receives initial tool input/result and displays it
- [ ] Click an in-app control in the iframe that calls a same-server MCP tool; verify the call succeeds and the iframe updates
- [ ] Attempt a cross-server tool call from the iframe; verify denial with an actionable error
- [ ] Iframe origin ≠ host renderer origin (sandbox proxy provides origin isolation via `mcp-app-sandbox://`)
- [ ] CSP blocks disallowed external loads; no Electron security warnings in CDP console
- [ ] Conversation clear / tab switch tears down iframe with no console errors or stale postMessage events

### Security warning collection
- [ ] CDP console listener active during all E2E steps; any `[Violation]`, `[Security]`, or CSP report is a test failure
