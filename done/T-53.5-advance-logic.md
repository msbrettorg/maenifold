# T-53.5 — `advance.rs` — Stage Advance

**Requirement**: FR-41 (File-Authoritative Pipeline Gate Cache)
**Component**: `crates/maenifold-gate/src/advance.rs`
**Depends on**: T-53.1 (`fs.rs`), T-53.2 (`db.rs`)

## Context

`gate advance` is the core mutation operation. It validates the requested stage transition against the file's current state, appends the canonical stage section to the task file, optionally moves the file to `done/`, and updates `gate.db` as a cache. This is the mechanism that enforces the TDD pipeline discipline.

## Acceptance Criteria

1. Implement `run_advance(args: &AdvanceArgs, root: &Path) -> Result<()>` that:

### Validation

2. Resolves the task file using `fs::resolve_task_path()`
3. Reads and parses the file using `parser::parse_task_content()`
4. Validates the advance is legal per the transition model:
   - `swe`: file must be in `Pending` status (no SWE section, or last red/blue rejected)
   - `red`: file must be in `Red` status (SWE section present, no red section after it)
   - `blue`: file must be in `Blue` status (Red section with PASS verdict, no blue section after it)
5. Validates verdict contract (already in `lib.rs::validate_advance_contract()`):
   - `swe`: verdict MUST be None
   - `red`: verdict MUST be `PASS` or `REJECT`
   - `blue`: verdict MUST be `PASS` or `FAIL`
6. Returns a clear error message on invalid transition (what the current state is, what was requested, why it's illegal)

### File mutation

7. Appends the canonical section to the task file:
   - For `swe`: appends `\n## SWE Remediation\n\n{notes}\n`
   - For `red`: appends `\n## Red-team Audit\n\n**Verdict**: {VERDICT}\n\n{notes}\n`
   - For `blue`: appends `\n## Blue-team Verification\n\n**Verdict**: {VERDICT}\n\n{notes}\n`
   - `{notes}` is from `--notes` argument, or empty string if not provided
   - `{VERDICT}` is uppercase: `PASS`, `REJECT`, or `FAIL`

### File movement

8. After appending blue with PASS verdict:
   - Moves the file from `todo/` to `done/` using `fs::move_task()`
   - Prints: `✓ {file} → done/`
9. After appending red with REJECT or blue with FAIL:
   - File stays in `todo/`
   - Prints: `✗ {file} rejected — remains in todo/`

### Cache update

10. Opens `gate.db` via `db::GateDb::open()` (non-fatal if DB doesn't exist — just skip cache update with a warning)
11. Upserts the task with new status and location
12. Inserts a `work_log` entry with: stage, verdict, agent_model (from `--model` arg), notes

### Output

13. Prints a one-line summary: `{file}: {old_status} → {new_status} [{stage} {verdict}]`
14. Example: `T-53.1-fs-operations.md: pending → red [swe]`
15. Example: `T-53.1-fs-operations.md: blue → done [blue PASS] ✓ moved to done/`

16. Module must be under 200 LOC.

## CLI Interface

```
gate advance <file> --stage swe [--notes "..."] [--model "gpt-5.4"]
gate advance <file> --stage red --verdict pass [--notes "..."] [--model "claude-sonnet-4.6"]
gate advance <file> --stage red --verdict reject [--notes "..."] [--model "claude-sonnet-4.6"]
gate advance <file> --stage blue --verdict pass [--notes "..."] [--model "gpt-5.4"]
gate advance <file> --stage blue --verdict fail [--notes "..."] [--model "gpt-5.4"]
```

### Check 4 — File Mutation: Verdict Format ⚠️ SPEC BUG (advance/parser internally consistent)

**Spec (T-53.5 item 7) says:**
```
\n## Red-team Audit\n\n**Verdict: {VERDICT}**\n\n{notes}\n
```
The entire `Verdict: PASS` string is bolded.

**advance.rs `section_for()` (line 94) writes:**
```rust
"\n{}\n\n**Verdict**: {}\n\n{notes}\n"
// Produces: **Verdict**: PASS
//           ^^^^^^^^^^^^  ^^^^
//           bold closes    plain text value
```

**parser.rs `VERDICT_PREFIX` (line 5):**
```rust
const VERDICT_PREFIX: &str = "**Verdict**:";
```

**Analysis:**
- `**Verdict**: PASS`.starts_with(`**Verdict**:`) → **TRUE** ✅ parser finds it
- `**Verdict: PASS**`.starts_with(`**Verdict**:`) → **FALSE** ❌ parser misses it

The spec is wrong. If anyone hand-writes a file using the spec's stated format (`**Verdict: PASS**`), the parser silently misses the verdict and throws `MissingVerdict`. The implementation (advance.rs) and parser.rs are mutually consistent and the round-trip works. However, the spec creates a maintenance trap — the spec for T-53.5 must be corrected to document the actual format: `**Verdict**: PASS` (not `**Verdict: PASS**`).

**Severity**: Medium — no runtime breakage, but spec is actively misleading and contradicts T-53.2's parser constants.

### Check 9 — Output Format ❌ SPEC DEVIATION

**Spec item 13/15** (one-line format):
```
T-53.1-fs-operations.md: blue → done [blue PASS] ✓ moved to done/
```

**advance.rs actual output** (two separate lines, different wording):

Two deviations:
1. The spec shows a **single summary line** with `✓ moved to done/` appended at the end. The implementation emits **two separate lines**, with the `✓` message printed *before* the summary.

Any tool or test that parses stdout output against the spec's documented format will fail.

**Severity**: Medium — stdout contract violation; tooling or integration tests that scrape advance output will break.
