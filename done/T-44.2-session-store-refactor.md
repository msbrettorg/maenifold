# T-44.2: Session Store → Tab Manager

**Requirement**: FR-44.2  
**Priority**: P0  
**Component**: `vendor/acp-ui/src/stores/session.ts`

## Context

The session store (`useSessionStore`) currently manages a single live session with global state. We need to refactor it into a tab manager that supports multiple concurrent sessions, each with its own AcpClientBridge, messages, permissions, and UI state.

## Current Architecture (what to change)

The store currently has:
- One `acpClient: AcpClientBridge | null`
- One `currentSession: SavedSession | null`
- One `messages: ChatMessage[]`
- One set of `isConnected`, `isLoading`, `isConnecting` flags
- One set of permissions, modes, models, config, plan, terminal state

## Target Architecture

Replace singleton state with:

```typescript
// NEW: Tab management
const tabs = ref<Map<string, TabState>>(new Map());
const activeTabId = ref<string | null>(null);

// NEW: Per-tab bridge storage (not in TabState because it's not reactive)
const bridges = new Map<string, AcpClientBridge>();

// KEEP GLOBAL: savedSessions, store (Tauri persistence)
```

## Acceptance Criteria

### 1. State Refactor

Replace all singleton session state with the `tabs` Map and `activeTabId`. Import `TabState`, `TabInfo`, `createEmptyTabState`, `generateTabId` from `types.ts`.

### 2. Computed Properties

Add these computed properties:

```typescript
// Active tab shortcuts
const activeTab = computed(() => activeTabId.value ? tabs.value.get(activeTabId.value) ?? null : null);
const isConnected = computed(() => activeTab.value?.isConnected ?? false);
const isConnecting = computed(() => activeTab.value?.isConnecting ?? false);
const isLoading = computed(() => activeTab.value?.isLoading ?? false);
const error = computed(() => activeTab.value?.error ?? null);
const messageList = computed(() => activeTab.value?.messages ?? []);
const currentSession = computed(() => activeTab.value?.session ?? null);
// ... same pattern for all other per-session computed props

// Tab management
const tabList = computed<TabInfo[]>(() => {
  return Array.from(tabs.value.values()).map(t => ({
    tabId: t.tabId,
    agentName: t.agentName,
    title: t.session?.title ?? t.agentName,
    isConnected: t.isConnected,
    isConnecting: t.isConnecting,
  }));
});
```

This preserves backward compatibility — existing consumers reading `sessionStore.isConnected` etc. still work, they just read from the active tab.

### 3. Action Refactor

Refactor these actions to be tab-aware:

#### `createSession(agentName, cwd)`
- Call `generateTabId()` to create a new tab ID
- Call `createEmptyTabState(tabId, agentName, cwd)` 
- Add to `tabs` Map
- Set `activeTabId` to the new tab
- Create the AcpClientBridge, store in `bridges` Map keyed by tabId
- Wire `onSessionUpdate` to update that tab's state (not global state)
- Wire permission/auth watchers for that tab
- Proceed with initialization as before, but writing to the tab's state

#### `resumeSession(session)`
- Same pattern: new tab, new bridge, set active
- Load session into that tab

#### `disconnect(tabId?: string)`
- If no tabId, use activeTabId
- Disconnect the bridge for that tab
- Remove from `bridges` Map
- Remove from `tabs` Map
- If the closed tab was active, set activeTabId to the next available tab (or null)

#### `setActiveTab(tabId)`
- New action. Sets `activeTabId`.

#### `closeTab(tabId)`
- If connected, disconnect first
- Remove tab from Map
- Adjust activeTabId

#### `sendPrompt(text, options?)`
- Operates on activeTab's bridge and messages

#### All other actions (setMode, setModel, setConfigOption, resolvePermission, cancelPermission, etc.)
- Operate on activeTab's state and bridge

### 4. Internal Helper

Add a private helper to get the tab state and bridge for mutation:

```typescript
function getTabContext(tabId?: string): { tab: TabState; bridge: AcpClientBridge } | null {
  const id = tabId ?? activeTabId.value;
  if (!id) return null;
  const tab = tabs.value.get(id);
  const bridge = bridges.get(id);
  if (!tab || !bridge) return null;
  return { tab, bridge };
}
```

### 5. handleSessionUpdate Scoping

The `handleSessionUpdate` callback currently writes to global `messages`, `toolCalls`, `currentPlan`, etc. It must be scoped to the tab that owns the bridge. Use a closure over `tabId` when wiring the callback:

```typescript
bridge.onSessionUpdate = (update) => handleSessionUpdate(tabId, update);
```

Then `handleSessionUpdate(tabId, update)` reads/writes from `tabs.value.get(tabId)`.

### 6. Backward Compatibility

All existing computed properties (`isConnected`, `messageList`, `currentSession`, etc.) must continue to work by reading from the active tab. This means `ChatView.vue` and other components don't need changes in THIS task.

## Constraints

- Only modify `vendor/acp-ui/src/stores/session.ts`
- Do NOT modify any component files — backward compat through computed props
- Do NOT modify types.ts (that's T-44.1)
- Do NOT modify acp-bridge.ts
- `savedSessions` stays global (it's the catalog, not live state)
- The store must still be importable as `useSessionStore()` with the same external API

### Non-Critical Observations (not spec violations, no REJECT criteria)

1. **Redundant cleanup in `disconnect`**: `detachBridge` deletes from `bridges`, `supportedAgentMethodsByTab`, and stops watchers. Then `removeTab` deletes those same keys again. All Map/array operations on missing keys are safe no-ops. Harmless but the abstraction leaks.

2. **`cancelConnection` leaves tab in `tabs` Map**: After a cancelled connection attempt, the tab stays in the Map in a reset/error state (line 1378 resets state but never calls `removeTab`). The user must manually close the tab. This is defensible UX but could accumulate zombie tabs. Spec does not specify disconnect-on-cancel.

3. **`acpClient` getter is not reactive** (line 1610): Returns the bridge for the active tab via a plain JS getter, not a Vue `computed`. Any Vue template that `watch`es `acpClient` would not see reactive updates. Inspection of `App.vue` and component files shows `acpClient` is accessed imperatively only (permission handling), not in templates. No consumers are broken.

4. **Debug `console.log` statements** at lines 968, 1000, 1009, 1179, 1197, 1306: Informational logging during session lifecycle. Pre-existing pattern; not introduced by this refactor.
