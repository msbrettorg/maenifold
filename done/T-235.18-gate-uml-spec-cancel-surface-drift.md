## Problem

While PM-verifying `T-235.17`, the repo surfaced a contradictory gate spec in
`docs/gate-uml-spec.md`.

Live repo/runtime evidence already shows shipped `cancel` support:

- `gate cancel --help`
- `done/T-202.7.md`
- `docs/gate-cancel-taxonomy.md`
- touched PM/operator docs from `T-235.17`

But `docs/gate-uml-spec.md` still says:

- the gate command surface is `status`, `append`, `history`, `pass`, `fail`,
  `sync`, `ui`
- MCP stdio / MCP HTTP expose exactly five tools: `status`, `append`, `pass`,
  `fail`, `sync`

That leaves the authoritative gate spec out of sync with the shipped
administrative-close surface.

## Scope Notes

- Fix the spec/docs only; do not change gate lifecycle code.
- Preserve the distinction that:
  - `pass` / `fail` are state-machine outcomes
  - `cancel` is an administrative close action, not a state-machine outcome
- Update **all command-surface representations inside
  `docs/gate-uml-spec.md`** so they match the shipped gate surface, including:
  - top-level command-surface summary
  - MCP stdio / MCP HTTP tool enumeration
  - `CommandRequest` / UML command-service representations
  - `GateToolService` command method inventory
  - allowed module inventory / module responsibilities anywhere the shipped
    command surface is enumerated
- Re-check any immediately adjacent wording that would become contradictory once
  `cancel` is added to those lists.
- Non-goal: do **not** add `cancel` as a legal state-machine transition outcome;
  the JSON/state-machine rules remain `pass` / `fail` only.
