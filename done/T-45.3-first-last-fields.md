# T-45.3: Session Frontmatter — `first` and `last` Fields

**Requirement**: FR-45.3
**RTM**: RTM-320, RTM-321, RTM-322, RTM-323
**Priority**: P0 — Foundation for pipeline predecessor context injection

## Context

All session types (workflow, sequential thinking, pipeline) need `first` and `last` fields in YAML frontmatter. These track the opening and most-recent content written to a session file, enabling downstream consumers to read session state without parsing markdown.

The pipeline engine (FR-45.2) reads `last` from upstream node sessions for predecessor context injection. The `RecentActivity` tool will also use these fields (separate spec).

## Scope

Modify `append_h2_section` in `crates/maenifold-core/src/markdown/storage.rs` to:
1. Set `first` on initial append (when no prior body exists)
2. Update `last` on every append

Both fields store the **heading + content** as written, including any `[[WikiLinks]]`.

## Acceptance Criteria

1. **`first` set on initial write**: When `append_h2_section` is called and the file has no existing body content (empty string or whitespace-only after frontmatter), set `first` in frontmatter to the content being appended. Include the heading.
2. **`first` never updated**: On subsequent `append_h2_section` calls where `first` is already set in frontmatter, do NOT overwrite it.
3. **`last` updated every time**: On every `append_h2_section` call, set/update `last` in frontmatter to the content being appended. Include the heading.
4. **WikiLinks preserved**: Both `first` and `last` store content verbatim, including `[[WikiLinks]]` markup.
5. **Cross-session-type**: Works for workflow sessions, sequential thinking sessions, and any future session type that uses `append_h2_section`.
6. **Frontmatter ordering**: Add `first` and `last` to the frontmatter key ordering in `storage.rs` (after `related`, before `tags` or at end of ordered keys).

## Implementation Notes

- `append_h2_section` is at `crates/maenifold-core/src/markdown/storage.rs` lines 109-125
- It calls `read_markdown` then `write_markdown` with updated content
- The frontmatter is a `BTreeMap<String, Value>` — add `first`/`last` as `Value::String`
- The content to store in `first`/`last` should be: `"{heading}: {content}"` truncated to a reasonable length (256 chars) to avoid bloating frontmatter
- Check `existing_content.trim().is_empty()` to determine if this is the first write

## Red-team Audit

**Verdict: PASS**

All acceptance criteria verified:

- **AC1 — `first` set on initial write**: ✅ `storage.rs:120-125` — condition `existing_content.trim().is_empty() && !envelope.contains_key("first")` fires when the file is new (content = `""`) or has whitespace-only body. Covers both the no-file path (`(None, String::new(), ...)` at line 113-116) and an existing file whose body is blank.

- **AC2 — `first` never updated**: ✅ `storage.rs:120` — the `!envelope.contains_key("first")` guard short-circuits the insert if `first` is already present, regardless of whether the body is empty or not. Both the pre-set-in-frontmatter case (test at line 318) and the body-present case are blocked by the same guard.

- **AC3 — `last` updated every time**: ✅ `storage.rs:126` — `envelope.insert("last", ...)` is unconditional, outside the `first`-guard block. Runs on every call.

- **AC4 — WikiLinks preserved**: ✅ `summarize_section_for_frontmatter` at `storage.rs:137-139` is a bare `chars().take(256)` collect — no stripping, escaping, or regex passes. WikiLinks markup (`[[...]]`) in the first 256 chars survives intact. Test at line 349-351 asserts `expected_last.contains("[[state]]")`.

- **AC5 — Cross-session-type**: ✅ `append_h2_section` is a generic storage primitive with no session-type coupling. Workflow, sequential-thinking, and future session types all call this same path.

- **AC6 — Frontmatter ordering**: ✅ `render_frontmatter` at `storage.rs:216-219` — explicit ordered key slice lists `"related"`, `"first"`, `"last"`, `"tags"` in that sequence. Test at line 356 independently verifies `related < first < last < tags` by byte-offset in the rendered string.

**Additional findings (non-blocking):**

- **Truncation is char-safe**: `.chars().take(256)` operates on Unicode scalar values, not bytes — correct for multibyte content.
- **WikiLink truncation at boundary**: If a `[[WikiLink]]` straddles the 256-char cut point it will be emitted partially (e.g. `[[some con`). The spec says "truncated to 256 chars" and only requires WikiLinks to be preserved (not split-safe), so this is within spec, but worth noting for future readers.
- **Retroactive `first` gap**: If `write_markdown` is called directly with body content but without a `first` key, a subsequent `append_h2_section` will never back-fill `first` (body is non-empty → condition false). This is per-spec; the field is defined as the first content written *via `append_h2_section`*, not retroactively.
- **No debug artifacts**: No `TODO`, `FIXME`, `dbg!`, or `println!` introduced. The sole `eprintln!` at line 152 is the pre-existing T-14.2 YAML-warning path, unchanged.
- **`first`/`last` survive `write_markdown`**: Only embedding keys are purged in `write_markdown` (lines 67-71); `first` and `last` pass through the round-trip unharmed.
