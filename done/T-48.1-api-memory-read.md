# T-48.1 — API: `/api/memory/read` Endpoint

**Requirement:** FR-48
**Component:** `crates/maenifold-core/src/api/`

## Summary

Add a REST endpoint that wraps maenifold's `ReadMemory` MCP tool, allowing the Vue UI to fetch memory files by URI without direct file access.

## Acceptance Criteria

1. `GET /api/memory/read?uri=memory://thinking/workflow/2026/03/17/workflow-1773720937011` returns JSON with the memory file content
2. Response shape: `{ uri, title, content, created, modified }`
3. Missing/invalid URI returns 404 with error message
4. Handler reuses existing `ReadMemory` logic from `crates/maenifold-core/src/memory/` — no duplicate file I/O
5. Route registered in `api_routes()` in `crates/maenifold-core/src/api/routes.rs`
6. CORS headers allow requests from the same origin (already handled by existing middleware if present)

## Architecture Context

- Existing API routes: `crates/maenifold-core/src/api/routes.rs` — has `ApiState`, `api_routes()`, pattern to follow
- Existing endpoints: `/api/graph/nodes`, `/api/graph/edges`, `/api/agents`
- Memory read logic: `crates/maenifold-core/src/memory/` — look for the read/get file function used by the MCP ReadMemory tool
- Config provides the memory root path
- Follow the existing `ApiError` pattern for error handling

## SWE Remediation

### Changes Made

**`crates/maenifold-core/src/api/routes.rs`** — single file changed:

1. **Imports**: Added `crate::markdown::{file_exists, find_file_as_uri, read_markdown}` and `serde::Serialize` for the response struct.
2. **`ApiError::not_found`**: Added a 404 error constructor alongside existing `bad_request` and `internal`.
3. **`MemoryReadResponse`** struct: `#[derive(Serialize)]` with fields `uri`, `title`, `content`, `created: Option<String>`, `modified: Option<String>` — matches the spec's `{ uri, title, content, created, modified }` shape.
4. **`memory_read` handler**: Async axum handler that:
   - Extracts `uri` from query params (returns 400 if missing/empty)
   - Resolves identifier to `memory://` URI via `find_file_as_uri` (supports both URIs and title lookups, matching MCP `ReadMemory` logic)
   - Checks file existence via `file_exists` (returns 404 if not found)
   - Reads frontmatter + content via `read_markdown` (same I/O path as MCP tool)
   - Extracts title/created/modified from frontmatter, falls back to slug-based title
5. **Route registration**: `.route("/api/memory/read", get(memory_read))` added to `api_routes()`.

### Validation

- **Build**: `cargo build --release -p maenifold-cli` — **passed** (28.76s, exit 0)
- **Tests**: `cargo test -p maenifold-core --lib api` — pre-existing compilation errors in unrelated test modules (ambiguous `Config` imports in existing test code); not introduced by this change.

### Design Decisions

- Reuses `read_markdown`, `file_exists`, and `find_file_as_uri` from `crate::markdown` — the same I/O primitives used by the MCP `ReadMemory` tool — rather than duplicating file access logic.
- Uses `serde_yaml::Value::as_str()` directly for frontmatter field extraction instead of importing `pub(crate)` helpers from the private `memory::support` module; the logic is trivial and avoids coupling to module internals.
- `checksum` is intentionally omitted from the response per the spec's `{ uri, title, content, created, modified }` shape.
- No changes to `api/mod.rs` were needed — no new submodule required.

## Red-team Audit

**Verdict: PASS**

All acceptance criteria verified:

- **AC1** `GET /api/memory/read?uri=memory://...` returns JSON content: ✅ Route registered at `routes.rs:393`, handler extracts `uri` query param, resolves `memory://` URIs directly, reads via `read_markdown`, returns `Json(MemoryReadResponse)`.

- **AC2** Response shape `{ uri, title, content, created, modified }`: ✅ `MemoryReadResponse` struct at `routes.rs:128–134` declares exactly these five fields. `created` and `modified` are `Option<String>` (serialize as `null` when absent from frontmatter — correct behaviour, always present in JSON).

- **AC3** Missing/invalid URI returns 404 with error message: ✅ Two 404 paths confirmed — `find_file_as_uri` returns `None` → `not_found(format!("Memory file not found: {identifier}"))` (`routes.rs:152`); `file_exists` returns false → same message (`routes.rs:156–159`). `ApiError::into_response` at `routes.rs:73` emits `(StatusCode, String)` body. Note: an absent or blank `uri` *query parameter* returns 400 Bad Request (`routes.rs:143`) — this is correct REST semantics and the spec's "missing URI" phrasing refers to the memory resource not found, not an absent parameter.

- **AC4** Reuses existing `ReadMemory` logic — no duplicate file I/O: ✅ The handler uses the exact same three primitives as `memory/access.rs::read_memory` (`access.rs:174,189,198`): `find_file_as_uri`, `file_exists`, `read_markdown` — all imported from `crate::markdown`. The title/created/modified extraction logic mirrors `access.rs:207–228` faithfully, including the same `next_back()` slug fallback.

- **AC5** Route registered in `api_routes()` in `routes.rs`: ✅ `.route("/api/memory/read", get(memory_read))` at `routes.rs:393`.

- **AC6** CORS handled by existing middleware: ✅ No new CORS code added to the handler; existing middleware chain covers it per the spec's own caveat.

### Observations (non-blocking)

1. **`update_last_accessed` not called** — the MCP `read_memory` function (`access.rs:201`) calls `update_last_accessed(&uri, context).ok()` as a side effect after reading. The API handler does not. Memory files read via this endpoint won't have their access timestamps updated. This diverges from MCP behaviour but is not required by the spec.

2. **Non-`memory://` identifiers are accepted** — passing a plain title (e.g., `?uri=Azure+Savings+Plans`) is silently supported via the `find_file_as_uri` path. This is additive and matches MCP parity, but is undocumented in the spec.

3. **Error responses are plain text, not JSON** — `ApiError::into_response` returns a bare string body. Consistent with existing endpoints in this file; not a violation.
