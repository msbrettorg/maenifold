### What exists locally

Observed on this machine:

- `~/.config/github-copilot/apps.json` exists
- `~/.config/github-copilot/hosts.json` does **not** exist
- `~/.config/github-copilot/oauth.json` exists and contains a list entry with keys `accessToken`, `account`, `id`, `scopes`
- key-only inspection of `apps.json` showed entries keyed like `github.com:Iv1.b507a08c87ecfe98` and `github.com:Iv1.b507a08c87ecfe98:zed`, each containing `oauth_token`
- `gh auth token --hostname github.com` succeeds on this machine
- `gh copilot --help` shows `gh copilot` is a launcher/wrapper for the Copilot CLI, not a token-sourcing API

### Live verification

I verified both token sources against the real endpoint:

- `gh auth token --hostname github.com` → `GET https://api.githubcopilot.com/models` returned `200`
- `~/.config/github-copilot/apps.json` Copilot token → same endpoint returned `200`
- the live `/models` response included `Cache-Control: private, max-age=21600`

### Options

#### Option A — read `apps.json` / `hosts.json` directly (Zed parity)

Pros:

- exact parity with Zed’s current implementation
- works even if `gh` is absent
- likely tracks the Copilot IDE token rather than the currently-selected `gh` account

Cons:

- reads plaintext bearer tokens from disk
- file formats are not stable API contracts
- local machine already shows one expected file (`hosts.json`) missing
- multiple entries in `apps.json` create account/app ambiguity that maenifold must resolve itself

#### Option B — call `gh auth token --hostname github.com`

Pros:

- no direct token-file parsing in maenifold
- delegates credential storage and account selection to `gh` / keychain
- experimentally works for both GraphQL endpoint discovery and `/models`
- simpler trust story for a localhost daemon than opening/copier-parsing plaintext token files

Cons:

- requires `gh` to be installed and authenticated
- may follow the active `gh` account, which could diverge from the Copilot IDE account if the user has multiple accounts configured
- adds a subprocess dependency

### Recommendation

Recommend **Option B as the primary path**: shell out to `gh auth token --hostname github.com`, and do **not** use `gh copilot` as a token source. It worked against both `/models` and GraphQL in this environment, avoids parsing plaintext tokens, and keeps credential lifecycle in one tool.

Recommendation for spec stage: explicitly decide whether a **non-default fallback** to `apps.json` is wanted when `gh` is missing or unauthenticated. That fallback is implementable, but it is a user-trust-boundary decision because it means the daemon will read plaintext Copilot bearer tokens from disk.

### Live result on this account

GraphQL endpoint discovery returned:

- `viewer.copilotEndpoints.api = https://api.enterprise.githubcopilot.com`

GitHub’s enterprise network-routing docs also explicitly call out:

- allow `*.business.githubcopilot.com` for Business
- allow `*.enterprise.githubcopilot.com` for Enterprise
- block `*.individual.githubcopilot.com` if you want to prevent personal-plan usage

### Mapping for maenifold’s Rust fetcher

Do **not** hardcode plan-host rules in maenifold. Mirror Zed’s current strategy:

1. Determine `oauthDomain` from configured `enterprise_uri` with the same host-stripping logic as Zed `parse_domain`.
2. Use GraphQL:
   - no enterprise URI → `https://api.github.com/graphql`
   - enterprise URI present → `https://<parsed-domain>/api/graphql`
3. Query `viewer.copilotEndpoints.api`.
4. Use the returned endpoint for `/models`.
5. If GraphQL discovery fails, fall back to `https://api.githubcopilot.com`.

This handles Business/Enterprise/Individual without embedding `api.individual`/`api.business`/`api.enterprise`/`cht.*` guesswork in maenifold.

## 4) Caching policy

### What I could verify

I could **not** verify a persisted ~24h Zed models cache in commit `450206e49dd070866dce81884bac61caa56dba44`. What I did verify instead:

- Zed refreshes when auth-file contents change (`copilot_chat.rs:552-570`)
- Zed refreshes on startup when it already has a token (`copilot_chat.rs:577-588`)
- live `/models` responses advertise `Cache-Control: private, max-age=21600` (= 6h)

### Recommendation

- **TTL:** 6 hours, matching the upstream `Cache-Control` header actually observed from `/models`
- **Location:** per-user state cache, not config:
  - Linux: `${XDG_STATE_HOME:-~/.local/state}/maenifold/copilot-models/<agent>@<domain>.json`
  - macOS: `~/Library/Application Support/maenifold/state/copilot-models/<agent>@<domain>.json`
- **Cache key:** `(agent, oauthDomain, apiEndpoint)`
- **Do not store the token**; store only:
  - `fetchedAt`
  - `expiresAt`
  - `oauthDomain`
  - `apiEndpoint`
  - `accountHint` if available
  - a non-secret auth fingerprint (for example current `gh` login + endpoint), not the raw token

### Invalidation rules

- force refresh when caller passes `forceRefresh: true`
- refresh on app launch if cache missing or expired
- refresh immediately if:
  - selected auth source changes (`gh` account changed, `apps.json` entry changed, enterprise URI changed)
  - GraphQL returns a different `copilotEndpoints.api`
- if live refresh fails and cache is still unexpired, return cached data with `source: "cache"`

- `ConfigOptionPicker.vue` uses `option.options` exactly as provided  
  — `apps/desktop/src/components/ConfigOptionPicker.vue:31-39, 199-289`

### Recommended overlay strategy

Use an **additive merge keyed by exact `model.id`**:

1. Keep ACP as the base source of truth for:
   - which config options exist
   - current selected values
   - model option ordering / names when the API is unavailable
2. Overlay API capability records by exact model id.
3. For the live `reasoning_effort` option:
   - find the currently selected model from the ACP `model` config option
   - if API capabilities exist for that exact model id, replace only the `reasoning_effort.options` list with the API’s ordered effort enum
   - otherwise leave the ACP option untouched

### Best merge hook

For the **live session** path, the safest hook is `apps/desktop/src/stores/session-getters.ts:56-58`, because it is the last shared computed before `ChatView` renders, and it avoids mutating raw ACP state in `session.configOptions`.

For the **pre-session** path, the natural hook is `apps/desktop/src/lib/agent-probe-normalizers-base.ts:249-261` (or a helper it calls), because that is where the model picker is derived from ACP today.

### Conflict rule

- **ACP wins for existence and current value**
- **API wins for per-model capability detail**
- If API is missing/stale/error, UI falls back to ACP-only behavior

This avoids breaking the current UI contract while still unlocking `xhigh` where the backend API says it exists.

## 7) Open risks / decisions needed before `spec`

1. **Auth-source trust boundary:** should the daemon be allowed to read plaintext Copilot tokens from `~/.config/github-copilot/apps.json`, or is `gh auth token` the only acceptable path? This is a user decision, not just an implementation detail.
2. **Exact-model-id vs family acceptance:** live API results do **not** support the task summary’s “all GPT-5 + Opus 4.7” generalization. On this account:
   - `gpt-5.5`, `gpt-5.4`, `gpt-5.4-mini`, `gpt-5.2`, `gpt-5.2-codex`, `gpt-5.3-codex`, and `claude-opus-4.7-1m-internal` expose `xhigh`
   - plain `claude-opus-4.7` returned only `["medium"]`
   - `gpt-5-mini` returned only `["low","medium","high"]`
   
   So spec-stage acceptance must be keyed to **exact model ids**, not family names.
3. **Workflow schema/UI contract breakage:** workflow code still hardcodes `ReasoningEffort = 'low' | 'medium' | 'high'` and rejects anything else:
   - `apps/desktop/src/lib/workflow-asset-types.ts:55`
   - `apps/desktop/src/lib/workflow-asset-runtime.ts:76-80`
   - `apps/desktop/src/stores/workflow-library-session-actions.ts:74-77`
   
   If `xhigh` should ever be persisted into workflow assets, that is a separate contract change and must be explicitly included or excluded in spec.
4. **New daemon egress path:** `GetCopilotModels` introduces direct daemon-to-GitHub egress outside ACP. That is probably acceptable for a read-only system command, but the spec should state it explicitly because it crosses the APIM trust boundary outward.
5. **Enterprise endpoint handling:** current evidence says GraphQL endpoint discovery is the correct source of truth. If the user expects literal `cht.<gh-domain>` reconstruction instead, that would diverge from current Zed and should be rejected unless they explicitly want that divergence.

## Recommended spec-stage direction

1. Ship a native `maenifold.system.GetCopilotModels` read command.
2. Use `gh auth token --hostname github.com` as the primary auth source.
3. Discover the actual Copilot endpoint via GraphQL `viewer.copilotEndpoints.api`; do not hardcode business/enterprise host rules.
4. Cache model metadata for 6h, matching the live upstream `Cache-Control` header.
5. Overlay API capabilities in the frontend by exact `model.id`, with ACP fallback.
6. Update acceptance text to name exact models that must show `xhigh`.
