# T-48.5 — Composable: `useWorkflowTree`

**Requirement:** FR-48
**Component:** `vendor/acp-ui/src/composables/`

## Summary

Vue composable that takes a workflow session URI and recursively resolves the full execution tree by fetching and parsing workflow and sequential thinking sessions via `useMemoryApi`.

## Acceptance Criteria

1. Create `vendor/acp-ui/src/composables/useWorkflowTree.ts`
2. Exports `useWorkflowTree()` returning:
   - `loadTree(uri: string): Promise<WorkflowTreeNode>` — fetches the root workflow, parses it, then recursively fetches submachines and child workflows
   - `tree: Ref<WorkflowTreeNode | null>` — reactive tree state
   - `loading: Ref<boolean>`
   - `error: Ref<string | null>`
3. **Workflow parsing**: Extract from markdown content:
   - Step headers (`## Step N/M`) and responses (`## Step N/M Response`)
   - Submachine session IDs: regex for `session-\d+-\d+` in response text
   - Child workflow references: regex for `workflow-\d+` in response text
   - Status: look for `## Session Abandoned` or `## Conclusion`
   - Timestamps: `*YYYY-MM-DD HH:MM:SS UTC*` patterns
4. **Thinking session parsing**: Extract from markdown content:
   - Thought headers (`## Thought N/M [agent]`)
   - Thought content and timestamps
   - Conclusion section
5. **Recursive resolution**: For each submachine ID found, fetch its URI via `readMemory(memory://thinking/sequential/...)`. For each child workflow ID, fetch via `readMemory(memory://thinking/workflow/...)`.
6. Uses types from `workflow-types.ts`

## Golden Test Case

Given `memory://thinking/workflow/2026/03/17/workflow-1773720937011`, the tree should resolve to:
- Root: workflow-dispatch (4 steps, all completed)
  - Step 1 submachine: session-1773720949468-20935 (5 thoughts)
  - Step 2 submachine: session-1773721125868-41308 (4 thoughts)
  - Step 3 submachine: session-1773721216626-22867 (3 thoughts)
  - Step 4 submachine: session-1773721291888-29182 (3 thoughts)
  - Step 4 child: workflow-1773721328318 (critical-thinking, 7 steps, abandoned)

### Minor Observations (not spec violations)

1. **Redundant regex group with `m` flag** (lines 201–204, 301–304): `/(^|\n)## Session Abandoned\b/m` — with the `m` flag, `^` already anchors to every line start; the `(^|\n)` alternation is redundant but harmless.

2. **Unreachable `catch` in `buildThinkingNode`** (lines 455–457): `Promise.resolve(synchronous-value)` can never reject, so the cache-cleanup catch block is dead code. No impact on correctness.

3. **Empty-body response not treated as completed**: If a response section's content reduces to an empty string after timestamp stripping, `response?.body` evaluates as falsy and the step receives `status = 'pending'` rather than `'completed'`. This edge case is not part of the spec's acceptance criteria or the golden test.

4. **Single integration test only**: The spec says "add test for parser logic". One comprehensive golden-scenario test is present; no isolated unit tests for `parseWorkflowSession` or `stripTimestampLines`. The golden test thoroughly exercises parser behaviour through the composable, which satisfies the spec's intent.

None of the observations constitute acceptance-criteria violations.
