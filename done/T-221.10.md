# T-221.10 - GatewayBatch Bounded In-Memory Batch Operations

## Problem

The gateway provides `GatewayExecute` for single-command dispatch but lacks a batch operation for submitting multiple commands atomically. Tools-only clients need a way to submit multiple gateway commands in a single call and query batch status.

## Scope

Implement `GatewayBatch` as a new MCP tool that wraps `GatewayExecute` dispatch:

- `submit` operation: validate all items against the GatewayCatalog, execute sequentially, store results
- `status` operation: look up batch results by batchId

## Input Contract

`GatewayBatch`:

- `operation` required enum: `submit` or `status`
- `items` required array when `operation=submit`
- `items[].domain` required
- `items[].command` required
- `items[].parameters` required object
- `items[].idempotencyKey` optional for mutating commands
- `continueOnError` required boolean when `operation=submit`
- `batchId` required when `operation=status`

## Batch State Policy

- Batch state is bounded, in-memory, and gateway-owned.
- If all items complete synchronously, `GatewayBatch` may return terminal results immediately while retaining batch status by batch ID for a bounded retention window.
- `GatewayBatch` status handling must not introduce new SQLite or durable job state.
- Max entries cap (e.g., 1000) with oldest-eviction.

## Acceptance Criteria

- [ ] `GatewayBatch` validates every item against GatewayCatalog before starting execution and rejects the whole batch on schema mismatch.
- [ ] `GatewayBatch` status operation reports queued/running/completed/failed state and per-item results for known batch IDs.
- [ ] `GatewayBatch` rejects any natural-language intent fields.
- [ ] Batch state is bounded, in-memory, and gateway-owned.
- [ ] Unknown batch IDs return a not-found error distinct from operational execution failures.
- [ ] `continueOnError=false` stops execution at first failure.
- [ ] `continueOnError=true` executes all items and reports per-item success/failure.
- [ ] `cargo build --release -p maenifold-cli` succeeds.

### Phase 1: Batch Types

**New:** `mcp/gateway_batch_types.rs`
- `BatchItem` — domain, command, parameters (Map), optional idempotency_key
- `BatchResult` — status (completed/failed), items with per-item success/failure/result
- `BatchState` — bounded `HashMap<String, BatchResult>` with `Arc<Mutex<...>>`, cap=1000, oldest-eviction

### Phase 2: Schema

**Modified:** `mcp/schema/gateway_tools.rs`
- `GatewayBatchParams` struct:
  - `operation: String` (enum: submit/status)
  - `items: Option<Vec<BatchItemParams>>` (required for submit)
  - `continue_on_error: Option<bool>` (required for submit)
  - `batch_id: Option<String>` (required for status)
- `gateway_batch_tool()` function

### Phase 3: Batch Handler

**New:** `mcp/gateway_batch.rs`
- `pub(crate) async fn handle_gateway_batch(state: &GatewayState, batch_state: &BatchState, params: GatewayBatchParams) -> Result<CallToolResult, ErrorData>`
- Submit flow:
  1. Validate ALL items against `GatewayCatalog.resolve()` — reject batch on first mismatch
  2. Generate batch_id (UUID v4)
  3. Execute items sequentially via `state.handle_gateway_execute()` per item
  4. On `continue_on_error=false`: stop at first failure
  5. On `continue_on_error=true`: execute all, collect per-item results
  6. Store result in BatchState
  7. Return terminal results immediately
- Status flow: lookup batch_id in BatchState, return not-found or result

### Phase 4: Wiring

**Modified:** `mcp/gateway_handler.rs`
- Add `if tool_name == "GatewayBatch" { ... }` branch (+6 LOC)
- Route to `handle_gateway_batch` in new file
- `BatchState` stored in `GatewayState` struct (add field)

**Modified:** `mcp/mod.rs`
- Add `mod gateway_batch;`, `mod gateway_batch_types;`
- Add `gateway_batch_tool()` to tool list
