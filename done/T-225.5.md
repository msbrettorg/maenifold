# T-225.5 — Pipeline Session Resource Emitters

## Problem

`pipeline://sessions` is subscribed by the frontend (`PipelineSidebar.vue:91,98`) but never emits `notifications/resources/updated`. The sidebar shows stale data.

## Duo Review R1 Findings

- Wrong path (fixed R2): actual pipeline code at `src/workflow/pipeline/`, not `src/tools/workflow/pipeline/`
- Pipeline tool is NOT the single mutation entry point — autonomous executor also mutates via persist functions
- Need debounce/coalescing for high-frequency executor transitions
- Frontend only subscribes to `pipeline://sessions`, not `pipeline://session/{id}`

## Fix

Create an `emit_pipeline_resource_updated(session_id)` helper following the Teams runtime pattern (`teams/runtime.rs:165-192`). Call it from the pipeline persist chokepoint functions, not from individual tool handlers.

### Emitter Helper

Create a helper function (in `crates/maenifold-core/src/workflow/pipeline/` or a shared location):
```rust
pub fn emit_pipeline_resource_updated(session_id: &str) {
    // Follow teams/runtime.rs:179-192 pattern:
    // Handle::try_current() → spawn, else use NOTIFICATION_RUNTIME
    // Emit notify_resource_updated("pipeline://sessions")
    // Emit notify_resource_updated(&format!("pipeline://session/{}", session_id))
}
```

### Instrumentation Strategy

Rather than a single chokepoint, instrument at **two levels**:

1. **Persist functions** in `session_write.rs` — covers state mutations during execution:
   - `persist_pipeline_state()` — called after state mutations
   - `persist_pipeline_state_with_status()` — called with status changes
   - `persist_final_pipeline_status()` — called at pipeline completion

2. **Additional mutation sites** not routed through persist functions:
   - `write_pipeline_session()` in `session_write_files.rs` — called by create and fork
   - `delete_pipeline_session_files()` — called by delete (emit `pipeline://sessions` only; session no longer exists)
   - `persist_pipeline_runtime_context()` in `session_write_files.rs` — called during `run`

For cancel: handler sends SIGTERM; the driver's cleanup/finalization path calls `persist_final_pipeline_status()` which is already instrumented at level 1.

### Coalescing

Use the existing `mcp/resources/throttle.rs` if available, or apply Teams-style change detection. High-frequency executor ticks can transition many nodes per second — emitting on every tick will spam subscribers. Recommended: throttle to at most 1 emit per 500ms per session.
