# T-45.7b: Dispatch Atomic Write Hardening

**Requirement**: FR-45.7
**RTM**: RTM-342
**Priority**: P1 — interrupt safety

## Context

Red-team audit of T-45.7 identified a two-phase write inconsistency: dispatch updates the node's workflow session status to `active` in one write, then renders the first step in a second write. If interrupted between, the session has `status: active` but no step content. An agent picking up this session would find an empty workflow.

Additionally, if dispatch fails mid-loop and is retried, already-activated nodes get re-activated, causing the first step to be appended a second time.

## Acceptance Criteria

1. **Single-write activation**: When dispatching a node, the status update (`pending` → `active`) and first step rendering SHALL happen in a single `write_markdown` call, not two sequential writes.
2. **Idempotent dispatch**: If a node is already `active` when dispatch runs (e.g., retry after partial failure), it SHALL be skipped — not re-activated or double-rendered.
3. **Skip guard**: Before activating a node, check if its session already has `status: active`. If so, skip it and do not include it in the `dispatched` response array.

## Implementation Notes

- Target: `crates/maenifold-core/src/workflow/pipeline/handler.rs`, `activate_workflow_node_session` function
- Currently: `write_markdown` (status update) then `append_h2_section` (step render)
- Fix: build the full content (status + step) and write once
- For idempotency: read session status before activation, skip if already active

## SWE Remediation

### What I changed
- `crates/maenifold-core/src/workflow/pipeline/handler.rs`
  - Changed `activate_workflow_node_session` to perform activation with a single `write_markdown` call by reading the workflow session once, updating frontmatter status to `active`, rendering the first step into in-memory content, and then writing the combined result once.
  - Added an `active` skip guard so already-active workflow sessions return without re-rendering or appending duplicate step content.
  - Updated `dispatch_pipeline` so skipped already-active sessions are not added to the `dispatched` response array, while the pipeline node state is still healed to `active` in pipeline frontmatter.
  - Added helper logic to preserve the appended step section formatting/frontmatter summary behavior during the single-write activation path.
  - Added tests covering direct activation idempotency and dispatch retry/idempotency behavior.

### Test results
- PASS — `cargo test -p maenifold-core --lib pipeline_dispatch -- --nocapture`
- PASS — `cargo test -p maenifold-core --lib activate_workflow_node_session_skips_active_session_without_duplication -- --nocapture`

### Notes
- I kept the existing step body format (`## Step 1/N`) and workflow-session summary/frontmatter update behavior while removing the second write.
- Dispatch now treats an already-active workflow session as an already-claimed node: it is excluded from `dispatched`, but the pipeline session's node state is updated to `active` so retries heal partial pipeline/session divergence.

## Red-team Audit

**Verdict: PASS**

All acceptance criteria verified:

- **AC1 — Single-write activation**: ✅ verified at `handler.rs:472–495`. `activate_workflow_node_session` mutates frontmatter (`status → "active"`) and builds the full body content (existing content + rendered step) entirely in-memory before issuing a single `write_markdown` call (line 490). No `append_h2_section` is called on the activation path; the three remaining call sites of `append_h2_section` in the file are in `upsert_h2_section` (a different helper, lines 945–954) and two test-fixture helpers (lines 2669, 2676) — none reachable from dispatch.

- **AC2 — Idempotent dispatch**: ✅ verified at `handler.rs:459–465`. Before any write, the function reads the current `status` field from the workflow session's frontmatter. If `status == "active"`, it returns `Ok(false)` immediately with no write. The test `activate_workflow_node_session_skips_active_session_without_duplication` (line 2236) confirms a second call on an already-active session returns `false` and the `## Step 1/1` heading appears exactly once in the session body.

- **AC3 — Skipped nodes excluded from `dispatched`**: ✅ verified at `handler.rs:398–404`. The `dispatched.push(...)` call is gated on `if activated { … }`. When `activate_workflow_node_session` returns `Ok(false)` (skip path), the node is not added to the `dispatched` Vec. The test `pipeline_dispatch_skips_already_active_workflow_sessions` (line 2296) confirms the `dispatched` array is empty when the only ready node was pre-activated.

**Implementation notes (not spec violations):**

- **Pipeline state healing (line 388)**: `state.status = NodeStatus::Active` is set unconditionally — even for skipped nodes — before checking `activated`. This means the pipeline frontmatter always converges the node to `Active` on retry, even if the workflow session was already active. This is the SWE's stated intent ("heal partial pipeline/session divergence") and is consistent with eventual-consistency semantics. The spec does not prohibit this side-effect; it only requires skipped nodes to be absent from `dispatched`.

- **Empty-steps edge case (lines 486–488)**: When a workflow definition has zero steps, the `else` branch returns `existing_content` unchanged, and `update_activation_section_frontmatter` is not called (so `first`/`last` summary fields are not populated). The single write still fires, marking status `active` with no step content. This is outside the scope of the spec's acceptance criteria (which assume a renderable first step exists), and idempotency is preserved because the skip guard at lines 459–465 will correctly short-circuit any subsequent call on the now-active session.

- **TOCTOU informational**: The guard reads session status at line 452 and writes at line 490 without holding a file lock. Two concurrent dispatch calls on the same node could both pass the guard and race to write. This is the same class of risk that exists in the broader pipeline write pattern and is not a regression introduced by this change. It is outside the scope of T-45.7b (which targets retry safety, not concurrent dispatch protection).
