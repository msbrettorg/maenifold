# T-51.7 — Pipeline Join and Fork Operations

**Requirement**: FR-40 (Pipeline Active Executor)
**RTM**: RTM-163 / TC-163
**Component**: `crates/maenifold-core/src/workflow/pipeline/handler.rs`

## Context

Join merges two pipeline DAGs into one. Fork clones a subgraph from a node forward. Both are graph surgery operations on `StableGraph`.

Depends on: T-51.1 (petgraph foundation).

## Acceptance Criteria

### Join

1. Add `join` operation, triggered by `sessionId + join: { sourceSessionId: "...", edges: [...] }`
2. Implement join logic:
   - Read both pipeline sessions
   - Build StableGraphs for both
   - Check for node ID collisions between the two DAGs. If collision: REJECT with error listing conflicting IDs.
   - Merge source graph nodes and edges into target graph
   - Add connecting edges from `join.edges` (these bridge the two former DAGs)
   - Validate merged graph is acyclic
   - Merge node states: source nodes keep their current status
   - Create any missing workflow sessions
   - Persist merged pipeline as the target session
   - Source pipeline session is NOT deleted (caller decides via separate delete)
3. Return updated pipeline view

### Fork

4. Add `fork` operation, triggered by `sessionId + fork: { fromNodeId: "...", newSessionId: "..." }`
5. Implement fork logic:
   - Read pipeline session, build StableGraph
   - Compute reachable subgraph: `fromNodeId` + all nodes transitively downstream (follow outgoing edges)
   - Deep-copy the subgraph into a new pipeline definition:
     - Node IDs prefixed with `fork-{newSessionId}-` to avoid collision if later joined back
     - Edges within the subgraph preserved
   - All copied node states reset to Pending
   - Create new pipeline session with the subgraph definition
   - Create workflow sessions for all copied nodes
   - Original pipeline is NOT modified
6. Return the new pipeline view

### Finding 1 — HIGH: Fork Non-Atomic Write Ordering Corrupts New Pipeline on I/O Failure

**Location**: `fork_pipeline`, lines 514–532 in `handler.rs`

```rust
// WRITE 1: pipeline session file created — nodeStates lists session IDs that don't exist yet
write_pipeline_session(context, &new_session_id, &forked_definition, ...)?;

// WRITE 2..N: workflow session files created AFTER pipeline already references them
for node in &forked_definition.nodes {
    write_workflow_node_session(context, &new_session_id, ...)?;
}
```

The forked pipeline session file is written **before** the workflow session files it references. If any `write_workflow_node_session` call fails mid-loop (disk full, permission error), the new pipeline exists on disk with `nodeStates` entries whose `session_id` files are missing.

Every subsequent read of the forked pipeline calls `derive_pipeline_node_states`, which fails immediately on missing workflow session files:

```rust
if !file_exists(&workflow_uri, &context.config)? {
    return Err(...) // pipeline permanently unreadable
}
```

The forked pipeline is permanently stuck — unviewable and undispatchable. No self-repair path exists short of manual file editing.

**Contrast with join**: `join_pipeline` gets the ordering correct — `ensure_workflow_sessions` runs first (creates missing workflow files), then `write_markdown` commits the pipeline state. Fork must follow the same pattern: write all workflow session files successfully, then write the pipeline session. The fix is to swap the two write blocks.

The same bug exists in `graft_pipeline` (covered in T-51.6).

### Finding 2 — HIGH: Join Has No Running-Pipeline Guard; Creates Silent State Divergence for Active Source Pipelines

**Location**: `join_pipeline` — no status guard on `source_session_id` or `target_session_id`

After a successful join:

- Source nodes are merged into the target pipeline's `definition` and `nodeStates`
- The **source workflow sessions are not updated** — their `pipelineId` frontmatter still points to `source_session_id`

When a source workflow node completes execution, it calls `update_pipeline_node_status(context, source_session_id, node_id, "completed", ...)`. This updates the **source** pipeline, not the merged target. The target pipeline's view of those nodes is **permanently frozen at the status at join time**.

If the source pipeline was running (Active/Ready nodes) at join time, those nodes will never transition in the merged target — they stay Active or Ready forever. `dispatch_pipeline` will never re-dispatch them (already Active), `compute_pipeline_status` will return "active" indefinitely, and any downstream nodes in the target that depend on source nodes completing will never become Ready.

This is a silent, unrecoverable deadlock with no error surfaced to the caller.

**Recommended mitigations** (in priority order):
1. **Guard**: Reject join when source pipeline has any node in `Active` or `Ready` status. Callers should pause/complete the source before joining. Add similar guidance for the target if it is actively running.
2. **Documentation**: If live joins are a desired feature, the spec must explicitly acknowledge that source workflow sessions remain bound to `source_session_id` and that their future completions will not be reflected in the merged target.

### Finding 3 — MEDIUM: Join Silently Creates Parallel Edges

**Location**: `join_pipeline`, lines 372–392

```rust
let merged_definition = PipelineDefinition {
    edges: target_definition.edges.iter().cloned()
        .chain(source_definition.edges.iter().cloned())
        .chain(join.edges.iter().cloned())  // no deduplication
        .collect(),
};
validate_pipeline(&merged_definition)?;
```

`validate_pipeline` does not check for duplicate edges — only duplicate node IDs. If `join.edges` contains an edge that already exists in `target_definition.edges` (or `source_definition.edges`), a **multi-edge** is silently created between the same pair of nodes.

This is normally harmless for same-type duplicate edges (two `Success` edges A→B behave like one). However, if a caller accidentally adds an `Always` edge where a `Success` edge already exists, `compute_ready_set` evaluates `.all(|edge| is_edge_satisfied(...))` across all edges between the pair. The `Always` edge is satisfied when A is Completed, Abandoned, or Stuck; the `Success` edge requires only Completed. Combined with `.all(...)`, the effective behavior becomes the intersection: only Completed satisfies both — which is the same as a single `Success` edge. The user's intent (add an `Always` bypass) is silently ignored.

The same applies to graft: if `graft.edges` duplicates an existing edge, `merge_graft_definition` will not reject it.

**Required fix**: add a duplicate-edge check (by source+target+type tuple) to `validate_pipeline`, or add deduplication before the `.collect()`. Also add a test: join with a duplicate edge in `join.edges` should either be rejected or be idempotent with explicit documentation.

### No Issues Found

- Node ID collision detection is correct and complete: `target_node_ids.intersection(&source_node_ids)` before any mutation. Self-join (same session ID for target and source) correctly rejects because all IDs collide.
- Cycle detection on the merged graph fires before any state is committed — no partial-write window for cycle injection. Both `validate_pipeline` (which includes `is_cyclic_directed`) and a second explicit `is_cyclic_directed` call run before `write_markdown`.
- Fork's `reachable_node_ids` BFS correctly collects all downstream nodes via `Outgoing` edges. A leaf-node fork correctly produces a single-node pipeline.
- Fork node ID remapping (`fork-{newSessionId}-{originalId}`) is applied consistently to both nodes and edges. The forked definition is validated by `validate_pipeline` before any files are written.
- `resolve_join_node_states` correctly falls back to persisted `nodeStates` when a workflow session file doesn't exist, allowing `ensure_workflow_sessions` to recreate it with the preserved status.
- `allocate_node_session_id` bump loop prevents workflow session ID collisions on rapid fork calls.
- `fork_pipeline` checks for an already-existing `new_session_id` before proceeding, preventing accidental overwrite of an existing pipeline.
