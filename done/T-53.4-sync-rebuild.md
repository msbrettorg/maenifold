# T-53.4 — `sync.rs` — Cache Rebuild

**Requirement**: FR-41 (File-Authoritative Pipeline Gate Cache)
**Component**: `crates/maenifold-gate/src/sync.rs`
**Depends on**: T-53.1 (`fs.rs`), T-53.2 (`db.rs`)

## Context

`gate sync` rebuilds `gate.db` from the authoritative task files on disk. This is the recovery mechanism — if the DB is lost, corrupted, or drifted, `sync` reconstructs it. It also serves as the consistency check during normal operation.

## Acceptance Criteria

1. Implement `run_sync(args: &SyncArgs, root: &Path) -> Result<()>` that:

### Discovery and parsing

2. Discovers all task files using `fs::discover_tasks(root)`
3. Parses each file using `parser::parse_task_file()` to extract:
   - Task ID (filename)
   - Title (from H1 heading)
   - Requirement ID (from `**Requirement**: FR-XX` line)
   - Current status (derived from stages/verdicts)
   - Location (todo/done from directory)
4. Collects parse errors as warnings — malformed files are reported but don't abort

### Reconciliation mode (default: `gate sync`)

5. Opens `gate.db` via `db::GateDb::open()`
6. For each parsed task:
   - Upserts into the `tasks` table with file-derived state
   - Reports drift if the DB had a different status/location (as a warning line)
7. Prints summary: `Synced N tasks (M updated, K unchanged, J errors)`

### Rebuild mode (`gate sync --rebuild`)

8. Deletes all existing data via `db::GateDb::delete_all_tasks()`
9. Inserts all parsed tasks fresh
10. Prints summary: `Rebuilt N tasks from disk (J errors)`

### Title and requirement extraction

11. Extract title from the first H1 line: `# T-53.1 — Title` or `# T-53.1: Title`
    - The title is the text after the separator (`—`, `:`, or `–`)
    - If no separator, use the full H1 text after `# `
12. Extract requirement from `**Requirement**: FR-XX` metadata line
    - Match pattern: `**Requirement**:` followed by `FR-\d+` or `NFR-\d+`
    - If not found, use `"UNKNOWN"` and emit a warning

13. Module must be under 150 LOC.

### Observations (non-blocking)

**OBS-1 — Double file read per task** (`Severity: Low / Informational`).  
`sync.rs` calls `fs::read_task(&task.path)` to obtain `content` for `extract_title` / `extract_requirement`, and then calls `parser::parse_task_file(&task.path)` which internally re-reads the same file via `std::fs::read_to_string`. Every task file is therefore opened and read twice. For the expected workload (small markdown files) this is harmless and there is no TOCTOU risk worth worrying about, but it is technically redundant. Fixing it would require `parser::parse_task_content(path, &content)` to be called instead (that public API already exists). No action required.

**OBS-2 — Zero unit tests for `sync.rs`** (`Severity: Informational`).  
`cargo test -p maenifold-gate sync -- --nocapture` matches 0 tests. The acceptance criteria do not explicitly require unit tests for this module, and the function is exercised end-to-end by the binary. However, covering `run_sync` in a temp-dir harness (similar to the `fs` and `db` tests) would improve regression safety for the reconciliation and rebuild paths. No action required for this ticket.

### Findings

**No regressions or new vulnerabilities introduced.**

**OBS-1 — Ambiguous return value from `delete_all_tasks()`** (`Severity: Low / Informational`).
The function returns `Ok(tasks + logs)` — the sum of deleted rows across two tables. The caller in `sync.rs` ignores this return value entirely (uses `?` with `_`). The `delete_all_tasks_clears_tasks_and_logs` test asserts `== 2` (1 task + 1 log), which happens to be correct arithmetic, but the semantics of "sum of rows deleted from two different tables" is opaque. A tuple `(tasks, logs)` would be more self-documenting. Non-blocking; no action required.

**OBS-2 — FK pragma is connection-scoped; no risk of cross-connection bleed** (`Severity: Informational`).
SQLite's `PRAGMA foreign_keys` is a per-connection flag, not a per-DB file flag. The fix correctly sets it per `Connection` instance in both `open()` and `open_memory()`. Any other connection to the same file that does not set the pragma will still silently skip FK enforcement — but all `GateDb` entry points go through one of these two constructors, so enforcement is consistent within this codebase.
