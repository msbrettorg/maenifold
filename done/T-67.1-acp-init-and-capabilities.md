# T-67.1: Capture ACP InitializeResponse and Agent Capabilities

## Requirement
FR-50 — Native ACP client must capture and expose agent capabilities from the ACP handshake.

## Problem
`native.rs` calls `conn.initialize()` but discards the `InitializeResponse`. This means:
- Protocol version mismatch goes undetected
- `agentCapabilities.promptCapabilities` (image/audio/embedded_context support) is unknown
- `agentInfo` (agent name, version, title) is never logged or stored
- `auth_methods` are thrown away (blocks T-67.4)

## Acceptance Criteria
1. `spawn_agent` must bind `InitializeResponse` and store it on the `AgentHandle`
2. Protocol version must be checked — log a warning if mismatch (don't hard-disconnect yet)
3. `AgentHandle` must expose `agent_info() -> Option<Implementation>` (name/version)
4. `AgentHandle` must expose `capabilities() -> &AgentCapabilities`
5. `auth_methods` must be stored for later use by T-67.4
6. Log agent info at connection time: `info!("Connected to {} v{}", name, version)`

## Files to modify
- `crates/maenifold-core/src/acp/native.rs` — capture init response, store on handle
- `crates/maenifold-core/src/acp/mod.rs` — re-export types if needed

## Reference
- `../pipeline-ui/src/composables/useSessionBootstrap.ts` lines 90-110
- `agent-client-protocol` types: `InitializeResponse`, `AgentCapabilities`, `PromptCapabilities`

## Tests
- Existing 234 lib + 125 CLI tests must still pass
- No new tests required (live agent integration)

(`native.rs` ~line 200–213)

**AC2 — Protocol version checked, warning logged on mismatch**: ✅ verified

```rust
if init_response.protocol_version != acp::ProtocolVersion::V1 {
    tracing::warn!(
        "ACP protocol mismatch: requested {}, got {}",
        acp::ProtocolVersion::V1,
        init_response.protocol_version
    );
}
```

`ProtocolVersion::V1 == ProtocolVersion::LATEST` (confirmed in `version.rs`), so the comparison is correct. Agent is not disconnected — matches the "warn, don't hard-disconnect" requirement. (`native.rs` ~line 190–197)

---

**AC3 — `agent_info() -> Option<Implementation>`**: ✅ verified

Signature matches spec exactly. Returns `None` if the mutex is poisoned or the init handshake has not yet completed. (`native.rs` ~line 97–101)

---

**AC4 — `capabilities() -> &AgentCapabilities` (spec) vs `Option<AgentCapabilities>` (impl)**: ✅ acceptable deviation

The spec prescribes `&AgentCapabilities`, but returning a borrowed reference through `Arc<StdMutex<Option<InitInfo>>>` is structurally impossible without surfacing a `MutexGuard` to the caller. The SWE's `Option<AgentCapabilities>` is the only safe design for this pattern — it also correctly models the pre-initialization window where init has not yet completed. The deviation is intentional, documented in the SWE notes, and does not weaken the contract. (`native.rs` ~line 102–106)

---

**AC5 — `auth_methods` stored for T-67.4**: ✅ verified

`auth_methods: init_response.auth_methods` in the `InitInfo` constructor plus `pub fn auth_methods(&self) -> Option<Vec<acp::AuthMethod>>` accessor. The `auth_methods` field on `InitializeResponse` is unconditionally present in the schema (no `unstable_auth_methods` feature gate on the struct field itself — confirmed by inspecting `agent-client-protocol-schema-0.11.2/src/agent.rs`). (`native.rs` ~line 107–111)

---

**AC6 — Log agent info at connection time**: ✅ verified

```rust
if let Some(agent_info) = init_response.agent_info.clone() {
    tracing::info!("Connected to {} v{}", agent_info.name, agent_info.version);
}
```

Message format matches spec exactly. Conditioned on `agent_info.is_some()` — correct, since the ACP schema marks `agent_info` as optional (`Option<Implementation>`) and there is nothing to log when it is absent. (`native.rs` ~line 198–200)

### Red-team focus area findings

**`InitInfo` field coverage** — all required fields captured; no missing data that could block downstream consumers of the handle.

**`Arc<StdMutex<Option<InitInfo>>>` safety** — safe in this async context. The `StdMutex` is never held across an `await` point: the write occurs synchronously inside `spawn_blocking` before the command loop begins; the reads are in synchronous accessor methods. No deadlock or priority-inversion risk.

**Race condition (by-design, not a bug)** — `spawn_agent` returns the handle before the ACP `initialize` handshake completes. A caller who immediately invokes `capabilities()` will receive `None`. This is inherent in the non-blocking spawn design and is the correct behavior given `Option` is used. Callers relying on capability data must account for the init window — T-67.4 should be aware of this.

**Protocol version comparison** — `V1 == LATEST`, so the check is correct today and will catch future version drift if/when V2 is introduced.

**Unused `Default` derive on `InitInfo`** — `InitInfo` derives `Default` but is only ever constructed via `Some(InitInfo { ... })`. The derive is dead code but wholly harmless.
