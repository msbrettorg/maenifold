# T-243.9.0 — Delta Review (architect duo)

Time-boxed 15-minute static review of the rendering stack ahead of the UAT walkthrough. Goal: predict the gaps before someone has to find them by hand. **No tests run.** Findings need confirmation in the actual UI.

## TL;DR

There are **two completely different markdown engines** wired into the desktop app, with non-overlapping feature sets, and neither is a superset of the other. Math is missing everywhere. Mermaid only fires on two surfaces. WikiLink pills look clickable in three surfaces but only navigate in one. The audit checklist will trip on most of these immediately.

## What's actually built today

### Engines

| Path | Library | Used by | Plugins / extensions |
|------|---------|---------|----------------------|
| **A — "rich"** | `markdown-it@14` | `ChatView`, `KnowledgeNoteRenderer` (which is reused by `GateTaskDetail` for the task body and by `GateTaskDetailHistory` for entry notes) | Shiki highlighter (all bundled langs, github-light/dark), custom `wikilinkPlugin` (emits `<span class="note-wiki-pill" data-wikilink="…">`), custom fence override that preserves ` ```mermaid` blocks for the Mermaid pass. `html: false`, `linkify: true`, `breaks: false`, `typographer: false`. |
| **B — "basic"** | `marked` | `ThinkingTraceView`, `PromptAssemblyPreview`, `WorkflowStepDetail` | None. `marked.parse(content, { async: false })` straight into DOMPurify. `WorkflowStepDetail` does a regex pre-pass that turns `[[x]]` into a `<span class="wiki-pill">` (different class, no `data-wikilink`). The other two render `[[x]]` as literal text. |

`marked-highlight` and `highlight.js` are in `package.json` but **not wired into the marked path** — Path B code blocks render unhighlighted.

### Mermaid

`useMermaid()` is invoked from exactly two components: `ChatView` and `KnowledgeNoteRenderer`. So Mermaid renders in chat, knowledge viewer, gate task body, and gate history notes (the last two via `KnowledgeNoteRenderer`). It does **not** render in `WorkflowStepDetail`, `ThinkingTraceView`, or `PromptAssemblyPreview` — those use `marked`, which doesn't preserve a hookable mermaid fence and doesn't call `renderMermaidBlocks`.

Theme is sampled once via `prefers-color-scheme` on first import; toggling app theme afterwards doesn't re-init mermaid.

### Math

No KaTeX, no MathJax, no `markdown-it-katex`, no `markdown-it-texmath`, no `marked-katex-extension` in `package.json`. `$E = mc^2$` and `$$…$$` will render as literal text on every surface. This is a clean miss across the board.

### Workflow tab

`WorkflowMetadataForm` renders the workflow description in a plain `<Textarea>`. There is no rendered preview — the audit's "workflow description" surface is currently raw text only. `WorkflowStepDetail` is the only workflow surface that renders markdown, and it's on Path B.

### Settings tab

No markdown rendering found anywhere under `Settings*.vue`. The audit checklist's "settings markdown surfaces" line is effectively N/A.

## What a user expects (Cursor / GitHub / Notion bar)

1. Same input → same output across every surface.
2. KaTeX-quality inline + display math.
3. Mermaid wherever there's a fence.
4. Syntax highlighting for the common languages on every code block, regardless of which tab.
5. GFM tables, task lists, autolinks, footnotes.
6. Inline images (`data:`, `https:`, and our own `memory://` for assets).
7. WikiLinks that look clickable and actually navigate.
8. Resilient to malformed input — render what you can, error inline for what you can't, never blank-screen.

## Predicted findings (file these against the audit)

Rough severity: **H** = breaks user flow, **M** = visible inconsistency / missing feature, **L** = polish.

### H1 — Two markdown engines, divergent output
Same `.md` will render differently in Chat vs ThinkingTrace vs WorkflowStepDetail. This is the headline gap. The audit's "all surfaces render the same" criterion **cannot pass** until Path B is migrated onto `getMarkdownIt()` (or vice versa, but `markdown-it` is the richer one and already has the WikiLink + mermaid wiring). Recommend: collapse to one engine, route everything through `KnowledgeNoteRenderer` or extract a `<MarkdownView>` wrapper.

### H2 — Mermaid silently broken on Path B surfaces
` ```mermaid ` fences in `WorkflowStepDetail` (workflow step responses), `ThinkingTraceView` (thought bodies), and `PromptAssemblyPreview` will render as a plain `<pre><code>` of mermaid source. Users will assume mermaid is broken. Same fix as H1.

### H3 — Math (`$…$`, `$$…$$`) absent on every surface
Need to add `@vscode/markdown-it-katex` (or `markdown-it-texmath`) + KaTeX CSS to Path A, then collapse Path B onto Path A. KaTeX > MathJax for bundle size — pick KaTeX. This is one fix that solves five surfaces.

### H4 — WikiLink pills are non-clickable in Chat, Gate body, Gate history
The Path A renderer emits `<span class="note-wiki-pill cursor-pointer hover:underline" data-wikilink="X">`. The only delegated click handler for `[data-wikilink]` is in `KnowledgeLeafPane.vue`. So in Chat, GateTaskDetail, and GateTaskDetailHistory the pill *looks* like a button (cursor pointer, underline on hover) but clicking does nothing. Either wire up a global router-level handler, or move the click handler into `KnowledgeNoteRenderer` itself so every consumer gets it for free.

### H5 — Two different WikiLink CSS classes
`useMarkdownIt` emits `note-wiki-pill`, `WorkflowStepDetail` emits `wiki-pill`. They will style differently. Same fix as H1.

### M6 — `markdown-it` core has no task-list support
`- [ ] todo` will render as a literal `[ ]` bullet on Path A. Marked's GFM gives task lists for free, so Path B works and Path A doesn't — perfectly inverted from H2. Add `markdown-it-task-lists` plugin.

### M7 — Footnotes
`marked` parses footnote-ish syntax loosely; `markdown-it` core does not. The corpus's `md-footnotes.md` will render differently across engines. Add `markdown-it-footnote` (or accept that footnotes aren't supported and trim the corpus).

### M8 — Path B code blocks unhighlighted
`marked-highlight` is installed but not wired. ThinkingTrace, PromptAssembly, WorkflowStepDetail render code as unhighlighted monospace. Either wire `marked-highlight` to the bundled Shiki instance, or collapse to Path A (preferred).

### M9 — `memory://` URI inline images stripped
DOMPurify's default URL allowlist is `http(s)|ftp|mailto|tel|callto|sms|cid|xmpp|data` (plus `data:` for images). `memory://` in `<img src>` will be silently stripped. If we want to support `![](memory://…)` we need either a DOMPurify URL allowlist tweak (`ALLOWED_URI_REGEXP`) or a transform in the renderer that resolves `memory://` to a data/blob URL.

### M10 — `<details>` / `<kbd>` / inline HTML divergent
Path A has `html: false` → raw HTML stripped at the parser before DOMPurify ever sees it. Path B uses `marked` defaults (HTML allowed) then DOMPurify (which keeps `<kbd>`, `<details>`, `<u>` in its default allowlist). So `md-html.md` from the corpus renders rich on Path B and as escaped text on Path A. Pick a side, document it.

### M11 — Mermaid theme stale on app theme toggle
`getMermaid()` calls `mermaid.initialize({ theme })` only the first time, sampling `prefers-color-scheme`. If the user toggles the app theme after first render, new diagrams keep the old theme. Re-init on theme change.

### M12 — Workflow description surface has no renderer
The audit lists "workflow descriptions" as a surface. `WorkflowMetadataForm` only shows a `<Textarea>` — no preview. Either wire `KnowledgeNoteRenderer` next to the textarea (split-pane preview) or remove the surface from the audit checklist.

### L13 — Emoji shortcodes (`:tada:`) won't expand
Raw Unicode emoji ✨ work fine on both paths; `:shortcode:` does not. Likely acceptable, but flag if the corpus exercises it.

### L14 — `breaks: false` in Path A vs marked default (also `false` for hard breaks but breaks differently on lists)
Path A treats single newlines as soft breaks (no `<br>`). Marked behaves similarly. Likely fine but worth eyeballing the long-paragraph test input across surfaces.

### L15 — `markdown-it-attrs` / `markdown-it-anchor` absent
No heading anchors → no in-page deep linking from a knowledge note. Probably out of scope for this sprint, note for later.

### L16 — Bundle size concern for Shiki + all bundled langs
`createHighlighter({ langs: Object.keys(bundledLanguages) })` ships every Shiki grammar in the renderer chunk. That's a lot of bytes for a desktop app to lazy-load. Prune to the languages we actually expect (rust, ts, js, py, bash, json, sql, yaml, md, toml, dockerfile, html, css) — probably a 10× shrink.

## Anti-pattern check (per AGENTS.md "Rendering Fallbacks")

The desktop renderer rightly aims to be a rich client. The anti-pattern that still applies: **agent-authored content should remain readable in terminal MCP clients**. We should not change authoring tools (memory writer, workflow definitions, gate notes) to start emitting KaTeX/mermaid/HTML as the *only* representation of a fact. Mermaid for an architecture diagram is fine because the prose around it carries the meaning; mermaid as the entire content of a memory note is not. Worth a one-line reminder in the gate skill / writer prompts after this sprint lands.

## Recommendation

Do these in order:

1. **One engine.** Migrate Path B to `getMarkdownIt()` via a shared `<MarkdownView>` component that wraps `KnowledgeNoteRenderer`'s logic. Kills H1, H2, H5, M6 (after #2), M7 (after #2), M8, M10 in one move.
2. **Plugin pack.** Add to Path A: `markdown-it-task-lists`, `markdown-it-footnote`, `@vscode/markdown-it-katex` (+ KaTeX CSS), optionally `markdown-it-attrs` / `markdown-it-anchor`. Kills H3, M6, M7.
3. **WikiLink click handler at the renderer.** Move the `[data-wikilink]` delegated click out of `KnowledgeLeafPane` and into `KnowledgeNoteRenderer` (or a small composable). Kills H4 across every consumer.
4. **`memory://` image URL handling.** Either widen DOMPurify's `ALLOWED_URI_REGEXP` for `<img>` or resolve `memory://` → `blob:` in the renderer. Kills M9.
5. **Mermaid theme reactive.** Re-init mermaid on app theme change. Kills M11.
6. **Workflow description preview.** Decide: render preview, or drop from audit. Kills M12.
7. **Shiki language prune.** Bundle shrink. L16.

After (1)–(3), the audit corpus should pass on every surface except math (which (2) handles) and `memory://` images (which (4) handles). That's a tight, well-scoped sprint follow-up.

## Open questions for the PM

1. Are we OK on bundle size if we add KaTeX (+CSS) to the desktop renderer chunk?
2. Should agent-authored memory notes be allowed to embed mermaid / math, or do we keep authoring portable and confine richness to client-side rendering of inherently visual content?
3. Is there appetite to drop `marked` + `marked-highlight` from `package.json` once Path B is migrated? (We should — fewer markdown engines = fewer divergence bugs.)

## Notes / caveats

- All findings are static (read of `apps/desktop/src/composables/useMarkdownIt.ts`, `useMermaid.ts`, the four `v-html` consumers, `package.json`). None were verified in a running app. The audit walkthrough should treat this as a hint sheet, not a bug report.
- Two engines, three WikiLink behaviors, one math story (none) — the consistency criterion in `T-243.9` cannot be met by testing alone; it needs the consolidation work above.
