# T-202.9 — Embedding model selection: settings UI, explicit model choice, re-embedding

## Problem

The current embedding model selection is implicit — the system picks the model file in the models directory with the highest dimensionality. There's no way for the user to:

1. See which model is active and why
2. Explicitly choose a different model from the catalog
3. Switch models after initial setup
4. Re-embed all memories when changing dimensions (requires dropping the vector DB and re-syncing)

The onboarding wizard's Model step lets you download a model, but after onboarding there's no way to manage models. The Settings > Models section (T-179.33) shows models but may not have full lifecycle controls.

## Questions for duo

1. **Current model selection logic**: How exactly does the system pick which model to use? Is it truly "highest dimensionality in the folder"? What happens with multiple ONNX files? Where is this code?

2. **Model switching UX**: What should the settings UI look like? A radio selector from the catalog? An "Activate" button per model? What happens to the existing embeddings when you switch?

3. **Re-embedding flow**: Changing dimensions means ALL existing vector embeddings are invalid. The user needs to:
   - Understand the cost (re-embedding N memories takes time)
   - Confirm the action
   - Delete the vector store / index
   - Re-run sync to regenerate embeddings
   Should this be a single "Switch model" button that handles all of this? Or explicit steps?

4. **Onboarding vs Settings**: The wizard downloads a model. Settings manages the model lifecycle. Are these the same UI or different? Should the wizard just set a flag and let Settings handle the details?

5. **Catalog accuracy**: Are the `size_bytes` values in the catalog accurate? Were the 6 models selected through research or just picked by RALPH? Do we need to verify/update the catalog?

## Scope

Cross-cutting: backend model management + frontend settings UI + onboarding model step alignment.
