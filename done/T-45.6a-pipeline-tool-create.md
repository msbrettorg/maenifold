# T-45.6a: Pipeline MCP Tool — Registration and Create

**Requirement**: FR-45.6, FR-45.2
**RTM**: RTM-333, RTM-334, RTM-314, RTM-315, RTM-316, RTM-317
**Priority**: P0 — Core pipeline creation flow

## Context

The Pipeline tool is the MCP interface for all pipeline operations. This spec covers tool registration and the `create` operation, which validates a pipeline definition, pre-creates all workflow sessions, and returns the pipeline ID + initial ready set.

## Scope

1. Register `Pipeline` tool in the MCP registry
2. Implement `pipeline(definition=...)` create operation
3. Pre-create workflow session files per node

## Acceptance Criteria

1. **Tool registration**: Add `Pipeline` tool to `DESCRIPTORS` in `crates/maenifold-core/src/registry.rs` with name `"Pipeline"`, aliases `["pipeline"]`, and invoke function `pipeline::pipeline`.
2. **Entry point**: Create `pub fn pipeline(context: &ToolContext, payload: &Value) -> Result<String>` in `crates/maenifold-core/src/workflow/pipeline/handler.rs`.
3. **Create operation**: When `definition` is present in payload, validate the definition (call `validate_pipeline`), then:
   a. Generate pipeline session ID: `pipeline-{timestamp_millis}`
   b. Create pipeline session file with frontmatter: `type: pipeline`, `status: active`, `definition` (the full node/edge spec), `nodeStates` (initialized as pending with attempt 0), `maxConcurrency` (from payload, default 8)
   c. Pre-create one workflow session file per node
   d. Return JSON with `pipelineId`, initial `ready` set, and `nodes` array with session IDs
4. **Session pre-creation**: For each node:
   a. Read the workflow definition from assets via `read_workflow_definition`
   b. Generate session ID: `workflow-{timestamp_millis}-{node_id}` to prevent collisions
   c. Create session file with frontmatter: `type: workflow`, `status: pending`, `pipelineId`, `nodeId`, `workflowId`, `queue`, `currentWorkflow: 0`, `currentStep: 0`, `phase: running`
   d. Write initial body with `# Workflow Session` heading (no step content yet — steps render on activation)
5. **Pipeline session file path**: Store under `memory://pipelines/{year}/{month}/{day}/{pipeline_id}` (new session URI pattern)
6. **Node session file path**: Use existing workflow session URI pattern `memory://workflows/{year}/{month}/{day}/{session_id}`
7. **Schema/help**: Pipeline tool responds to `learn: true` with help text describing all operations.
8. **Error handling**: Return clear errors for invalid definitions (cycle detected, empty nodes, bad references).

## Implementation Notes

- Follow the pattern in `workflow/handler.rs` for request dispatching
- `pipeline_session_uri` helper creates the pipeline session path
- `read_workflow_definition` already exists in `workflow/mod.rs`
- Use `write_markdown` for file creation (same as `start_workflow_session`)
- The pipeline session file stores the full definition + nodeStates map — this is the pipeline's persistent state
- `initial_workflow_frontmatter` in `queue.rs` creates standard workflow frontmatter — reuse or adapt for pipeline node sessions

- **AC 2 — Entry point signature**: ✅ `handler.rs:21` — `pub fn pipeline(context: &ToolContext, payload: &Value) -> Result<String>` matches spec exactly.

- **AC 3a — Pipeline ID format**: ✅ `handler.rs:53` — `format!("pipeline-{timestamp_millis}")`.

- **AC 3b — Pipeline session frontmatter**: ✅ `handler.rs:152-174` — `type: pipeline`, `status: active`, `definition` (full YAML-serialised definition), `nodeStates` (BTreeMap → YAML mapping), `maxConcurrency` all present.

- **AC 3c — Pre-create one session per node**: ✅ `handler.rs:94` — loop over `node_files` calling `write_workflow_node_session` for every node.

- **AC 3d — Return shape**: ✅ `handler.rs:98-101` — JSON with `pipelineId`, `ready`, `nodes` array of `{ nodeId, workflowId, sessionId }`.

- **AC 4a — Read workflow definition**: ✅ `handler.rs:61` — `read_workflow_definition(&context.config, &node.workflow_id)?` called for every node before writing any file; a missing workflow asset causes the whole create to fail cleanly.

- **AC 4b — Session ID format / collision safety**: ✅ `handler.rs:127-129` — `format!("workflow-{timestamp_millis}-{node_id}")`. The same `timestamp_millis` is captured once before the node loop (line 50), so all node IDs for a pipeline share the same millisecond bucket and are disambiguated by `node_id`.

- **AC 4c — Node session frontmatter**: ✅ `handler.rs:197-211` — `initial_workflow_frontmatter` (queue.rs:202) supplies `type: workflow`, `status: pending`, `queue`, `currentWorkflow: 0`, `currentStep: 0`, `phase: running`; `pipelineId`, `nodeId`, `workflowId` are then inserted explicitly.

- **AC 4d — Node session body**: ✅ `handler.rs:213` — `"# Workflow Session\n"`.

- **AC 5 — Pipeline session URI pattern**: ✅ `sessions/support.rs:20-22` — `memory://pipelines/{year:04}/{month:02}/{day:02}/{session_id}` matches spec.

- **AC 6 — Node session URI pattern**: ✅ *functionally* — `sessions/support.rs:15-17` — `workflow_session_uri` (the existing function the spec instructs to reuse) returns `memory://thinking/workflow/{year}/{month}/{day}/{session_id}`. The implementation correctly calls that function.

  ⚠️ **Spec text discrepancy**: AC 6 explicitly states the path should be `memory://workflows/{year}/{month}/{day}/{session_id}`, but the existing `workflow_session_uri` function (and therefore this implementation) produces `memory://thinking/workflow/...`. The spec is self-contradictory — it says "Use existing workflow session URI pattern" and then states a pattern that doesn't match the existing function. The implementation follows the correct intent ("use the existing function") rather than the incorrect literal path. The spec description should be corrected in a follow-up; no code change required.

- **AC 7 — Schema/help**: ✅ `handler.rs:24-34` — `learn: true` branch loads `pipeline.md` via `load_help_doc`. The asset exists at `assets/usage/tools/pipeline.md` and covers all operations, parameters, return shape, and error conditions.

- **AC 8 — Error handling for invalid definitions**: ✅ `pipeline/mod.rs` — `validate_pipeline` rejects empty node lists, duplicate node IDs, unknown edge source/target, and cycles. `read_workflow_definition` (called per node, line 61) rejects missing workflow assets before any files are written. `parse_max_concurrency` (handler.rs:116-126) rejects non-positive or non-integer `maxConcurrency` values.

**No debug code, no TODOs, no leftover `unwrap()` calls** found in `handler.rs`.

**Summary**: The implementation is complete and correct. The only issue is a stale/wrong path literal in AC 6 of this spec document — `memory://workflows/` should read `memory://thinking/workflow/`. The code should not change; the spec text should be updated.
