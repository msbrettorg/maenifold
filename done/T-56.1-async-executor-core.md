# T-56.1 — Async Pipeline Executor Core

**Requirement**: FR-40 (Pipeline Active Executor)
**RTM**: RTM-159 / TC-159
**Component**: `crates/maenifold-core/src/workflow/pipeline/executor.rs`

## Context

The pipeline currently executes via a bash bridge: `supervisor.rs` spawns `bash maenifold-acp pipeline` which round-trips every dispatch/update through the CLI. This adds latency, requires bash 4.3+, and creates a double-process-spawn chain.

We replace this with a Rust-native async executor that directly calls the existing dispatch and update functions. No new abstractions — just wire existing pieces into a `tokio::task::JoinSet` loop.

### Verified Preconditions

- `ToolContext` is Send+Sync (all owned PathBuf + Copy enum). Safe across tokio task boundaries.
- `AcpxDriver` derives Clone, is Send+Sync, already uses `tokio::process::Command`.
- `tokio::sync::Semaphore`, `CancellationToken` (tokio-util), `JoinSet` are all available — zero Cargo.toml changes.
- `update_pipeline_node_status("completed", conclusion)` requires non-empty `conclusion` string. Use `AcpxResponse.text`.
- `update_pipeline_node_status("abandoned", None)` for failures.
- Tokio runtime already exists in `cli.rs` via `Runtime::new()`.

## Acceptance Criteria

1. Create `crates/maenifold-core/src/workflow/pipeline/executor.rs`
2. Implement `pub(super) async fn execute_pipeline(context: &ToolContext, session_id: &str, prompt: &str, cancel: CancellationToken) -> Result<ExecutionResult>` where `ExecutionResult` is a simple struct with `completed: usize, abandoned: usize, status: String`.
3. The run loop SHALL:
   a. Call `dispatch_pipeline(context, session_id)` to get dispatched nodes (parse the JSON result to extract `dispatched` array with `nodeId`, `sessionId`, `workflowId` entries)
   b. For each dispatched node, spawn an async task into a `JoinSet` that:
      - Creates an `AcpxDriver` for the node's `acpClient` (or a default agent)
      - Calls `driver.prompt(&workflow_session_id, prompt)` 
      - Returns `(node_id, Result<AcpxResponse>)`
   c. Bound concurrency with `tokio::sync::Semaphore` — acquire a permit before spawning, release on completion. Read `maxConcurrency` from pipeline frontmatter (default 8).
   d. As tasks complete from the JoinSet, call `update_pipeline_node_status`:
      - Success (no error): status="completed", conclusion=`response.text` (truncated to 4096 chars if needed)
      - Failure (error or empty text): status="abandoned", conclusion=None
   e. After processing completions, loop back to (a) to dispatch newly-ready nodes
   f. Break when: `dispatch` returns 0 dispatched AND JoinSet is empty (no in-flight work), OR `cancel` is triggered
   g. On cancel: drop the JoinSet (which kills acpx subprocesses via `kill_on_drop`), mark all Active nodes as Abandoned
4. The function SHALL NOT manage processes, signals, PIDs, or threads. All concurrency is via tokio.
5. Add `pub(super) mod executor;` to `mod.rs`.

Prefer the shell script stub approach — it tests the real `AcpxDriver` parsing path without mocking. Create a test helper that writes a temp script returning canned NDJSON, and point `AcpxDriver::new_for_tests` at it.

### Behavioral Analysis (No Bugs Found)

**Dispatch → semaphore interaction**: `dispatch_pipeline` already limits to `max_concurrency - active_count` new nodes. Since each in-flight task holds exactly one semaphore permit, the available permit count always equals `max_concurrency - active_count`. The `for` loop's `acquire_owned().await` will therefore never block. No starvation.

**Cancellation race**: The `biased` select gives priority to `cancel.cancelled()` over `join_next()`. Tasks that complete after cancel fires but before the next poll are not processed — their nodes remain Active on disk and are correctly picked up by `abandon_active_nodes`. Nodes that completed and were processed before cancel are Completed, not touched by `abandon_active_nodes` (which filters for `NodeStatus::Active` only).

**Error propagation**: If `dispatch_pipeline` or `update_pipeline_node_status` returns an error, it propagates via `?` and the JoinSet is dropped without marking in-flight nodes Abandoned. This is an acceptable design given that an infrastructure error is unrecoverable in this context, and the spec does not prescribe failure-mode cleanup.

**Conclusion truncation**: `truncate_chars` uses `.chars().take(4096)` (line 214) — Unicode-safe, will not split multi-byte sequences. Trims whitespace from `response.text` before truncation (line 202). ✅

**Test quality**: 5/5 required tests implemented and passing. Shell-script acpx stub correctly sets cwd via `AcpxDriver.cwd` (`acp/driver.rs:187`: `.current_dir(&self.cwd)`), so `os.getcwd()` in the stub resolves to `maenifold_root`. `PathGuard` restores `PATH` on drop; `#[serial(config)]` prevents concurrent PATH mutations. All 5 required test names present and covering their specified scenarios.

**File size observation (not a rejection criterion)**: 603 lines of test code vs 263 lines of implementation. The acpx stub script (71 lines), `PathGuard`, `install_acpx_stub`, `write_stub_config`, and the stub state reader helpers are test infrastructure that could be moved to `test_support.rs` for reuse. This does not violate the spec but will create duplication if other executor tests need the same stub.
