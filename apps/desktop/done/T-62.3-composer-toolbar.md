# T-62.3 — Type-Aware Node Creation Toolbar

**Requirement**: FR-47
**Component**: `pipeline-ui/src/components/PipelineComposer.vue`
**Design Reference**: `pipeline-ui/docs/design/node-types-ui.md` §1
**Depends on**: T-62.1, T-62.2

## Context

PipelineComposer.vue (397 lines) has a single inline form for adding workflow nodes: workflow ID input + ACP client input + Add Node button. It needs to support all 3 node types with dynamic fields.

## Acceptance Criteria

1. Replace the current single-type toolbar with a type-aware form:
   - **Row 1**: Node type `<select>` (Workflow / Prompt / Sequential Thinking) + Add Node button + Delete Selected + Layout buttons (existing)
   - **Row 2+**: Dynamic fields that change based on selected type

2. Dynamic fields per type:
   - **Workflow**: Workflow ID input (with existing datalist), ACP client input, optional Prompt textarea
   - **Prompt**: Agent input, Tool mode select (disabled/allowed), Prompt template textarea (required)
   - **Sequential Thinking**: Topic input, Agent input, Total thoughts number input, Analysis type input (optional)

3. Validation before addNode():
   - Workflow: `workflowId` required
   - Prompt: `prompt` and `agent` required
   - Sequential Thinking: `topic` and `agent` required

4. On submit, construct a properly typed node using `createNode()` from pipeline-types.ts and call `store.addNode()`.

5. Existing functionality preserved: design mode toggle, layout buttons, delete selected, edge creation, zoom controls.

6. Typecheck: `cd pipeline-ui && npx vue-tsc --noEmit` must pass.

### Criterion 4 — Calls `createNode()` or `store.addNode(type, fields)` on submit
**PASS** ⚠️ with **Medium finding**

Both are called. `createNode()` is called in `submitNode()` and `store.addNode()` follows in each switch branch. Typecheck passes (`vue-tsc --noEmit` exit 0); the store's typed overloads (`WorkflowNodeInput`, `PromptNodeInput`, `SequentialThinkingNodeInput`) are satisfied.

**Finding M-1 (Medium) — `createNode()` return value is silently discarded**

```typescript
// PipelineComposer.vue  submitNode()
function submitNode(type: PipelineNodeType, fields: Record<string, unknown>): void {
  createNode(type, fields);          // ← node constructed, ID generated, DISCARDED
  switch (type) {
    case 'prompt':
      store.addNode('prompt', { ... }); // store calls createNode() internally → second ID
```

`store.addNode(type, fields)` calls `createNode()` internally (confirmed in `pipeline.ts:142`). This means two `PipelineNode` objects are constructed per submit, each with a distinct `Date.now()`-based ID, and the first is thrown away. The spec AC says "construct a properly typed node using `createNode()` … and call `store.addNode()`" — the intent is to use the constructed node, not to call `createNode()` as a validator and reconstruct separately.

**Impact:** No runtime bug today because the store's second `createNode()` call has identical inputs and the form validation already ensures required fields are present. However, the pattern is fragile: the two field-reconstruction paths (inline in `submitNode` and inside `store.addNode`) can diverge if either is updated without updating the other.

**Recommended fix:**
```typescript
function submitNode(type: PipelineNodeType, fields: Record<string, unknown>): void {
  const node = createNode(type, fields); // use the node
  store.addNode(node);                   // addNode(PipelineNode) overload — no double-construct
  nextTick(() => fitView());
}
```

### Criterion 5 — Form clears after successful add
**PASS**

`handleSubmit()` calls `props.submitNode()` then `resetCurrentDraft()`. Because the call is synchronous and sequential, `resetCurrentDraft()` only executes if `submitNode` returns without throwing — correct behaviour. `resetCurrentDraft()` clears only the currently active type's fields, leaving drafts for other types intact, which is correct UX (switching types and back preserves in-progress work, only a successful submit resets).

**Finding L-1 (Low) — `Record<string, any>` annotation retained in modified `PipelineComposer.vue`**

```typescript
// Line 60 — pre-existing, reformatted to single line by T-62.3
const nodeTypes: Record<string, any> = { pipelineNode: markRaw(PipelineNodeCard) };
```

This annotation predates T-62.3 (confirmed via `git diff HEAD` — the `-` side also contains `Record<string, any>`; T-62.3 only collapsed it from multi-line to single-line). It does not violate the literal criterion (`as any` cast), but it is an `any` annotation in a modified file. The correct type for VueFlow's `nodeTypes` registry is `Record<string, Component>` or the VueFlow-provided `NodeTypesObject`.

**Recommended fix:**
```typescript
import type { NodeTypesObject } from '@vue-flow/core';
const nodeTypes: NodeTypesObject = { pipelineNode: markRaw(PipelineNodeCard) };
```
