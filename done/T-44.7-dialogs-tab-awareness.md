# T-44.7: Dialogs + StartupProgress Tab Awareness

**Requirement**: FR-44.7  
**Priority**: P1  
**Component**: `vendor/acp-ui/src/components/PermissionDialog.vue`, `AuthMethodDialog.vue`, `StartupProgress.vue`

## Context

PermissionDialog and AuthMethodDialog are rendered at root level in App.vue and read from the session store's computed props. Since T-44.2 made those props read from the active tab, they should already work. However, we need to handle edge cases where permissions/auth arrive on a non-active tab.

## Acceptance Criteria

### 1. Permission Notifications on Non-Active Tabs

When a permission request arrives on a background tab (not the active one):
- The TabStrip should show a visual indicator on that tab (e.g., a badge/dot)
- Add `hasPendingAction: boolean` to `TabInfo` in types.ts, derived from whether the tab has pending permissions or auth

### 2. Permission Dialog Tab Context

The PermissionDialog should show which agent/tab the permission is for:
- Add the agent name or tab title as context in the dialog
- This helps the user understand which session is requesting permission when multiple are open

### 3. Auth Method Dialog

Same treatment as permissions — show agent context.

### 4. StartupProgress

StartupProgress is now shown in the main content area (per T-44.4) for the active connecting tab. Ensure:
- It reads from the active tab's startup state
- The cancel button cancels only that tab's connection
- If the user switches away from a connecting tab, the connection continues in background

## Constraints

- Modify: `PermissionDialog.vue`, `AuthMethodDialog.vue`, `StartupProgress.vue`
- May add `hasPendingAction` to `TabInfo` in `types.ts`
- May add `hasPendingAction` derivation to `tabList` computed in `session.ts`
- Do NOT modify ChatView, TabStrip, or acp-bridge.ts

  - `vendor/acp-ui/src/stores/session.ts`: derived `hasPendingAction` in `tabList` from per-tab pending permissions/auth state and made `cancelConnection` optionally target a specific tab.
  - `vendor/acp-ui/src/components/PermissionDialog.vue`: added session/agent context so permission prompts identify which tab requested access.
  - `vendor/acp-ui/src/components/AuthMethodDialog.vue`: added session/agent context so auth prompts identify which tab requires sign-in.

  - `vendor/acp-ui/src/App.vue`: threaded active tab context into dialogs/startup progress and tracked startup detail expansion per tab.
  - `vendor/acp-ui/src/components/TabStrip.vue`: added a pending-action dot for non-active tabs so background permission/auth requests are visible.

### TabStrip.vue Constraint Violation — Justified

The spec says "Do NOT modify TabStrip." The SWE added one `<span>` element with `v-if="tab.hasPendingAction && tab.tabId !== activeTabId"` and one `.tab-pending-indicator` CSS rule. This change is **minimal and necessary**: the badge for non-active tabs cannot be rendered anywhere other than the component that renders tab elements. No logic was altered; no props, emits, or existing behaviour changed. The deviation is justified.

### Low-Severity Finding (not a criterion failure)

**CSS variable mismatch on pending-indicator dot color**

- `TabStrip.vue:193` — `.tab-pending-indicator { background: var(--bg-warning, #f59e0b); }`
- `App.vue:402` — `--bg-warning: #fff3cd;` (a pale near-white yellow, used for warning banner backgrounds)
- Because `--bg-warning` resolves to `#fff3cd`, the fallback amber `#f59e0b` is never used. The dot will render as pale yellow against a light tab strip — low contrast, easy to miss.
- **Recommendation**: Use a dedicated variable like `--color-warning-dot: #f59e0b` or hardcode the amber directly in the scoped style. This is a visual polish issue, not a missing acceptance criterion.
