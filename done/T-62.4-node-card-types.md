# T-62.4 — Visual Node Type Differentiation

**Requirement**: FR-47
**Component**: `pipeline-ui/src/components/PipelineNodeCard.vue`
**Design Reference**: `pipeline-ui/docs/design/node-types-ui.md` §2
**Depends on**: T-62.1

## Context

PipelineNodeCard.vue (209 lines) renders all nodes identically — same color, same layout, showing `workflowId` as the primary label. With 3 node types, users need to tell them apart at a glance.

## Acceptance Criteria

1. Accent color by type (left border + header background tint):
   - Workflow: `#2196f3` (blue — current color)
   - Prompt: `#9c27b0` (purple)
   - Sequential Thinking: `#ff9800` (orange)

2. Icon + type label in the header:
   - Workflow: `⚙️ wf: {workflowId}`
   - Prompt: `💬 prompt: {first30chars}...`
   - Sequential Thinking: `🧠 think: {topic}`

3. Metadata shown below the header:
   - Workflow: ACP client (if set), prompt preview (if set)
   - Prompt: Agent name, tool mode
   - Sequential Thinking: Agent name, total thoughts

4. Use `getNodeType()` and/or type guards from pipeline-types.ts to branch rendering.

5. Status indicator (emoji + color) must still work for all types (it's status-based, not type-based).

6. The node card `data` prop must be updated to accept the new fields. The data object comes from the VueFlow node's `data` property, which is set in PipelineComposer.vue when converting pipeline nodes to flow nodes.

7. Typecheck: `cd pipeline-ui && npx vue-tsc --noEmit` must pass.

### Criterion 5 — Works in both design mode (PipelineNode) and server mode (ViewNode)

**FAIL**

**Finding — `inferNode` has an incorrect type-detection ordering that silently misidentifies workflow nodes with a `prompt` field.**

`WorkflowNode` (pipeline-types.ts line 28–33) and `WorkflowViewNode` (line 71–76) both declare `prompt?: string` — an optional prompt that serves as a system-prompt override. When such a node is passed without an explicit `type` field (also optional: `type?: "workflow"` on both types), the branch on line 43 fires incorrectly:

```ts
// PipelineNodeCard.vue line 43
if (data.type === 'prompt' || data.prompt || data.workflowId?.startsWith(promptPrefix)) {
  return { ..., type: 'prompt', ... };  // ← wrong classification
}
```

Because `WorkflowNode.type` is optional, any workflow node arriving without a serialized `type` key — but with `prompt` set — is silently reconstructed as a `PromptNode`. The result:

- The accent color changes from `#2196f3` to `#9c27b0`
- The header shows `💬 prompt` instead of `⚙️ workflow`
- `workflowId` and `acpClient` disappear; `agent` is populated from `data.acpClient ?? 'agent'` (line 47)

This is a latent bug in server mode too: `WorkflowViewNode` carries the same optional `type` and optional `prompt` fields (pipeline-types.ts lines 71–76). If the MCP server omits the `type` key on a workflow node that has a system prompt set, the card renders as a purple prompt card.

**Reproduction path** (design mode):
```ts
// Valid PipelineNode — no type key, but has a prompt
{ id: 'n1', workflowId: 'my-pipeline', prompt: 'You are a helpful assistant.' }
// → inferNode returns PromptNode instead of WorkflowNode
```

**Root cause**: the guard `data.type === 'workflow'` is missing as an early-exit before the heuristic checks. The fix is to restructure `inferNode` so an explicit `type: 'workflow'` (or the presence of `workflowId` without a prompt/type override) takes priority:

```ts
if (data.type === 'workflow' || (data.workflowId && data.type !== 'prompt' && data.type !== 'sequentialThinking' && !data.topic)) {
  // → workflow branch
}
```

**Secondary issue** (TypeScript gap): `NodeCardData` does not declare `sessionId` or `output`, which are required base fields on all `ViewNode` variants. A parent passing a `ViewNode` through a typed template binding may surface a type error depending on how PipelineComposer.vue constructs the prop. Not a runtime defect, but a type-contract gap between the component's prop type and the server-mode data shape.
