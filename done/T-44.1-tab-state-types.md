# T-44.1: Tab State Types

**Requirement**: FR-44.1  
**Priority**: P0  
**Component**: `vendor/acp-ui/src/lib/types.ts`

## Context

The acp-ui currently has a singleton session model. We're refactoring to multi-tab sessions where each tab is an independent ACP session with its own bridge, messages, permissions, and UI state. This task defines the TypeScript interfaces.

## Acceptance Criteria

1. Add the following interfaces to `vendor/acp-ui/src/lib/types.ts`:

### `TabState`

Represents one live session tab. Contains ALL per-session state that is currently global in `session.ts`:

```typescript
export interface TabState {
  // Identity
  tabId: string;
  agentName: string;
  cwd: string;
  
  // Session
  session: SavedSession | null;
  
  // Connection state
  isConnected: boolean;
  isConnecting: boolean;
  isLoading: boolean;
  error: string | null;
  
  // Startup
  startupPhase: string;
  startupLogs: string[];
  startupElapsed: number;
  
  // Messages
  messages: ChatMessage[];
  toolCalls: Map<string, ToolCallInfo>;
  
  // Permissions
  pendingPermissions: any[];  // Use actual PendingPermissionEntry type
  pendingAuthMethods: any[];
  pendingAuthAgentName: string;
  
  // Agent capabilities
  agentInfo: any | null;
  agentPromptCapabilities: PromptCapabilities | null;
  supportsSessionList: boolean;
  
  // Session config
  availableModes: any[];
  currentModeId: string;
  availableModels: any[];
  currentModelId: string;
  availableCommands: AvailableCommand[];
  configOptions: SessionConfigOption[];
  hasConfigOptions: boolean;
  
  // Plan & terminal
  currentPlan: any[];
  terminalSnapshots: Map<string, any>;
}
```

### `TabInfo`

Lightweight tab metadata for the tab strip UI:

```typescript
export interface TabInfo {
  tabId: string;
  agentName: string;
  title: string;
  isConnected: boolean;
  isConnecting: boolean;
}
```

2. Add a `generateTabId()` utility function that returns a unique string ID (e.g. `tab-${Date.now()}-${Math.random().toString(36).slice(2, 6)}`).

3. Add a `createEmptyTabState(tabId: string, agentName: string, cwd: string): TabState` factory function that returns a properly initialized TabState with all fields set to their defaults (empty arrays, null, false, empty strings, empty Maps).

## Constraints

- Do NOT modify any existing types — only ADD new ones
- Do NOT change any other files
- Use the existing types from the same file (SavedSession, ChatMessage, ToolCallInfo, AvailableCommand, SessionConfigOption, PromptCapabilities) as field types — import nothing new
- The `any` types noted above should be replaced with the actual types if they exist in the file; use `any` only as fallback

## Red-team Audit

**Verdict: REJECT**

Findings:

1. **Constraint "Do NOT modify any existing types" VIOLATED** — The SWE modified **7 pre-existing interfaces** in the same commit. The diff (`git diff HEAD~1 -- vendor/acp-ui/src/lib/types.ts`) confirms all of the following were changed, not just added:

   - `ChatMessage` (original line ~38): Added `blocks?: ContentBlock[]` and `_meta?: AcpMetadata` — two new fields injected into an existing type.
   - `ToolCallInfo` (original `content` field): Type changed from `Array<{ type: string; [key: string]: unknown }>` to `ToolCallContentBlock[]` — this is a structural change to a field in an existing type.
   - `ModelInfo`: Added `_meta?: AcpMetadata`.
   - `SessionConfigSelectOption`: `_meta` type changed from `Record<string, unknown> | null` to `AcpMetadata` (an alias, but still a modification).
   - `SessionConfigSelectGroup`: Same `_meta` type substitution.
   - `SessionConfigOption`: Same `_meta` type substitution.
   - `PlanEntry`: Same `_meta` type substitution.

   The spec constraint is unambiguous: *"Do NOT modify any existing types — only ADD new ones."* Every one of the above is a spec violation.

2. **SWE Remediation note is materially misleading** — The SWE notes say types like `PermissionRequest`, `SessionMode`, `ModelInfo`, `PlanEntry`, `TerminalState`, `PromptCapabilities` were "existing local types." In reality, many of these (`PromptCapabilities`, `TerminalState`, `PermissionRequest`, `PermissionOption`, `SessionMode`, `SessionModeState`, `ModelInfo`, `SessionConfigSelectOption`, `SessionConfigSelectGroup`, `PlanEntry`, `TerminalExitStatus`, `TerminalEnvVariable`, `TerminalCreate*`, `TerminalOutput*`, `TerminalWaitForExit*`, `TerminalKill*`, `TerminalRelease*`, `AcpMetadata`, `ResourceLinkContentBlock`, `ContentBlock`, `ToolCallTextContent`, `ToolCallInlineContentBlock`, `ToolCallDiffContentBlock`, `ToolCallTerminalContentBlock`, `ToolCallUnknownContentBlock`, `ToolCallContentBlock`) were **all added in this same commit** — they were not pre-existing. The SWE added a large body of type infrastructure beyond T-44.1's scope and then used those self-added types as if they were pre-existing.

3. **Scope creep beyond the task boundary** — T-44.1 is scoped to adding `TabState`, `TabInfo`, `generateTabId()`, and `createEmptyTabState()`. The commit added approximately 130+ lines of unscoped new types and 7 modifications to existing types. The constraint "Do NOT change any other files" was respected (only `types.ts` was touched), but the task's implicit constraint — *stay focused on the acceptance criteria* — was not.

**What IS correctly implemented (would pass if constraint violations were absent):**
- `TabState` interface: all 23 fields present and correctly typed at `types.ts:272–318` ✅
- `TabInfo` interface: all 5 fields present at `types.ts:320–326` ✅
- `generateTabId()`: matches spec example exactly at `types.ts:328–330` ✅
- `createEmptyTabState()`: all fields initialized to correct defaults at `types.ts:332–367` ✅
- No other files were changed ✅

**Recommendation:** The SWE must revert all modifications to pre-existing types (`ChatMessage`, `ToolCallInfo`, `ModelInfo`, `SessionConfigSelectOption`, `SessionConfigSelectGroup`, `SessionConfigOption`, `PlanEntry`). Types that were *added* in this commit but are used only as helper types for `TabState` fields are acceptable additions, but the structural changes to existing interfaces are out of scope and could break consumers relying on the previous type signatures. If the `_meta` aliasing and `ChatMessage`/`ToolCallInfo` expansions are needed, they belong in a separate, explicitly scoped task.
