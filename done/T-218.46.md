# T-218.46 — Wire Teams Auth Lifecycle into TeamsMonitor

## Problem

TeamsMonitor can initiate device-code flow but has no composed lifecycle: no completion action, no secure persistence, no restart restore, no refresh, no sign-out.

## Decomposed from T-218.30

This is sub-task 2 of 3. Depends on T-218.45 (keyring credential store).

## Design Decisions (from duo review)

1. **client_id/tenant_id source**: The `authenticate` action payload already provides `clientId` and `tenantId`. On `authenticate_start`, persist these into `TeamsMonitorConfig` (or a parallel static registry) so `enable` can call `credential_store::retrieve_token` on restart without user input.

2. **Device-code pending flow**: Store pending `device_code` in a `LazyLock<RwLock<Option<PendingDeviceCode>>>` alongside TeamsRuntimeState — NOT in TeamsRuntimeState itself (avoids leaking secret material into status snapshots). Single-flight: reject `authenticate_start` if a pending code already exists.

3. **Auth state vocabulary**: Add `pending_auth`, `authenticated`, `unauthenticated` to `connection_state` vocabulary via new helpers (`set_teams_pending_auth`, `set_teams_authenticated`, `set_teams_unauthenticated`) in `runtime.rs`.

4. **Refresh failure**: Delete stored credentials + transition to `unauthenticated`. Stale refresh tokens are unrecoverable.

5. **Action naming**: Keep existing `"authenticate"` as alias for `authenticate_start`. Add `authenticate_complete`, `refresh`, `sign_out` as new actions in the MCP schema.

## Implementation

Wire existing `TeamsAuth` methods through `TeamsMonitor` with credential store integration:

- `authenticate` (existing, becomes `authenticate_start`): calls `initiate_device_code`, stores `(client_id, tenant_id)` in config, transitions to `pending_auth`
- `authenticate_complete` (new): calls `acquire_token` with pending device code, stores token via `credential_store`, transitions to `authenticated`
- `refresh` (new): checks `is_token_valid`, calls `refresh_token` if expired, updates `credential_store`. On failure: delete creds + `unauthenticated`
- `sign_out` (new): calls `credential_store.delete_token`, transitions to `unauthenticated`
- On `enable` (app start): reads `(client_id, tenant_id)` from config → `credential_store.retrieve_token` → valid: `authenticated`; expired: attempt refresh; none: `unauthenticated`

## Acceptance Criteria

- [ ] TeamsMonitor exposes authenticate (start), authenticate_complete, refresh, sign_out actions
- [ ] authenticate persists client_id/tenant_id for later restore
- [ ] authenticate_complete stores tokens via credential_store
- [ ] Pending device code is stored in a static registry, not in TeamsRuntimeState
- [ ] Concurrent authenticate_start calls are rejected (single-flight)
- [ ] On enable, TeamsMonitor restores token from credential_store using persisted client_id/tenant_id
- [ ] Expired stored tokens trigger automatic refresh attempt
- [ ] Refresh failure deletes stored credentials and transitions to unauthenticated
- [ ] sign_out deletes stored credentials and transitions state
- [ ] All state transitions emit resource notifications for teams://status
- [ ] `cargo build --release -p maenifold-cli` succeeds
