# T-177.3 — Update WHAT_WE_DONT_DO.md — reconcile plugin rejection with T-126.x backlog

## Intent

The "Features We've Explicitly Rejected" section says:

> ### 1. **Plugin System**
> "We should add a plugin system so users can extend functionality!"
> **No.** Users can modify the source. A plugin system adds complexity and constraints. The absence of a plugin API means users can change anything.

Meanwhile T-126.0 through T-126.8 define a full plugin runtime with trust, provenance, transactional install, MCP registration, lifecycle management, and rollback. This is a direct contradiction.

WHAT_WE_DONT_DO.md already has a "What We Changed Our Minds About" section that handles this gracefully for decay weighting. The plugin evolution deserves the same honest treatment.

## Scope

1. Move the Plugin System entry from "Features We've Explicitly Rejected" to "What We Changed Our Minds About"
2. Add an evolution entry explaining:
   - Original position: no plugin system, users modify source
   - What changed: the MCP ecosystem matured, and maenifold's role as a cognitive control plane requires hosting third-party capabilities under explicit policy
   - What we preserved: plugins run under consent, provenance, namespacing, ownership metadata, and disabled-by-default lifecycle — not an open "anything goes" extension point
   - Reference the T-126.x backlog as the concrete plan

## Files touched

- `docs/ma/WHAT_WE_DONT_DO.md` (edit)

## Acceptance criteria

1. Plugin system no longer listed as "explicitly rejected"
2. Evolution entry in "What We Changed Our Minds About" table and narrative
3. Honest about why the position changed
4. Clear about what constraints are preserved
