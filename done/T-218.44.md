# T-218.44 — Teams Monitor Trouter Lifecycle Wiring

## Problem

The Teams Monitor has all the infrastructure pieces in place but nothing wires them together:
- `TrouterClient` in `teams/trouter.rs` handles WebSocket connection + message parsing but is orphaned (no caller)
- `TeamsRuntimeState` in `teams/runtime.rs` tracks connection/auth state and emits MCP resource notifications
- `MessageHandler` in `teams/handler.rs` does keyword matching on messages
- `CredentialStore` in `teams/credential_store.rs` persists tokens in the OS keychain (T-218.45)
- `TeamsDispatchRequest` in `teams/dispatch.rs` builds ACP payloads for matched messages

This task creates a `TrouterSupervisor` that manages the lifecycle: `enable` starts a `TrouterClient` with a valid token, pipes messages through `MessageHandler`, and dispatches matched messages via `AcpExec`. `disable` cancels via `CancellationToken`.

## Dependencies (all shipped)

- **T-218.45** (keyring credential store) — `credential_store.rs` for token persistence
- **T-218.46** (auth lifecycle) — `auth.rs` for device code flow, token refresh

## Design

### Supervisor struct (`teams/supervisor.rs`, new file)

```rust
pub struct TrouterSupervisor {
    cancel: CancellationToken,
    join_handle: Option<JoinHandle<()>>,
}
```

- `start(token, handler_config, dispatch_agent, dispatch_fn)` → spawns a tokio task that:
  1. Reports `set_teams_connecting()` before entering the run loop
  2. Creates `TrouterClient::new(token, cancel.child_token())`
  3. Creates `let mut handler = MessageHandler::new(handler_config)` (mutable — tracks cooldown)
  4. Creates `mpsc::channel::<EventMessage>` for messages
  5. Spawns two concurrent tasks within the supervisor:
     - **Runner**: calls `client.run(msg_tx)` — this internally loops, reconnects, backs off. Injected via `RunnerFn` trait for testability:
       ```rust
       type RunnerFn = Arc<dyn Fn(CancellationToken, mpsc::Sender<EventMessage>) -> Pin<Box<dyn Future<Output = Result<()>>>> + Send + Sync>;
       ```
       Default creates a real `TrouterClient` and calls `run()`. Tests inject a fake that sends controlled messages.
     - **Processor**: reads from `msg_rx` and for each `EventMessage`:
       - Updates `lastMessageAt` via `update_teams_runtime_state`
       - On first message received: reports `set_teams_authenticated()` (coarse-grained connection proof)
       - Calls `handler.handle(&message)` → `Option<MatchResult>` (`&mut self`)
       - On match: updates `lastMatchAt`, `matchCount` via `update_teams_runtime_state`
       - On match with dispatch_agent: calls `dispatch_fn(payload)` (see Dispatch below)
  6. If runner returns `Err`: reports `set_teams_error(message)`, supervisor exits
  7. If runner returns `Ok` (cancellation): reports `set_teams_disabled()`, supervisor exits
- `stop()` → cancels token, awaits join handle

### State reporting (coarse-grained, no TrouterClient changes)

`TrouterClient::run()` owns the connect/reconnect/listen loop internally. The supervisor uses coarse-grained state:
- Before `run()`: `set_teams_connecting()` — supervisor is attempting connection
- On first `EventMessage` received via mpsc: `set_teams_authenticated()` — connection is alive and receiving
- On `run()` returning `Err`: `set_teams_error()` — connection failed terminally
- On `run()` returning `Ok` (cancel): `set_teams_disabled()` — clean shutdown
- Per-message: `lastMessageAt` updated on every received message
- Per-match: `lastMatchAt` and `matchCount` updated on keyword match
- Per-dispatch: `activeDispatches` incremented on dispatch, decremented via drop guard (`ActiveDispatchGuard`) on completion

This avoids modifying `TrouterClient` (truly no changes to `trouter.rs`).

### Dispatch mechanism

ACP dispatch uses `spawn_blocking` to bridge the sync/async boundary:

```rust
type DispatchFn = Arc<dyn Fn(Value) -> Result<String, String> + Send + Sync>;
```

Default implementation wraps `ToolRegistry`:
```rust
let dispatch: DispatchFn = Arc::new(|payload| {
    ToolRegistry::global()
        .try_invoke("AcpExec", &payload, OutputFormat::Json)
        .map_err(|e| e.to_string())
});
```

Supervisor calls dispatch via:
```rust
tokio::task::spawn_blocking(move || {
    let _guard = ActiveDispatchGuard::new(); // held for entire dispatch lifetime
    dispatch(payload)
});
```

The `DispatchFn` trait object enables test injection — tests can provide a mock that records calls without invoking a real ACP session.

### TeamsMonitor enable wiring

Fold into existing `restore_on_enable()` flow in `teams_monitor_auth.rs`:
1. `restore_on_enable` already runs on enable — extend it to start the supervisor
2. Retrieves token from `credential_store::retrieve_token(client_id, tenant_id)`
3. If `None`: returns error "authentication required — run authenticate_start first"
4. If expired: attempts refresh via existing `refresh_if_needed()`
5. Spawns supervisor on a dedicated multi-thread runtime (use same pattern as `ACP_EXEC_RUNTIME` in `acp_exec.rs`):
   ```rust
   static SUPERVISOR_RUNTIME: LazyLock<Result<Runtime, String>> = ...;
   ```
6. Stores supervisor handle in a global `LazyLock<Mutex<Option<TrouterSupervisor>>>`

Note: `teams_monitor_auth.rs` is at 299 LOC. If supervisor-start wiring pushes it over 300, extract the supervisor runtime + global handle into `supervisor.rs` and call through from `restore_on_enable`.

### TeamsMonitor disable wiring

1. Takes supervisor from the global, calls `stop()`
2. State transitions to "disabled" via `set_teams_disabled()`

### Token expiry during long-lived sessions

Out of scope for this task. If the token expires while `TrouterClient` is running, the WebSocket will receive an auth error, `run()` will attempt reconnect with the stale token, and eventually surface a terminal error → supervisor reports `set_teams_error()`. Token refresh during supervisor lifetime is a follow-up task.

### Restart/restore (stretch goal — defer if > 300 LOC per file)

The daemon-startup-restore path (auto-reconnect on daemon restart when previously enabled) requires persisting the "enabled" flag and is explicitly deferred to a follow-up task if it pushes scope.

## Acceptance Criteria

- [ ] `TeamsMonitor enable` starts a managed `TrouterClient` when a valid token exists in credential store
- [ ] `TeamsMonitor enable` with no stored token returns error "authentication required"
- [ ] `TeamsMonitor disable` cancels the supervisor and closes WebSocket cleanly
- [ ] Coarse-grained state: `connecting` before `run()`, `authenticated` on first message, `error` on terminal failure, `disabled` on cancel — all update `TeamsRuntimeState`
- [ ] Per-message: `lastMessageAt` updated on every received `EventMessage`
- [ ] Per-match: `lastMatchAt` and `matchCount` updated on `handler.handle()` returning `Some(MatchResult)`
- [ ] When `dispatch_agent` is configured, matched messages invoke `AcpExec` with `TeamsSessionMetadata` in payload via `spawn_blocking`
- [ ] `ActiveDispatchGuard` increments/decrements `activeDispatches` around dispatch calls
- [ ] Supervisor accepts injectable `DispatchFn` for test seams — tests can verify dispatch calls without live ACP
- [ ] `cargo build --release -p maenifold-core` succeeds
- [ ] No file exceeds 300 LOC
