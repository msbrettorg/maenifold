# T-214.0 — Session-as-Node Phase 1

## Vision

Every AI session is already a repository of hard-won context. Session-as-Node makes those sessions composable — users browse live sessions across connected ACP agents, wire them into pipeline DAGs, and execute pipelines that leverage accumulated session context. This is maenifold's defining capability.

**Full spec:** `memory://build/specs/sessionasnode-product-specification`

## Phase 1 Scope: Browse + Wire (Query-Only)

Users can browse sessions from connected ACP agents and wire them into pipelines as prompt nodes. **Phase 1 ships Query mode only** — load session, send prompt, collect response. Snapshot mode (frozen output, no agent contact) deferred to Phase 1.5 per duo review.

## What Already Exists

- `list_sessions()` / `load_session()` — in `crates/maenifold-core/src/tools/sessions.rs`
- `ListedSession.status` already encodes `supports_load_session` capability (via `sessions_query.rs:181`)
- `PipelineNode::Prompt` — in `types_node.rs`, ready for `session_ref` extension
- `AgentSessionConfig.session_id` — already exists at `runner_prompt.rs:25`
- `keep_session_alive = true` — already hardcoded at `executor_nodes_prompt.rs:36`
- Pipeline executor — dispatches prompt nodes via ACP

## Duo Review Consensus (opus-4.7 + gpt-5.4)

**Verdict: REQUEST CHANGES → accepted, epic updated.**

Key findings incorporated:
1. **T-214.2 under-scoped**: No existing ACP resume primitive in executor. Need spike first to verify if passing known sessionId to `execute_runtime` resumes sessions vs needs explicit `session/load` RPC.
2. **Snapshot deferred**: Query-only for Phase 1. Snapshot adds a second executor code path — defer until Query is proven.
3. **T-214.4 merged into T-214.1**: Wire format (`types_wire.rs`) is coupled to `PipelineNode` via `TryFrom` — can't compile independently.
4. **Locking needed**: Two nodes referencing same session would race. Either advisory lock per (agent, sessionId) or schema-prohibit duplicates.
5. **Frontend propagation missing**: TS node types, schema forms, factory, view transforms all need updates.
6. **T-214.9 split**: Separate serde tests, executor tests, live e2e.

## Sub-Tasks (Phase 1, Query-Only)

### Spike
- **T-214.S**: Spike — verify session/load RPC behavior in `open_agent_session`. Does passing a known sessionId to `execute_runtime` resume the agent's session, or do we need an explicit `session/load` call?

### Backend
- **T-214.1**: Add `SessionRef` type + extend `PipelineNode::Prompt` with `session_ref: Option<SessionRef>` + wire format (`types_wire.rs`). SessionRef = `{ agent: String, session_id: String }`. Must be `#[serde(default, skip_serializing_if = "Option::is_none")]`. Invariant: `prompt.agent == session_ref.agent`.
- **T-214.2**: Executor session dispatch — plumb `session_ref` → `AgentSessionConfig.session_id`. Verify/add explicit `session/load` in `open_agent_session` for resume path. Capability-check `supports_load_session`; fail hard if absent. No silent fallback to `new_session`. (Depends on spike T-214.S)
- **T-214.3**: MCP schema extension — add `sessionRef` to `PipelinePromptNodeSchema` + validation
- **T-214.L**: Session uniqueness constraint — validate at schema level that no two nodes in a pipeline share a `sessionRef` (alternative to runtime locking)

### Tests
- **T-214.T1**: Rust unit tests — `SessionRef` serde round-trip + backwards-compat fixture (pipeline JSON without `sessionRef` deserializes cleanly)
- **T-214.T2**: Rust executor test — session-backed prompt dispatch, capability check, failure on missing session

### Frontend
- **T-214.5**: Session Browser store — Pinia store for session listing (extend/wrap `useAgentStore()`)
- **T-214.6**: Session Browser panel — Vue component listing sessions grouped by agent, capability badges, empty/error states
- **T-214.F1**: Frontend TS type propagation — node types, factory, schema forms, view transforms, flow-node data for `sessionRef`
- **T-214.7**: Session node visual treatment — conversation bubble icon, agent badge on pipeline canvas
- **T-214.8**: Add session node to pipeline — context menu "Add session node" (defer drag-and-drop to later)

### Integration
- **T-214.9**: End-to-end validation — list sessions → add session node → run pipeline → verify output + preserved session
