# T-59.7: Unwrap Server Response Envelope in Pipeline MCP Composable

**Requirement**: FR-43
**RTM**: RTM-192
**Priority**: P0 — Blocking: all pipeline operations return wrong shape

## Context

The maenifold server wraps ALL tool responses in an envelope:
```json
{"success": true, "data": <actual_payload>, "error": null}
```

The `usePipelineMcp.ts` composable calls `mcp.callTool()` which parses the JSON content text, yielding the envelope object. But all pipeline functions type-assert the result as the inner payload type (e.g., `PipelineListItem[]`, `PipelineView`), when it's actually `{ success, data, error }`.

This means every pipeline operation returns the wrong shape to the store.

## Scope

Fix `src/composables/usePipelineMcp.ts` in the pipeline-ui project.

## Acceptance Criteria

1. **Envelope unwrapping**: The `callPipeline` helper must detect the `{ success, data, error }` envelope and return `data` instead of the full envelope. If `success` is false, throw an error using the `error` field.
2. **Passthrough for non-envelope responses**: If the response doesn't have the envelope shape (e.g., it's already a raw value), return it as-is. This ensures backward compatibility if the server ever returns unwrapped responses.
3. **Type signature preserved**: All function return types remain the same — callers get the unwrapped payload.
4. **All operations work**: `listPipelines` returns `PipelineListItem[]`, `viewPipeline` returns `PipelineView`, `createPipeline` returns `{ pipelineId }`, `learn` returns a string, etc.
5. **Implementation**: Something like:
   ```typescript
   function callPipeline<T = unknown>(payload: Record<string, unknown>): Promise<T> {
     return mcp.callTool<T>('Pipeline', payload).then(unwrapEnvelope);
   }
   
   function unwrapEnvelope<T>(result: unknown): T {
     if (result && typeof result === 'object' && 'success' in result && 'data' in result) {
       const envelope = result as { success: boolean; data: T; error?: string | null };
       if (!envelope.success) {
         throw new Error(envelope.error || 'Pipeline operation failed');
       }
       return envelope.data;
     }
     return result as T;
   }
   ```
6. **Store normalization still works**: After this fix, `normalizePipelineList` in the store receives the correct shape (`PipelineListItem[]` or `{ pipelines: [] }`), not the envelope.
7. **Build + tests pass**: `npm run build`, `npm test`, and `npm run test:e2e` (with server running) all pass.

### AC Verdicts

#### AC1 — Envelope detected; `data` returned ✅ PASS

`isPipelineEnvelope` (`usePipelineMcp.ts` lines 17–25) correctly gates on three independent conditions: the value is a non-null object, it has a `success` key whose runtime type is strictly `boolean`, and it has a `data` key. `unwrapEnvelope` (lines 47–57) returns `result.data as T` on the happy path.  
`callPipeline` (line 63) wires this into every `mcp.callTool('Pipeline', …)` call via `.then(unwrapEnvelope)`.

No bypass exists on the `callPipeline` path.

#### AC2 — `success: false` throws with the error field ✅ PASS

`unwrapEnvelope` line 52–54 throws when `!result.success`.  
`getEnvelopeErrorMessage` (lines 27–45) handles all three server-side error shapes correctly:
- Plain string → returned verbatim (line 28)
- `Error` instance → `.message` extracted (line 32)
- Structured object → `JSON.stringify` with `String()` fallback (lines 40–43)
- Null/undefined → canonical fallback string `'Pipeline operation failed'` (line 37)

**Caveat**: The `PipelineEnvelope` interface declares `error?: unknown` (line 14). This is intentionally permissive and `getEnvelopeErrorMessage` handles it correctly, but TypeScript will not warn if the server ever changes the error shape. Acceptable risk given the runtime guard.

#### AC3 — Non-envelope responses pass through ✅ PASS

`unwrapEnvelope` (line 48–50): `if (!isPipelineEnvelope(result)) return result as T`.  
`callTool` in `useMcpClient.ts` (line 277–279) already returns `undefined as T` when `content[0].text` is absent; `isPipelineEnvelope(undefined)` evaluates to `false` (typeof check fails), so undefined falls through cleanly. Raw string responses from `callTool` (line 284) likewise fail the object check.

#### AC4 — All function return types preserved ✅ PASS (with noted gap)

Functions with explicit generic annotations are correct:
- `listPipelines(): Promise<PipelineListItem[]>` via `callPipeline<PipelineListItem[]>` (line 71) ✅
- `viewPipeline(): Promise<PipelineView>` via `callPipeline<PipelineView>` (line 79) ✅

Functions with no generic annotation (`createPipeline`, `runPipeline`, `pausePipeline`, etc.) infer `Promise<unknown>`, which is correct for fire-and-forget operations. The store handles the create result with a runtime guard (`isCreateResult`, `pipeline.ts` line 49–51), which is sound.

**Noted gap**: The spec example lists `learn` as a function returning a string. No `learn` function exists in the implementation. This appears to be a spec artifact (the SWE remediation does not mention it), but if `learn` is a real server tool, it is entirely unimplemented and would not benefit from this fix.

#### AC5 — Store normalization receives correct unwrapped shape ✅ PASS (scoped to `listPipelines`)

`refreshList` (`pipeline.ts` line 90–92) calls `mcp.listPipelines()` → `callPipeline<PipelineListItem[]>` → envelope unwrapped → `normalizePipelineList` receives `PipelineListItem[]` or `{ pipelines: [] }` as expected. The normalizer's `Array.isArray` / `.pipelines` fallback is correct for both shapes.

### Findings

#### 🔴 FINDING-1 — `listWorkflows` bypasses the envelope unwrapper (HIGH)

**File**: `usePipelineMcp.ts` lines 152–154  
**Code**:
```typescript
function listWorkflows() {
  return mcp.callTool('ListAssets', { type: 'workflow' });
}
```

This is the only exported call that uses `mcp.callTool` directly rather than `callPipeline`. The spec states the server wraps *all* tool responses in the `{ success, data, error }` envelope. If `ListAssets` follows this convention, `listWorkflows` returns the raw envelope object.

**Downstream impact**: `pipeline.ts` line 196 casts the result as `string[] | WorkflowListResult | undefined` and passes it to `normalizeWorkflows`. The envelope object is not an array and does not have an `.assets` key, so `normalizeWorkflows` silently returns `[]` (line 46). The workflow dropdown is always empty. No error is surfaced because `refreshWorkflows` swallows all exceptions (line 197–199).

**Why this matters**: This is the exact same class of bug T-59.7 was filed to fix, just on a different tool call. The fix was incomplete.

**Remediation**: Replace the direct `mcp.callTool` call with `callPipeline` (or a separate `callMcpTool` helper that also applies `unwrapEnvelope`):
```typescript
function listWorkflows() {
  return callPipeline({ type: 'workflow' });  // if 'ListAssets' tool accepts this shape
  // or: mcp.callTool('ListAssets', { type: 'workflow' }).then(unwrapEnvelope)
}
```
Note: `unwrapEnvelope` is a module-level function and could be applied here without changing the `callPipeline` interface.

---

#### 🟡 FINDING-2 — `success: true` with `data: null` or `data: undefined` silently coerces to wrong type (MEDIUM)

**File**: `usePipelineMcp.ts` lines 47–57  
**Scenario**: Server returns `{ "success": true, "data": null }` (e.g., an empty view or a missing resource).

`isPipelineEnvelope` returns `true` because `'data' in value` only checks key presence, not value. `unwrapEnvelope` returns `null as T`. TypeScript accepts this cast silently.

**Downstream impact**:
- `viewPipeline` typed as `Promise<PipelineView>` would resolve to `null`. The store's `refreshView` assigns `currentView.value = view` (line 218) which is fine, but `view.running` (polling callback, `pipeline.ts` line 242) would throw `TypeError: Cannot read properties of null`.
- `listPipelines` typed as `Promise<PipelineListItem[]>` would resolve to `null`. `normalizePipelineList(null)` calls `Array.isArray(null)` → `false`, then `null?.pipelines ?? []` → `[]`. Silent data loss.

**Note**: `undefined` is handled safely because `isPipelineEnvelope(undefined)` → `false` → passthrough. The risk is specifically `data: null` on the `success: true` path.

**Remediation**: Add a null guard in `unwrapEnvelope` after the success check, or add a server-side contract that `data` is never null on success.

---

#### 🟡 FINDING-3 — `isPipelineEnvelope` can false-positive on domain payloads (MEDIUM-LOW)

**File**: `usePipelineMcp.ts` lines 17–25

Any object with a `success: boolean` and any `data` property will be treated as an envelope and double-unwrapped. For example, if the server ever returns a `PipelineView` whose shape happens to include `{ success: boolean, data: ... }` (plausible for a "node result" or "operation result" nested object), the unwrapper would strip it.

The implementation is stricter than the spec's suggestion (it requires `typeof success === 'boolean'` rather than just `'success' in result`), which reduces the false-positive rate. But the discriminant is not unique enough to be robust against evolving server schemas.

**Remediation**: Consider adding a discriminant key (e.g., `'__envelope': true` on the server side), or use a structural check specific to the known envelope shape (e.g., check that `data` is an object/array and `error` is null/string/undefined, not just any value).

---

#### 🟢 FINDING-4 — `createPipeline` return type is untyped (LOW / informational)

**File**: `usePipelineMcp.ts` line 74–76  
`createPipeline` has no generic annotation, so it returns `Promise<unknown>`. The store compensates with a runtime `isCreateResult` guard (`pipeline.ts` lines 116). This is functionally safe but TypeScript cannot statically verify the call site.

No action required, but adding `callPipeline<{ pipelineId: string }>` would improve type safety.
