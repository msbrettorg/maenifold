# T-43.12: Tool call rawInput/rawOutput

**Requirement**: Tool-calls audit gap  
**Priority**: P2  
**Files**: `vendor/acp-ui/src/lib/types.ts`, `vendor/acp-ui/src/stores/session.ts`

## Acceptance Criteria

1. Add `rawInput` and `rawOutput` to `ToolCallInfo`:
   ```ts
   rawInput?: Record<string, unknown>;
   rawOutput?: Record<string, unknown>;
   ```

2. In the `tool_call` handler, store `update.rawInput` if present.

3. In the `tool_call_update` handler, store `update.rawOutput` if present (tool output typically arrives via update).

4. Propagate both into message-level `toolCalls[]` entries.

## SWE Remediation

- What I changed:
  - `vendor/acp-ui/src/lib/types.ts`: added optional `rawInput` and `rawOutput` fields to `ToolCallInfo` with the required `Record<string, unknown>` shape.
  - `vendor/acp-ui/src/stores/session.ts`: added tool-payload normalization and persisted `rawInput`/`rawOutput` on initial `tool_call` records, global tool-call map entries, and message-level `toolCalls[]` entries during `tool_call_update`.
- Test results:
  - FAIL (pre-existing unrelated errors) — `cd vendor/acp-ui && npx vue-tsc --noEmit`
- Notes:
  - Used a small normalization helper so only object-shaped ACP payloads are stored on `ToolCallInfo`, matching the required TypeScript type.
  - Frontend typecheck is currently blocked by existing `pendingPermissionRequest` / `resolvePermission` API mismatches in `vendor/acp-ui/src/stores/session.ts` and `vendor/acp-ui/src/lib/acp-bridge.ts`, outside this spec's scope.

## Red-team Audit

**Verdict: PASS**

All acceptance criteria verified:

- **AC1 — `rawInput`/`rawOutput` added to `ToolCallInfo`**: ✅ `types.ts` declares:
  ```ts
  rawInput?: Record<string, unknown>;
  rawOutput?: Record<string, unknown>;
  ```
  Exact shape matches the spec.

- **AC2 — `tool_call` handler stores `update.rawInput`**: ✅ In the `tool_call` case of `session.ts`, the `toolCallInfo` object is built with `rawInput: normalizeToolCallPayload(update.rawInput)`. The `normalizeToolCallPayload` helper returns `Record<string, unknown> | undefined` (passing through non-array objects, discarding primitives/arrays), which correctly narrows to the declared type.

- **AC3 — `tool_call_update` handler stores `update.rawOutput`**: ✅ In the `tool_call_update` case: `if ('rawOutput' in update) { existing.rawOutput = normalizeToolCallPayload(update.rawOutput); }`. Uses `'rawOutput' in update` (presence check) rather than truthiness, so an explicit `null`/`undefined` payload in the update is handled safely. `rawInput` updates are also accepted here (beyond spec minimum — harmless).

- **AC4 — Both fields propagated into message-level `toolCalls[]`**: ✅ On initial `tool_call`, `toolCallInfo` (including `rawInput`/`rawOutput`) is pushed directly into `currentAssistantMsg.toolCalls`. On `tool_call_update`, the message-level entry is also updated with matching `'rawInput' in update` / `'rawOutput' in update` guards (lines 417–421 of `session.ts`).

**Noted caveat (non-blocking):** The SWE reported `vue-tsc --noEmit` failing with pre-existing errors attributed to the old `pendingPermissionRequest`/`resolvePermission` API shape. Those errors originate from T-43.10 (now remediated in the same codebase). Blue-team should confirm typecheck is clean after both T-43.10 and T-43.12 are merged together.
