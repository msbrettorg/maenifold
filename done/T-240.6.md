# T-240.6 - OpenCode auth smoke still fails against live maenifold daemon

**Pipeline**: sdd

## Problem

After `T-238.47` was moved to `done`, blue-team ran the real `opencode mcp auth maenifold` smoke test. The live daemon on `127.0.0.1:8080` still behaves like the pre-fix server.

Evidence from 2026-04-27:

```text
$ opencode --version
1.4.3

$ curl --include --silent --show-error --max-time 10 http://127.0.0.1:8080/mcp
HTTP/1.1 401 Unauthorized
content-type: application/json
...
{"error":"missing or invalid bearer token"}
```

The required header was absent:

```text
WWW-Authenticate: Bearer resource_metadata="http://127.0.0.1:8080/.well-known/oauth-protected-resource/mcp"
```

OpenCode still fails:

```text
$ opencode mcp debug maenifold
Auth status: not authenticated
HTTP response: 401 Unauthorized
Testing OAuth flow (without completing authorization)...
Connection error: HTTP 404: Invalid OAuth error response: SyntaxError: JSON Parse error: Unexpected EOF. Raw body:

$ opencode mcp auth maenifold
Authentication failed
HTTP 404: Invalid OAuth error response: SyntaxError: JSON Parse error: Unexpected EOF. Raw body:
```

Direct OAuth discovery endpoints also return `404`:

```text
/.well-known/oauth-protected-resource
/.well-known/oauth-protected-resource/mcp
/.well-known/oauth-authorization-server
/.well-known/oauth-authorization-server/mcp
```

The likely immediate cause is that the daemon currently listening on `127.0.0.1:8080` is not serving the `T-238.47` OAuth-enabled build/config. Regardless of cause, the product-level acceptance criterion was not met in the running system.

## Required Behavior

- Treat this first as a live-daemon deployment/restart verification task, not a code task.
- Do not edit source unless a freshly rebuilt/restarted current daemon still fails the live probes.
- The running local maenifold HTTP daemon serves the `T-238.47` OAuth-enabled code.
- Unauthenticated `GET /mcp` returns `401` with the required `WWW-Authenticate` protected-resource metadata pointer.
- OAuth protected-resource and authorization-server metadata endpoints return valid JSON at bare and `/mcp` suffixed paths.
- `opencode mcp auth maenifold` completes successfully, or the verification documents a specific OpenCode interaction requirement that must be handled.
- The verification path distinguishes "code compiles/tests pass" from "running daemon was upgraded/restarted and the real client flow works."

## Ordered Workflow

SWE must follow this order:

1. Identify the process listening on `127.0.0.1:8080`:

   ```bash
   lsof -nP -iTCP:8080 -sTCP:LISTEN
   ps -p <PID> -o pid,ppid,command
   ```

   Record PID, executable path, parent PID, and command line.

2. Compare the listener to the expected current install paths:

   ```bash
   command -v maenifold
   /usr/local/bin/maenifold --version
   target/release/maenifold --version
   ```

   If version output does not include a build SHA, record that explicitly. Do not invent one.

3. If the listener is stale, mismatched, or cannot be proven current, run the supported repo rebuild/restart path:

   ```bash
   ./rebuild.sh
   ```

   `./rebuild.sh` is the supported path because it rebuilds release binaries, updates `/usr/local/bin/maenifold`, and restarts launchd services. If the daemon is intentionally being run manually instead, use the same rebuilt binary with the documented HTTP mode:

   ```bash
   /usr/local/bin/maenifold --http --port 8080
   ```

   Do not start a second listener on the same port; stop or reuse only the identified daemon owner.

4. Re-run the live HTTP probes against the restarted daemon.

5. Re-run real OpenCode authentication:

   ```bash
   opencode mcp auth maenifold
   opencode mcp debug maenifold
   ```

6. Stop condition:
   - If the restarted daemon passes all curl probes and OpenCode reports `maenifold` authenticated, complete this task with zero source changes.
   - Only if the freshly rebuilt/restarted daemon still fails may SWE inspect or change implementation code.

## Live Probe Contracts

Required probes:

```bash
curl -i http://127.0.0.1:8080/mcp
curl -i http://127.0.0.1:8080/.well-known/oauth-protected-resource
curl -i http://127.0.0.1:8080/.well-known/oauth-protected-resource/mcp
curl -i http://127.0.0.1:8080/.well-known/oauth-authorization-server
curl -i http://127.0.0.1:8080/.well-known/oauth-authorization-server/mcp
```

Expected `/mcp` unauthenticated response:

- status `401 Unauthorized`
- `WWW-Authenticate: Bearer resource_metadata="http://127.0.0.1:8080/.well-known/oauth-protected-resource/mcp"`

Expected protected-resource metadata JSON fields:

- `resource`
- `authorization_servers`
- `bearer_methods_supported`
- `resource_documentation`

For the default local daemon, `resource` must identify `http://127.0.0.1:8080/mcp`.

Expected authorization-server metadata JSON fields:

- `issuer`
- `authorization_endpoint`
- `token_endpoint`
- `registration_endpoint`
- `response_types_supported`
- `grant_types_supported`
- `code_challenge_methods_supported`
- `token_endpoint_auth_methods_supported`

`code_challenge_methods_supported` must include `S256`.
