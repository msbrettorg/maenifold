# T-62.2 — Pinia Store Handles All Node Types

**Requirement**: FR-47
**Component**: `pipeline-ui/src/stores/pipeline.ts`
**Design Reference**: `pipeline-ui/docs/design/node-types-ui.md` §6
**Depends on**: T-62.1

## Context

The Pinia store at `pipeline.ts` (294 lines) manages pipeline state. Its `addNode()` only creates workflow nodes. `runPipeline()` accepts a prompt but the UI never passes one. Node loading doesn't handle type discrimination.

## Acceptance Criteria

1. `addNode()` must accept a `PipelineNode` (the discriminated union from T-62.1) instead of `(workflowId, acpClient?)`. Use `createNode()` helper if constructing internally, or accept a pre-built node.

2. `runPipeline()` must accept and forward an optional `prompt: string` parameter to the MCP call.

3. When loading a pipeline from the server (via `viewPipeline`), normalize nodes:
   - If a node has no `type` field, set `type: 'workflow'`
   - Map server ViewNode fields to the local discriminated union

4. `localDefinition.nodes` must be typed as `PipelineNode[]` (the union type).

5. Any internal code that accesses `node.workflowId` directly must use type guards or the `getNodeType()` helper to branch correctly.

6. Typecheck: `cd pipeline-ui && npx vue-tsc --noEmit` must pass.

## SWE Remediation

- Updated `src/stores/pipeline.ts` to use the T-62.1 discriminated union end-to-end, including typed `addNode()` overloads that accept either a prebuilt `PipelineNode` or a node type plus type-specific fields and delegate creation to `createNode()`.
- Added server-view normalization so workflow nodes missing `type` are hydrated as `type: 'workflow'`, and synchronized `localDefinition` from loaded/polled server views using a proper `ViewNode -> PipelineNode` mapping.
- Kept `runPipeline(prompt?)` forwarding the optional run-level prompt through the MCP call path while removing the store-side cast/workaround used for workflow listing.

### Criterion 1 — `addNode()` accepts discriminated union PipelineNode OR (type + fields) and uses `createNode()`

**PASS**

Lines 138–148 define four TypeScript overloads:

```
138: function addNode(node: PipelineNode): PipelineNode;
139: function addNode(type: 'workflow', fields: WorkflowNodeInput): PipelineNode;
140: function addNode(type: 'prompt', fields: PromptNodeInput): PipelineNode;
141: function addNode(type: 'sequentialThinking', fields: SequentialThinkingNodeInput): PipelineNode;
142: function addNode(nodeOrType: PipelineNode | PipelineNodeType, fields?: AddNodeFields): PipelineNode {
143:   return appendNode(
144:     typeof nodeOrType === 'string'
145:       ? createNode(nodeOrType, fields ?? {})
146:       : createNode(nodeOrType.type ?? 'workflow', nodeOrType),
147:   );
148: }
```

Both branches delegate to `createNode()`. `vue-tsc --noEmit` exits 0, confirming TypeScript is satisfied with passing `PipelineNode` as `Record<string, any>`.

> ⚠️ **Concern (non-blocking)**: The pre-built-node path (line 146) re-runs the node through `createNode` rather than passing it through unchanged. This silently normalises optional fields: a `PromptNode` without `toolMode` will emerge with `toolMode: 'disabled'`; a `SequentialThinkingNode` without `totalThoughts` will emerge with `totalThoughts: 5`. The spec says "accept a pre-built node" and this interpretation is defensible, but callers relying on field absence will be surprised. Recommend a passthrough fast-path (`appendNode(nodeOrType)`) for the PipelineNode overload in a follow-up.

### Criterion 2 — `runPipeline()` accepts optional prompt and passes it in the MCP tool call payload

**PASS**

```
149: async function runPipeline(prompt?: string) {
150:   if (!currentPipelineId.value) return;
151:   await mcp.runPipeline(currentPipelineId.value, prompt);
152:   startViewPolling();
153:   await refreshView();
154: }
```

`usePipelineMcp.ts` line 132–134:
```
function runPipeline(sessionId: string, prompt?: string) {
  return callPipeline({ sessionId, run: true, ...(prompt ? { prompt } : {}) });
}
```

The prompt is forwarded through the MCP call payload. Existing call site `PipelineRunner.vue:118` invokes `store.runPipeline()` with no argument; the optional parameter is backwards-compatible.

> ⚠️ **Concern (non-blocking)**: The MCP composable uses a falsy check (`prompt ? ...`), so an empty string `''` is silently dropped from the payload rather than forwarded or rejected. This is unlikely to matter in practice but could mask a UI bug where the prompt field is cleared before submission.

### Criterion 4 — Server node normalization: nodes without `type` field get `type: 'workflow'`

**PASS**

Two independent defensive layers ensure this:

**Layer 1 — `normalizeViewNode` (lines 30–32)**:
```
30: function normalizeViewNode(node: ViewNode): ViewNode {
31:   return node.type === undefined ? { ...node, type: 'workflow' } : node;
32: }
```
Applied in `normalizeView` (line 37) before `setView` stores the server response.

**Layer 2 — `toLocalNode` switch (lines 61–69)**:
```
61:   case 'workflow':
62:   case undefined:
63:     return { id: node.nodeId, type: 'workflow', workflowId: node.workflowId, ... };
```
Inside a switch on `node.type`, TypeScript narrows to `WorkflowViewNode` in this branch, making `node.workflowId` (line 66) type-safe without any cast.

Both `loadPipeline` (line 116) and `refreshView` (line 212) call `normalizeView(...)` before delegating to `setView`, so the normalization applies on initial load, manual refresh, and poll callbacks.
